# 설계의 완성: ERD를 넘어선 테이블 기술 명세서(Data Dictionary) 작성 실무

앞선 장들을 통해 우리는 정규화(Normalization)의 논리적 뼈대를 세우고, ERD(Entity Relationship Diagram)라는 훌륭한 시각적 지도를 완성했습니다. 여러 개의 네모 상자(테이블)와 그 사이를 잇는 선(관계)을 보며 연구팀은 비로소 데이터의 전체 흐름을 한눈에 파악할 수 있게 되었습니다.

하지만 프로젝트를 실제 시스템으로 구현하는 단계에 접어들면, 그림으로 된 ERD만으로는 심각한 소통의 부재가 발생합니다. 개발자나 후속 연구자는 화살표의 존재는 알 수 있지만, `"**그 화살표 이면에 숨겨진 인문학적 맥락과 데이터 입력의 구체적인 규칙**"`은 결코 그림만으로 유추할 수 없기 때문입니다.

따라서 데이터 모델링의 최종 기착지는 ERD를 그리는 것이 아니라, 이를 글로 풀어낸 `"**테이블 기술 명세서(Data Dictionary, 데이터 사전)**"`를 작성하는 것입니다. 이 장에서는 인문학 전공자가 데이터 엔지니어와 협업하고, 학술 재단에 결과 보고서를 제출하기 위해 반드시 알아야 할 명세서 작성 실무를 다룹니다.



## 1. 왜 그림(ERD)만으로는 부족한가?

ERD가 도시의 전체적인 '지도'라면, 테이블 기술 명세서는 각 건물의 용도와 출입 규칙을 적어둔 `"**건축 대장**"`에 해당합니다. 

예를 들어 ERD 상에는 '인물' 테이블에 '생년_정밀도'라는 속성이 있다고만 표시됩니다. 만약 명세서가 없다면 데이터를 입력하는 보조 연구원이나 시스템을 세팅하는 개발자는 다음과 같은 혼란에 빠집니다.
* "생년 정밀도에 '정확함', '모름'이라고 한글로 적어야 하나? 아니면 'Y', 'N' 코드를 써야 하나?"
* "생년이 아예 기록에 없는 사람은 빈칸(NULL)으로 두어야 하나, 아니면 0을 넣어야 하나?"

명세서(Data Dictionary)는 이러한 모호성을 원천적으로 차단하는 `"**연구팀 내의 법적 계약서**"` 역할을 수행합니다.

## 2. 데이터 명세서의 필수 구성 요소

표준적인 테이블 기술 명세서는 보통 엑셀(스프레드시트)이나 마크다운 표 형태로 작성되며, 다음과 같은 핵심 열(Column)들을 포함해야 합니다.

1. **논리명 (Logical Name):** 인간이 읽고 이해하는 이름입니다. (예: `생년 정밀도 코드`)
2. **물리명 (Physical Name):** 실제 데이터베이스(MySQL, 오라클 등) 시스템에 생성될 영문 컬럼명입니다. 띄어쓰기 대신 언더바(`_`)를 사용하는 스네이크 케이스(Snake Case)가 주로 쓰입니다. (예: `birth_year_precision`)
3. **데이터 타입 (Data Type):** 기계가 해당 공간에 어떤 형태의 데이터를 담을지 지정합니다. 정수는 `INT`, 텍스트는 `VARCHAR`, 날짜는 `DATE` 등으로 표기합니다. 
4. **길이/크기 (Length):** 텍스트의 경우 최대 몇 자까지 허용할 것인지 제한합니다. (예: `VARCHAR(10)`)
5. **PK / FK (기본키 / 외래키 여부):** 해당 컬럼이 테이블의 고유 식별자인지(PK), 다른 테이블을 참조하는 키인지(FK) 명시합니다.
6. **NULL 허용 여부 (Nullability):** 데이터가 비어 있어도 시스템이 허용할 것인지(`NULL`), 반드시 입력해야만 저장이 되도록 강제할 것인지(`NOT NULL`)를 결정합니다.
7. **비고 / 설명 (Description & Constraints) ★:** 인문학 데이터 모델링에서 `"**가장 중요한 영역**"`입니다. 이 컬럼이 지니는 인문학적 의미, 특정 코드가 의미하는 바, 예외 처리 규칙 등을 상세히 기록합니다.

## 3. 실전: 조선시대 인물 테이블 명세서 작성 예시

앞서 다루었던 '역사적 모호성 해결 패턴'을 적용한 조선시대 인물 마스터 테이블(`person_tb`)의 기술 명세서를 작성해 보겠습니다.

**[표 1. 테이블 정의서 - 테이블 단위의 개요]**
* **테이블 논리명:** 인물 마스터
* **테이블 물리명:** `person_tb`
* **설명:** 조선시대 사료에 등장하는 인물의 고유 식별 정보와 생몰년 데이터를 관리하는 최상위 마스터 테이블. 동명이인 구분을 위해 반드시 본관 코드를 참조해야 함.

**[표 2. 컬럼(속성) 정의서 - 세부 스펙 명세]**

| 논리명 | 물리명 | 데이터 타입 | 길이 | PK | FK | NULL | 비고 및 도메인 규칙 (Description) |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 인물 ID | `person_id` | `VARCHAR` | 10 | **Y** | N | `NOT NULL` | 인물의 고유 식별자. 'P' + 일련번호 6자리 체계 사용 (예: P000001). 자동 증가(Auto-increment) 대신 규칙 채번 사용. |
| 이름 | `person_name` | `VARCHAR` | 50 | N | N | `NOT NULL` | 인물의 한글 성명. 한자는 별도 테이블에서 관리함. |
| 본관 코드 | `clan_id` | `VARCHAR` | 10 | N | **Y** | `NOT NULL` | 본관 마스터 테이블(`clan_tb`)의 `clan_id`를 참조. 출신지가 불분명할 경우 임시 코드 'F9999'를 입력함. |
| 생년 | `birth_year` | `INT` | - | N | N | `NOT NULL` | 서기 연도 기준 정수 입력. **[주의] 미상일 경우 NULL이 아닌 `9999`를 입력하여 정렬 시 후순위로 밀리도록 처리함.** |
| 생년 정밀도 | `birth_precision` | `VARCHAR` | 1 | N | N | `NOT NULL` | 생년 데이터의 신뢰도 코드. <br> `D`: 일(Day) 단위까지 정확함 <br> `Y`: 연도(Year)까지만 정확함 <br> `C`: 세기(Century) 추정치 <br> `U`: 미상(Unknown) |
| 몰년 | `death_year` | `INT` | - | N | N | `NULL` | 서기 연도 기준 정수. 생존 인물이거나 기록이 전혀 없는 경우 NULL 허용. |

### 3.1 명세서가 가져오는 협업의 기적
위의 명세서를 읽은 데이터 엔지니어나 보조 연구원은 더 이상 교수(PM)에게 질문할 필요가 없습니다. 
"생년이 미상일 때는 어떻게 하나요?"라는 질문은 명세서의 비고란(`미상일 경우 9999를 입력`)을 통해 이미 답변이 완료되었습니다. 또한 `NOT NULL` 제약 조건이 명시되어 있으므로, 개발자는 시스템 구축 시 이름을 입력하지 않으면 에러 메시지를 뱉어내는 완벽한 방어 로직을 쉽게 구현할 수 있습니다.

## 4. 요약: 데이터 거버넌스(Data Governance)의 출발점

테이블 기술 명세서(Data Dictionary)를 작성하는 것은 번거로운 서류 작업이 아닙니다. 이는 디지털 인문학 지식베이스가 수십 년간 유지보수될 수 있도록 돕는 `"**데이터 거버넌스의 가장 강력한 무기**"`입니다. 

* 엑셀에서 무작정 데이터를 타이핑하던 과거(플랫 데이터)를 반성하고,
* ERD 시각화 도구를 통해 제1~제3 정규화의 논리적 뼈대를 세웠으며,
* 마지막으로 데이터 명세서를 작성함으로써 기계와 인간 모두가 이해할 수 있는 완벽한 설계도를 완성했습니다.

기나긴 데이터 모델링의 여정이 끝났습니다. 이제 도면은 완성되었으니, 빈 창고(데이터베이스)에 건축 자재(데이터)를 쏟아부을 차례입니다.
