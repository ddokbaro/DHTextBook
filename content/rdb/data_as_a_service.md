# 데이터의 서비스화(DaaS): 내 데이터베이스를 세상과 연결하기

우리는 지금까지 기나긴 여정을 거쳐왔습니다. 엑셀의 한 셀에 욱여넣었던 플랫 데이터를 논리적으로 분해하여 정규화(Normalization)하고, 역사적 모호성을 극복하는 템포럴(Temporal) 모델을 설계했으며, 이를 DBeaver와 같은 클라이언트를 통해 데이터베이스에 적재했습니다. 그리고 SQL이라는 강력한 질의어를 통해 숨겨진 역사적 관계망을 복원해 냈습니다.

하지만 여기서 스스로에게 가장 근본적인 질문을 던져보아야 합니다. 
`"**이 훌륭한 데이터베이스를 내 컴퓨터 안에만 가두어 둔다면, 그것이 과거의 엑셀 파일과 본질적으로 무엇이 다른가?**"`

디지털 인문학(Digital Humanities)의 궁극적인 지향점은 지식의 독점이 아니라 `"**연결과 개방**"`입니다. 이 에필로그 장에서는 구축된 데이터베이스를 연구실의 담장 밖으로 꺼내어 전 세계의 학자들과 기계(Machine)가 자유롭게 활용할 수 있도록 만드는 `"**데이터의 서비스화(Data as a Service, DaaS)**"` 패러다임을 살펴봅니다.

## 1. 지식의 사일로(Silo)와 전통적 데이터 공유의 한계

전통적인 인문학 프로젝트에서 데이터를 공유하는 방식은 매우 정적이고 원시적이었습니다. 연구가 끝나면 구축된 데이터를 CSV 파일로 내보내어 학술지 부록으로 첨부하거나, 연구소 홈페이지 구석에 `.zip` 파일로 올려두는 식입니다.

이러한 방식은 다음과 같은 치명적인 한계를 가집니다.
1. **단절된 업데이트:** 엑셀 파일이 다운로드되는 그 순간, 데이터는 죽은 지식이 됩니다. 원본 데이터베이스에서 새로운 인물이나 사료가 추가되어도, 다운로드해 간 연구자의 엑셀 파일은 영원히 과거의 상태에 머무릅니다.
2. **기계 가독성(Machine-readability)의 부재:** 다른 연구팀이 내 데이터를 자신들의 지식 네트워크(LOD)에 실시간으로 연동하거나, 데이터 시각화 대시보드에 즉각적으로 반영할 수 없습니다.

데이터베이스가 네트워크와 단절된 채 갇혀 있는 상태를 컴퓨터 공학에서는 `"**사일로(Silo, 고립된 곡물 창고)**"` 현상이라고 부릅니다. 우리는 이 사일로를 허물어야 합니다.

## 2. 데이터의 서비스화 (Data as a Service)와 REST API

현대의 데이터는 파일 형태로 다운로드되는 것이 아니라, 언제든 질문을 던지면 최신의 답변을 돌려주는 `"**살아있는 서비스(Service)**"`로 제공되어야 합니다. 이를 가능하게 하는 핵심 기술이 바로 `"**API(Application Programming Interface)**"`입니다.



### 2.1 API란 무엇인가?
API는 식당의 `"**웨이터**"`와 같습니다. 손님(외부 연구자나 프로그램)이 주방(데이터베이스)에 직접 들어와 냉장고를 뒤지게 할 수는 없습니다. 대신, 손님이 정해진 메뉴판(API 명세서)을 보고 "이순신의 관직 이력 데이터를 줘"라고 웨이터에게 주문(Request)하면, 웨이터가 주방에서 데이터를 안전하게 꺼내어 손님 테이블에 배달(Response)해 줍니다.

### 2.2 REST API와 JSON
특히 현대 웹에서 가장 널리 쓰이는 표준이 `"**REST API**"`입니다. 이는 웹 브라우저가 주소를 입력해 웹페이지를 보듯, 특정한 URL(예: `http://my-archive.com/api/persons/P001`)을 호출하면 기계가 가장 읽기 쉬운 텍스트 형식인 `"**JSON(JavaScript Object Notation)**"`으로 데이터를 반환해 주는 구조입니다.

```json
// API 호출 시 반환되는 JSON 데이터의 예시
{
  "person_id": "P001",
  "name": "이순신",
  "birth_year": 1545,
  "careers": [
    {"office": "정읍현감", "year": 1589},
    {"office": "삼도수군통제사", "year": 1593}
  ]
}
```
API가 구축되면, 타 대학의 연구팀은 이 URL을 통해 우리 데이터베이스를 자신들의 웹사이트나 파이썬 분석 코드에 실시간으로 연동할 수 있게 됩니다.

## 3. 인문학자를 위한 로우코드(Low-code) API 배포의 필요성

"API가 좋은 건 알겠습니다. 그럼 어떻게 만드나요?"
과거에는 API를 만들기 위해 인문학 전공자가 Python(Django, FastAPI)이나 Java(Spring) 같은 백엔드(Back-end) 프로그래밍 언어를 바닥부터 배워야 했습니다. 서버를 세팅하고, 라우팅을 설정하고, 보안을 적용하는 과정은 SQL을 배우는 것과는 차원이 다른 거대한 통곡의 벽이었습니다.

하지만 2020년대 이후, 기술의 발전은 프로그래밍 지식이 없는 인문학자들도 클릭 몇 번으로 데이터베이스를 API로 변환할 수 있는 `"**서버리스(Serverless) 및 로우코드(Low-code) 도구**"`들을 탄생시켰습니다.

## 4. 요약 및 다음 단계

데이터베이스의 진정한 가치는 엑셀의 대체제가 아니라, 전 세계의 지식과 연결될 수 있는 `"**허브(Hub)**"`가 될 때 비로소 완성됩니다. 여러분이 만든 조선시대 인물 데이터베이스는 이제 다른 이들의 연구에 실시간으로 인용되고 융합될 준비가 되었습니다.

이 교재의 가장 마지막 장, **"경량 도구(Datasette)를 활용한 코딩 없는 REST API 배포 실무"**에서는 우리가 로컬에서 만든 SQLite 파일 하나를 던져주기만 하면, 백엔드 코딩 단 한 줄 없이 1초 만에 멋진 웹 UI와 JSON API를 동시에 생성하여 전 세계로 퍼블리싱(Publishing)해 주는 마법 같은 도구, `"**Datasette**"`의 활용법을 알아보겠습니다.
