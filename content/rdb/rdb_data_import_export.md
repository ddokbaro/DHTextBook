# 플랫 파일 처리와 데이터 파이프라인 구축

앞선 모델링 파트를 통해 우리는 제1~제3 정규화를 거치며 튼튼한 테이블 구조를 설계했고, ERD와 데이터 명세서(Data Dictionary)라는 완벽한 도면을 완성했습니다. 하지만 아무리 아름답게 설계된 창고(데이터베이스)라 하더라도, 그 안에 물건(데이터)이 없다면 무용지물입니다.

이제 우리는 엑셀 시트나 메모장 파일로 흩어져 있는 인문학 사료들을 이 엄격한 관계형 데이터베이스의 규격에 맞추어 밀어 넣는 `"**데이터 파이프라인(Data Pipeline)**"` 구축 단계로 진입합니다. 이 장에서는 원시 데이터가 시스템으로 흘러 들어가는 전체적인 흐름을 이해하고, 플랫 파일(Flat File)을 다룰 때 발생하는 근본적인 패러다임의 충돌을 다룹니다.

## 1. 인문학 데이터의 ETL (추출, 변환, 적재)

컴퓨터 공학에서는 데이터가 이동하고 가공되는 일련의 과정을 `"**ETL(Extract, Transform, Load)**"`이라고 부릅니다. 디지털 인문학 연구에서도 이 파이프라인은 동일하게, 하지만 문헌 데이터 특유의 노이즈로 인해 훨씬 더 험난하게 작동합니다.



1. **추출 (Extract):** 고문헌의 OCR(광학 문자 인식) 결과물이나, 연구 보조원이 수작업으로 타이핑한 엑셀 파일, 혹은 공공기관의 Open API에서 원시 데이터를 수집합니다.
2. **변환 (Transform):** 수집된 데이터는 결측치, 띄어쓰기 오류, 섞여 있는 다중값으로 오염되어 있습니다. 파이썬(Python)의 Pandas 라이브러리나 엑셀의 함수를 사용하여 정규화(Normalization) 원칙에 맞게 테이블을 쪼개고, ID를 부여하며, 기계가 읽을 수 있는 플랫 파일(`CSV` 또는 `TXT`) 포맷으로 변환합니다.
3. **적재 (Load):** 정제된 플랫 파일을 DBeaver나 HeidiSQL 같은 클라이언트 도구를 이용해 최종적으로 데이터베이스의 빈 테이블(Table) 안으로 밀어 넣습니다(Import).

우리가 이 파트에서 집중적으로 다룰 영역은 바로 마지막 단계인 `"**적재(Load)**"` 실무입니다.

## 2. 규격의 충돌: 유연한 엑셀 vs 엄격한 RDB

데이터를 임포트(Import)할 때 연구자들이 가장 많이 겪는 좌절은, 엑셀에서는 아무 문제 없이 열리던 데이터가 데이터베이스에 들어가는 순간 수많은 에러를 뿜어내며 튕겨 나온다는 것입니다. 

이러한 현상은 두 매체가 가진 본질적인 철학의 차이에서 발생합니다.

* **스프레드시트의 관대함:** 엑셀은 하나의 열(Column)에 숫자와 문자가 섞여 있어도, 날짜 형식이 `1592-04-13`이든 `1592년 4월 13일`이든 불평하지 않고 모두 화면에 보여줍니다. 
* **RDB의 엄격함:** 반면 관계형 데이터베이스는 `"**테이블 기술 명세서**"`에 정의된 제약 조건(Constraint)을 광신도처럼 따릅니다. `INT`(정수) 타입으로 선언된 컬럼에 빈칸이나 '미상'이라는 텍스트가 들어오면 즉시 `"**Data truncation(데이터 잘림) 에러**"`나 `"**Type mismatch(타입 불일치) 에러**"`를 발생시키고 적재를 전면 중단(Rollback)해 버립니다.

따라서 성공적인 데이터 임포트를 위해서는, 단순히 파일을 업로드하는 버튼을 누르는 것이 아니라 대상 테이블의 물리적 스키마(Schema)와 원본 파일의 데이터 타입이 100% 완벽하게 일치하도록 맵핑(Mapping)하는 고도의 주의력이 필요합니다.

## 3. 중간 매개체로서의 플랫 파일: CSV와 TSV

데이터베이스 클라이언트(DBeaver 등)는 데이터 적재 시 무겁고 복잡한 `.xlsx` 엑셀 파일보다는, 구조가 단순하고 가벼운 `"**플랫 파일(Flat File)**"` 포맷을 표준 매개체로 사용합니다.

* **CSV (Comma-Separated Values):** 데이터를 쉼표(`,`)로 구분하는 가장 보편적인 형식입니다. 하지만 인문학 사료 내부(예: 인물의 여러 호를 나열한 텍스트나 사료의 원문 텍스트)에 이미 쉼표가 포함되어 있는 경우, 열(Column)이 어긋나는 치명적인 파싱(Parsing) 에러가 자주 발생합니다.
* **TSV (Tab-Separated Values):** 데이터를 탭(`Tab`)으로 구분합니다. 일반적인 역사 텍스트 데이터에는 탭 문자가 포함되는 경우가 거의 없으므로, 디지털 인문학 데이터 파이프라인에서는 CSV보다 TSV를 사용하는 것이 훨씬 안전한 실무적 선택입니다.

## 4. 다음 단계: 영혼을 파괴하는 트러블슈팅의 세계로

"CSV 파일을 만들어서 임포트 마법사(Wizard) 버튼을 누르면 끝나는 것 아닌가?"라고 생각하셨다면 오산입니다. 
윈도우(Windows) 운영체제와 한글 엑셀이 만들어내는 환장의 콜라보레이션은, 겉보기엔 멀쩡한 데이터를 데이터베이스 안에서 기괴한 외계어로 둔갑시키거나 첫 번째 컬럼의 이름을 알 수 없는 기호로 오염시킵니다.

다음 장인 **"CSV/TXT 데이터 임포트 실무와 인코딩(UTF-8 BOM) 트러블슈팅"**에서는 데이터 임포트 과정에서 인문학도들의 영혼을 가장 많이 파괴하는 악명 높은 `"**인코딩(Encoding) 깨짐 현상**"`과, 마이크로소프트의 끔찍한 유산인 `"**BOM(Byte Order Mark)**"`의 실체를 해부하고 이를 우아하게 타개하는 실무 트러블슈팅을 전개하겠습니다.
