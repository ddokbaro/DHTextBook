# DDL과 DML의 구조 및 이기종 SQL 문법 비교 (MSSQL vs MySQL)

SQL(구조화된 질의어)이라는 언어는 수십 가지의 명령어로 이루어져 있지만, 그 목적에 따라 크게 두 가지의 핵심 카테고리로 나뉩니다. 하나는 데이터를 담을 `"**그릇(테이블) 자체를 빚어내는 언어**"`이고, 다른 하나는 그 `"**그릇 안에 담긴 내용물(데이터)을 요리하는 언어**"`입니다.

인문학도들이 SQL을 처음 배울 때 이 두 가지의 층위를 혼동하면, "테이블을 지워야 하는데 데이터를 지우는 명령어를 쓴다거나", "데이터를 수정해야 하는데 테이블 구조를 바꾸려 드는" 치명적인 실수를 범하게 됩니다. 이 장에서는 SQL의 양대 산맥인 **DDL(데이터 정의어)**과 **DML(데이터 조작어)**의 구조적 차이를 이해하고, 우리가 실습에서 마주하게 될 로컬(MySQL)과 클라우드(MSSQL) 환경의 결정적인 문법 차이를 해부합니다.



## 1. DDL (Data Definition Language): 뼈대를 세우는 건축가

**DDL(데이터 정의어)**은 데이터베이스, 테이블, 인덱스 등 데이터베이스의 `"**물리적 구조(Schema)**"`를 정의하고 변경하며 파괴하는 명령어입니다. 건축에 비유하자면 디지털 인문학 지식베이스라는 도서관의 건물을 올리고, 서가(테이블)를 짜 맞추는 작업입니다.

### 1.1 DDL의 3대 핵심 명령어
* **`CREATE` (창조):** 무에서 유를 창조합니다. 새로운 데이터베이스나 빈 테이블을 생성합니다. (우리가 앞서 ERD를 그리고 명세서를 작성한 궁극적인 목적이 바로 이 `CREATE TABLE` 문을 완벽하게 작성하기 위함입니다.)
* **`ALTER` (변형):** 이미 지어진 건물의 구조를 바꿉니다. 테이블에 새로운 컬럼(열)을 추가하거나, 데이터 타입(VARCHAR -> INT)을 변경할 때 사용합니다.
* **`DROP` (파괴):** 건물 자체를 폭파시킵니다. 테이블의 뼈대와 그 안의 모든 데이터를 영구적으로 날려버립니다. `"**가장 극도로 주의해야 할 파멸의 명령어**"`입니다.

### 1.2 이기종 DDL 방언의 충돌: MySQL vs MSSQL

학생들이 로컬 컴퓨터(XAMPP)에 설치된 **MySQL(MariaDB)**에서 완벽하게 작동하던 `CREATE TABLE` 코드를 클라우드 실습 환경인 Azure의 **MSSQL(SQL Server)**에 복사해 넣으면 십중팔구 붉은색 에러를 뿜어냅니다. 이는 각 데이터베이스 벤더가 한글(유니코드)을 처리하고 고유 번호를 생성하는 방식에 `"**독자적인 방언(Dialect)**"`을 쓰기 때문입니다.

**[사례: 조선시대 인물 테이블 생성 DDL 비교]**

**① MySQL (로컬 환경)의 DDL 방언**
```sql
CREATE TABLE person_tb (
    person_id INT AUTO_INCREMENT PRIMARY KEY,
    person_name VARCHAR(50) NOT NULL,
    birth_year INT
) DEFAULT CHARSET=utf8mb4;
```
* **특징 1:** 고유 번호를 자동으로 1씩 증가시킬 때 `"**AUTO_INCREMENT**"`라는 직관적인 키워드를 사용합니다.
* **특징 2:** 다국어(한글, 한자)를 완벽히 지원하기 위해 테이블 끝에 인코딩 세팅(`DEFAULT CHARSET=utf8mb4`)을 명시하는 것이 관례입니다.

**② MSSQL / Azure (클라우드 환경)의 DDL 방언**
```sql
CREATE TABLE person_tb (
    person_id INT IDENTITY(1,1) PRIMARY KEY,
    person_name NVARCHAR(50) NOT NULL,
    birth_year INT
);
```
* **특징 1 (치명적 차이):** MSSQL은 `AUTO_INCREMENT`라는 단어를 전혀 알아듣지 못합니다. 대신 `"**IDENTITY(1,1)**"`이라는 고유 문법을 사용합니다. (1부터 시작해서 1씩 증가하라는 의미입니다.)
* **특징 2 (한글/한자 깨짐 방지):** MSSQL에서 다국어를 안전하게 저장하려면 문자열 타입 앞에 반드시 **'N'**을 붙여 `"**NVARCHAR**"` 타입으로 선언해야 합니다. 그냥 `VARCHAR`로 선언하고 한자를 집어넣으면 전부 물음표(`???`)로 깨져버립니다.

이처럼 자신이 서 있는 인프라가 무엇인지 정확히 파악하고, 그 지역의 방언에 맞게 명세서의 DDL을 번역(Translation)하는 것이 데이터 엔지니어의 핵심 소양입니다.

## 2. DML (Data Manipulation Language): 데이터를 다루는 거주자

서가(테이블)가 완성되었다면, 이제 그 빈 공간에 역사 사료(데이터)를 채워 넣고, 검색하고, 수정하고, 지울 차례입니다. 이때 사용하는 언어가 바로 **DML(데이터 조작어)**입니다. 
인문학 전공자들이 데이터베이스와 소통할 때 평생 가장 많이 쓰게 될 명령어들이며, DDL과 달리 이기종 간의 방언 차이가 비교적 적은 `"**공용어**"`에 가깝습니다.



### 2.1 DML의 4대 핵심 명령어 (CRUD)
소프트웨어 공학에서는 데이터를 다루는 4가지 기본 작업을 `"**CRUD (Create, Read, Update, Delete)**"`라고 부릅니다. 이는 정확히 DML의 4대 명령어와 1:1로 매칭됩니다.

* **[C] `INSERT` (삽입):** 빈 테이블에 새로운 행(Row)을 추가합니다. 앞서 우리가 플랫 파일(CSV)을 임포트 마법사로 밀어 넣을 때, 내부적으로는 수만 줄의 `INSERT` 구문이 실행된 것입니다.
* **[R] `SELECT` (조회) ★:** 데이터베이스의 꽃이자, 이 커리큘럼의 알파와 오메가입니다. 얽혀있는 테이블에서 조건에 맞는 데이터를 추출합니다. 데이터베이스에 어떠한 물리적 변형도 가하지 않는 안전하고 우아한 읽기 전용 명령어입니다.
* **[U] `UPDATE` (수정):** 기존에 존재하는 데이터의 값을 변경합니다. (예: 이순신의 품계를 종3품에서 정3품으로 수정)
* **[D] `DELETE` (삭제):** 조건에 맞는 특정 데이터 행(Row)을 삭제합니다. (주의: `DROP`은 테이블 상자 자체를 태워버리는 것이고, `DELETE`는 상자 안의 내용물만 골라 버리는 것입니다.)

### 2.2 영혼을 파괴하는 DML의 저주: "WHERE 절의 누락"

`SELECT`는 아무리 잘못 쳐도 컴퓨터가 잠시 멈출 뿐 데이터가 망가지지 않습니다. 하지만 `"**UPDATE와 DELETE 명령어**"`를 사용할 때는 디지털 인문학 연구자의 등골을 서늘하게 만드는 절대 원칙이 있습니다.

> `"**WHERE 절(조건문)이 없는 UPDATE와 DELETE는 재앙이다.**"`

```sql
-- [안전한 쿼리] P001 인물의 이름만 '이순신'으로 바꾼다.
UPDATE person_tb 
SET person_name = '이순신' 
WHERE person_id = 'P001';

-- [파멸의 쿼리] 조건(WHERE)을 빼먹었다!!!
UPDATE person_tb 
SET person_name = '이순신';
```

만약 여러분이 실수로 두 번째 쿼리를 실행했다면 어떤 일이 벌어질까요? 데이터베이스는 "아, 이 테이블에 있는 **모든 사람의 이름**을 '이순신'으로 바꾸고 싶구나!"라고 완벽하게 명령을 수행해 버립니다. 10만 명의 조선시대 인물이 0.1초 만에 전부 이순신으로 개명되는 대참사가 발생합니다. 

이러한 참사를 막기 위해 우리는 DBeaver에서 해당 데이터베이스 연결을 `"**Production(운영) 모드**"`로 설정하여, `UPDATE`를 칠 때마다 붉은색 경고창(Confirm)이 뜨도록 안전장치를 걸어둔 것입니다.

## 3. 요약

* **DDL (`CREATE`, `ALTER`, `DROP`):** 그릇을 만드는 명령어. MSSQL과 MySQL 간의 방언 차이(`IDENTITY` vs `AUTO_INCREMENT`, `NVARCHAR` vs `VARCHAR`)가 극심하므로 인프라 환경에 맞춰 정밀하게 작성해야 합니다.
* **DML (`INSERT`, `SELECT`, `UPDATE`, `DELETE`):** 그릇 안의 데이터를 다루는 명령어. 언제나 `"**WHERE 절(조건)**"`을 확인하는 강박관념을 가져야 데이터의 무결성을 지킬 수 있습니다.

테이블의 뼈대와 데이터를 다루는 패러다임을 확립했습니다. 이제 다음 장에서는 방금 살짝 엿보았던 방언의 차이 중, 인문학 웹 서비스 개발 시 가장 치명적인 장벽으로 작용하는 **"PK 자동 증가 메커니즘과 문자열/페이징 처리의 철학적 차이"**를 딥다이브(Deep Dive)하여 파헤쳐보겠습니다.
