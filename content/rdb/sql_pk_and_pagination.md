# PK 자동 증가 메커니즘과 문자열/페이징 처리의 철학적 차이

데이터베이스에 인문학 사료를 적재하고 나면, 궁극적으로 이를 세상에 공개하기 위한 `"**웹 기반의 디지털 아카이브 서비스**"`를 구축하게 됩니다. 웹 브라우저를 통해 수만 건의 역사 데이터를 검색하고 열람하는 게시판을 만들 때, 개발자와 데이터 엔지니어는 SQL 방언(Dialect)이 빚어내는 가장 끔찍한 호환성 문제와 직면하게 됩니다.

이 장에서는 단순한 명령어의 차이를 넘어, 각 데이터베이스 벤더(MySQL, MSSQL, Oracle 등)가 데이터를 다루는 철학이 어떻게 다른지 `"**PK(기본키) 자동 증가 메커니즘**"`과 게시판 구현의 핵심인 `"**페이징(Pagination) 처리**"`를 중심으로 심층 해부합니다.

## 1. 기본키(PK) 자동 증가: 테이블 종속 vs 독립 객체

인물이나 문헌 데이터를 새로 입력(`INSERT`)할 때마다 P001, P002처럼 ID를 수동으로 계산해서 넣는 것은 불가능합니다. 시스템이 알아서 절대 중복되지 않는 고유 번호를 발급해 주어야 합니다. 이 자동 발급기를 구현하는 철학은 크게 두 진영으로 나뉩니다.

### 1.1 테이블 종속형 (MySQL, SQLite, MSSQL)
가장 직관적이고 널리 쓰이는 방식입니다. 번호 발급기가 `"**해당 테이블 안에 귀속**"`되어 있습니다. 테이블이 삭제되면 발급기도 함께 사라집니다.

* **MySQL / MariaDB:** 앞서 DDL에서 보았듯 컬럼 옆에 `"**AUTO_INCREMENT**"`를 선언합니다.
* **MSSQL:** `"**IDENTITY(1,1)**"`을 선언합니다. (1부터 시작해서 1씩 증가하라는 의미입니다.)

이 방식은 매우 간편하지만, 여러 테이블이 하나의 공통된 일련번호 체계를 공유해야 할 때(예: '인물' 테이블과 '관직' 테이블이 절대 겹치지 않는 통합 ID를 가져야 할 때)는 치명적인 한계를 드러냅니다.

### 1.2 독립 객체형: 시퀀스 (Oracle, PostgreSQL)
엔터프라이즈 환경의 절대 강자인 오라클(Oracle)과 학계에서 사랑받는 PostgreSQL은 번호 발급기를 테이블에 종속시키지 않습니다. 대신 `"**시퀀스(Sequence)**"`라는 완전히 독립된 데이터베이스 객체를 별도로 창조합니다.

```sql
-- 1. 오라클 방언: 번호 발급기(시퀀스)를 독립적으로 먼저 생성
CREATE SEQUENCE person_seq START WITH 1 INCREMENT BY 1;

-- 2. 데이터를 넣을 때 발급기의 스위치(NEXTVAL)를 눌러서 번호를 뽑아옴
INSERT INTO person_tb (person_id, person_name) 
VALUES (person_seq.NEXTVAL, '이순신');
```

이 방식은 초보자에게는 매우 번거롭게 느껴집니다. 테이블 외에 시퀀스라는 객체를 따로 관리해야 하기 때문입니다. 그러나 여러 테이블이 하나의 시퀀스를 공유하여 `"**전역적인 고유 식별자(Global Unique ID)**"`를 생성할 수 있다는 점에서, 복잡한 인문학 지식 네트워크(LOD)를 구축할 때 압도적인 아키텍처적 우위를 가집니다.

## 2. 문자열 결합: 철학의 파편화

역사 데이터베이스에서 쪼개져 있는 데이터를 하나로 합쳐서 보여주는 작업은 매우 빈번합니다. 본관과 이름을 합쳐 "덕수이씨 이순신"으로 만들거나, 연/월/일을 합쳐 날짜 문자열로 만드는 작업입니다. 안타깝게도 이 단순한 `"**문자열 결합(Concatenation)**"`조차 데이터베이스마다 기호가 모두 다릅니다.

* **표준 ANSI & SQLite & Oracle:** 파이프 기호 두 개(`||`)를 사용하여 직관적으로 연결합니다.
  ```sql
  SELECT clan_name || ' ' || person_name AS full_name FROM person_tb;
  ```
* **MSSQL:** 엑셀이나 프로그래밍 언어처럼 덧셈 기호(`+`)를 사용합니다.
  ```sql
  SELECT clan_name + ' ' + person_name AS full_name FROM person_tb;
  ```
* **MySQL:** 연산자 기호를 허용하지 않고 오직 전용 함수인 `"**CONCAT()**"`만을 강제합니다.
  ```sql
  SELECT CONCAT(clan_name, ' ', person_name) AS full_name FROM person_tb;
  ```

이러한 방언의 차이는 연구자가 로컬(SQLite)에서 테스트한 쿼리를 클라우드 운영 서버(MSSQL)로 이관할 때마다 문법 에러(Syntax Error)를 유발하는 주범이 됩니다.

## 3. 웹 서비스의 척추: 페이징(Pagination) 처리의 극단적 차이

디지털 아카이브 웹사이트를 상상해 보십시오. 사용자가 '조선왕조실록'을 검색했을 때 10만 건의 기사가 존재한다면, 데이터베이스가 이 10만 건을 한 번에 브라우저로 전송해서는 안 됩니다. 서버 메모리가 터지거나 사용자의 브라우저가 멈춰버리기 때문입니다.

따라서 데이터를 10건, 혹은 20건씩 잘라서(예: 1페이지 1~10번, 2페이지 11~20번) 가져오는 `"**페이징(Pagination) 기술**"`이 필수적입니다. 이 페이징 처리는 데이터베이스 방언의 차이가 가장 극명하게 드러나는 지점입니다.

### 3.1 개발자 친화적인 MySQL / SQLite / PostgreSQL
이 진영은 매우 직관적이고 단순한 `"**LIMIT**"`와 `"**OFFSET**"`이라는 혁신적인 키워드를 도입했습니다.

```sql
-- MySQL 방언: 21번째 데이터부터(OFFSET 20), 딱 10개만(LIMIT 10) 가져와라 (즉, 3페이지)
SELECT * FROM annal_articles
ORDER BY article_date DESC
LIMIT 10 OFFSET 20; 
```
코드가 인간의 언어와 매우 유사하여 직관적이며, 웹 개발자들이 이 진영을 열광적으로 지지하게 만든 일등 공신입니다.

### 3.2 복잡성의 극치: 구형 MSSQL 및 Oracle
엔터프라이즈 진영은 오랫동안 LIMIT/OFFSET 같은 편의 기능을 제공하지 않았습니다. 개발자들은 데이터를 자르기 위해 쿼리 안에 쿼리를 넣는 서브쿼리(Subquery)와 `"**ROW_NUMBER()**"`라는 분석 함수를 동원한 기괴한 코드를 짜야만 했습니다.

```sql
-- 구형 MSSQL 방언: 페이징을 위해 가상의 번호를 매기고 서브쿼리로 필터링
SELECT * FROM (
    SELECT ROW_NUMBER() OVER (ORDER BY article_date DESC) AS row_num, *
    FROM annal_articles
) AS temp_table
WHERE row_num BETWEEN 21 AND 30;
```
인문학 전공자가 이 코드를 처음 마주하면 극심한 인지적 과부하에 빠집니다.

### 3.3 현대의 대통합: ANSI 표준 페이징 문법
웹 생태계의 거센 항의에 직면한 MSSQL(2012년 이후)과 Oracle(12c 이후)은 결국 표준화 기구가 제정한 새로운 페이징 문법을 수용했습니다. 

```sql
-- 최신 MSSQL / Oracle (ANSI 표준 문법)
SELECT * FROM annal_articles
ORDER BY article_date DESC
OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY;
```
MySQL의 `LIMIT`보다는 타이핑할 글자가 훨씬 많고 번거롭지만, 최소한 복잡한 서브쿼리를 쓰지 않고도 `"**몇 개를 건너뛰고(OFFSET), 몇 개를 가져올지(FETCH NEXT)**"` 선언할 수 있게 되었습니다.

## 4. 요약

인문학 데이터베이스를 설계하고 쿼리를 작성할 때, 우리는 자신이 서 있는 인프라의 철학을 명확히 이해해야 합니다.
1. **PK 생성:** 테이블 안에서 자동으로 숫자가 올라가는지(`AUTO_INCREMENT`, `IDENTITY`), 아니면 밖에서 스위치를 눌러 번호를 가져오는지(`SEQUENCE`).
2. **페이징 처리:** 직관적인 `LIMIT/OFFSET`을 쓸 수 있는 환경인지, 아니면 보수적이고 길다란 `FETCH NEXT` 문법을 써야 하는 환경인지.

이기종 방언의 거대한 두 산맥을 넘었습니다. 이제 데이터베이스의 문법적 차이를 숙지했으니, 다음 장에서는 조선시대 인물 데이터베이스를 띄워놓고 순수한 SQL 질의의 즐거움을 만끽해 보겠습니다. **"한국학 데이터 추출 실습: 패턴 매칭(LIKE)과 문자열 함수 활용"**을 통해 묻혀있던 사료의 맥락을 데이터로 캐내어 봅시다.
