# DTD 속성 설계: ATTLIST 선언과 식별자 관계망

앞선 장에서 `<!ELEMENT>` 선언을 통해 XML 문서의 뼈대인 트리(Tree) 구조를 설계했다면, 이제는 그 뼈대에 부착되는 이름표, 즉 “**속성(Attribute)**”의 규칙을 강제할 차례입니다. 

속성은 주로 요소의 고유한 식별자, 분류 기준, 메타데이터를 담는 데 사용됩니다. DTD의 속성 선언(`<!ATTLIST>`)은 단순히 어떤 속성 이름이 허용되는가를 넘어서, 값이 반드시 있어야 하는지, 정해진 목록 중에서만 선택해야 하는지, 그리고 다른 데이터와 어떻게 연결되는지(ID와 IDREF)를 엄격하게 통제합니다. 

이 장에서는 디지털 문헌학에서 텍스트를 거대한 지식 그래프(Knowledge Graph)로 엮어내는 가장 핵심적인 문법인 ATTLIST 선언과 식별자 관계망 구축 실무를 탐구합니다.

## 1. ATTLIST 선언의 기본 문법

특정 요소가 가질 수 있는 속성들을 정의할 때는 `<!ATTLIST>` 키워드를 사용합니다. 기본 문법 구조는 다음과 같습니다.

```dtd
<!ATTLIST 요소명 
          속성명1 데이터타입 기본값조건
          속성명2 데이터타입 기본값조건>
```

예를 들어, `<잡지 발행일="1920-06-25" 상태="완간">`이라는 XML 코드가 유효하려면 DTD에 다음과 같은 선언이 있어야 합니다.

```dtd
<!ATTLIST 잡지 
          발행일 CDATA #REQUIRED
          상태 (창간 | 발행중 | 완간 | 폐간) "발행중">
```

이 코드를 완벽하게 해독하기 위해, 먼저 “**기본값 조건**”부터 살펴보겠습니다.

## 2. 속성의 등장 여부 통제: 기본값 조건

요소의 빈도 제어 연산자(`?`, `*`, `+`)처럼, 속성 역시 파서(Parser)에게 이 속성이 필수인지 선택인지를 명확히 알려주어야 합니다.

### 2.1 `#REQUIRED` (필수 속성)
이 조건이 붙은 속성은 XML 문서에서 **절대 생략할 수 없습니다**. 만약 작성자가 이 속성을 누락하면 파서는 즉시 유효성(Valid) 오류를 발생시킵니다. 데이터베이스의 “**기본 키(Primary Key)**”처럼 고유 식별자가 반드시 필요한 곳에 사용합니다.

### 2.2 `#IMPLIED` (선택 속성)
이 조건은 **“있어도 좋고, 없어도 그만이다”**라는 의미입니다. 저자의 이메일 주소나, 한문 사료의 이본(Variants) 교감주처럼 모든 요소에 존재하지는 않는 부가적인 메타데이터에 주로 사용됩니다.

### 2.3 `"기본값"` (디폴트 값 할당)
작성자가 속성을 명시적으로 적지 않았을 때, 파서가 **자동으로 채워 넣을 기본값**을 지정합니다. (예: `상태 CDATA "발행중"`이라고 선언해 두면, 작성자가 `<잡지>`라고만 써도 기계는 내부적으로 `<잡지 상태="발행중">`으로 파싱합니다.)

### 2.4 `#FIXED "고정값"` (변경 불가)
속성의 값을 영구적으로 하나로 못 박습니다. 작성자가 속성을 아예 생략하거나, 정확히 이 고정값과 똑같이 썼을 때만 통과됩니다. 다른 값을 적으면 에러가 납니다. 주로 문서의 버전 정보나 네임스페이스 URI를 고정할 때 사용합니다.

## 3. 데이터 타입(Data Type)의 통제

ATTLIST는 속성에 들어갈 값의 성격을 규정합니다. XML 1.0 DTD에서 제공하는 대표적인 데이터 타입은 다음과 같습니다.

1. **CDATA (Character Data):** 일반적인 문자열입니다. 띄어쓰기나 숫자, 기호 등 파서가 분석하지 않는 순수한 텍스트가 들어갑니다. (요소 내부의 PCDATA와 혼동하지 마십시오. 속성값은 항상 CDATA입니다.)
2. **열거형 (Enumeration):** 속성에 들어갈 수 있는 값의 후보군을 괄호와 수직선(`|`)으로 미리 정해둡니다. (예: `성별 (남 | 여 | 미상) #REQUIRED`). 데이터의 일관성을 유지하는 강력한 도구입니다.

## 4. 지식 네트워크의 구축: ID와 IDREF ★

지금부터 다룰 내용이 DTD 속성 설계의 백미이자, 단순한 계층형 트리 구조의 XML을 거미줄 같은 “**네트워크(Network) 모델**”로 도약시키는 핵심 기술입니다.

### 4.1 `ID` (고유 식별자)
속성의 데이터 타입을 `ID`로 지정하면, 그 속성값은 해당 XML 문서 전체에서 **절대 중복될 수 없는 고유한 주소**가 됩니다. 
* **규칙:** ID 값은 반드시 알파벳이나 밑줄(`_`)로 시작해야 하며, 숫자로 시작할 수 없습니다.

```dtd
<!ATTLIST 인물 고유번호 ID #REQUIRED>
```
위와 같이 선언하면, `<인물 고유번호="P001">이순신</인물>`과 같이 마크업할 수 있습니다. 만약 다른 인물에 또다시 `P001`을 부여하면 치명적인 오류가 발생합니다.

### 4.2 `IDREF` (식별자 참조)와 `IDREFS` (다중 참조)
`IDREF`는 앞서 정의된 `ID` 값을 정확히 가리키는 “**포인터(Pointer)**”입니다. 이를 통해 XML 문서 내의 멀리 떨어진 두 정보가 논리적으로 연결됩니다. `IDREFS`는 공백으로 구분하여 여러 개의 ID를 동시에 참조할 수 있게 해줍니다.



### 4.3 실전 마크업: 관계망(Graph)의 융합
국사편찬위원회의 근현대잡지자료에서 한 기사에 여러 필자가 등장하고, 이 필자들이 다른 기사에도 반복적으로 등장한다고 가정해 봅시다. 요소만으로는 이 인물들이 동일 인물임을 증명하기 어렵습니다. ID와 IDREF를 사용하면 완벽한 관계망이 형성됩니다.

**[DTD 설계]**
```dtd
<!ELEMENT 잡지데이터 (인물사전, 기사목록)>
<!ELEMENT 인물사전 (인물+)>
<!ELEMENT 인물 (#PCDATA)>
<!ATTLIST 인물 
          인물ID ID #REQUIRED
          직업 CDATA #IMPLIED>

<!ELEMENT 기사목록 (기사+)>
<!ELEMENT 기사 (제목)>
<!ELEMENT 제목 (#PCDATA)>
<!ATTLIST 기사 
          필자참조 IDREFS #REQUIRED>
```

**[XML 마크업 데이터]**
```xml
<잡지데이터>
    <인물사전>
        <인물 인물ID="P_001" 직업="소설가">이광수</인물>
        <인물 인물ID="P_002" 직업="시인">최남선</인물>
    </인물사전>

    <기사목록>
        <기사 필자참조="P_001">
            <제목>무정</제목>
        </기사>
        <기사 필자참조="P_001 P_002">
            <제목>소년 창간사</제목>
        </기사>
    </기사목록>
</잡지데이터>
```

이 마크업 구조는 혁명적입니다. 기사 데이터 안에는 필자의 이름이 문자로 직접 적혀 있지 않지만, 컴퓨터는 `필자참조="P_001 P_002"`라는 지시어를 따라가 `<인물사전>`에 있는 이광수와 최남선을 실시간으로 끌어옵니다. 

이것이 바로 현대 인공지능이 환각 없이 사실을 추론할 때 의존하는 “**지식 그래프(Knowledge Graph)**”의 원형입니다. 수직적인 트리(Tree) 구조의 한계를 부수고, 정보와 정보를 횡적으로 엮어내는 힘, 그것이 바로 DTD의 `ID`와 `IDREF`가 디지털 문헌학에 선사한 가장 위대한 정보공학적 무기입니다.

우리는 DTD를 활용해 요소와 속성의 엄격한 통제법을 모두 마스터했습니다. 그러나 DTD는 XML과 문법 체계가 다르고 정교한 데이터 타입(예: 숫자만 입력, 날짜 형식만 입력)을 제한하는 데 한계가 있습니다. 이어지는 장에서는 DTD의 한계를 극복하기 위해 등장한 현대 디지털 아카이브의 새로운 법전, “**XML 스키마(XSD)**”의 세계로 진입하겠습니다.
