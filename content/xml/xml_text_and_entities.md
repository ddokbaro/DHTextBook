# 텍스트 처리 규칙: PCDATA, CDATA, 개체 참조

앞선 장에서 우리는 요소(Element)와 속성(Attribute)이라는 XML 문서의 견고한 “**뼈대(Tree)**”를 세우는 방법을 학습했습니다. 이제 그 뼈대 안에 인문학적 지식의 실체인 “**살(Text)**”을 채워 넣을 차례입니다.

XML 문서를 해석하는 컴퓨터 프로그램인 “**파서(Parser)**”는 문서 내의 텍스트를 읽을 때 일정한 규칙을 적용합니다. 파서의 눈에는 우리가 무심코 작성한 수학 기호나 괄호가 문법적인 명령어(태그)로 오인될 수 있습니다. 이 장에서는 파서가 텍스트를 처리하는 두 가지 핵심 방식인 “**PCDATA**”와 “**CDATA**”의 개념을 명확히 구분하고, 기호 충돌을 우회하기 위한 “**개체 참조(Entity Reference)**” 기술을 심층적으로 다룹니다.

## 1. PCDATA (Parsed Character Data): 파싱되는 텍스트

XML 문서의 요소 내부에 입력되는 대부분의 일반적인 텍스트는 “**PCDATA(Parsed Character Data)**”로 취급됩니다. 이는 단어 뜻 그대로 “**파서에 의해 구문 분석(Parsing)이 이루어지는 문자 데이터**”를 의미합니다.

파서가 PCDATA 구역을 읽을 때, 컴퓨터는 단순히 글자를 스쳐 지나가지 않고 항상 신경을 곤두세운 채 두 가지 특수 기호를 애타게 찾습니다.
1. ` < ` (여는 꺾쇠괄호): “**아, 여기서부터 새로운 태그(요소)가 시작되는구나!**”
2. ` & ` (앰퍼샌드): “**아, 여기서부터 특수한 개체(Entity)가 시작되는구나!**”

### 1.1 치명적인 구문 오류(Fatal Error)의 발생
파서의 이러한 예민함은 인문학 데이터를 마크업할 때 종종 심각한 충돌을 일으킵니다. 예를 들어, 수학사 사료를 마크업하거나 텍스트 내에서 부등호를 사용해야 하는 경우를 가정해 봅시다.

```xml
<기록>세종 10년, A의 수확량이 B의 수확량보다 < (작다)는 보고가 올라왔다.</기록>
```

이 문서를 파서가 읽는 순간, 에러를 내뿜으며 작동을 멈추게 됩니다. 파서는 ` < (작다) ` 부분의 `<` 기호를 보는 순간 이를 “**새로운 태그의 시작**”으로 인식합니다. 하지만 그 뒤에 태그 이름 규칙에 어긋나는 공백과 괄호가 이어지고 닫는 태그조차 없기 때문에, 문서 전체가 규칙 위반(Well-formedness 훼손)으로 판정되어 시스템이 붕괴하는 것입니다.



## 2. 개체 참조 (Entity Reference): 기호의 우회

이러한 PCDATA 구역 내의 기호 충돌을 방지하기 위해 XML이 고안한 안전장치가 바로 “**개체 참조(Entity Reference)**”입니다. 이는 파서가 오해할 수 있는 특수 기호를 컴퓨터가 안전하게 읽을 수 있는 대체 문자열로 치환하는 문법입니다. 

개체 참조는 반드시 앰퍼샌드(`&`)로 시작하여 세미콜론(`;`)으로 끝납니다.

### 2.1 XML의 5대 미리 정의된 개체 (Predefined Entities)
XML은 마크업에 사용되는 핵심 기호들을 우회하기 위해 5가지의 개체를 기본적으로 내장하고 있습니다. 본문 텍스트 내에서 아래의 기호를 사용할 때는 반드시 우측의 개체 참조 코드로 치환하여 작성해야 합니다.

* ` < ` (Less than) ➔ `&lt;`
* ` > ` (Greater than) ➔ `&gt;`
* ` & ` (Ampersand) ➔ `&amp;`
* ` " ` (Double quote) ➔ `&quot;`
* ` ' ` (Apostrophe) ➔ `&apos;`

위의 수학사 사료 오류는 다음과 같이 개체 참조를 적용하여 완벽하게 해결할 수 있습니다.

```xml
<기록>세종 10년, A의 수확량이 B의 수확량보다 &lt; (작다)는 보고가 올라왔다.</기록>
```

### 2.2 문자 개체 참조 (Character References)
키보드에 존재하지 않는 고문헌의 특수 한자나 옛한글, 혹은 유니코드 특수 기호를 본문에 삽입해야 할 때도 이 문법을 응용할 수 있습니다. 십육진수 유니코드 값을 `&#x` 와 `;` 사이에 넣으면, 파서가 이를 해당 문자로 변환하여 출력합니다.
* 예시: `&#x20A9;` ➔ ₩ (원화 기호)
* 예시: `&#x97F3;` ➔ 音 (소리 음)

실제 **조선왕조실록** 데이터베이스와 같은 거대한 디지털 아카이브에서는, 디지털 폰트로 구현되지 않는 희귀한 한자(결자, Gaiji)를 표기하기 위해 이러한 문자 개체 참조 방식이 아주 빈번하게 사용됩니다.

## 3. CDATA (Character Data): 파싱의 면책 특권 구역

개체 참조(`&lt;` 등)는 훌륭한 해결책이지만, 텍스트 본문 내에 `<` 와 `&` 기호가 수백 개씩 등장한다면 어떨까요? 예를 들어 디지털 문헌학 논문 안에서 방대한 프로그래밍 소스 코드나 수식을 통째로 인용해야 할 경우, 모든 기호를 일일이 `&lt;` 로 바꾸는 작업은 끔찍한 노동이 될 것입니다.

이때 사용하는 강력한 문법이 바로 “**CDATA(Character Data)**” 구역입니다. 

]>` shielding internal text from the XML parser]

CDATA는 파서에게 “**지금부터 내가 지정한 구역이 끝날 때까지, 이 안에 있는 모든 꺾쇠괄호나 앰퍼샌드는 문법적 태그가 아니라 순수한 글자(문자 데이터)일 뿐이니 절대로 파싱(구문 분석)하지 마라!**”라고 명령하는 “**파싱 면책 특권 구역**”입니다.

### 3.1 CDATA의 문법 구조
CDATA 구역은 `<![CDATA[` 로 시작하여 `]]>` 로 끝납니다.

```xml
<논문_본문>
    다음은 조선왕조실록을 마크업한 XML 코드의 예시입니다.
    <![CDATA[
        <사료>
            <왕대>세종</왕대>
            <기사>훈민정음을 창제하였다.</기사>
        </사료>
    ]]>
    위 코드를 통해 기계가독성을 확인할 수 있습니다.
</논문_본문>
```

위의 예시에서 파서는 `<![CDATA[` 를 만나는 순간 분석의 칼날을 거둡니다. 따라서 그 내부에 있는 `<사료>`, `<왕대>` 등의 문자는 새로운 XML 태그로 취급되어 구조를 꼬이게 만들지 않고, 그저 “**<사료>**”라는 텍스트 덩어리 자체로 안전하게 데이터베이스에 저장됩니다.

## 4. 실무 설계 가이드: PCDATA vs CDATA

디지털 아카이브를 구축하는 인문학자는 언제 개체 참조를 사용하고, 언제 CDATA를 사용해야 할지 정보공학적으로 판단해야 합니다.

1. **원칙적인 사용 (개체 참조):** 인문학적 텍스트의 본문은 기본적으로 PCDATA로 취급되어야 합니다. 문장 중간에 한두 번 등장하는 특수 기호는 반드시 `&lt;` 나 `&amp;` 등의 개체 참조를 사용하여 정석대로 처리하는 것이 검색 및 데이터 통일성 유지에 유리합니다.
2. **예외적인 캡슐화 (CDATA 구역):** 수십 줄의 프로그래밍 코드, 수많은 특수문자가 섞인 원시 데이터(Raw Data), 혹은 아직 정제되지 않아 에러를 일으킬 확률이 높은 외부 문서의 조각을 통째로 XML 문서 안에 “**캡슐화(Encapsulation)**”하여 보관해야 할 때 전략적으로 CDATA 구역을 활용합니다.

결론적으로 파서가 텍스트를 읽어 들이는 원리를 이해하고, 개체 참조와 CDATA를 능수능란하게 다루는 능력은 공들여 만든 문서가 사소한 기호 충돌로 인해 시스템 에러로 붕괴하는 것을 막아주는 필수적인 방어 기술입니다. 

이제 우리는 뼈대(요소와 속성)와 살(텍스트 규칙)을 모두 갖추었습니다. 이어지는 장에서는 이 요소들이 제멋대로 쓰이지 않도록, 학문적 목적에 맞게 엄격한 문법과 규칙을 강제하는 두 가지 중요한 개념, “**웰폼드(Well-formed) 문서**”와 “**네임스페이스(Namespace)**”에 대해 알아보겠습니다.
