# Schematron: XPath 기반의 논리적 제약과 비즈니스 룰 검증

지금까지 우리가 학습한 DTD, XSD, RelaxNG는 모두 “**문법 기반(Grammar-based)**” 스키마입니다. 이들은 어떤 요소가 누구의 부모인지, 속성의 타입은 무엇인지 등 문서의 “**형태와 구조**”를 검증하는 데 탁월합니다. 

그러나 인문학 데이터를 편찬하다 보면 형태가 아니라 “**논리적 모순**”을 잡아내야 할 때가 있습니다. 예를 들어, “**생년월일은 반드시 사망일보다 앞서야 한다**”거나, “**문서의 상태가 ‘번역완료’라면 반드시 `<번역문>` 요소가 존재해야 한다**”와 같은 규칙입니다. 기존의 문법 기반 스키마들은 이러한 요소 간의 교차 검증을 수행할 능력이 없습니다.

이러한 논리적 제약, 즉 “**비즈니스 룰(Business Rule)**”을 검증하기 위해 탄생한 ISO 국제 표준 스키마가 바로 “**Schematron(스케마트론)**”입니다. 이 장에서는 트리 탐색 언어인 XPath를 엔진으로 삼아 데이터의 논리적 결함을 찾아내는 Schematron의 설계 철학과 실무를 심층적으로 탐구합니다.

## 1. Schematron의 철학과 XPath 엔진

Schematron은 문서의 전체 뼈대를 처음부터 끝까지 통제하려 하지 않습니다. 대신, 데이터베이스 관리자가 특별히 지정한 “**특정 논리적 조건**”이 위배되었는지만을 핀셋처럼 집어내어 검사합니다. 

이러한 정밀 타격을 가능하게 하는 Schematron의 핵심 엔진이 바로 “**XPath(XML Path Language)**”입니다. XPath는 XML이라는 거대한 가상의 나무에서 특정한 조건(예: “**속성값이 A인 요소의 두 번째 자식**”)을 만족하는 노드(Node)를 찾아내는 강력한 경로 탐색 언어입니다. Schematron은 이 XPath를 활용하여 요소들의 값을 서로 비교하고, 모순이 발견되면 사람이 읽기 편한 에러 메시지를 출력해 줍니다.



## 2. Schematron의 5대 핵심 문법

Schematron 스키마(`.sch` 확장자)는 XML 문법으로 작성되며, 구조가 매우 직관적이고 단순합니다. 다음의 5가지 핵심 요소만 이해하면 어떠한 복잡한 논리도 검증할 수 있습니다.

### 2.1 `<schema>` (스키마 선언)
Schematron 문서의 루트 요소입니다. 네임스페이스를 선언하고 전체 규칙을 묶어줍니다.

### 2.2 `<pattern>` (패턴 그룹)
관련 있는 규칙(Rule)들을 논리적으로 묶어주는 그룹화 요소입니다. (예: “**날짜 관련 검증 패턴**”, “**인물 정보 검증 패턴**” 등)

### 2.3 `<rule context="XPath">` (검사 대상 지정)
`context` 속성에 XPath를 입력하여, “**이 규칙을 XML 문서 내의 어떤 요소에 적용할 것인가**”를 타겟팅합니다.

### 2.4 `<assert test="XPath">` (참이어야 하는 조건)
Schematron의 심장입니다. `test` 속성에 입력된 XPath 조건이 “**반드시 참(True)이어야 한다**”고 주장(Assert)합니다. 만약 이 조건이 거짓(False)으로 판명되면, `<assert>` 태그 사이에 적어둔 에러 메시지를 사용자에게 출력합니다.

### 2.5 `<report test="XPath">` (거짓이어야 하는 조건)
`<assert>`의 정확한 반대입니다. `test` 속성의 조건이 “**참(True)이 되면 안 된다**”고 경고합니다. 만약 이 조건이 참으로 판명되면 경고 메시지를 출력합니다. 주로 예외 상황이나 금지된 패턴을 찾아낼 때 유용합니다.

## 3. 실전 인문학 데이터 교차 검증 (Practicum)

역사 인물 사전 데이터베이스를 구축하는 상황을 가정해 보겠습니다. 이 데이터에는 다음과 같은 치명적인 휴먼 에러가 포함되어 있습니다. 사망년도가 출생년도보다 빠르고, 직업이 명시되지 않았음에도 상세 정보가 기입되어 있습니다.

**[오류가 포함된 원본 XML 데이터]**
```xml
<인물사전>
    <인물>
        <이름>홍길동</이름>
        <출생년도>1500</출생년도>
        <사망년도>1490</사망년도>
    </인물>
    <인물 직업="미상">
        <이름>아무개</이름>
        <소속기관>조정</소속기관>
    </인물>
</인물사전>
```

XSD나 RelaxNG는 이 문서가 “**정수(Integer) 형태를 갖추었고, 요소들이 잘 배치되었다**”며 정상적인 데이터로 통과시킬 것입니다. 하지만 Schematron을 적용하면 숨어있는 논리적 모순을 완벽하게 잡아낼 수 있습니다.

**[비즈니스 룰을 적용한 Schematron 설계]**
```xml
<?xml version="1.0" encoding="UTF-8"?>
<schema xmlns="[http://purl.oclc.org/dsdl/schematron](http://purl.oclc.org/dsdl/schematron)">

    <pattern id="Chronology_Check">
        <title>생몰년도 역전 검사</title>
        <rule context="인물[사망년도]">
            <assert test="number(사망년도) >= number(출생년도)">
                논리 오류 발생: 사망년도(<value-of select="사망년도"/>)가 
                출생년도(<value-of select="출생년도"/>)보다 빠를 수 없습니다!
            </assert>
        </rule>
    </pattern>

    <pattern id="Dependency_Check">
        <title>직업과 소속기관의 논리 검사</title>
        <rule context="인물[@직업=&quot;미상&quot;]">
            <report test="소속기관">
                모순 발생: 직업이 "미상"으로 분류된 인물은 
                <소속기관> 요소를 가질 수 없습니다.
            </report>
        </rule>
    </pattern>

</schema>
```

위의 Schematron 코드는 파서가 문서를 읽을 때 다음과 같이 작동합니다.
1. 첫 번째 `<assert>`는 인물의 사망년도가 출생년도보다 크거나 같아야 한다고 강제합니다. 홍길동의 데이터(1490 < 1500)는 이 조건에 거짓이 되므로, 즉시 “**논리 오류 발생: 사망년도가 빠를 수 없습니다!**”라는 에러를 내뿜습니다.
2. 두 번째 `<report>`는 직업이 “**미상**”인데 내부에 `<소속기관>`이라는 자식 요소가 존재하는지를 검사합니다. 아무개의 데이터에 `<소속기관>`이 존재하므로 조건이 참이 되어, “**모순 발생: 소속기관을 가질 수 없습니다.**”라는 경고를 띄웁니다.

## 4. 완벽한 스키마 전략: XSD/RelaxNG + Schematron

Schematron은 구조를 정의하는 스키마가 아닙니다. 따라서 DTD나 XSD를 대체하는 것이 아니라, 그들과 “**상호 보완적(Complementary)**”으로 작동해야 합니다.

실제 국가 단위의 거대 디지털 아카이브 프로젝트에서는 다음과 같은 2단계 검증 파이프라인(Pipeline)을 구축합니다.
1. **1단계 (형태 검증):** XSD나 RelaxNG를 통해 XML 문서의 트리 구조와 데이터 타입(정수, 날짜 등)이 올바른지 거시적으로 검증합니다.
2. **2단계 (논리 검증):** 1단계를 통과한 문서에 Schematron을 적용하여, 데이터 간의 모순이나 비즈니스 룰 위반 사항을 미시적으로 교차 검증합니다.

이 완벽한 이중 방어막을 거친 인문학 데이터만이 비로소 인공지능(AI)과 그래프 데이터베이스(Graph RAG) 생태계에 편입될 자격을 얻게 됩니다. 이제 우리는 마크업 문법과 스키마 설계의 모든 것을 마스터했습니다. 이어지는 장에서는 이 구축된 XML 트리에서 특정 데이터를 정밀하게 추출하고 변환하는 본격적인 쿼리 기술, “**XPath와 XPointer**”의 세계로 진입하겠습니다.
