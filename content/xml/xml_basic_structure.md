# XML의 뼈대: 요소와 속성

하이퍼텍스트의 역사와 매체 철학을 통해 기계가독성의 중요성을 인식했다면, 이제 아날로그 텍스트를 기계의 뇌 속으로 이식하기 위한 구체적인 문법을 학습할 차례입니다. 

XML(eXtensible Markup Language)은 텍스트에 질서를 부여하는 고도로 정교한 건축 도구입니다. 이 장에서는 XML 문서를 지탱하는 거대한 골조인 “**트리(Tree) 구조**”를 이해하고, 지식을 담는 그릇인 “**요소(Element)**”와 그 그릇의 메타데이터인 “**속성(Attribute)**”의 문법적 정의 및 실무적 설계 가이드를 심층적으로 탐구합니다.

## 1. XML 문서의 해부학: 트리(Tree) 구조

모든 정상적인 XML 문서는 가상의 “**거꾸로 선 나무(Tree)**” 형태의 논리적 계층 구조를 가집니다. 컴퓨터 과학과 디지털 문헌학에서는 이러한 구조를 통해 문서 내의 모든 정보(노드, Node)가 정확히 어디에 위치하는지 좌표를 추적합니다.



트리 구조를 구성하는 핵심 관계망은 다음과 같습니다.

* **루트 노드(Root Node):** 나무의 기둥이자 문서 전체를 감싸는 단 하나의 최상위 요소입니다. 하나의 XML 문서에는 반드시 단 하나의 루트 요소만 존재해야 합니다.
* **부모(Parent)와 자식(Child):** 특정 요소를 직접 감싸고 있는 상위 요소를 부모라고 하며, 그 내부에 포함된 하위 요소를 자식이라고 부릅니다.
* **형제(Sibling):** 동일한 부모 요소 바로 아래에 병렬로 나란히 위치한 요소들을 의미합니다.

예를 들어, 한국학 사료를 마크업한 아래의 코드를 살펴봅시다.

```xml
<조선왕조실록>
    <왕대 이름="세종">
        <기사 년도="1446">훈민정음을 반포하다.</기사>
        <기사 년도="1447">용비어천가를 간행하다.</기사>
    </왕대>
</조선왕조실록>
```

여기서 `<조선왕조실록>`은 “**루트 요소**”입니다. `<왕대>`는 `<조선왕조실록>`의 “**자식**”이자 두 개의 `<기사>` 요소를 거느린 “**부모**”입니다. 그리고 두 개의 `<기사>` 요소는 서로 “**형제**” 관계를 맺고 있습니다. 컴퓨터는 이 엄격한 족보(Tree)를 바탕으로 데이터의 위계를 파악합니다.

## 2. 요소(Element): 지식을 담는 그릇

XML에서 정보를 묶어내는 가장 기본적이고 핵심적인 단위가 바로 “**요소(Element)**”입니다. 요소는 꺾쇠괄호(`< >`)로 둘러싸인 “**시작 태그(Start Tag)**”와 슬래시(`/`)가 포함된 “**종료 태그(End Tag)**”의 쌍으로 구성되며, 그사이에 내용(Content)을 품습니다.

### 2.1 요소의 작성 규칙
XML은 대중적인 HTML과 달리 문법에 있어 한 치의 자비도 허용하지 않는 엄격한 언어입니다. 
* **대소문자의 엄격한 구분:** `<Person>`과 `<person>`은 컴퓨터에게 완전히 다른 요소로 인식됩니다.
* **이름 생성 규칙:** 요소의 이름은 반드시 문자(알파벳, 한글 등)나 밑줄(`_`)로 시작해야 하며, 공백이나 수학 기호(`+`, `-` 등)를 포함할 수 없습니다.

### 2.2 빈 요소(Empty Element)
만약 요소 내부에 들어갈 텍스트 내용이 전혀 없다면, 시작 태그와 종료 태그를 결합하여 간략하게 표기할 수 있습니다. 이를 “**빈 요소**”라고 부릅니다. 주로 이미지의 경로를 지정하거나 구조적인 분기점을 나눌 때 사용됩니다.
* 일반 표기: `<이미지></이미지>`
* 빈 요소 표기: `<이미지/>`

## 3. 속성(Attribute): 그릇의 메타데이터

“**속성(Attribute)**”은 요소가 품고 있는 데이터에 대한 추가적인 정보(메타데이터)를 제공하는 역할을 합니다. 속성은 독립적으로 존재할 수 없으며, 반드시 요소의 “**시작 태그 내부**”에 `이름="값"`의 형태로 기입되어야 합니다.

### 3.1 속성의 작성 규칙
* **인용 부호의 필수 사용:** 속성의 값은 반드시 큰따옴표(`" "`)로 묶어야 합니다. (문법적으로는 다른 부호도 가능하나, 디지털 문헌학 실무에서는 데이터 파싱의 안정성을 위해 큰따옴표 사용을 엄격한 표준으로 삼습니다.)
* **중복 불가:** 하나의 시작 태그 내에서 동일한 이름의 속성을 두 번 사용할 수 없습니다.

예컨대 `<인물 id="P001" 신분="무관">이순신</인물>`에서 “**id**”와 “**신분**”은 이순신이라는 요소 데이터를 시스템적으로 분류하고 고유하게 식별하기 위해 부여된 속성입니다.

## 4. 실무 설계 가이드: 요소로 뺄 것인가, 속성으로 뺄 것인가?

디지털 아카이브를 구축하기 위해 처음 마크업 스키마를 설계할 때, 연구자들이 가장 많이 부딪히는 정보공학적 딜레마는 “**특정 정보를 요소(Element)로 만들 것인지, 아니면 속성(Attribute)으로 처리할 것인지**”를 결정하는 것입니다.

예를 들어 잡지의 발행일 정보를 마크업할 때, 다음의 두 방식은 모두 문법적으로 옳습니다.

**[방식 A: 요소 중심 설계]**
```xml
<잡지>
    <발행일>1920-06-25</발행일>
    <잡지명>개벽</잡지명>
</잡지>
```

**[방식 B: 속성 중심 설계]**
```xml
<잡지 발행일="1920-06-25" 잡지명="개벽">
    <본문>...</본문>
</잡지>
```

정답은 연구의 목적과 데이터의 성격에 따라 달라지지만, 디지털 인문학 데이터 편찬 실무에서는 다음과 같은 명확한 기준을 따릅니다.

### 4.1 요소(Element)를 선택해야 하는 경우
* **하위 구조를 가질 가능성이 있을 때:** 정보가 단순히 하나의 단어가 아니라, 쪼개질 여지가 있다면 반드시 요소로 만들어야 합니다. 예컨대 발행일이 연, 월, 일로 세분화될 수 있다면 `<발행일><연>1920</연><월>06</월></발행일>`처럼 계층 구조를 품을 수 있는 요소가 적합합니다. 속성은 그 자체로 하위 속성을 가질 수 없는 단일 값(Atomic Value)이기 때문입니다.
* **데이터의 길이가 길거나 다중행(Multi-line)일 때:** 기사의 본문이나 장문의 주석 등은 속성값으로 넣기 부적절합니다.

### 4.2 속성(Attribute)을 선택해야 하는 경우
* **데이터를 식별하거나 정렬하기 위한 메타데이터일 때:** 실제 화면이나 종이에 출력될 내용이 아니라, 컴퓨터가 데이터를 검색하고 분류하기 위한 고유 식별자(ID)나 상태값인 경우 속성으로 처리하는 것이 유리합니다. 
* 실제 국사편찬위원회의 **한국근현대잡지자료**와 같은 거대 데이터베이스의 스키마를 해부해 보면, 잡지의 권호 정보, 발행일, 저자명 등은 계층 구조를 관장하는 상위 태그(`<level1>`, `<level2>`)의 “**속성**”으로 깔끔하게 밀어 넣고, 실제 연구자가 읽고 분석해야 할 기사의 본문 텍스트 자체만을 “**요소**” 내부에 남겨두는 고도화된 설계를 취하고 있습니다.

이처럼 요소와 속성의 역할을 엄격하게 구분하여 스키마를 설계하는 것은 데이터베이스의 연산 효율성을 극대화하는 핵심 실무입니다. 이어지는 장에서는 이 거대한 트리 구조 속에서 파싱되는 텍스트와 파싱되지 않는 텍스트를 통제하는 “**엔티티(Entity)**”와 “**CDATA**”의 규칙을 심도 있게 알아보겠습니다.
