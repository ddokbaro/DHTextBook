# XSD의 탄생과 기본 구조: DTD의 한계 극복

이전 장들에서 우리는 DTD(Document Type Definition)를 활용하여 XML의 트리 구조를 설계하고 속성을 통제하는 방법을 마스터했습니다. DTD는 SGML 시절부터 문헌을 구조화해 온 훌륭하고 역사적인 뼈대입니다. 

그러나 인문학 데이터가 단순한 텍스트의 구조화를 넘어, 인공지능과 데이터베이스가 연산할 수 있는 “**정밀한 데이터 자산**”으로 격상되면서 DTD는 치명적인 한계를 드러내기 시작했습니다. 이 장에서는 DTD가 왜 역사 속으로 물러나게 되었는지 그 정보공학적 한계를 낱낱이 해부하고, 현대 디지털 아카이브의 새로운 헌법으로 자리 잡은 “**XML Schema(XSD)**”의 등장 배경과 기본 구조를 심층적으로 다룹니다.

## 1. DTD의 3가지 치명적 한계

DTD는 훌륭한 구조 검증 도구이지만, 데이터의 “**내용 자체**”를 정밀하게 검증하는 데에는 완전히 무력합니다.



### 1.1 데이터 타입(Data Type)의 부재
이것이 DTD의 가장 뼈아픈 한계입니다. DTD에서 요소의 내용은 오직 `(#PCDATA)`라는 “**단순 문자열**”로만 정의될 수 있습니다. 
예를 들어 `<발행년도>`라는 요소에 오직 숫자만 들어가게 하거나, `<생년월일>`에 `YYYY-MM-DD` 형태의 날짜 형식만 들어가도록 강제할 방법이 DTD에는 전혀 없습니다.

* **DTD의 관점:** `<발행년도>조선시대</발행년도>` (PCDATA이므로 **통과**)
* **발생하는 문제:** 데이터베이스 연산 시 숫자형 필드에 문자가 들어와 시스템이 붕괴합니다.

### 1.2 자체 문법의 이질성
DTD는 XML 문서 내에서 활동하지만, 그 자신은 XML 문법을 따르지 않습니다. `<!ELEMENT>`, `<!ATTLIST>`와 같은 낡은 SGML식 표기법을 사용합니다. 이는 개발자와 연구자가 XML 문법과 DTD 문법을 이중으로 학습해야 하는 부담을 주며, 표준 XML 파서(Parser)만으로는 DTD의 구조를 손쉽게 파싱하거나 수정하기 어렵게 만듭니다.

### 1.3 네임스페이스(Namespace) 지원의 취약성
현대의 데이터베이스 융합(Mashup) 환경에서는 여러 기관의 태그가 섞이는 네임스페이스 활용이 필수적입니다. 그러나 DTD는 태그 이름에 콜론(`:`)이 들어가는 것을 단순히 이름의 일부로만 취급할 뿐, 네임스페이스의 고유한 URI를 동적으로 검증하고 통제하는 기능을 제대로 지원하지 못합니다.

## 2. XML Schema(XSD)의 패러다임 전환

이러한 DTD의 치명적 결함을 완벽하게 해결하기 위해, 2001년 W3C(월드와이드웹 컨소시엄)는 “**XML Schema Definition (XSD)**”이라는 혁명적인 표준을 발표합니다.

XSD가 가져온 가장 거대한 패러다임의 전환은 다음 두 가지입니다.

1. **XSD 스스로가 완벽한 XML 문서이다:** XSD는 더 이상 이상한 기호(`<! >`)를 쓰지 않습니다. XSD 문서 자체가 `<xs:element>`와 같은 XML 태그로 이루어져 있습니다. 즉, XML을 다루는 모든 프로그래밍 언어와 도구로 XSD 문서 자체를 쉽게 조작하고 분석할 수 있습니다.
2. **강력하고 풍부한 데이터 타입(Rich Data Typing):** XSD는 정수, 소수, 날짜, 시간, 불리언(True/False) 등 프로그래밍 언어에 필적하는 40여 가지의 내장 데이터 타입을 지원합니다. 이제 기계는 텍스트를 단순한 글자가 아니라 “**연산 가능한 데이터 객체**”로 인식하게 됩니다.

## 3. XSD 문서의 해부학: 기본 뼈대와 선언

XSD 문서(주로 `.xsd` 확장자를 가짐)는 그 자체로 XML 문서이므로, 최상단에 XML 선언을 가져야 하며 루트 요소로 `<schema>`를 사용합니다.

XSD 스키마 문서의 가장 기본적인 골격은 다음과 같습니다.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<xs:schema xmlns:xs="[http://www.w3.org/2001/XMLSchema](http://www.w3.org/2001/XMLSchema)"
           targetNamespace="[http://dh.aks.ac.kr/magazine](http://dh.aks.ac.kr/magazine)"
           xmlns="[http://dh.aks.ac.kr/magazine](http://dh.aks.ac.kr/magazine)"
           elementFormDefault="qualified">
    
    </xs:schema>
```

이 압도적인 선언부를 정보공학적으로 하나씩 분해해 보겠습니다.

### 3.1 `xmlns:xs="http://www.w3.org/2001/XMLSchema"`
이 구문은 “**이 문서에서 `xs:` 라는 접두사가 붙은 모든 태그는 W3C가 제정한 표준 XML Schema 문법 명령어이다**”라는 것을 기계에게 선언하는 네임스페이스 바인딩입니다. 따라서 `<xs:element>`, `<xs:complexType>` 등은 내가 만든 데이터가 아니라, 법을 집행하는 “**규칙 그 자체**”로 작동합니다. (접두사는 `xsd:`로 써도 무방하나 `xs:`가 실무 표준입니다.)

### 3.2 `targetNamespace` (목표 네임스페이스)
이 속성은 매우 중요합니다. “**지금 이 XSD 설계도를 통해 내가 새롭게 정의하고 있는 요소들(예: 잡지, 기사, 저자)이 최종적으로 어느 네임스페이스(소속)에 등록될 것인가**”를 명시하는 곳입니다. 내가 만든 태그들에 고유한 호적(URI)을 부여하는 행위입니다.

### 3.3 `elementFormDefault="qualified"`
이 설정은 검증의 엄격성을 통제합니다. `"qualified"`로 설정하면, 실제 XML 문서를 작성할 때 이 스키마에서 파생된 모든 자식 요소들이 반드시 위에서 지정한 목표 네임스페이스에 명시적으로 소속되어야 함(접두사나 기본 네임스페이스를 통해)을 강제합니다. 어휘 충돌을 원천 차단하는 가장 안전한 실무적 세팅입니다.

결론적으로 XSD의 등장은 인문학 데이터베이스가 텍스트의 모음을 넘어, 엄격한 수학적 검증과 데이터 타입 통제를 받는 고도의 “**지식 정보 시스템**”으로 진화했음을 알리는 신호탄입니다. 

이제 우리는 XSD가 제공하는 진정한 힘, 즉 요소의 복잡도(Complex/Simple)를 설계하고 정규표현식(Regex)을 통해 입력값을 바늘구멍처럼 통제하는 “**XSD 데이터 타입 설계의 심연**”으로 진입하겠습니다.
