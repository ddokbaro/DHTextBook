# 30.3. 다중 홉 논리 탐색: RelFinder를 이용한 관계망 발견

## 1. 도입: "이순신과 원균은 도대체 어떤 경로로 얽혀 있는가?"

우리는 30.1장의 **LodLive**를 통해 하나의 노드에서 출발하는 "점진적 탐색"을, 30.2장의 **WebVOWL**을 통해 지식 그래프 전체의 "조감도"를 확인했습니다. 

하지만 역사학자와 데이터 탐정들의 가장 깊은 호기심은 완전히 다른 곳을 향합니다. 
만약 여러분이 수백만 건의 데이터가 얽힌 조선시대 지식 그래프 서버를 띄워놓고, 다음과 같은 질문을 던진다고 상상해 보십시오.
**"전라좌수사 이순신과 경상우수사 원균, 이 두 사람 사이에 도대체 어떤 숨겨진 인맥이나 사건들이 연결 고리로 작용했는가? 이 둘을 잇는 모든 경로를 찾아내라!"**

LodLive로는 이순신의 주변을 수십 번 클릭하며 우연히 원균을 마주칠 때까지 헤매야 합니다. 일반적인 SPARQL 쿼리로 이를 알아내려면 `?s ?p1 ?o1 . ?o1 ?p2 ?o2 ...` 처럼 끝을 알 수 없는 미로 같은 코드를 짜야 합니다. 인간의 두뇌로는 두 개체 사이에 존재하는 복잡한 "**다중 홉(Multi-hop, 징검다리)**"의 경로를 단번에 꿰뚫어 볼 수 없습니다. 우리는 기계에게 두 점 사이의 최단 경로를 계산하는 네비게이션을 장착해야 합니다.

## 2. 해결책 제시: 지식망의 숨은 징검다리 찾기, "**RelFinder**"

서로 멀리 떨어져 있는 두 개체(Node) 사이의 숨겨진 관계망을 기하학적으로 추론하여 시각화해 주는 독보적인 오픈소스 웹 도구가 바로 "**RelFinder(릴파인더)**"입니다.

인문학적으로 비유하자면, 이것은 이른바 **"케빈 베이컨의 6단계 법칙"**을 조선시대 사료에 적용하는 것과 같습니다.
"이순신(A)"과 "원균(B)"이라는 두 명의 타겟을 RelFinder의 검색창에 입력하면, 뒷단의 기계는 엄청난 속도로 수만 개의 경우의 수를 계산하며 두 사람을 잇는 징검다리(Hop)를 탐색합니다.

그리고 마침내 화면 위에 다음과 같은 숨겨진 인과관계의 선들을 찬란하게 그려냅니다.
* **1-Hop (직접 연결):** 두 사람이 직접 주고받은 서신이 있는가?
* **2-Hop (1명 건너뛰기):** 이순신을 모함한 "윤두수"가 원균을 옹호했는가? (이순신 ➔ 윤두수 ➔ 원균)
* **3-Hop (사건을 통한 연결):** 이순신이 파직당한 "칠천량 해전"에서 원균이 전사했는가? (이순신 ➔ 파직 ➔ 칠천량 해전 ➔ 전사 ➔ 원균)

| 비교 항목 | 수동 SPARQL 탐색 | RelFinder (다중 홉 시각화) |
| :--- | :--- | :--- |
| **탐색 방식** | 인간이 경로의 길이를 미리 짐작하고 코딩해야 함 | **시작점과 끝점만 지정하면 기계가 스스로 경로를 찾음** |
| **결과 형태** | 이해하기 힘든 텍스트 표 (Table) | **두 노드를 잇는 인터랙티브 시각화 네트워크** |
| **인문학적 가치** | 이미 알고 있는 사실의 확인 | **전혀 예상치 못한 역사적 인맥과 교차점(Serendipity)의 발견** |

## 3. 실전 적용: 우리 서버에 RelFinder 연결하고 인맥 캐기

RelFinder를 실무에 도입하는 과정은 매우 직관적입니다. 우리의 Virtuoso SPARQL 엔드포인트를 RelFinder 설정 파일에 연결하고, 시각적 탐험을 시작해 보겠습니다.

1. **엔드포인트 연동:** RelFinder의 `config.xml` 파일에 우리의 지식 그래프 주소(`http://localhost:8890/sparql`)를 등록합니다.
2. **타겟 입력:** 웹 브라우저에 뜬 RelFinder 화면 왼쪽 검색창에 "이순신", 오른쪽 검색창에 "원균"을 타건합니다.
3. **탐색 길이 설정:** 징검다리를 최대 몇 개까지 허용할 것인지(Max Distance)를 '2' 또는 '3'으로 설정하고 탐색(Find) 버튼을 누릅니다.
4. **결과 조망:** 1초 뒤, 두 인물 사이에 거미줄처럼 얽힌 관계망이 떠오릅니다. 중앙에는 두 사람의 공통 주군인 "선조(Person)"가 핵심 허브로 등장하고, 아래쪽에는 두 사람의 운명이 교차한 "칠천량 해전(Event)" 노드가 시각적으로 확연히 드러납니다. 

연구자는 이 시각적 결과를 논문에 캡처하여 싣는 것만으로도, 복잡한 당파 싸움과 인맥의 교차점을 가장 직관적으로 증명할 수 있습니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 피눈물: "탐색 거리를 '5'로 설정했더니 서버가 다운되었습니다!"**

이것은 다중 홉(Multi-hop) 탐색의 무서운 이면을 모르는 초보 연구원들이 100% 겪게 되는 "**데카르트 곱(Cartesian Product)의 폭발**" 현상입니다.

사용자가 RelFinder에서 거리를 1칸 늘릴 때마다, 기계가 뒤에서 계산해야 하는 SPARQL 쿼리의 경우의 수는 기하급수적으로(10배, 100배) 팽창합니다. 만약 여러분이 "선조"와 "이순신"을 넣고 거리를 "5"로 설정했다면, 기계는 5단계를 거쳐가는 수천만 개의 경로를 모두 탐색하려 들 것입니다. 결국 서버의 CPU와 메모리는 한계치를 돌파하고, Virtuoso 데이터베이스는 그대로 장렬하게 뻗어버립니다.

**[승리하는 아키텍트의 '깊이 통제'와 '허브 차단' 기술]**
지식 그래프 서버의 생존을 위해, 총괄 아키텍트는 다음 두 가지 안전장치를 반드시 걸어두어야 합니다.

1. **최대 탐색 깊이(Max Depth)의 강제 제한:** RelFinder 설정에서 사용자가 탐색할 수 있는 최대 거리를 무조건 **2~3(Hop)**으로 제한하십시오. 역사적 인과관계는 3단계를 넘어가면 인문학적 유의미성이 극도로 떨어지며, "모든 조선 사람은 단군으로 연결된다"는 식의 무가치한 결과만 도출됩니다.
2. **초거대 노드(Hub Node)의 필터링 (블랙리스트):** 쿼리 속도를 지옥으로 떨어뜨리는 주범은 "조선", "남자", "인간" 같이 너무 많은 데이터가 몰려 있는 범용 노드들입니다. 이순신과 원균이 "둘 다 조선 시대 사람이다"라는 정보는 경로 탐색에 아무런 가치가 없습니다. RelFinder의 필터(Filter) 기능이나 서버 측 설정에서 `core:Human`, `core:Male` 같은 초거대 클래스들을 경로 탐색에서 제외(Ignore)하도록 블랙리스트로 등록해야만 날카롭고 유의미한 역사적 관계망만을 초고속으로 얻어낼 수 있습니다.

## 5. 요약 및 다음 단계

* 두 역사적 개체 사이에 숨겨진 인맥과 사건의 경로를 시각적으로 추론해 내기 위해, 다중 홉(Multi-hop) 논리 탐색 도구인 "**RelFinder**"를 사용합니다.
* 시작점과 끝점만 지정하면, 기계가 수많은 경우의 수를 계산하여 예상치 못한 연결 고리(Serendipity)를 시각적인 네트워크로 엮어 보여줍니다.
* 연산 폭주로 인한 서버 붕괴를 막기 위해, 아키텍트는 반드시 **최대 탐색 거리를 3 홉(Hop) 이내로 제한**하고 무가치한 초거대 노드들을 필터링하는 튜닝을 수행해야 합니다.

이제 우리는 LodLive, WebVOWL, RelFinder라는 시각화 3대장을 통해, 시커먼 SPARQL 터미널 창 없이도 웹 브라우저에서 지식의 바다를 우아하게 항해할 수 있게 되었습니다. 이로써 대중을 위한 시각적 포털이 완벽하게 완성되었습니다.

하지만, 가장 끔찍하고도 치명적인 보안 문제가 하나 남아 있습니다.
여러분이 멋진 시각화 화면을 서비스하기 위해, 웹 브라우저(프론트엔드)가 백엔드의 SPARQL 엔드포인트(`http://localhost:8890/sparql`)에 직접 쿼리를 날리도록 문을 활짝 열어두었습니다. 

만약 악의적인 해커가 시각화 툴 대신 접속하여, 브라우저 콘솔 창에 **`DROP GRAPH <http://dh.aks.ac.kr/joseon/>` (조선시대 지식 그래프 전체 삭제!)** 라는 악성 쿼리를 날린다면 어떻게 될까요? 여러분이 수년간 구축한 1,000만 건의 데이터가 단 1초 만에 허공으로 증발해 버립니다.
