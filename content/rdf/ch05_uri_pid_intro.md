# 5장. 지식의 영속성을 보장하는 식별자 설계: URI와 영구 식별자(PID)

## 1. 도입: 사라지는 지식과 "404 Not Found"의 공포

디지털 인문학 프로젝트를 진행하며 연구재단으로부터 3년짜리 거대 사업을 수주했다고 상상해 보십시오. 연구팀은 밤낮없이 조선시대 고문헌을 분석하여 완벽한 지식 그래프를 구축했고, 마침내 `http://한국대학교.ac.kr/2026_조선프로젝트/인물/P001`이라는 주소로 훌륭한 데이터를 전 세계에 개방했습니다. 해외의 학자들도 여러분의 데이터를 신뢰하며 자신들의 데이터와 앞다투어 링크(Link)를 연결했습니다.

그런데 3년 뒤, 프로젝트 지원금이 끊겼습니다. 연구소 홈페이지를 관리하던 조교가 졸업하고, 학교 전산소에서는 트래픽을 차지하는 옛날 서버를 정리한다며 웹사이트를 개편해 버렸습니다. 

이제 전 세계에서 여러분의 데이터를 가리키던 그 수많은 연결선들은 어떻게 될까요? 접속하는 순간 새하얀 화면에 끔찍한 에러 메시지, `"**404 Not Found(페이지를 찾을 수 없습니다)**"`가 뜹니다.

인터넷 서핑을 하다가 깨진 링크를 발견하는 것은 그저 약간의 짜증을 유발할 뿐입니다. 하지만 전 세계의 지식이 사슬처럼 엮여 있는 시맨틱 웹(LOD)의 세계에서, 어떤 주소(URI)가 죽어버리는 현상, 즉 `"**링크 부패(Link Rot)**"`는 단순한 에러가 아닙니다. 그것은 내 데이터에 의존하고 있던 다른 모든 연구자의 지식 그래프까지 연쇄적으로 붕괴시키는 `"**학술적 대참사**"`입니다. 

우리가 만든 데이터가 세대가 바뀌어도 무너지지 않으려면, 이 주소가 영원히 변하지 않을 것이라는 절대적인 보증 수표가 필요합니다.

## 2. 해결책 제시: 쿨한 URI는 변하지 않는다 (Cool URIs don't change)

웹의 창시자 팀 버너스리(Tim Berners-Lee)는 1998년에 쓴 역사적인 에세이에서 이렇게 일갈했습니다. 
**"쿨한 URI는 변하지 않는다. (Cool URIs don't change.)"**

주소가 변하는 이유는 기술이 부족해서가 아니라, 인간이 주소를 설계할 때 근시안적인 실수를 저지르기 때문입니다. 변하지 않는 영구적인 주소를 만들기 위해서는 주소 안에 다음과 같은 `"**썩기 쉬운 정보**"`를 절대 넣어서는 안 됩니다.

1. **기술 종속적인 확장자:** `.php`, `.jsp`, `.html` 같은 확장자를 넣지 마십시오. 서버 기술은 5년만 지나도 바뀝니다.
2. **조직의 부서명이나 프로젝트명:** `.../2026_사업단/` 이나 `.../인문융합센터/` 같은 이름을 넣지 마십시오. 조직은 통폐합되고 프로젝트는 언젠가 끝납니다.
3. **데이터의 상태나 권한:** `.../draft/` (초고)나 `.../public/` (공개) 같은 경로를 피하십시오.

이러한 인간의 행정적, 기술적 변화로부터 데이터를 완벽히 격리하기 위해 등장한 개념이 바로 `"**영구 식별자(PID, Persistent Identifier)**"`입니다. 논문에 부여되는 `"**DOI**"`가 대표적인 PID입니다. 학술지가 폐간되거나 출판사 웹사이트가 바뀌어도, DOI 번호만 누르면 현재 논문이 있는 올바른 새 주소로 알아서 연결(Redirect)해 주는 마법의 중계소 역할을 합니다. 

## 3. 실전 적용: 좋은 URI와 나쁜 URI의 설계 비교

조선시대 데이터베이스를 구축할 때, 식별자 주소를 어떻게 설계해야 100년을 버티는 `"**쿨한 URI**"`가 되는지 단계별로 진화하는 과정을 실증해 보겠습니다.

### 1단계: 최악의 URI (시한부 주소)
당장 작동은 하지만, 1~2년 안에 반드시 접속 불량이 될 구조입니다.
* `http://history.hanguk.ac.kr/hk_project_2026/db_view.php?id=P123`
* **실패 원인:** 특정 사업명(`hk_project_2026`), 특정 기술(`php`), 그리고 물음표(`?`)가 들어간 동적 파라미터는 시맨틱 웹에서 절대 피해야 할 금기입니다.

### 2단계: 깔끔한 URI (의미론적 웹)
RESTful API 방식에 맞게 기술적 종속성을 걷어낸 깔끔한 주소입니다.
* `http://history.hanguk.ac.kr/person/P123`
* **개선점:** 확장자와 프로젝트명이 사라졌습니다. 하지만 여전히 대학교의 특정 서버(`history.hanguk.ac.kr`)가 다운되면 연결이 끊어지는 위험을 안고 있습니다.

### 3단계: 궁극의 영구 식별자 (PID / w3id 활용)
우리가 최종적으로 도달해야 할 가장 완벽한 형태의 URI입니다.
* `https://w3id.org/joseon/person/P123`
* **궁극의 마법:** `"**w3id.org**"`는 W3C 커뮤니티가 전 세계 LOD 연구자들을 위해 무료로 제공하는 영구 중계소입니다. 이 주소는 영원히 존재합니다. 만약 우리 대학교 서버가 터져서 연구소 홈페이지를 클라우드 서버로 이사하게 되면, 우리는 그저 w3id 설정 파일에 들어가 "앞으로 P123으로 들어오는 접속은 새로운 클라우드 주소로 보내주세요"라고 한 줄만 수정하면 됩니다. 

전 세계는 오직 `https://w3id.org/...` 라는 불변의 껍데기만 바라보기 때문에, 우리 연구소 서버가 수십 번 이사를 다녀도 데이터의 연결은 단 한 번도 끊어지지 않습니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

현업에서 국책 사업이나 대학교 연구소의 인문학 데이터베이스 사업을 총괄하시다 보면, 윗선에서 이런 지시가 내려올 때가 있습니다.

"교수님, 우리 기관이 수십억을 들여서 구축한 데이터인데, 왜 주소를 `w3id.org` 같은 남의 외국 사이트 이름으로 씁니까? 무조건 우리 기관의 공식 도메인(`aks.ac.kr` 등)이 맨 앞에 와야 기관의 위상이 섭니다!"

이것은 데이터 주권(Data Sovereignty) 측면에서 매우 타당한 요구이며, 실무적으로 100% 직면하는 딜레마입니다. 

이때는 기관의 도메인을 URI로 사용하되, 전산 시스템을 구축하는 외주 개발업체(SI)에게 과업지시서 상에 다음의 요건을 `"**반드시(Mandatory)**"` 명시해야 합니다.

**"본 사업에서 생성되는 모든 개체의 URI는 아파치(Apache)나 엔진엑스(Nginx) 웹 서버의 리버스 프록시(Reverse Proxy) 혹은 URL 재작성(Rewrite) 룰을 통해, 백엔드 시스템(WAS)의 물리적 변화와 무관하게 영구적으로 리다이렉션되어야 한다."**

기관의 도메인을 쓰기로 결심했다는 것은, 이 서버를 5년 뒤에도 10년 뒤에도 절대 내리지 않고 우리 기관의 명운을 걸고 사수하겠다는 `"**디지털 아카이빙의 서약**"`과 같습니다. 전산 담당자에게 이 도메인 주소가 시맨틱 웹 생태계에서 가지는 막중한 책임을 명확히 인지시키는 것이 연구책임자의 가장 중요한 역할입니다.

## 5. 요약 및 다음 단계

* 시맨틱 웹에서 식별자 주소가 사라지는 `"**링크 부패(Link Rot)**"`는 전 세계 지식망을 붕괴시키는 대참사입니다.
* 이를 막기 위해 URI 안에는 확장자, 프로젝트명 등 변하기 쉬운 정보를 모두 배제해야 하며, 이를 `"**쿨한 URI**"`라고 부릅니다.
* 서버가 바뀌어도 주소를 영구히 유지하기 위해 `"**w3id.org**"`와 같은 영구 식별자(PID) 리다이렉션 서비스를 적극 활용하거나, 기관 차원의 강력한 영구 보존 정책을 수립해야 합니다.

자, 이제 우리는 절대로 변하지 않는 영원불멸의 주소(URI)를 설계하는 법을 마스터했습니다. 
그런데 아주 철학적인 문제가 하나 남았습니다. 기계가 이 영구적인 주소 `.../person/P123`으로 접속했을 때, 우리는 기계에게는 RDF 코드를 던져주어야 하고, 인간이 웹 브라우저로 접속했을 때는 예쁜 HTML 웹페이지를 보여주어야 합니다. 

하나의 주소(URI)를 가지고, 접속한 상대가 기계인지 인간인지 귀신같이 알아채서 맞춤형 데이터를 던져주는 마법이 필요합니다. 다음 장인 **[5.1. 콘텐츠 협상(Content Negotiation): 기계와 인간을 동시에 만족시키는 마법]**에서 시맨틱 웹 서버 기술의 가장 아름다운 통신 규약을 해부해 보겠습니다.
