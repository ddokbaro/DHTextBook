# 27.3. 속성 쌍 교차 검증: 연대기 오류의 기계적 차단

## 1. 도입: 단일 검증기를 통과해 버린 "시간 여행자"의 등장

우리는 앞선 27.1장과 27.2장을 통해 지식 그래프 서버의 입구에 아주 깐깐한 세관원("**SHACL**")을 배치했습니다. 이제 "이순신의 출생 연도는 '명종 원년'이다" 같은 문자열 오타나, "사망 연도는 1958년이다" 같은 미래의 숫자는 완벽하게 차단됩니다.

하지만 디지털 인문학의 데이터베이스는 생각보다 훨씬 더 교묘한 모순을 숨기고 있습니다. 
만약 밤샘 작업에 지친 연구원이 "이순신의 출생 연도"를 "**1545**"로 정상 입력하고, "무과 급제 연도"를 "**1540**"으로 입력했다고 상상해 보십시오.

단일 속성 검증기의 눈에는 "1545"도 훌륭한 4자리 숫자이고, "1540"도 완벽한 4자리 숫자입니다. 기계는 아무런 의심 없이 이 데이터를 지식 그래프에 통과시킵니다. 하지만 인간 사학자가 이 데이터를 보는 순간 경악하게 됩니다. **태어나기도 전인 마이너스 5살의 나이에 무과에 급제한 시간 여행자**가 탄생했기 때문입니다. 

역사학은 시간의 선후 관계를 다루는 학문입니다. 하나의 속성이 완벽하더라도, 두 개의 속성이 서로 충돌하면 그것은 역사적 진실이 될 수 없습니다. 우리는 기계에게 단편적인 숫자를 넘어, **"두 사건 사이의 시간적 흐름(연대기)"**을 비교하고 추론하는 고차원적인 논리를 가르쳐야 합니다.

## 2. 해결책 제시: 알리바이를 교차 검증하는 탐정, "**속성 쌍 검증(Property Pair Validation)**"

W3C의 천재적인 공학자들은 이 문제를 해결하기 위해 "**SHACL**" 안에 "**속성 쌍 교차 검증(Property Pair Validation)**"이라는 놀라운 기능을 심어두었습니다.

이것은 단순히 신분증의 글자를 확인하는 세관원을 넘어, 용의자의 알리바이를 추궁하는 "**명탐정 셜록 홈즈**"와 같습니다. 명탐정은 용의자가 "오후 2시에 기차를 탔다"는 진술(출생 연도)과 "오후 1시에 서울에 도착했다"는 진술(급제 연도)을 따로 떼어놓고 보지 않습니다. 두 진술을 나란히 책상 위에 올려두고 시간의 선후 관계가 맞는지 논리적으로 교차 검증합니다.

이 탐정 기법을 구현하는 핵심 마법의 주문이 바로 "**sh:lessThan**"(~보다 작아야 한다)과 "**sh:lessThanOrEquals**"(~보다 작거나 같아야 한다)입니다.

| 검증 수준 | 컴퓨터 공학적 접근법 | 인문학적 검증 결과 |
| :--- | :--- | :--- |
| **단일 속성 검증** | `core:birthYear`가 정수(Integer)인가? | **"1545도 숫자, 1540도 숫자. 통과!" (역사적 모순 발생)** |
| **속성 쌍 교차 검증** | `core:birthYear` < `core:passedExamYear` 인가? | **"출생이 급제보다 미래일 수 없다. 입국 거부!" (무결성 수호)** |

## 3. 실전 적용: 이순신의 시간 역행을 차단하는 교차 검증 코드

이제 이순신 장군의 뼈아픈 입력 실수를 원천 차단하기 위해, 파이프라인의 헌법(Shapes Graph)에 교차 검증 조항을 추가해 보겠습니다.

```turtle
# 1. 네임스페이스 선언
@prefix sh: [http://www.w3.org/ns/shacl#](http://www.w3.org/ns/shacl#) .
@prefix joseon: [http://dh.aks.ac.kr/joseon/](http://dh.aks.ac.kr/joseon/) .
@prefix core: [http://dh.aks.ac.kr/ontology/core/](http://dh.aks.ac.kr/ontology/core/) .
@prefix xsd: [http://www.w3.org/2001/XMLSchema#](http://www.w3.org/2001/XMLSchema#) .

# 2. 인물(Person) 헌법 조항 선언
joseon:PersonShape a sh:NodeShape ;
    sh:targetClass core:Person ;

    # 3. 출생 연도(birthYear)에 대한 교차 검증 규칙
    sh:property [
        sh:path core:birthYear ;
        sh:datatype xsd:integer ;
        
        # [핵심] 출생 연도의 숫자는 무과 급제 연도의 숫자보다 무조건 작아야 한다!
        sh:lessThan core:passedExamYear ;
        
        # [핵심] 출생 연도의 숫자는 사망 연도의 숫자보다 무조건 작거나 같아야 한다!
        sh:lessThanOrEquals core:deathYear ;
        
        sh:message "치명적 논리 오류: 출생 연도가 급제 연도나 사망 연도보다 나중일 수 없습니다. 시간 역행을 확인하십시오."
    ] .
```

이 단 세 줄의 코드(`sh:lessThan`)가 추가되는 순간, 지식 그래프 서버는 인간의 상식을 가진 역사학자로 진화합니다. 
만약 누군가 출생 연도에 "**1545**"를, 급제 연도에 "**1540**"을 입력하면, 기계는 1545가 1540보다 작지 않다는 수학적 사실을 통해 연대기적 모순을 완벽하게 색출하고 새빨간 경고 창을 띄웁니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 치명적 실수: "태어난 해에 죽은 영아의 데이터가 모두 에러로 처리됩니다!"**

이것은 깐깐한 논리학의 함정에 빠진 초보 아키텍트들이 100% 겪는 비극입니다. 
시간의 흐름을 통제하겠다는 의욕이 앞선 나머지, 코드를 짤 때 출생 연도는 사망 연도보다 무조건 작아야 한다며 **`sh:lessThan core:deathYear`** 라고 엄격하게 적어버리는 경우가 있습니다. 

**[승리하는 아키텍트의 포용적 논리술]**
이 코드가 서버에 반영되면, 1592년에 태어나 안타깝게도 1592년에 전염병으로 사망한 갓난아기의 데이터가 들어올 때 시스템은 이를 "거짓말"로 규정하고 파이프라인을 멈춰 세웁니다. 1592는 1592보다 "작지 않기" 때문입니다. 역사의 비극을 기계가 차가운 수학으로 거부하는 셈입니다.

사건과 사건 사이에는 명백한 선후가 있는 경우(예: 태어난 후 최소 10년은 지나야 과거에 급제함)가 있고, 동시에 일어날 수 있는 경우(예: 태어난 해와 죽은 해가 같음, 또는 임명된 해와 파직된 해가 같음)가 있습니다.
따라서 아키텍트는 역사적 맥락을 꼼꼼히 살펴, 동갑이나 동시 발생이 가능한 속성 쌍에 대해서는 절대로 **`sh:lessThan`**을 쓰면 안 되며, 반드시 **`sh:lessThanOrEquals`**(작거나 같다)라는 관대한 논리 연산자를 배치해야만 데이터의 억울한 누락을 막을 수 있습니다.

## 5. 요약 및 대단원 마무리 (모듈 7의 중반부)

* 단일 속성의 오타를 잡는 것을 넘어, 두 속성 간의 논리적 모순과 시간 역행을 차단하기 위해 "**속성 쌍 교차 검증(Property Pair Validation)**"을 도입해야 합니다.
* "**SHACL**"의 "**sh:lessThan**"과 "**sh:lessThanOrEquals**" 문법을 사용하면, 출생과 급제, 임명과 파직 등 역사적 연대기의 선후 관계를 기계가 스스로 비교하고 검증하게 만들 수 있습니다.
* 기계적 논리를 세울 때는 역사적 특수성(태어난 해에 사망하는 경우 등)을 고려하여 두 연산자를 섬세하게 구분해 사용하는 인문학적 통찰이 필수적입니다.

축하합니다! 여러분은 이제 지식 그래프의 구조를 세우는 것을 넘어, 데이터의 무결성과 논리적 완벽성까지 기계적으로 통제할 수 있는 시맨틱 기술의 정점에 섰습니다. 이로써 텍스트와 숫자로 이루어진 모든 인문학 데이터는 가장 안전하고 완벽한 지식망으로 짜였습니다.

하지만, 역사적 사건은 종이 위의 "시간(Time)" 위에서만 일어나는 것이 아닙니다. 이순신 장군은 "전라좌수영"이라는 거대한 "**공간(Space)**" 위에서 일본군과 교전했습니다. 
만약 기계에게 "한산도에서 반경 50km 이내에 있는 모든 조선시대 진(鎭)을 찾아라"라고 명령하고 싶다면 어떻게 해야 할까요?
