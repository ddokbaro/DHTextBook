# 7.1. 기본 구문: SELECT, WHERE, OPTIONAL, FILTER, BIND

## 1. 도입: 완벽하지 않은 역사 데이터, 어떻게 검색할 것인가?

우리는 지난 장에서 `SELECT`와 `WHERE`라는 SPARQL의 가장 기본적인 뼈대를 배웠습니다. `WHERE` 블록 안에 주어, 술어, 목적어로 이루어진 트리플 패턴(도면)을 그리고 빈칸(변수)을 뚫어두면, 기계가 그 도면과 정확히 일치하는 데이터를 쏙쏙 뽑아주었습니다.

하지만 역사 데이터베이스, 특히 우리가 다루는 고문헌 기반의 지식 그래프는 결코 현대의 행정 데이터처럼 완벽하지 않습니다. 
만약 우리가 **"한국 근대 인물 중 종묘에 배향된 공신들의 이름과 호(號)를 모두 찾아라"**라고 기계에게 `WHERE` 패턴을 던져주었다고 가정해 보겠습니다.

기계는 그래프를 뒤져 이름과 호가 모두 명확하게 기록된 인물들은 훌륭하게 찾아낼 것입니다. 그런데 평생 호를 갖지 않았거나, 사료가 소실되어 호가 기록되지 않은 공신들은 어떻게 될까요? 기계는 아주 냉정하게 **"이 인물은 도면(이름+호)과 100% 일치하지 않으므로 검색 결과에서 통째로 날려버리겠다"**라고 판정합니다. 호가 없다는 이유만으로 역사적으로 중요한 종묘배향공신 명단에서 그 인물의 이름조차 아예 누락되어 버리는 대참사가 발생하는 것입니다.

우리는 앞서 6장에서 시맨틱 웹이 "기록이 없다고 해서 존재하지 않는 것은 아니다"라는 너그러운 열린 세계 가정(OWA)을 따른다고 배웠습니다. 그렇다면 검색을 할 때도, **"호가 있으면 있는 대로 가져오고, 없으면 빈칸으로 두되 사람 이름은 무조건 출력해 다오"**라고 유연하게 명령할 수 있는 마법의 문법이 필요합니다.

## 2. 해결책 제시: 유연하고 강력한 3대 핵심 문법

SPARQL은 이처럼 불완전하고 복잡한 인문학 데이터를 효율적으로 요리하기 위해 `OPTIONAL`, `FILTER`, `BIND`라는 3대 핵심 무기를 제공합니다.

1. **너그러운 포용자, OPTIONAL:** 조건이 완벽히 일치하지 않아도 데이터를 버리지 않습니다. 지정한 패턴이 그래프에 존재하면 그 값을 가져오고, 없으면 에러를 내거나 데이터를 통째로 날리는 대신 그냥 빈칸(`UNBOUND`)으로 남겨둔 채 나머지 정보는 살려서 출력해 줍니다. 엑셀의 데이터 누락(NULL) 스트레스를 완벽히 날려주는 일등 공신입니다.
2. **날카로운 검문소, FILTER:**
   찾아낸 수많은 데이터 중, 우리가 원하는 특정 조건(예: "1880년 이후 출생자만", "이름에 '김'이 들어가는 사람만")에 부합하는 데이터만 예리하게 걸러냅니다.
3. **효율적인 창조자, BIND:**
   데이터베이스에 원래 없던 새로운 정보나 계산 결과를 쿼리 실행 도중에 실시간으로 만들어내어 새로운 빈칸(변수)에 할당합니다. 구조를 바꾸지 않고도 데이터의 활용도를 극대화합니다.

## 3. 실전 적용: 종묘배향공신 데이터를 꿰뚫는 단일 쿼리 작성

이 세 가지 문법이 실제 연구 현장에서 어떻게 결합하여 폭발적인 시너지를 내는지, "한국 근대 인물 LOD - 종묘배향공신" 데이터를 모델로 하여 단 하나의 강력한 SPARQL 코드로 시연해 보겠습니다.

**우리의 퀘스트:** "종묘배향공신들의 이름과 출생 연도를 찾고, 호(號)가 있다면 같이 가져오라. 단, 1800년 이후에 태어난 근대 인물만 걸러내고, 이들의 '환갑(60세) 연도'를 실시간으로 계산하여 함께 출력하라!"

```sparql
PREFIX 근대: [http://조선.kr/modern/](http://조선.kr/modern/)
PREFIX 속성: [http://조선.kr/prop/](http://조선.kr/prop/)

# 출력할 변수들을 선언합니다. 환갑연도는 DB에 없지만 우리가 만들어서 출력할 것입니다.
SELECT ?공신이름 ?출생연도 ?호 ?환갑연도
WHERE {
  # 1. 필수 패턴: 종묘배향공신 클래스에 속한 인물(?공신)의 이름과 출생연도를 찾습니다.
  ?공신 a 근대:종묘배향공신 .
  ?공신 속성:이름 ?공신이름 .
  ?공신 속성:출생연도 ?출생연도 .
  
  # 2. OPTIONAL: 호(號)가 있으면 ?호 변수에 담고, 없으면 공신 데이터 자체를 날리지 말고 그냥 둡니다.
  OPTIONAL { 
    ?공신 속성:호 ?호 . 
  }
  
  # 3. FILTER: 찾아낸 출생연도 중, 1800년 이후 출생자만 통과시킵니다.
  FILTER (?출생연도 >= 1800)
  
  # 4. BIND: 찾아낸 출생연도에 숫자 60을 더하여, ?환갑연도 라는 새로운 변수를 실시간으로 창조합니다.
  BIND ((?출생연도 + 60) AS ?환갑연도)
}
```

이 코드를 실행하면, 호가 없는 무관 출신 공신들도 명단에서 누락되지 않으며, 데이터베이스 구조를 뜯어고칠 필요 없이 '환갑연도'라는 완전히 새로운 인문학적 파생 지식이 단 1초 만에 깔끔한 표의 형태로 여러분의 모니터에 출력됩니다. 

| 공신이름 | 출생연도 | 호 | 환갑연도 |
| :--- | :--- | :--- | :--- |
| 조병세 | 1827 | 산재 | 1887 |
| 민영환 | 1861 | 계정 | 1921 |
| 이준용 | 1870 | (빈칸) | 1930 |

## 4. 실무 트러블슈팅 (Street-smart Tips)

코드를 작성할 때 불필요한 중복을 싫어하고 극도의 효율성을 추구하는 연구원들이 `BIND` 문법을 처음 배울 때 100% 확률로 저지르는 뼈아픈 실수가 있습니다. 바로 `"**변수의 실행 순서(Execution Order) 무시**"`입니다.

위의 코드에서 환갑을 계산하는 `BIND` 구문을 `WHERE` 블록의 맨 첫 줄로 끌어올렸다고 상상해 보십시오.

* **초보자의 흔한 실수 (에러 발생 코드):**
    ```sparql
    WHERE {
      # 효율적으로 변수부터 다 만들어두고 시작해야지!
      BIND ((?출생연도 + 60) AS ?환갑연도) 
      
      # 그 다음에 출생연도를 찾아야겠다.
      ?공신 속성:출생연도 ?출생연도 .
    }
    ```

여러분이 이렇게 코드를 짜면 기계는 즉시 멍청해지며 아무런 계산 결과도 내뱉지 않습니다. SPARQL 엔진은 `WHERE` 블록 안의 코드를 기본적으로 **위에서부터 아래로 순차적으로 읽어 들입니다.** 기계가 첫 줄의 `BIND`를 마주했을 때, `?출생연도`라는 변수에는 아직 아무런 데이터도 들어있지 않은 상태(`UNBOUND`)입니다. 텅 빈 허공의 값에 숫자 60을 더하라고 명령을 내리니 연산이 실패하고, 그 결과로 `?환갑연도` 변수는 영원히 빈칸으로 남아버리는 것입니다.

**시맨틱 아키텍트의 황금률:** `BIND`나 `FILTER`를 사용하여 연산을 수행할 때는, 반드시 그 연산의 재료가 되는 변수(예: `?출생연도`)가 **트리플 패턴을 통해 명확하게 그래프에서 멱살을 잡혀 추출된(선언된) 이후**에 코드를 위치시켜야 합니다. 변수가 먼저고, 가공은 나중입니다.

## 5. 요약 및 다음 단계

* 완벽하지 않은 역사 데이터에서 빈칸 때문에 전체 결과가 누락되는 것을 막으려면, 너그러운 포용자 `"**OPTIONAL**"`을 사용해야 합니다.
* 수많은 지식의 거미줄 속에서 원하는 조건의 데이터만 예리하게 잘라내고 싶을 때는 `"**FILTER**"`를 사용합니다.
* 데이터베이스(DB) 자체를 건드리지 않고, 기존 변수들을 조합하여 실시간으로 새로운 파생 지식을 창조할 때는 `"**BIND**"`를 사용합니다.

자, 이제 우리는 SPARQL의 가장 핵심적인 뼈대와 살을 모두 붙일 수 있게 되었습니다. 하나의 도면 안에서 데이터를 찾고, 가공하고, 걸러내는 작업은 완벽해졌습니다.
