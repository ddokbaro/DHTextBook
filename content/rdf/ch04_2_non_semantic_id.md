# 4.2. 이름은 데이터가 아니다: 무의미 식별자(Non-semantic ID)와 다중 라벨링 전략

## 1. 도입: URI에 이름을 넣는 순간 시작되는 끔찍한 저주

우리는 바로 앞 장에서 동명이인을 완벽하게 구분하기 위해 URI 끝에 `http://조선.kr/인물/이순신_무신`과 같이 직업이나 특징을 나타내는 꼬리표를 붙여 고유한 식별자를 만들었습니다. 인간의 눈으로 볼 때는 직관적이고 아주 훌륭해 보입니다. 

하지만 시맨틱 웹과 데이터 엔지니어링의 관점에서 이 방식은 언젠가 반드시 터지게 될 시한폭탄과 같은 치명적인 위험을 품고 있습니다. 만약 10년 뒤, 새로운 고문서가 발견되어 역사적 고증이 완전히 뒤집혔다고 상상해 보십시오. 우리가 평생 "무신"이라고 굳게 믿었던 그 인물이 사실은 과거를 보지 않은 "음서" 출신의 문관이었음이 밝혀지면 어떻게 될까요? 

여러분은 당장 데이터베이스를 열어 `.../이순신_무신`이라는 주소를 `.../이순신_문신`으로 황급히 수정하고 싶을 것입니다. 하지만 그 주소를 바꾸는 순간, 이미 전 세계의 수만 개의 지식 그래프와 논문들이 여러분의 데이터를 향해 걸어두었던 모든 연결(Link)은 일순간에 뚝뚝 끊어지며 데이터는 우주 미아가 되어버립니다. 

이처럼 식별자(ID) 주소 그 자체 안에 인간이 이해하는 정보(이름, 직업, 성별 등)를 함부로 담는 순간, 그 역사적 정보가 변할 때 식별자의 영구성도 함께 산산조각 나는 현상을 우리는 `"**식별자 부패(Identifier Decay)**"`라고 부릅니다. 

## 2. 해결책 제시: 무의미한 ID와 "라벨(Label)"의 완벽한 분리

진정한 시맨틱 아키텍트(Semantic Architect)는 식별자 주소 안에 그 어떤 인문학적 의미도 결코 담지 않습니다. 대신, 기계적으로 무작위 생성된 아무 의미 없는 고유 번호를 뼈대로 부여하고, 우리가 일상적으로 부르는 "이름"이나 "호"는 별도의 `"**라벨(Label)**"`이라는 겉옷(속성)으로 떼어내어 완벽하게 분리하여 관리합니다.

이것은 마치 대한민국 국민이 주민등록번호라는 무의미한 13자리 숫자로 국가 시스템에 등록되고, 이름이나 개명 여부, 혹은 별명은 언제든 수정 가능한 부가 정보로 따로 관리되는 원리와 정확히 같습니다. 

이를 공학 용어로 `"**불투명 식별자(Opaque Identifier)**"` 혹은 `"**무의미 식별자(Non-semantic ID)**"`라고 부릅니다.

* **식별자(URI):** 절대 변하지 않는 영원한 우주적 뼈대 (예: `http://조선.kr/person/P000456`)
* **라벨(Label):** 인물을 지칭하는 풍부하고 언제든 유동적인 텍스트 이름들 (본명, 호, 자, 시호 등)

이 위대한 구조를 도입하면 한 인물이 시대에 따라 여러 이름을 가졌거나(다중 이름), 후대의 역사적 고증에 의해 이름이나 속성이 완전히 뒤바뀌더라도 식별자의 뼈대는 100년이 지나도 변함없이 굳건하게 지식의 중심을 잡을 수 있습니다.

## 3. 실전 적용: 다중 라벨링을 활용한 이이(율곡)의 지식 그래프 설계

조선시대 지식인들의 족보와 문집을 분석할 때 이 구조는 빛을 발합니다. 그들은 본명 외에도 자(字)와 호(號), 사후에 내려진 시호(諡號) 등 한 사람당 수많은 이름을 가졌습니다. 이를 `"**무의미 ID + 다중 라벨링**"` 구조로 정교하게 설계하면 다음과 같이 우아하고 견고한 시맨틱 데이터가 탄생합니다.

```turtle
# 1. 인물에게 인문학적 의미가 전혀 없는, 무의미하면서 유니크한 고유 ID를 부여합니다. (P00123)
[http://조선.kr/person/P00123](http://조선.kr/person/P00123) [http://www.w3.org/1999/02/22-rdf-syntax-ns#type](http://www.w3.org/1999/02/22-rdf-syntax-ns#type) [http://조선.kr/ontology/인물](http://조선.kr/ontology/인물) .

# 2. 이 불변의 ID에 국제 표준 온톨로지(RDFS, SKOS)를 사용하여 다양한 이름들을 포스트잇처럼 붙여줍니다.
# rdfs:label은 기계가 모니터 화면에 가장 대표적으로 출력할 때 쓸 "기본 이름"입니다.
[http://조선.kr/person/P00123](http://조선.kr/person/P00123) [http://www.w3.org/2000/01/rdf-schema#label](http://www.w3.org/2000/01/rdf-schema#label) "이이" .

# skos:altLabel은 "호"나 "자" 같은 "대안적인 이름(Alternative Label)"을 다중으로 담기에 가장 완벽한 속성입니다.
[http://조선.kr/person/P00123](http://조선.kr/person/P00123) [http://www.w3.org/2004/02/skos/core#altLabel](http://www.w3.org/2004/02/skos/core#altLabel) "율곡(栗谷)" .
[http://조선.kr/person/P00123](http://조선.kr/person/P00123) [http://www.w3.org/2004/02/skos/core#altLabel](http://www.w3.org/2004/02/skos/core#altLabel) "숙헌(叔獻)" .

# 3. 만약 훗날 학계의 고증 결과 이이의 자(字)가 숙헌이 아니라 다른 글자임이 밝혀져도, 
# 우리는 단지 마지막 줄의 텍스트(Label) 정보만 살짝 수정하면 그만입니다. 
# 전 세계가 바라보고 있는 핵심 ID인 P00123 주소는 영원히 변하지 않고 데이터의 신뢰를 지켜냅니다.
```

이 두 가지 설계 철학의 차이를 한눈에 파악할 수 있도록 표로 정리해 드립니다.

| 구분 | 의미론적 식별자 (Bad Practice) | 무의미 식별자 (Best Practice) |
| :--- | :--- | :--- |
| **URI 형태** | `.../인물/이순신_무신` | `.../person/P000045` |
| **변경 가능성** | 역사적 고증이 바뀌면 URI 주소 자체를 뜯어고쳐야 함 | 어떤 역사적 뒤집힘에도 URI 주소는 절대 변하지 않음 |
| **기계 가독성** | 인간은 주소만 봐도 알기 편하나 기계는 텍스트 파싱 오류 위험 존재 | 인간의 언어가 배제되어 기계가 처리하기에 가장 안정적임 |
| **시스템 확장성** | 이름이나 속성이 바뀌면 전 세계의 연결 링크가 모두 깨짐 | 뼈대는 두고 겉옷(라벨)만 추가/수정하면 되어 극도로 유연함 |

## 4. 실무 트러블슈팅 (Street-smart Tips)

데이터 랩(Lab)에서 무의미 식별자 원칙을 도입하여 대규모 구축 사업을 시작하면, 데이터를 직접 입력하고 검수하는 대학원생 연구원들이 모니터 화면의 `P00123`, `P08421` 같은 기계적인 숫자들을 보며 비명을 지를 것입니다.

"교수님! 화면에 온통 알 수 없는 외계어 번호만 떠다녀서 누가 누구인지 한눈에 안 들어옵니다. 네트워크 선을 연결하다가 눈이 빠질 것 같고 오타가 날 확률이 너무 높아서 작업이 불가능합니다!"

이때 쏟아지는 불평에 결코 타협하여 URI 주소에 이름을 다시 슬쩍 밀어 넣는 우를 범하지 마십시오. 해답은 데이터의 뼈대를 망가뜨리는 것이 아니라, 화면을 보여주는 `"**소프트웨어의 렌더링 기능**"`을 활용하는 것에 있습니다.

여러분이 데이터를 편집할 때 사용하는 그래프 도구(Protégé 등)나 시각화 분석 툴(Neo4j Bloom 등)의 설정 창에 들어가 보십시오. 그곳에는 반드시 `"**라벨로 렌더링(Render by Label / Display Property)**"`이라는 강력한 디스플레이 옵션이 숨어 있습니다. 이 옵션을 켜고 앞서 우리가 입력한 `rdfs:label`을 화면에 보여줄 글자로 지정하기만 하면 됩니다. 

그러면 데이터베이스 내부의 진짜 주소는 굳건하게 `P00123`으로 유지되지만, 연구원들이 바라보는 모니터 화면의 둥근 노드 위에는 `이이(율곡)`라는 친숙한 한글 이름이 마법처럼 예쁘게 덮어씌워져 나타납니다. 

데이터 모델링의 절대 명제를 가슴에 새기십시오. **"URI 주소는 오직 기계의 영원한 연산을 위한 것이고, 라벨(Label)은 오직 나약한 인간의 눈을 돕기 위한 것입니다."** 이 두 가지 역할을 섞는 순간, 인문학 데이터의 영구성은 돌이킬 수 없이 파괴됩니다.

## 5. 요약 및 다음 단계

* URI 주소 안에 의미 있는 사람의 이름이나 직업 속성을 담는 것은, 훗날 역사적 고증이 바뀔 때 전 세계의 링크를 파괴하는 가장 끔찍하고 위험한 행동입니다.
* 영구적으로 살아 숨 쉬는 지식 그래프를 구축하려면 `"**무의미한 고유 식별자(Opaque ID)**"`를 주소로 사용해야 합니다.
* 본명, 호, 자와 같은 가변적이고 다양한 인문학적 정보는 `"**라벨(Label)**"`이라는 속성을 통해 옷을 입히듯 다중으로 연결하는 것이 디지털 인문학 데이터 모델링의 궁극적인 정석입니다.

교수님들의 날카로운 통찰과 결단 덕분에 우리는 이제 어떤 비바람에도 흔들리지 않는 가장 단단한 지식의 식별자 뼈대를 갖추게 되었습니다. 이제 이 뼈대 위에, "이름이다", "대안적 이름이다"와 같이 전 세계가 약속하고 공통으로 사용하는 술어(Predicate)의 표준 도면들을 가져다 쓰는 방법을 본격적으로 알아보겠습니다.
