# 8.1. 마이크로서비스 데이터 오케스트레이션: SERVICE 키워드의 마법

## 1. 도입: 원격 서버의 지식을 소환하는 주문

우리는 앞서 8장 도입부에서 우리 연구실 서버에 부족한 지식(예: 현대 GPS 좌표, 다국어 번역어 등)을 보충하기 위해 외부의 거대한 지식 창고를 활용해야 한다는 당위성을 배웠습니다. 이제 그 당위성을 현실로 바꿔줄 구체적인 주문서를 작성할 시간입니다.

SPARQL 연합 질의의 심장부에는 `"**SERVICE**"`라는 이름의 마법 같은 키워드가 존재합니다. 

여러분이 조선시대 연행사들의 이동 경로를 연구하면서, 로컬 서버에 저장된 **"지명(地名)"** 데이터와 위키데이터(Wikidata)가 보유한 **"정밀 좌표"** 데이터를 합치고 싶다고 가정해 봅시다. `SERVICE` 키워드를 사용하면, 쿼리문 실행 도중에 특정 부분만 떼어내어 인터넷 선 너머의 위키데이터 서버에게 "이것 좀 대신 계산해서 보내줘!"라고 부탁할 수 있습니다. 

이는 마치 요리사가 메인 요리를 만들다가(로컬 쿼리), 특수한 향신료를 구하기 위해 조수에게 전화를 걸어(SERVICE 호출) 시장에서 재료를 공수해 오게 하는 것과 같습니다.

## 2. 해결책 제시: SERVICE 구문의 구조와 작동 원리

`SERVICE` 키워드는 `WHERE` 절 내부에서 마치 하나의 섬처럼 존재합니다. 기본 구조는 다음과 같습니다.

```sparql
WHERE {
  # [1] 로컬 패턴: 우리 연구실 서버에서 가져오는 데이터
  ?인물 <속성:방문지> ?지명 .

  # [2] 원격 패턴: 외부 서버(예: 위키데이터)에 외주를 주는 데이터
  SERVICE <원격_서버의_SPARQL_엔드포인트_주소> {
    ?지명 <위키데이터_속성:좌표> ?좌표 .
  }
}
```

이 코드가 실행될 때 벌어지는 마법 같은 통신 메커니즘은 다음과 같습니다:
1. **로컬 엔진의 판단:** 쿼리 엔진이 `WHERE` 절을 읽다가 `SERVICE` 문구를 발견하면, 중괄호 `{ }` 안의 내용은 자신이 처리하지 않기로 결정합니다.
2. **HTTP 파견:** 엔진은 중괄호 안의 트리플 패턴을 들고 지정된 원격 주소(URL)로 HTTP 요청을 보냅니다.
3. **원격 엔진의 응답:** 위키데이터 서버는 요청받은 내용을 자신의 데이터베이스에서 뒤져 결과셋을 만든 뒤, 다시 우리 서버로 쏴줍니다.
4. **최종 융합:** 우리 서버는 로컬에서 뽑은 `?지명`과 위키데이터에서 건너온 `?지명`을 비교하여, 같은 지명끼리 `"**조인(JOIN)**"`하여 최종 결과를 출력합니다.

## 3. 실전 적용: 위키데이터에서 홍대용의 방문지 좌표 훔쳐오기

실제로 작동하는 코드를 통해 연합 질의의 위력을 실감해 봅시다. 아래 쿼리는 우리 연구소 서버의 홍대용(P00456) 데이터와 위키데이터의 지리 데이터를 실시간으로 결합합니다.

```sparql
PREFIX wd: [http://www.wikidata.org/entity/](http://www.wikidata.org/entity/)
PREFIX wdt: [http://www.wikidata.org/prop/direct/](http://www.wikidata.org/prop/direct/)
PREFIX 속성: [http://조선.kr/prop/](http://조선.kr/prop/)

SELECT ?지명 ?좌표
WHERE {
  # 우리 서버에서 홍대용의 방문지 URI를 찾습니다.
  [http://조선.kr/person/P00456](http://조선.kr/person/P00456) 속성:방문지 ?지명_URI .
  ?지명_URI 속성:한글명 ?지명 .

  # [마법의 SERVICE 구간]
  # 위키데이터의 공식 SPARQL 엔드포인트를 호출합니다.
  SERVICE [https://query.wikidata.org/sparql](https://query.wikidata.org/sparql) {
    # 우리 서버에서 찾은 ?지명_URI와 동일한 위키데이터 개체를 찾아 좌표를 가져옵니다.
    # (owl:sameAs 등으로 연결되어 있다고 가정)
    ?지명_URI wdt:P625 ?좌표 . # P625는 위키데이터의 'coordinate location' 속성입니다.
  }
}
```

이 쿼리 한 줄로 여러분은 수천 명의 대학생 조교가 며칠 밤을 새워 구글 지도를 뒤져야 했을 노가다를 **단 1초** 만에 끝낸 것입니다. 이것이 바로 시맨틱 아키텍처가 선사하는 '연구의 생산성 혁명'입니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

`SERVICE` 키워드를 처음 접한 연구자들은 신이 나서 여러 개의 외부 서버를 동시에 호출하곤 합니다. 하지만 현장에서는 이 `SERVICE` 구문 때문에 전체 시스템이 마비되는 사고가 빈번합니다.

**치명적인 실수: "바보 같은 웨이터" 문제**
여러분이 `SERVICE` 블록을 `WHERE` 절의 **맨 윗줄**에 배치했다고 상상해 보십시오.

```sparql
# 나쁜 사례: 에러 혹은 타임아웃의 지름길
WHERE {
  SERVICE [https://query.wikidata.org/sparql](https://query.wikidata.org/sparql) {
    ?지명_URI wdt:P625 ?좌표 . # "세상의 모든 좌표를 다 가져와!"
  }
  [http://조선.kr/person/P00456](http://조선.kr/person/P00456) 속성:방문지 ?지명_URI . # "아, 그중에서 홍대용 거만 골라줘."
}
```

기계는 위에서부터 읽습니다. 첫 줄에서 위키데이터에 "모든 좌표를 다 달라"고 요청하면 위키데이터 서버는 수억 개의 데이터를 보내려다 타임아웃을 냅니다.

**시맨틱 아키텍트의 "선(先) 바인딩" 전략:**
반드시 로컬 서버에서 `?지명_URI`를 **먼저(Above)** 확정 지어야 합니다. 로컬에서 "홍대용이 간 곳은 '북경'과 '열하' 뿐이다"라는 사실을 먼저 알아낸 뒤에 `SERVICE`를 호출하면, 우리 서버는 위키데이터에 질문할 때 이렇게 속삭입니다.
*"야, 딴 건 필요 없고 딱 '북경'이랑 '열하' 좌표만 좀 알려줄래?"*
이것을 **바인딩(Binding)**이라고 합니다. 질문을 구체적으로 좁혀서 던질수록 쿼리는 빛의 속도로 빨라지고 외부 서버에 민폐를 끼치지 않게 됩니다.

## 5. 요약 및 다음 단계

* `SERVICE` 키워드는 로컬 쿼리 도중에 원격 SPARQL 엔드포인트에 특정 연산을 위임하는 도구입니다.
* 연합 질의는 데이터의 소유가 아닌 `"**실시간 융합**"`을 통해 지식의 외연을 무한히 확장합니다.
* 성능 최적화를 위해 반드시 로컬에서 변수를 먼저 확정(Binding)한 뒤에 외부 서버를 호출해야 합니다.

이제 우리는 외부 서버의 문을 두드리는 법을 배웠습니다. 그런데 한 가지 큰 숙제가 남았습니다. 
우리 서버의 '북경' URI와 위키데이터의 '북경' URI가 서로 다르게 생겼다면 기계는 두 데이터가 같은 대상인지 어떻게 알까요?
