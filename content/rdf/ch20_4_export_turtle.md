# 20.4. 설계도의 추출과 배포: Turtle(TTL) 및 RDF/XML 포맷 변환과 서버 이관 준비

## 1. 도입: 내 PC의 하드디스크를 벗어나 글로벌 지식망으로

"시맨틱웹과한국학자료" 수업이나 "고문헌자료정보화연구" 실무를 통해 우리는 참으로 험난하고도 위대한 여정을 거쳐왔습니다. Protégé라는 캔버스 위에서 종묘배향공신의 뼈대(Class)를 세우고, 관계(Property)를 엮었으며, Cellfie를 통해 수만 명의 인스턴스를 폭포수처럼 쏟아부었습니다. HermiT 추론기로 숨겨진 진실까지 끄집어냈습니다.

하지만 연구실 PC의 하드디스크에 저장된 `.owl` 파일 하나만으로는 세상을 바꿀 수 없습니다. 한국근대인물LOD가 진정한 "Linked Open Data(개방형 연결 데이터)"로 거듭나려면, 이 데이터베이스가 전 세계의 학자들과 시스템이 접속하여 질의(Query)를 던질 수 있는 거대한 **"그래프 데이터베이스 서버(Graph DB Server, 예: GraphDB, Blazegraph)"**로 이사해야 합니다.

문제는 Protégé의 기본 저장 방식과 서버가 원하는 언어 포맷이 다를 수 있다는 점입니다. 수만 건의 무결점 데이터를 단 한 줄의 유실이나 인코딩 깨짐 없이 서버로 이관하기 위해, 우리는 설계도를 글로벌 웹 표준 포맷으로 우아하게 변환하여 추출(Export)하는 마지막 관문을 통과해야 합니다.

## 2. 해결책 제시: 기계와 인간의 언어, "Turtle"과 "RDF/XML"

시맨틱 웹의 W3C 표준은 지식 그래프를 텍스트 파일로 저장하는(직렬화, Serialization) 여러 가지 문법을 제공합니다. 서버 이관 시 디지털 인문학 아키텍트가 실무에서 마주하는 두 가지 핵심 포맷을 직관적으로 비교해 보겠습니다.



| 저장 포맷(문법) | 파일 확장자 | 인문학적 비유 및 실무적 특징 | 효율성 및 가독성 |
| :--- | :--- | :--- | :--- |
| **Turtle** | `.ttl` | **[효율성 극대화의 미학]**<br>중복되는 주어와 서술어를 생략하여 코드의 길이를 획기적으로 줄인 가장 직관적이고 모던한 문법. | **최상.** 인간이 눈으로 읽고 디버깅하기 매우 쉬우며, 파일 용량도 작음. |
| **RDF/XML** | `.rdf` 또는 `.owl` | **[전통의 굴레와 범용성]**<br>초기 웹 표준인 XML의 엄격한 태그(`< >`) 구조에 억지로 데이터를 구겨 넣은 과거의 유산. | **최하.** 기계는 잘 읽지만, 인간의 눈에는 태그가 너무 많아 가독성이 끔찍함. 단, 구형 레거시 시스템과의 호환성은 높음. |

과거에는 많은 도구가 RDF/XML을 강제했지만, 현재는 문법이 간결하고 데이터 용량을 극적으로 줄여주는 **"Turtle(터틀)"** 포맷이 압도적인 글로벌 표준으로 자리 잡았습니다. 불필요한 태그 반복을 싫어하고 극강의 효율성을 추구하는 아키텍트라면 무조건 Turtle 포맷을 선택해야 합니다.

## 3. 실전 적용: 한국근대인물LOD 설계도의 Turtle 추출 (Export)

Protégé에 구축된 방대한 지식망을 `.ttl` 파일로 안전하게 추출하여 서버 이관 준비를 마치는 과정을 실습해 보겠습니다.

**[작업 1: 온톨로지 IRI(절대 주소) 최종 점검]**
1. Protégé 상단의 **"Active Ontology"** 탭으로 이동합니다.
2. **"Ontology IRI"** 항목이 `http://aks.ac.kr/ontologies/joseon` 처럼 우리가 처음 설계했던 고유 주소로 명확하게 박혀 있는지 확인합니다. (이 주소가 꼬여 있으면 서버에 올라가서 다른 데이터와 충돌합니다.)

**[작업 2: Turtle 포맷으로 "Save As(다른 이름으로 저장)"]**
1. 상단 메뉴에서 **"File ➔ Save As..."**를 클릭합니다.
2. 팝업창에서 저장할 포맷을 묻습니다. 기본값인 `RDF/XML Format`을 과감하게 버리고, 드롭다운 메뉴를 내려 **"Turtle"**을 선택합니다.
3. 파일명을 `modern_figures_lod_v1.ttl`로 지정하고 저장(Save)합니다.

추출된 `modern_figures_lod_v1.ttl` 파일을 메모장이나 VS Code 같은 텍스트 에디터로 열어보십시오.

```turtle
@prefix rdfs: [http://www.w3.org/2000/01/rdf-schema#](http://www.w3.org/2000/01/rdf-schema#) .
@prefix xsd: [http://www.w3.org/2001/XMLSchema#](http://www.w3.org/2001/XMLSchema#) .
@prefix joseon: [http://aks.ac.kr/ontologies/joseon/](http://aks.ac.kr/ontologies/joseon/) .

# 데이터가 군더더기 없이 깔끔한 세미콜론(;)과 마침표(.) 규칙으로 정렬되어 있습니다.
joseon:Min_Yeong_hwan a joseon:Meritorious_Subject ;
    joseon:hasName "민영환"^^xsd:string ;
    joseon:passedCivilExam "true"^^xsd:boolean ;
    joseon:dateOfDeath "1905-11-30"^^xsd:date .
```

이토록 아름답고 간결한 파일 하나에 여러분이 구축한 수만 명의 뼈대와 관계, 그리고 데이터가 완벽하게 압축되어 담겼습니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 마지막 실수: 인코딩(Encoding)이 박살 난 한글 데이터**

Graph DB 서버(예: GraphDB)에 방금 추출한 `.ttl` 파일을 업로드(Import)하고 쿼리를 던졌는데, **"민영환"**이라는 글자가 **"ㅁㅣㄴㅇㅕㅇㅎㅗㅏㄴ"**으로 깨지거나 물음표(???)로 표시되는 대참사가 가끔 발생합니다.

**"교수님! 분명히 IRI 식별자는 영문자로 잘 지켰고, 라벨(`hasName`)에만 한글을 조심스럽게 넣었는데도 서버에서 한글이 다 깨져버립니다. Turtle 변환 과정에서 뭔가 잘못된 것입니까?"**

Turtle 포맷 자체의 잘못이 아닙니다. 이것은 윈도우 환경에서 텍스트 파일을 다룰 때 영원히 고통받는 **"문자 인코딩(Character Encoding)"** 문제입니다.

Protégé에서 파일을 저장할 때, 시스템 환경에 따라 기본 인코딩이 전 세계 웹 표준인 **"UTF-8"**이 아니라, 구형 윈도우 방식인 **"EUC-KR"**이나 **"CP949"**로 엉켜서 저장되는 경우가 있습니다. GraphDB 같은 글로벌 서버는 오직 UTF-8만을 정상적인 문자로 인식하기 때문에, 한글 포스트잇(문자열)들이 서버에 들어가는 순간 외계어로 변이하는 것입니다.

**[승리하는 아키텍트의 인코딩 방어 철칙]**
서버에 `.ttl` 파일을 업로드하기 직전, 반드시 텍스트 에디터(VS Code, Notepad++ 등)로 해당 파일을 열어보십시오.
1. 프로그램 우측 하단이나 설정 메뉴를 확인하여 현재 파일의 인코딩이 **"UTF-8"**로 되어 있는지 점검합니다.
2. 만약 다른 인코딩으로 되어 있다면, **"UTF-8로 인코딩하여 저장(Save with Encoding)"** 기능을 사용하여 파일을 덮어쓴 뒤 서버로 이관하십시오. 이 1분의 확인 과정이 수만 건의 한글 데이터가 증발하는 참사를 막아내는 가장 든든한 방패입니다.

## 5. 요약 및 다음 단계

* Protégé에서 완성된 지식 그래프를 Graph DB 서버로 이관하기 위해서는 설계도를 웹 표준 포맷으로 추출(Export)해야 합니다.
* 구형 시스템을 위한 무거운 `RDF/XML` 포맷보다는, 코드가 직관적이고 파일 용량을 극적으로 줄여주어 작업 효율성이 높은 **"Turtle (.ttl)"** 포맷을 사용하는 것이 디지털 인문학 실무의 절대 표준입니다.
* 서버 이관 시 한글 문자열(String)이 깨지는 현상을 방지하기 위해, 저장된 텍스트 파일의 인코딩이 **"UTF-8"**인지 최종 확인하는 과정을 반드시 거쳐야 합니다.

드디어 상향식(Bottom-up) 데이터 입력의 고통을 끝내고, Protégé를 활용한 하향식(Top-down) 지식 그래프의 설계와 구축이라는 거대한 산맥을 완벽하게 등반했습니다. 로컬 PC에서의 작업은 이것으로 모두 끝났습니다. 여러분이 정제해 낸 `modern_figures_lod_v1.ttl` 파일은 이제 좁은 연구실을 벗어나 세상을 향해 개방될 준비를 마쳤습니다.

하지만 이 텍스트 파일 자체만으로는 어떠한 서비스도 할 수 없습니다. 이 찬란한 지식망을 전 세계 연구자들과 공유하고, 외부의 수많은 시스템과 연동하며, 대규모 데이터 질의를 실시간으로 처리하려면 이 데이터를 담아낼 튼튼한 물리적 '그릇', 즉 **서버 인프라(Infra)**가 필요합니다.

이제부터 시작될 **[모듈 4. 지식 그래프 인프라 구축]**에서는 개인의 PC를 벗어나 실제 서비스 서버를 구축하는 본격적인 엔지니어링의 세계로 도약합니다. 

그 첫걸음으로 다음 장인 **"21장. W3C 표준 트리플 스토어 구축: Apache Jena와 Virtuoso"**로 진입하여, 우리가 정성껏 추출한 Turtle 파일을 바탕으로 Linux 서버 환경에 강력한 지식 그래프 엔진을 올리고, 전 세계가 접속할 수 있는 SPARQL 엔드포인트를 세팅하는 인프라 실무를 파헤쳐 보겠습니다!
