# 10.3. DCMI 유형 어휘(Type Vocabulary)와 어플리케이션 프로파일(DCAP) 설계

## 1. 도입: 속성(Predicate)은 통일했는데, 값(Object)이 난장판이라면?

우리는 앞선 장들을 통해 `dcterms:`라는 훌륭한 시맨틱 표준 네임스페이스를 도입하여 "어떤 속성(Predicate)으로 설명할 것인가"에 대한 글로벌 합의를 이루어냈습니다. 

하지만 실제 디지털 인문학 연구실에서 대학원생들에게 데이터를 입력하라고 엑셀 시트를 나눠주면, 며칠 뒤 여러분은 참담한 광경을 목격하게 됩니다. 여러분이 조선시대 문집과 그 안에 그려진 삽화들을 지식 그래프로 구축하려 할 때, 자원의 유형을 나타내는 `dcterms:type`의 값(Object) 칸에 연구원들이 다음과 같이 각자의 철학을 담아 자유롭게 타이핑을 해옵니다.

* 연구원 A (문집): `dcterms:type "Text"`
* 연구원 B (문집): `dcterms:type "책"`
* 연구원 C (문집): `dcterms:type "Book"`
* 연구원 D (삽화): `dcterms:type "그림"`
* 연구원 E (삽화): `dcterms:type "Image"`

속성(Predicate)의 바벨탑은 허물었지만, **값(Object)의 바벨탑**이 다시 세워진 것입니다. 기계의 입장에서 "Text", "책", "Book"은 완전히 다른 자원입니다. 여러분이 나중에 SPARQL로 `WHERE { ?문서 dcterms:type "Text" . }`라고 검색하면, 연구원 B와 C가 입력한 수만 건의 데이터는 검색 결과에서 영원히 누락되는 끔찍한 결측(Missing) 사태가 발생합니다.

## 2. 해결책 제시 1: DCMI 유형 어휘 (DCMI Type Vocabulary)

더블린 코어 커뮤니티(DCMI)는 이 값의 파편화를 막기 위해 속성(Property)뿐만 아니라, `dcterms:type`의 목적어 자리에 들어갈 수 있는 **"공식적이고 제한된 단어장"**을 아예 제정해 버렸습니다. 이것이 바로 `"**DCMI 유형 어휘(DCMI Type Vocabulary)**"`입니다.

[Image conceptualizing the mapping of chaotic, free-text resource types (책, Book, 그림, Image) into the strict, globally standardized URIs of the DCMI Type Vocabulary]

이 단어장에는 세상의 모든 자원을 분류할 수 있는 단 12개의 거대한 범주(Class)만이 존재합니다. 
접두사는 `dctype: <http://purl.org/dc/dcmitype/>`를 사용합니다.

1. **`dctype:Collection`**: 수집물 (예: 규장각 고도서 컬렉션)
2. **`dctype:Dataset`**: 데이터셋 (예: 조선왕조실록 형태소 분석 데이터)
3. **`dctype:Event`**: 사건 (예: 전시회, 학술대회)
4. **`dctype:Image`**: 시각적 자원 (2D/3D 포함, 예: 동여도)
5. **`dctype:InteractiveResource`**: 상호작용 자원 (예: 웹 포털, 멀티미디어 CD)
6. **`dctype:MovingImage`**: 동영상 (예: 탈춤 공연 영상)
7. **`dctype:PhysicalObject`**: 물리적 사물 (예: 백자 달항아리, 경복궁)
8. **`dctype:Service`**: 서비스 (예: SPARQL 엔드포인트)
9. **`dctype:Software`**: 소프트웨어 (예: 형태소 분석기 프로그램)
10. **`dctype:Sound`**: 소리 (예: 판소리 녹음본)
11. **`dctype:StillImage`**: 정지 이미지 (예: 사진, 스캔본)
12. **`dctype:Text`**: 텍스트 (문자로 기록된 모든 것, 예: 목민심서, 논문)

이제 연구원들에게 타이핑의 자유를 빼앗고, 오직 이 12개의 URI 중 하나만 선택하도록 강제해야 합니다. 이것이 **통제 어휘(Controlled Vocabulary)**의 위력입니다.

## 3. 해결책 제시 2: 어플리케이션 프로파일 (DCAP) 설계

DCMI 유형 어휘가 값(Value)을 통제한다면, 전체 프로젝트의 메타데이터 품질을 통제하는 것은 무엇일까요?
"우리 연구소는 더블린 코어를 쓸 거야!"라고 말하는 것만으로는 턱없이 부족합니다. 어떤 속성은 반드시 입력해야 하고(필수), 어떤 속성은 여러 번 입력해도 되는지(반복 가능), 값으로 텍스트를 쓸지 URI를 쓸지 명확한 헌법이 필요합니다.

이러한 **"우리 연구소만의 정밀한 데이터 입력 규칙과 표준의 조합을 명문화한 설계도"**를 정보학에서는 `"**더블린 코어 어플리케이션 프로파일(DCAP, Dublin Core Application Profile)**"`이라고 부릅니다. 

DCAP는 새로운 온톨로지를 만드는 것이 아닙니다. **"전 세계 마트(표준 온톨로지)에서 파는 식재료(어휘)들을 가져다가, 우리 식당(연구소)만의 레시피(규칙)를 작성하는 것"**입니다. 여기에는 더블린 코어뿐만 아니라 FOAF, SKOS 등 여러 표준이 섞일 수 있습니다.

### [실전 적용: '조선시대 지식 네트워크'를 위한 DCAP 설계 명세서 예시]

시맨틱 아키텍트인 여러분이 작성해야 할 DCAP 명세서의 뼈대는 다음과 같습니다.

| 속성명 (Property) | URI (어휘 출처) | 의무(Obligation) | 반복(Repeat) | 값의 형태 (Value Space) / 통제 어휘 |
| :--- | :--- | :--- | :--- | :--- |
| **식별자** | `dcterms:identifier` | 필수 (M) | 불가 (N) | 리터럴 (String: 고유 관리 번호) |
| **제목** | `dcterms:title` | 필수 (M) | 가능 (Y) | 리터럴 (String: 한자/한글 등 다국어) |
| **자원 유형** | `dcterms:type` | 필수 (M) | 불가 (N) | URI (`dctype:Text` 또는 `dctype:Image` 만 허용) |
| **창작자** | `dcterms:creator` | 조건부 (C) | 가능 (Y) | URI (위키데이터 Q-ID 또는 로컬 인물 URI) |
| **발행일** | `dcterms:issued` | 선택 (O) | 불가 (N) | 리터럴 (ISO 8601 형식: YYYY-MM-DD) |
| **주제어** | `dcterms:subject` | 선택 (O) | 가능 (Y) | URI (한국학중앙연구원 SKOS 통제 어휘) |

이러한 명세서가 프로젝트 착수 전에 완벽하게 확정되어 벽에 붙어있지 않다면, 그 지식 그래프 프로젝트는 이미 실패한 것이나 다름없습니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

"교수님, 완벽한 DCAP 설계도를 만들어서 엑셀 파일 첫 장에 붙여두고 연구원들에게 신신당부를 했습니다만, 한 달 뒤 엑셀을 걷어보니 여전히 `dcterms:type`에 'Book'이라고 적고, 발행일에 '조선 선조 때'라고 적어 놓았습니다. 인간의 실수를 어떻게 막습니까?"

가장 훌륭한 아키텍트도 인간의 꼼수와 실수를 이길 수는 없습니다. 

**시맨틱 아키텍트의 실무 가이드: "문서(DCAP)를 기계적 강제(Validation)로 전환하라"**
DCAP는 인간이 읽는 문서에 불과합니다. 이를 시스템적으로 강제하지 않으면 무용지물입니다.

1. **프론트엔드 통제 (입력기 제한):** 엑셀이나 데이터 입력 웹 폼(Web Form)을 만들 때, `dcterms:type` 칸은 타이핑을 금지하고 반드시 드롭다운(Drop-down) 메뉴에서 `dctype:`의 12개 항목 중 하나만 클릭하게 만드십시오. 날짜 칸에는 달력 위젯(Date-picker)을 달아 ISO 8601 형식만 들어가게 강제해야 합니다.
2. **백엔드 통제 (SHACL 검증):** 시맨틱 웹 생태계에는 입력된 RDF 데이터가 DCAP 규칙에 맞는지 기계적으로 검사해 주는 `"**SHACL (Shapes Constraint Language)**"`이라는 W3C 표준이 있습니다. 데이터베이스에 트리플을 붓기 전에 SHACL 엔진을 돌려, 필수 항목이 누락되거나 값의 타입이 틀린 데이터는 서버가 거부(Reject)하도록 파이프라인(ETL)을 구축하십시오.

## 5. 요약 및 다음 단계

* 속성(Predicate)뿐만 아니라 목적어 값(Object)의 혼란을 막기 위해, 더블린 코어는 12개의 공식 통제 어휘인 `"**DCMI Type Vocabulary (`dctype:`)**"`를 제공합니다.
* 여러 표준 온톨로지를 조합하여 우리 연구소만의 필수/선택, 값의 형태(URI vs String) 등 엄격한 입력 규칙을 명문화한 문서를 `"**어플리케이션 프로파일(DCAP)**"`이라고 합니다.
* 훌륭한 DCAP 설계는 필수적이지만, 실무에서는 이를 드롭다운 메뉴나 SHACL과 같은 시스템적 강제 장치로 구현해야만 데이터의 무결성을 지킬 수 있습니다.

이제 우리는 더블린 코어의 문법, 시맨틱 확장, 통제 어휘, 그리고 설계 문서(DCAP) 작성법까지 마스터하며 범용 메타데이터의 전문가가 되었습니다. 

하지만 아무리 DCAP를 정교하게 짠다고 해도, 서양에서 온 `dcterms:`의 그릇 자체가 동양 고문헌의 "편찬", "교감", "서발"이라는 복잡한 인간관계를 온전히 담아낼 수 없다는 본질적인 딜레마는 여전히 남아있습니다. 

10장의 대미를 장식할 다음 장인 **[10.4. 동양 고문헌의 딜레마: 편찬, 교감, 서발의 다중 속성 크로스워크 전략]**에서, 글로벌 표준과의 호환성을 100% 유지하면서도 우리 고문헌의 눈물겨운 디테일을 살려내는 위대한 **'시맨틱 크로스워크'와 '이중 등재'**의 궁극적 해법을 제시하겠습니다.
