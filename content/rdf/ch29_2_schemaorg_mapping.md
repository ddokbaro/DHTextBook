# 29.2. 인문학 사료의 Schema.org 매핑 전략

## 1. 도입: 구글 로봇은 "영의정"과 "본관"을 알아듣지 못한다

우리는 29.1장을 통해 화면(HTML)과 데이터(JSON-LD)를 완벽하게 분리하는 "데이터 아일랜드"를 구축했습니다. 이제 우리의 서버(Virtuoso)에서 이순신 장군의 트리플 데이터를 뽑아와 JSON-LD 보증서에 예쁘게 담아 구글 봇에게 건네줄 준비를 마쳤습니다.

하지만 인문학자가 자신이 심혈을 기울여 만든 온톨로지 규칙(`core:hasPost`, `joseon:영의정`)을 그대로 JSON-LD에 적어 넣으면, 구글 봇은 이 보증서를 읽고도 고개를 갸우뚱거리며 그냥 지나쳐 버립니다. 

구글 봇은 전 세계의 수백억 개 웹페이지를 긁어모으는 기계입니다. 그들은 한국학중앙연구원이 정의한 세밀하고 훌륭한 "조선시대 관직 온톨로지"를 일일이 공부할 시간이 없습니다. 구글, 마이크로소프트, 야후 등 세계적인 IT 공룡들은 기계들이 소통할 수 있는 단 하나의 거대한 글로벌 공용어 사전을 만들었고, "이 사전에 있는 단어만 써서 보증서를 제출하라"고 전 세계 웹마스터들에게 강제했습니다. 이 거대한 범용 사전의 이름이 바로 "**Schema.org(스키마닷오알지)**"입니다. 

우리가 만든 고차원적인 역사 지식을 대중에게 검색되게 하려면, 우리의 언어를 그들의 언어로 통역하는 피눈물 나는 타협의 과정이 필요합니다.

## 2. 해결책 제시: 깐깐한 사학자와 글로벌 가이드의 타협, "**시맨틱 매핑**"

디지털 인문학 아키텍트에게 이 통역 과정은 자존심이 상하는 일일 수 있습니다. 우리는 이순신의 "본관(Clan)"과 "과거 급제(Passing Exam)"라는 고유한 역사적 맥락을 표현하기 위해 밤을 새워 온톨로지를 설계했습니다. 하지만 Schema.org 사전에는 그런 섬세한 단어가 존재하지 않습니다.

인문학적으로 비유해 보겠습니다. 여러분은 조선 왕실의 복잡한 의례와 철학이 담긴 두꺼운 "**궁중 법도서(우리의 온톨로지)**"를 썼습니다. 하지만 경복궁을 방문한 수백만 명의 외국인 관광객(구글 봇)에게 이 책을 그대로 주면 아무도 읽지 않습니다. 우리는 눈물을 머금고 이 법도서의 핵심만을 추려, 아주 쉽고 납작한 영어 단어로 쓰인 얇은 "**외국인용 관광 가이드북(Schema.org)**"으로 번역(Mapping)해야만 합니다.

| 한국학 고유 온톨로지 (학술적 깊이) | Schema.org 범용 온톨로지 (글로벌 노출용) | 번역의 한계와 타협 |
| :--- | :--- | :--- |
| `core:Person` (조선시대 인물) | `"@type": "Person"` | 완벽한 1:1 매핑 성공 |
| `core:birthYear` (출생 연도) | `"birthDate"` | 연도만 있어도 날짜 형식으로 타협 |
| `core:hasPost` (관직 임용) | `"jobTitle"` 또는 `"hasOccupation"` | "관직"이라는 고유 개념이 현대의 "직업(Job)"으로 평면화됨 |

## 3. 실전 적용: 이순신 장군의 생애를 구글의 언어로 번역하기

이제 이순신 장군의 복잡한 학술 데이터를 구글이 100% 이해할 수 있는 Schema.org 기반의 JSON-LD 포맷으로 번역해 보겠습니다.

```html
<script type="application/ld+json">
{
  "@context": "[https://schema.org](https://schema.org)",
  "@type": "Person",
  "name": "이순신",
  "alternateName": "여해",           "birthDate": "1545",               "deathDate": "1598",
  
  "hasOccupation": {
    "@type": "Occupation",
    "name": "삼도수군통제사",
    "estimatedSalary": "무보수 혹은 군량미"  },

  "memberOf": {
    "@type": "Organization",
    "name": "조선 수군"
  },
  
  "sameAs": "[http://dh.aks.ac.kr/joseon/person/이순신](http://dh.aks.ac.kr/joseon/person/이순신)"
}
</script>
```

이렇게 번역된 가이드북(JSON-LD)을 웹페이지에 달아주면, 구글 봇은 "아, 이순신이라는 사람(Person)이 삼도수군통제사라는 직업(Occupation)을 가졌구나!"라고 완벽하게 이해하고, 전 세계 수십억 명의 스마트폰 화면 "지식 패널"에 이순신 장군의 위대한 생애를 띄워주게 됩니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 피눈물: "과거 급제 연도를 넣을 단어가 Schema.org에 없어서 에러가 납니다!"**

번역(Mapping) 실무에서 가장 빈번하게 마주하는 절망입니다. 이순신 장군의 생애에서 가장 중요한 "무과 급제 연도(1576년)"를 구글에 알려주고 싶은데, Schema.org 사전을 아무리 뒤져봐도 "과거시험(Gwageo)"이나 "급제(Passing Exam)"라는 속성은 존재하지 않습니다. 미국인들이 만든 사전이기 때문입니다.

초보 아키텍트들은 마음이 급한 나머지 `"gwageoExamYear": "1576"` 이라는 존재하지 않는 단어를 마음대로 만들어 JSON-LD에 끼워 넣습니다. 
그러면 구글의 "리치 리절트 테스트(Rich Results Test)" 검사기는 즉각 새빨간 에러를 뿜어냅니다. "사전에 없는 단어를 썼으므로 이 보증서 전체를 무효 처리하겠다!"라는 끔찍한 판정입니다.

**[승리하는 아키텍트의 안전한 우회로: additionalProperty]**
구글의 깐깐한 사전을 위반하지 않으면서도 우리의 고유한 역사적 지식을 전달하는 마법의 탈출구가 있습니다. 바로 **`"additionalProperty"`(추가 속성)** 또는 **`"description"`(설명)** 속성이라는 "자유 기재란"을 활용하는 것입니다.

사전에 없는 단어는 절대로 속성 이름(Key)으로 쓰면 안 됩니다. 대신 구글이 합법적으로 허락한 `PropertyValue` 구조 안에 우리의 지식을 안전하게 포장하여 넣어야 합니다.

```json
{
  "@context": "[https://schema.org](https://schema.org)",
  "@type": "Person",
  "name": "이순신",
  
  "additionalProperty": {
    "@type": "PropertyValue",
    "name": "무과 급제 연도",   "value": "1576"
  }
}
```

이 방식을 사용하면 구글의 엄격한 문법 검사기를 무사히 통과(Pass)하면서도, 우리의 소중한 인문학적 데이터가 유실되지 않고 기계의 뱃속으로 안전하게 전달됩니다. 이것이 바로 범용 엔진과 맞춤형 학술 데이터 사이를 줄타기하는 아키텍트의 묘수입니다.

## 5. 요약 및 다음 단계

* 우리가 구축한 한국학 고유의 섬세한 온톨로지를 구글 검색에 노출하려면, 그들의 범용 글로벌 사전인 "**Schema.org**"의 언어로 번역(Mapping)하는 과정이 필수적입니다.
* 역사적으로 복잡한 "관직"이나 "당파" 같은 개념들은 Schema.org의 `"Occupation"`이나 `"Organization"` 같은 현대적이고 평면적인 단어로 타협하여 매핑해야 합니다.
* Schema.org에 존재하지 않는 "본관", "과거 급제" 등의 고유 개념은 억지로 단어를 창조하지 말고, 구글이 허락한 합법적 우회로인 **`"additionalProperty"`**를 사용하여 안전하게 주입해야 합니다.

이제 우리는 구글 봇과 대화하는 완벽한 번역기까지 손에 넣었습니다. 지식 그래프의 데이터는 훌륭하게 포장되어 웹페이지의 뒷면(HTML 소스코드)에 매끄럽게 심어질 준비를 마쳤습니다.

하지만 이 JSON-LD 코드를 웹페이지에 심는 작업 자체를 "인간"이 수작업으로 할 수는 없습니다. 사용자가 브라우저에서 이순신을 클릭하는 그 찰나의 순간, 백엔드 서버가 지식 그래프(Virtuoso)에서 데이터를 퍼 올려서 JSON-LD로 번역한 뒤, 화면이 뜨기도 전에 HTML에 박아 넣어야 합니다. 

다음 장인 "**29.3. 프론트엔드 SSR 렌더링 파이프라인**"으로 진입하여, 검색엔진 로봇이 눈치채기 전에 서버 측에서 이 모든 마법을 초고속으로 조립해 내는 "서버 사이드 렌더링(SSR)" 기술과, 이 과정에서 발생할 수 있는 끔찍한 해킹 공격(XSS)을 방어하는 최전선의 보안 아키텍처를 마스터해 보겠습니다!
