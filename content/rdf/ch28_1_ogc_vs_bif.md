# 28.1. OGC 표준 함수(geof:)와 내부 연산자의 매핑

## 1. 도입: 국제 표준어 책을 들고 시골 장터에 가다

우리는 앞선 28장 도입부에서 이순신 장군의 한산도 통제영과 전라좌수영 본영에 위도와 경도라는 지리적 영혼(WKT 좌표)을 불어넣었습니다. 이제 부푼 마음으로 두 진영 사이의 물리적 거리를 계산해 볼 차례입니다.

디지털 인문학자는 W3C에서 발표한 국제 표준 매뉴얼을 펼칩니다. 매뉴얼에는 두 점 사이의 거리를 구할 때 "**geof:distance**"라는 아름답고 우아한 함수를 쓰라고 적혀 있습니다. 여러분은 자랑스럽게 SPARQL 쿼리 창에 이 표준 함수를 입력하고 실행(Run) 버튼을 누릅니다.

하지만 기대했던 50km라는 결과 대신, 서버는 새빨간 에러 메시지를 뱉어냅니다. "**Error: Unknown function geof:distance**". 분명히 국제 표준을 따랐는데 왜 기계는 알아듣지 못할까요? 

이것은 마치 외국인 학자가 완벽한 서울 표준어 사전만 달달 외운 뒤, 깊은 시골 장터에 가서 국밥을 주문하려다 실패하는 것과 같습니다. 국제 표준 기구(OGC)가 정한 문법은 존재하지만, 우리가 실제로 사용하는 데이터베이스 엔진(Virtuoso 등)의 밑바닥 주방장들은 각자의 고유한 "**사투리(방언)**"를 쓰고 있기 때문입니다.

## 2. 해결책 제시: 국제 표준어와 주방장의 사투리, "**시맨틱 매핑**"

공간 질의(GeoSPARQL)를 실무에서 다루려면 이 뼈아픈 현실을 받아들여야 합니다. 
W3C와 OGC(개방형 공간정보 컨소시엄)가 제정한 "**geof:**" 접두어는 이상적인 "**국제 표준어**"입니다. 하지만 우리가 구축한 Virtuoso 서버나 GraphDB 같은 트리플 스토어들은 성능을 극한으로 끌어올리기 위해 자기들만의 내장 함수, 즉 "**BIF(Built-In Function)**"라는 "**사투리**"를 사용합니다.

디지털 인문학 아키텍트라면 이상적인 표준어에 고집부리지 말고, 주방장이 알아듣는 사투리로 쿼리를 번역(Mapping)하여 원하는 역사적 결과물을 빠르게 얻어내야 합니다.

| 공간 추론 목적 | OGC 국제 표준어 (이상) | Virtuoso 방언 (현실 실무) | 인문학적 작동 결과 |
| :--- | :--- | :--- | :--- |
| **거리 계산** | `geof:distance` | **`bif:st_distance`** | 한산도와 전라좌수영 사이의 거리를 km 단위로 반환함 |
| **반경 내 탐색** | `geof:sfWithin` | **`bif:st_within`** | 한산도 반경 50km 안에 있는 모든 조선 수군 진영을 찾아냄 |
| **면적 교차 확인** | `geof:sfIntersects` | **`bif:st_intersects`** | 경상우수영의 관할 구역과 전라좌수영의 관할 구역이 겹치는지 확인함 |

## 3. 실전 적용: 사투리를 활용하여 두 수군 진영의 거리 계산하기

이제 Virtuoso 주방장이 알아듣는 "**bif:**" 사투리를 사용하여, 한산도와 전라좌수영 사이의 실제 거리를 계산하는 SPARQL 쿼리를 작성해 보겠습니다.

```sparql
# 1. 공간 추론을 위한 네임스페이스 선언
PREFIX geo: [http://www.opengis.net/ont/geosparql#](http://www.opengis.net/ont/geosparql#)
PREFIX joseon: [http://dh.aks.ac.kr/joseon/](http://dh.aks.ac.kr/joseon/)

# 2. 거리 결과값을 담을 변수(?distance)를 요청합니다.
SELECT ?distance
WHERE {
    # 3. 한산도의 WKT 좌표를 찾아 변수(?h_wkt)에 담습니다.
    joseon:한산도 geo:asWKT ?h_wkt .
    
    # 4. 전라좌수영의 WKT 좌표를 찾아 변수(?j_wkt)에 담습니다.
    joseon:전라좌수영 geo:asWKT ?j_wkt .
    
    # 5. [핵심] Virtuoso의 사투리(bif:st_distance)를 사용하여 두 좌표의 거리를 계산합니다.
    # 계산된 숫자를 ?distance 변수에 묶어줍니다(BIND).
    BIND(bif:st_distance(?h_wkt, ?j_wkt) AS ?distance)
}
```

이 코드를 실행하면, 기계는 즉시 두 좌표 사이의 구면 삼각법을 계산하여 "**58.3**"이라는 경이로운 숫자를 화면에 띄워줍니다. 인문학자가 자를 대고 지도를 잴 필요 없이, 기계 스스로 공간의 거리를 추론해 낸 것입니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 대참사: "한산도와 부산포의 거리를 계산했더니 '0.8'이 나옵니다!"**

이것은 공간 질의를 처음 시도하는 연구원들이 100% 마주하게 되는 가장 무서운 함정입니다. 분명히 한산도에서 부산포까지는 수십 킬로미터가 넘는데, 기계는 "**0.8**"이라는 터무니없이 작은 숫자를 정답이라고 우깁니다. 단위가 미터(m)라면 80센티미터라는 뜻일까요?

**[승리하는 아키텍트의 공간 참조 시스템(SRID) 통제술]**
기계가 뱉어낸 "**0.8**"이라는 숫자의 정체는 킬로미터(km)도 아니고 미터(m)도 아닙니다. 그것은 바로 "**도(Degree)**"입니다. 

여러분은 기계에게 위도와 경도 숫자를 주었을 뿐, **"지구가 둥근 구형이다"**라는 사실을 알려주지 않았습니다. 기계는 평평한 모눈종이 위에서 X축과 Y축의 단순한 피타고라스 직선거리를 계산한 것입니다. (예: X축 1도 차이, Y축 1도 차이의 거리 계산)

기계에게 둥근 지구 표면의 곡률을 반영하여 킬로미터(km) 단위로 실제 거리를 계산하게 만들려면, 좌표 텍스트 앞에 반드시 **"지구의 형태 모델 번호"**를 붙여주어야 합니다. GPS의 전 세계 표준 모델 번호는 "**SRID=4326**"입니다. 

데이터를 입력할 때 반드시 아래와 같이 마법의 주문을 추가해야 대참사를 막을 수 있습니다.

```turtle
# [실패하는 평면 좌표]
joseon:한산도 geo:asWKT "POINT(128.48 34.76)"^^geo:wktLiteral .

# [성공하는 둥근 지구 좌표 (SRID=4326 주입)]
joseon:한산도 geo:asWKT "[http://www.opengis.net/def/crs/OGC/1.3/CRS84](http://www.opengis.net/def/crs/OGC/1.3/CRS84) POINT(128.48 34.76)"^^geo:wktLiteral .
```

좌표계 주소를 명시적으로 텍스트 앞에 붙여주면, Virtuoso 엔진은 비로소 지구가 둥글다는 것을 깨닫고 도(Degree) 단위가 아닌 완벽한 킬로미터(km) 단위로 거리를 환산해 줍니다. 

## 5. 요약 및 다음 단계

* GeoSPARQL의 국제 표준 함수("**geof:**")는 이상적이지만, 실제 거대한 지식 그래프 서버를 구동할 때는 각 엔진에 최적화된 내부 사투리 함수("**bif:**")를 사용하는 유연한 시맨틱 매핑이 필수적입니다.
* 데이터베이스 엔진이 알아듣는 "**bif:st_distance**" 함수를 사용하면 텍스트로 이루어진 두 장소의 물리적 거리를 즉각적으로 계산할 수 있습니다.
* 기계가 평면 모눈종이가 아닌 둥근 지구의 표면 곡률을 따라 킬로미터(km) 단위로 계산하도록 만들려면, 반드시 좌표 앞에 국제 표준 공간 참조 번호("**SRID=4326**")를 선언해야 합니다.

이제 우리는 기계에게 지도를 쥐여주고, 사투리 명력을 통해 거리를 계산하는 법까지 완벽하게 터득했습니다. 
그렇다면 특정 장소 하나를 찍고, "이곳을 중심으로 반경 50km 원을 그린 뒤, 그 안에 들어오는 모든 데이터를 쓸어 담아라!"라는 훨씬 고차원적인 지리적 질문은 어떻게 던질 수 있을까요?
