# 24장. 정형 데이터(CSV/RDB)의 3대 ETL 파이프라인 실무

## 1. 도입: 지식의 성채를 위협하는 "오염된 원시 데이터"의 습격

우리는 앞선 모듈을 통해 지식 그래프를 담아낼 수 있는 견고하고 거대한 3개의 성채(Virtuoso, Neo4j, Wikibase)를 성공적으로 축조했습니다. 이제 이 빈 성채에 우리가 평생을 바쳐 모은 역사적 사실들을 채워 넣을 차례입니다.

하지만 현실의 연구 현장으로 돌아와 우리의 하드디스크를 열어봅시다. 수십 년간 여러 선배 연구원과 조교들의 손을 거치며 누적된 엑셀(CSV) 파일이나 낡은 관계형 데이터베이스(RDB) 속 데이터는 참혹한 수준입니다. 
동일한 "이순신"이라는 인물이 어떤 칸에는 "李舜臣"으로, 어떤 칸에는 "이 순 신(띄어쓰기)"으로, 심지어 "덕수이씨 충무공"으로 제각각 기록되어 있습니다. 관직 임용 연도를 적는 칸에는 "1592", "선조 25년", "임진년 4월 경" 등 기계가 절대 연산할 수 없는 텍스트가 뒤섞여 있습니다.

이러한 "**원시 데이터(Raw Data)**"를 있는 그대로 우리의 완벽한 지식 그래프 서버에 쏟아부으면 어떻게 될까요? 그 즉시 우리의 지식망은 쓰레기장이 되어버립니다. 아무리 완벽한 온톨로지를 설계했더라도, "이순신"과 "李舜臣"을 다른 사람으로 인식하는 순간 지식의 연결은 끊어지고 맙니다. 수작업으로 수십만 건의 엑셀 칸을 일일이 수정하는 것은 인간의 수명으로는 불가능한 일입니다.

이 참사를 막고 오염된 기록을 깨끗한 지식의 결정체로 연성하기 위해, 우리는 컴퓨터 공학의 강력한 무기인 "**ETL 파이프라인**"을 도입해야 합니다.

## 2. 해결책 제시: 진흙탕 물을 식수로 바꾸는 거대한 정수장, "**ETL**"

컴퓨터 공학에서 말하는 "**ETL(Extract, Transform, Load)**"은 데이터를 한 곳에서 다른 곳으로 옮기는 일련의 자동화된 공정을 의미합니다. 인문학적으로 비유하자면, 산에서 내려오는 흙탕물(원시 데이터)을 끌어와서 필터로 불순물을 걸러내고(데이터 정제 및 구조 변환), 맑은 물만 모아 거대한 식수 댐(지식 그래프)에 채워 넣는 "**거대한 정수장**"을 짓는 일입니다.

* **추출(Extract):** 여기저기 흩어진 엑셀 파일, CSV, 낡은 데이터베이스에서 데이터를 긁어모으는 단계입니다.
* **변환(Transform):** "**ETL**"의 핵심이자 가장 고통스러운 단계입니다. 오타를 수정하고("이 순 신" ➔ "이순신"), 연도를 표준화하며("선조 25년" ➔ "1592"), 단순한 표 형태의 데이터를 주어-서술어-목적어의 "**트리플(Triple)**" 구조로 빚어냅니다.
* **적재(Load):** 깨끗하게 정제되고 변환된 트리플 데이터를 Virtuoso나 Neo4j 같은 종착지에 쏟아붓는 단계입니다.

디지털 인문학 아키텍트라면, 우리가 가진 데이터의 "오염도"와 "크기"에 맞추어 다음의 "**3대 ETL 파이프라인**" 밸브를 자유자재로 열고 닫을 수 있어야 합니다.

## 3. 실전 적용: 지식 그래프 생태계를 위한 3대 ETL 무기

우리가 실무에서 마주하게 될 상황은 크게 세 가지로 나뉩니다. 각 상황에 맞는 최적의 도구를 살펴보겠습니다.

| 상황 분류 | 데이터의 특징 | 최적의 ETL 도구 | 핵심 인문학적 기능 |
| :--- | :--- | :--- | :--- |
| **상황 1: 오염도가 극심할 때** | 수만 건 규모의 지저분한 CSV/엑셀 파일 (오타, 띄어쓰기 오류 난무) | **OpenRefine (오픈리파인)** | **"노이즈 클렌징의 제왕"**<br>유사한 단어들을 기계가 찾아내어 일괄 통일해주고, 마우스 클릭만으로 직관적인 RDF 변환을 지원합니다. |
| **상황 2: 데이터가 너무 거대할 때** | 이미 정제는 끝났으나 수백만 건이 넘어가는 초대형 CSV 파일 | **Tarql (타르큐엘)** | **"초고속 스트리밍 변환기"**<br>무거운 엑셀을 메모리에 올리지 않고, SPARQL 문법을 이용해 읽는 즉시 트리플로 맵핑하여 뿜어냅니다. |
| **상황 3: 레거시 DB에 갇혀 있을 때** | 국가 기관의 거대한 관계형 데이터베이스 (MySQL, Oracle 등) | **R2RML (알투알엠엘)** | **"RDB의 가상 지식 그래프화"**<br>데이터를 엑셀로 빼낼 필요 없이, 관계형 DB의 테이블과 컬럼을 온톨로지에 직접 연결하여 가상의 지식망을 구축합니다. |

이 세 가지 무기는 경쟁하는 것이 아닙니다. 
예를 들어, "조선시대 무과 방목" 데이터를 건네받았다면, 먼저 **OpenRefine**으로 합격자 이름의 한자 오탈자를 씻어냅니다. 정제가 완료된 깔끔한 수십만 건의 데이터를 텍스트(CSV)로 저장한 뒤, **Tarql**을 이용해 단 몇 초 만에 거북이 파일(.ttl)로 변환하여 서버에 올리는 식의 연계 플레이가 필수적입니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 피눈물: "한글 데이터가 전부 외계어로 깨져서 들어갔습니다!"**

ETL 파이프라인을 처음 구축하는 인문학도들이 100% 겪는 통곡의 벽입니다. 엑셀에서 정성껏 작성한 "이순신", "전라좌수사" 데이터를 CSV로 저장하여 파이프라인에 넣었는데, 결과물에는 "̼", "" 같은 끔찍한 기호들만 가득합니다.

**[승리하는 아키텍트의 인코딩(Encoding) 방어술]**
이것은 윈도우(Windows) 운영체제와 국제 표준인 "**UTF-8**" 사이의 소통 오류입니다. 
엑셀에서 문서를 저장할 때, 그냥 "CSV (쉼표로 분리)"를 선택하면 윈도우만의 독자적인 언어(euc-kr)로 저장되어 서버가 읽지 못합니다. 반드시 **"CSV UTF-8 (쉼표로 분리)"** 확장자를 선택하여 저장해야 합니다. 
또한 메모장으로 CSV를 열었을 때 우측 하단에 "**UTF-8**"이라고 적혀 있는지 확인하는 습관을 들여야 파이프라인의 입구에서부터 오염물이 들어오는 것을 막을 수 있습니다.

**시맨틱 아키텍트의 경고: "가비지 인, 가비지 아웃 (Garbage In, Garbage Out)"**

컴퓨터 공학의 가장 유명한 격언입니다. 쓰레기를 넣으면 쓰레기가 나온다는 뜻입니다. 아무리 Tarql이나 R2RML 코드를 아름답게 짰더라도, 원본 데이터에 "원균"이 "원 균"으로 잘못 적혀 있다면 기계는 이를 영원히 다른 사람으로 취급합니다. ETL의 시작과 끝은 오직 끝없는 데이터 관찰과 "**정제(Cleansing)**"에 있음을 잊지 마십시오.

## 5. 요약 및 다음 단계

* 우리가 수집한 파편화되고 오염된 인문학 데이터를 지식 그래프로 변환하기 위해서는 추출, 변환, 적재를 자동화하는 "**ETL 파이프라인**" 구축이 필수적입니다.
* 데이터의 규모와 상태에 따라 노이즈를 씻어내는 "**OpenRefine**", 대용량을 초고속 변환하는 "**Tarql**", 관계형 DB를 직접 연결하는 "**R2RML**"을 전략적으로 활용해야 합니다.
* 모든 파이프라인의 대전제는 완벽한 문자 인코딩(UTF-8)과 철저한 원본 데이터 정제입니다.

이제 거대한 정수장의 설계도를 머릿속에 담았습니다. 소매를 걷어붙이고 직접 데이터의 진흙탕 속으로 뛰어들 시간입니다.
