# 10.1. 단순 더블린 코어(Simple DC)의 15가지 핵심 요소와 서지 데이터 매핑

## 1. 도입: 세상을 묘사하는 15개의 뼈대 (DCMES)

더블린 코어 메타데이터 이니셔티브(DCMI)가 1995년에 처음 발표한 15개의 기본 어휘 집합을 우리는 `"**단순 더블린 코어(Simple Dublin Core)**"` 또는 **DCMES(Dublin Core Metadata Element Set)**라고 부릅니다. 

이 15개의 속성(Property)은 세상에 존재하는 어떠한 형태의 정보 자원(종이책, 웹페이지, 동영상, 박물관의 도자기 등)이든 그 핵심적인 뼈대를 설명할 수 있도록 극도로 추상화되어 있습니다. 

단순 더블린 코어의 네임스페이스(URI 접두사)는 다음과 같이 선언됩니다.
`@prefix dc: <http://purl.org/dc/elements/1.1/> .`

이 15가지 마법의 단어들은 그 성격에 따라 크게 **콘텐츠(Content), 지적 재산(Intellectual Property), 물리적 구체화(Instantiation)**라는 세 가지 그룹으로 나뉩니다. 이제부터 하나씩 완벽하게 해부해 보겠습니다.

## 2. 해결책 제시: 15가지 핵심 요소의 시맨틱 해부

### [그룹 1] 콘텐츠 (Content) 자체에 대한 설명
자원의 내용물이 "무엇"인지, "어떤 주제"를 다루는지를 묘사합니다.

1. **`dc:title` (제목):** 자원에 주어진 이름입니다. (예: "징비록", "조선왕조실록")
2. **`dc:subject` (주제):** 자원의 내용이 다루는 핵심 주제나 키워드입니다. 도서관의 십진분류표나 통제어휘(SKOS)를 주로 사용합니다. (예: "임진왜란", "역사")
3. **`dc:description` (설명):** 자원의 내용에 대한 설명, 요약, 초록(Abstract), 또는 목차입니다.
4. **`dc:type` (유형):** 자원의 본질적인 성격이나 장르입니다. (예: "Text", "Image", "Sound", "Dataset")
5. **`dc:source` (출처):** 현재 자원이 파생되어 나온 원본 자원입니다. (예: 번역본의 경우 원어 판본)
6. **`dc:relation` (관계):** 다른 자원과의 관계를 나타냅니다. (예: "A는 B의 일부이다", "A는 B를 대체한다")
7. **`dc:coverage` (범위):** 자원의 내용이 적용되는 공간적(지명, 위경도) 또는 시간적(시대, 연도) 범위입니다. (예: "16세기", "한양")

### [그룹 2] 지적 재산 (Intellectual Property)에 대한 설명
자원을 "누가" 만들었고, "누가" 배포하며, "어떤 권리"가 얽혀 있는지를 묘사합니다.

8. **`dc:creator` (생성자):** 자원의 내용 창작에 일차적인 책임을 지는 주체입니다. (예: "류성룡", "정약용")
9. **`dc:contributor` (기여자):** 자원의 내용 창작에 부차적인 기여를 한 주체입니다. (예: 번역자, 삽화가, 혹은 고문헌의 편찬자나 교감자)
10. **`dc:publisher` (출판자):** 자원을 접근 가능한 상태로 배포한 주체입니다. (예: "규장각", "한국학중앙연구원 출판부")
11. **`dc:rights` (권리):** 자원에 대한 저작권 및 이용 권리 정보입니다. (예: "공공누리 제1유형", "Creative Commons")

### [그룹 3] 구체화/형태 (Instantiation)에 대한 설명
자원이 "어떤 언어"로, "어떤 물리적/디지털 형태"로 존재하는지를 묘사합니다.

12. **`dc:date` (날짜):** 자원의 생성, 출판, 변경 등 생애주기와 관련된 날짜입니다. (ISO 8601 형식인 YYYY-MM-DD 권장)
13. **`dc:format` (형식):** 자원의 파일 형식(MIME Type)이나 물리적 매체입니다. (예: "application/pdf", "목판본", "JPEG")
14. **`dc:identifier` (식별자):** 자원을 특정 맥락에서 고유하게 참조할 수 있는 번호나 문자열입니다. (예: "ISBN", "URI", "DOI")
15. **`dc:language` (언어):** 자원의 내용이 작성된 언어입니다. (ISO 639 표준 코드 사용 권장. 예: "ko", "lzh"(한문))

## 3. 실전 적용: 류성룡의 《징비록》 서지 데이터 매핑 (Turtle)

이제 우리가 배운 15개의 `dc:` 요소를 사용하여, 류성룡이 임진왜란의 참상을 기록한 《징비록(懲毖錄)》이라는 고문헌 데이터를 지식 그래프(RDF Turtle)로 코딩해 보겠습니다.

```turtle
@prefix dc: [http://purl.org/dc/elements/1.1/](http://purl.org/dc/elements/1.1/) .
@prefix 국학: [http://aks.ac.kr/data/](http://aks.ac.kr/data/) .

# 징비록이라는 서지 자원을 단순 더블린 코어(Simple DC)로 묘사합니다.
국학:book/징비록 
    # 1. 콘텐츠 그룹
    dc:title "징비록(懲毖錄)" ;
    dc:description "조선 선조 때 영의정 류성룡이 임진왜란의 원인과 전황을 기록한 책" ;
    dc:subject "임진왜란", "국방", "역사" ;
    dc:type "Text" ;
    dc:coverage "1592-1598 (조선)" ;
    
    # 2. 지적 재산 그룹
    dc:creator "류성룡" ; 
    dc:publisher "조선 간행소" ;
    dc:rights "퍼블릭 도메인" ;
    
    # 3. 구체화/형태 그룹
    dc:date "1604" ; # 간행 연도
    dc:format "목판본" ;
    dc:language "lzh" ; # 한문
    dc:identifier "KRM_00012345" .
```

이 코드는 매우 직관적이며 인간이 읽기에 훌륭합니다. 여러분이 이 데이터를 배포하면, 구글 검색 엔진은 이 책이 "류성룡"이 쓴 "징비록"임을 즉각적으로 인덱싱할 수 있습니다. 이것이 링구아 프랑카(공용어)의 위력입니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

그러나 시맨틱 아키텍트인 여러분은 방금 작성한 위의 코드를 보며 **치명적인 한계**를 직감해야 합니다. 

"교수님! 방금 코드를 보니 `dc:creator`의 목적어 자리에 URI가 아니라 `"류성룡"`이라는 단순한 **문자열(String, 리터럴)**이 들어갔습니다. 시맨틱 웹과 LOD의 핵심은 기계가 클릭해서 따라갈 수 있는 **링크(URI, Thing)**를 만드는 것인데, 이렇게 텍스트만 덜렁 적어놓으면 위키데이터에 있는 류성룡(Q485121) 데이터와 결합(JOIN)할 수가 없지 않습니까?"

**[시맨틱 아키텍트의 딜레마: "문자열(String)이냐 사물(Thing)이냐"]**

정확한 지적입니다! 초창기 웹(1995년)에 만들어진 오리지널 1.1버전(`dc:`)은 본질적으로 **"값으로 문자열(String)을 가지는 것을 암묵적인 규칙"**으로 삼았습니다. 

당시 사서들은 복잡한 하이퍼링크보다는 도서관 카드 목록에 들어갈 단순한 텍스트 덩어리가 필요했기 때문입니다. 하지만 지식 네트워크(Knowledge Graph)를 구축하는 현대의 관점에서, 목적어가 전부 문자열로 닫혀버린 이 상태는 거대한 연결을 가로막는 **"문자열 사일로(String Silo)"**에 불과합니다.

또한, '단순 더블린 코어'는 너무 단순한 나머지 정밀함이 떨어집니다. `dc:date`라고만 쓰면 이것이 저자가 원고를 탈고한 날짜인지, 인쇄소에서 책을 찍어낸 날짜인지, 도서관에 입고된 날짜인지 기계는 영원히 알 길이 없습니다.

## 5. 요약 및 다음 단계

* 1995년 제정된 **단순 더블린 코어(Simple DC, `dc:`)**는 세상의 모든 자원을 콘텐츠, 지적 재산, 구체화라는 3가지 그룹의 15개 속성으로 설명합니다.
* 이 15가지 어휘는 메타데이터의 가장 훌륭한 공용어(Lingua Franca)로서, 엑셀에 흩어진 서지 데이터를 표준화하는 첫걸음입니다.
* 그러나 초창기 버전인 `dc:`는 목적어 값으로 링크(URI) 대신 **단순 문자열(String)**을 취하는 태생적 한계를 가지며, 속성의 의미가 너무 포괄적이라 학술적인 정밀함이 떨어집니다.

그렇다면 이 치명적인 한계를 어떻게 극복할까요? 우리는 문자열(String)을 넘어 세상의 사물(Thing, URI)을 부드럽게 연결해야 하며, `date`를 넘어 `created(창작일)`, `issued(발행일)`처럼 더 정밀한 메타데이터를 기계에게 쥐여주어야 합니다.

다음 장인 **[10.2. 한계 돌파: 한정어(Qualifier)와 dcterms의 시맨틱 확장]**에서, 낡은 `dc:` 접두사를 버리고 최신 시맨틱 웹 표준으로 진화한 `"**dcterms:**"` 네임스페이스의 강력한 문법과 확장 전략을 마스터해 보겠습니다.
