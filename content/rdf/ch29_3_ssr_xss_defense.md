# 29.3. 프론트엔드 SSR 렌더링 파이프라인과 XSS 방어

## 1. 도입: 빈 종이를 들고 찾아온 사신과 성질 급한 구글 봇

우리는 29.2장에서 구글이 완벽하게 이해할 수 있는 "Schema.org" 기반의 JSON-LD 보증서를 작성하는 법을 배웠습니다. 이제 웹 개발자에게 이 보증서를 웹페이지에 넣어달라고 부탁했습니다. 요즘 유행하는 리액트(React)나 뷰(Vue) 같은 프론트엔드 기술을 사용해서 말입니다.

그런데 며칠 뒤, 구글 검색 결과에서 우리의 웹사이트가 통째로 사라지는 대참사가 발생합니다! 원인은 무엇일까요?

현대의 웹 기술(CSR, 클라이언트 사이드 렌더링)은 사용자가 웹사이트에 접속하면 일단 "**빈 화면(HTML)**"을 먼저 던져주고, 사용자의 브라우저 안에서 자바스크립트가 천천히 돌면서 뒤늦게 서버(Virtuoso)에서 데이터를 가져와 화면과 JSON-LD를 채워 넣는 방식을 씁니다. 

인문학적으로 비유하자면, 구글 봇이라는 성질 급한 사신이 조선의 궁궐에 도착했는데, 승정원 사관이 일단 "**아무것도 적히지 않은 빈 두루마리**"를 건네주며 "조금만 기다리시면 먹물이 스며들어 글자가 나타날 것입니다"라고 말하는 꼴입니다. 하루에 수백억 개의 문서를 읽어야 하는 구글 봇은 1초도 기다려주지 않습니다. 빈 종이를 본 구글 봇은 "이곳엔 아무런 지식이 없다"고 결론 내리고 매몰차게 떠나버립니다. 

## 2. 해결책 제시: 사관이 직접 도장을 찍어 내보내는 "**SSR(서버 사이드 렌더링)**"

성질 급한 구글 봇을 붙잡기 위해, 디지털 인문학 아키텍트는 아키텍처의 패러다임을 완전히 뒤집어야 합니다. 브라우저(클라이언트)에서 지식을 조립하게 놔두는 것이 아니라, 서버(Server) 내부에서 HTML 화면과 JSON-LD 보증서를 완벽하게 하나로 조립한 뒤, 완성된 문서를 구글 봇에게 한 번에 던져주어야 합니다.

이 위대한 패러다임을 컴퓨터 공학에서는 "**SSR(Server-Side Rendering, 서버 사이드 렌더링)**"이라고 부릅니다.

승정원의 사관(백엔드 서버)이 사용자의 요청을 받는 그 즉시, 지식 그래프 서버(Virtuoso)로 달려가 이순신의 데이터를 뽑아옵니다. 그리고 붓을 들어 완벽한 HTML 문서와 JSON-LD 보증서를 한 땀 한 땀 작성하고 옥새를 찍어 완성된 문서를 문밖으로 내보냅니다. 구글 봇은 문서를 받아 드는 0.1초의 찰나에 완벽한 시맨틱 데이터를 읽고 만족하며 돌아갑니다.

| 렌더링 방식 | 작동 원리 (비유) | 구글 로봇(SEO)의 반응 |
| :--- | :--- | :--- |
| **CSR (클라이언트 렌더링)** | 일단 빈 종이를 주고 나중에 글씨가 나타남 | **"빈 문서군. (수집 포기 및 이탈)"** |
| **SSR (서버 사이드 렌더링)** | 서버에서 먹물이 마른 완벽한 문서를 건네줌 | **"완벽한 JSON-LD 지식 획득! (검색 최상단 노출)"** |

## 3. 실전 적용: 파이썬(Python) 백엔드에서 JSON-LD 조립하여 쏘아 올리기

웹 서버(예: 파이썬 Flask, Node.js 등)가 사용자의 접속 요청을 받았을 때, 찰나의 순간에 SPARQL 쿼리를 날려 데이터를 가져오고 JSON-LD를 조립하여 HTML로 찍어내는 "SSR 파이프라인"의 뼈대를 살펴보겠습니다.

```python
# 파이썬(Python) 기반의 백엔드 서버 SSR 처리 로직 예시
import json
from flask import Flask, render_template

app = Flask(__name__)

@app.route("/person/이순신")
def show_person():
    # 1. 지식 그래프(Virtuoso) 서버에 SPARQL 쿼리를 날려 데이터를 퍼옵니다.
    # (실제 쿼리 실행 코드는 생략, 결과만 딕셔너리로 받았다고 가정)
    kg_data = {
        "name": "이순신",
        "birthYear": "1545",
        "jobTitle": "전라좌수사"
    }
    
    # 2. 퍼온 인문학 데이터를 구글이 좋아하는 Schema.org 규격(JSON-LD)으로 매핑합니다.
    json_ld_dict = {
        "@context": "[https://schema.org](https://schema.org)",
        "@type": "Person",
        "name": kg_data["name"],
        "birthDate": kg_data["birthYear"],
        "jobTitle": kg_data["jobTitle"]
    }
    
    # 3. 딕셔너리를 완벽한 JSON 문자열로 직렬화(Serialization)합니다.
    json_ld_string = json.dumps(json_ld_dict, ensure_ascii=False)
    
    # 4. 완성된 JSON-LD 문자열을 HTML 템플릿에 박아 넣어서(SSR) 브라우저로 전송합니다!
    return render_template("person_detail.html", json_ld_data=json_ld_string)
```

이 코드를 통해 만들어진 웹사이트는 구글 봇이 접속하는 순간, 자바스크립트의 실행을 기다릴 필요 없이 소스 코드(View Source)에 이미 완벽한 `<script type="application/ld+json">` 블록이 새겨져 있는 상태가 됩니다. 구글 검색 최적화(SEO)의 완벽한 승리입니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 피눈물: "데이터에 섞여 들어간 악성 코드 때문에 사이트가 털렸습니다!"**

SSR 파이프라인을 구축하고 기뻐하던 여러분의 연구실에 갑자기 비상이 걸립니다. 누군가 웹사이트에 접속하면 갑자기 화면이 깨지면서 "해킹당했습니다!"라는 팝업창이 뜨거나, 방문자의 쿠키 정보가 해커의 서버로 줄줄 새어나가기 시작합니다. 도대체 완벽한 지식 그래프에 무슨 일이 벌어진 것일까요?

**[승리하는 아키텍트의 XSS(크로스 사이트 스크립팅) 방어술]**
이것은 오픈 데이터 생태계에서 벌어지는 가장 무서운 공격인 "**XSS(크로스 사이트 스크립팅)**"입니다.
우리는 앞서 데이터베이스를 개방하고 불특정 다수(Crowdsourcing)가 위키베이스(Wikibase) 등을 통해 지식을 수정할 수 있게 허용했습니다. 그런데 악의적인 해커가 "이순신"의 이름 칸에 다음과 같은 끔찍한 코드를 적어 넣고 저장했다고 가정해 봅시다.

`"name": "</script><script>alert('해킹완료!');</script>"`

백엔드 서버는 아무 생각 없이 이 이름 데이터를 퍼와서 `json.dumps()`로 문자열로 만든 뒤, HTML의 `<script>` 태그 안에 그대로 욱여넣습니다. 
브라우저는 이 문자를 읽다가 `</script>`를 만나는 순간, JSON-LD 블록이 끝났다고 착각하고 뒤이어 나오는 해커의 악성 자바스크립트(`alert('해킹완료!');`)를 무방비 상태로 실행해 버립니다.

이 끔찍한 XSS 공격을 막아내려면, 백엔드 서버에서 JSON-LD 문자열을 HTML에 박아 넣기 직전에 **"반드시 HTML 특수 문자를 무력화(Sanitization)"**해야 합니다.

```python
# [위험한 코드] 해커의 괄호(<, >)가 그대로 HTML에 렌더링됩니다.
json_ld_string = json.dumps(json_ld_dict)

# [안전한 방어 코드] HTML 렌더링을 파괴하는 괄호를 유니코드로 강제 치환합니다.
safe_json_ld = json.dumps(json_ld_dict).replace("<", "\\u003c").replace(">", "\\u003e")
```

이렇게 꺾쇠 기호(`<`, `>`)를 이빨 빠진 유니코드(`\u003c`)로 강제 치환해 버리면, 해커가 아무리 악성 스크립트를 주입해도 브라우저는 이를 단순한 텍스트로 인식하여 화면에 문자 그대로 출력할 뿐, 절대 코드로 실행하지 않습니다. 이것이 지식 그래프의 무결성을 넘어, 사용자(Human)의 안전을 지키는 아키텍트의 최종 방어선입니다.

## 5. 요약 및 대단원 마무리 (모듈 8의 전반부)

* 지식 그래프를 구글 검색에 완벽하게 노출시키려면, 빈 화면을 던져주는 클라이언트 렌더링(CSR)을 버리고 서버에서 HTML과 JSON-LD를 한 번에 조립해서 보내주는 "**서버 사이드 렌더링(SSR)**" 아키텍처를 구축해야 합니다.
* 백엔드 서버는 사용자 요청 즉시 SPARQL 쿼리를 날리고, 데이터를 Schema.org 포맷의 JSON 문자열로 치환하여 HTML 템플릿의 `head`에 박아 넣습니다.
* 지식 그래프 서버의 데이터가 악의적으로 오염되었을 경우를 대비하여, JSON-LD를 렌더링할 때는 반드시 꺾쇠 기호(`<`, `>`)를 유니코드로 이스케이프 처리하여 끔찍한 "**XSS 해킹 공격**"을 원천 봉쇄해야 합니다.

축하합니다! 이제 여러분의 거대한 지식 그래프는 구글이라는 전 세계에서 가장 거대한 문을 통해 대중에게 뻗어나갈 완벽한 고속도로를 타게 되었습니다. 누군가 이순신을 검색하면, 우측 "지식 패널"에 여러분이 구축한 데이터가 당당히 빛날 것입니다.

하지만 구글 검색은 "이순신의 출생 연도" 같은 단편적인 정답을 던져줄 뿐, 우리가 엮어낸 거대하고 입체적인 "관계망(Network)" 자체를 보여주지는 못합니다. 이순신을 중심으로 거미줄처럼 뻗어 나가는 수백 명의 인맥과 전투의 궤적을 일반인들이 마우스로 클릭하며 탐험하게 만들 수는 없을까요?
