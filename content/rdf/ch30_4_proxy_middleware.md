# 30.4. 안전한 퍼블리싱: SPARQL 프록시 미들웨어

## 1. 도입: 대문을 활짝 열어둔 춘추관, 그리고 암살자의 침입

우리는 앞선 30장의 챕터들을 통해 LodLive, WebVOWL, RelFinder라는 화려한 시각화 도구들을 웹 브라우저 위에 성공적으로 띄웠습니다. 일반 대중들은 마우스를 클릭하며 이순신과 원균의 관계망을 탐험하며 감탄을 금치 못합니다. 

하지만 이 화려한 축제의 이면에는 디지털 인문학 아키텍트를 밤잠 설치게 만드는 가장 끔찍하고 치명적인 보안의 구멍이 뚫려 있습니다. 
시각화 도구가 웹 브라우저(사용자의 컴퓨터)에서 돌아간다는 것은, 브라우저가 직접 여러분의 지식 그래프 서버(Virtuoso의 `http://localhost:8890/sparql`)로 통신을 시도한다는 뜻입니다. 이를 위해 여러분은 서버의 방화벽을 내리고, 전 세계 누구든 쿼리를 보낼 수 있도록 대문을 활짝 열어두었습니다.

만약 악의적인 해커나 코딩을 갓 배운 철없는 학생이 웹 브라우저의 개발자 도구(F12)를 열고, 시각화 도구가 보내는 정상적인 `SELECT` 쿼리 대신 다음과 같은 파괴적인 쿼리를 날린다면 어떻게 될까요?

**`DROP GRAPH <http://dh.aks.ac.kr/joseon/>`**

이 짧은 한 줄의 코드가 서버에 도달하는 순간, 여러분의 연구팀이 수년간 밤을 새워가며 구축한 1,000만 건의 조선시대 지식 그래프는 단 1초 만에 허공의 먼지로 증발해 버립니다. 춘추관(서버)의 대문을 활짝 열어두었더니, 사관(정상 사용자)뿐만 아니라 횃불을 든 암살자(해커)까지 무사통과한 셈입니다. 

## 2. 해결책 제시: 춘추관을 지키는 기미상궁, "**프록시 미들웨어(Proxy Middleware)**"

이 끔찍한 대참사를 막기 위해, 우리는 사용자(브라우저)와 데이터베이스(Virtuoso)가 절대로 직접 대화하지 못하게 만들어야 합니다. 그 둘 사이에 아주 깐깐하고 의심이 많은 문지기를 세워야 하는데, 이를 컴퓨터 공학에서는 "**프록시 미들웨어(Proxy Middleware)**"라고 부릅니다.

인문학적으로 비유하자면, 이 미들웨어는 임금의 수라상에 오르는 음식을 미리 맛보고 독을 걸러내는 "**기미상궁**"과 같습니다. 
사용자의 브라우저에서 출발한 SPARQL 쿼리는 데이터베이스로 직행하지 못하고, 반드시 중간에 있는 프록시 서버(Node.js, Python 등)에 먼저 도착합니다. 프록시 서버는 쿼리의 내용을 샅샅이 뒤져봅니다. "데이터를 조회하는 `SELECT` 쿼리인가? 통과시켜라." "데이터를 지우려는 `DROP`이나 `DELETE` 쿼리인가? 즉시 폐기하고 해커의 IP를 차단하라!" 

| 통신 방식 | 직접 연결 (위험천만) | 프록시 미들웨어 경유 (철통 보안) |
| :--- | :--- | :--- |
| **아키텍처** | 브라우저 ➔ Virtuoso DB | **브라우저 ➔ 프록시 서버 ➔ Virtuoso DB** |
| **보안 검증** | 묻지도 따지지도 않고 실행함 | **`DROP`, `INSERT`, `DELETE` 등 파괴적 명령어 사전 차단** |
| **서버 부하** | 누군가 무한 루프 쿼리를 날리면 DB가 터짐 | **미들웨어가 동일한 질문의 답을 기억(캐싱)하여 DB를 보호함** |

## 3. 실전 적용: 파이썬(Python)으로 기미상궁 서버 구축하기

실무에서 지식 그래프를 안전하게 퍼블리싱하기 위해, 파이썬 기반의 가벼운 웹 프레임워크(Flask 또는 FastAPI)를 사용하여 쿼리를 검열하는 프록시 미들웨어를 구축해 보겠습니다.

```python
# 안전한 지식 그래프 퍼블리싱을 위한 Python 프록시 미들웨어
from flask import Flask, request, jsonify
import requests
import re

app = Flask(__name__)
VIRTUOSO_ENDPOINT = "http://localhost:8890/sparql"

@app.route("/api/safe-sparql", methods=["GET", "POST"])
def proxy_sparql():
    # 1. 사용자가 보낸 쿼리를 가로챕니다.
    user_query = request.args.get("query") or request.form.get("query")
    
    if not user_query:
        return "쿼리가 비어 있습니다.", 400

    # 2. [핵심] 기미상궁의 독성 검사 (정규표현식 필터링)
    # 쿼리문에 DROP, DELETE, INSERT, UPDATE, CLEAR 등의 파괴적 단어가 있는지 검사합니다.
    forbidden_words = re.compile(r'\b(DROP|DELETE|INSERT|UPDATE|CLEAR|LOAD)\b', re.IGNORECASE)
    
    if forbidden_words.search(user_query):
        # 파괴적 단어가 발견되면 데이터베이스로 보내지 않고 즉시 차단합니다!
        return "경고: 허용되지 않는 파괴적인 명령어가 포함되어 있습니다!", 403

    # 3. 독성 검사를 무사히 통과한 안전한 SELECT 쿼리만 진짜 서버(Virtuoso)로 전달합니다.
    response = requests.get(VIRTUOSO_ENDPOINT, params={"query": user_query})
    
    # 4. 서버가 안전하게 반환한 결과를 사용자 브라우저로 고스란히 돌려줍니다.
    return (response.content, response.status_code, response.headers.items())

if __name__ == "__main__":
    app.run(port=3000)
```

이제 프론트엔드의 시각화 도구(LodLive 등) 설정 파일에서 엔드포인트 주소를 Virtuoso(`8890` 포트)가 아닌, 우리가 방금 만든 안전한 기미상궁 서버(`3000` 포트의 `/api/safe-sparql`)로 변경하기만 하면 됩니다. 여러분의 1,000만 건 데이터는 완벽한 방패 뒤에 숨게 되었습니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 절망: "해커가 대소문자를 섞고 띄어쓰기를 조작해서 DROP 필터를 뚫었습니다!"**

방금 우리가 만든 파이썬 코드의 정규표현식 필터를 비웃기라도 하듯, 데이터가 또다시 날아가는 참사가 벌어질 수 있습니다. 
영악한 해커들은 `DROP GRAPH`라고 정직하게 쓰지 않습니다. 그들은 URL 인코딩을 섞거나, 주석을 교묘하게 끼워 넣어 필터링 엔진을 속입니다.
예를 들어, `D R O P GRAPH`라고 띄어쓰기를 변형하거나, `DELETE /* 메롱 */ DATA` 처럼 중간에 주석을 삽입하면 단순한 문자열 검사기(Regex)는 이를 얌전한 쿼리로 착각하고 문을 열어줍니다.

**[승리하는 아키텍트의 심층 방어(Defense in Depth) 아키텍처]**
미들웨어의 문자열 필터링만 믿는 것은 하수들의 방식입니다. 진정한 아키텍트는 방어선을 2중, 3중으로 겹쳐 짓는 "**심층 방어**"를 구축해야 합니다.

가장 완벽한 방어는 미들웨어를 세우는 동시에, 뒷단의 데이터베이스(Virtuoso) 자체의 "**계정 권한(Role)**"을 거세해 버리는 것입니다.
Virtuoso의 관리자 콘솔에 접속하여, 외부로 공개된 기본 SPARQL 계정(`SPARQL` user)의 권한 설정으로 들어갑니다. 그리고 이 계정이 가지고 있는 **"SPARQL_UPDATE" 권한을 완전히 박탈**하고, 오직 **"SPARQL_SELECT" 권한만 남겨두십시오.**

이렇게 세팅하면, 해커가 기발한 꼼수로 프록시 미들웨어를 뚫고 `DROP` 명령어를 Virtuoso에 도달시키더라도, 데이터베이스 엔진 자체가 "당신의 계정은 삭제 권한이 없습니다(Access Denied)"라며 실행을 거부합니다. 미들웨어의 논리적 방어와 DB의 물리적 권한 통제가 결합할 때, 비로소 누구도 뚫을 수 없는 난공불락의 지식의 성채가 완성됩니다.

## 5. 요약 및 대단원 마무리 (모듈 8의 시각화 파트 종료)

* 시각화 도구를 위해 SPARQL 엔드포인트를 외부에 퍼블리싱할 때는, 끔찍한 데이터 삭제(DROP)나 변조 공격으로부터 서버를 보호할 방패가 반드시 필요합니다.
* 사용자의 브라우저와 DB 사이에 "**프록시 미들웨어(Proxy Middleware)**"를 구축하여, 들어오는 쿼리의 내용을 검열하고 오직 안전한 조회(`SELECT`) 쿼리만 통과시켜야 합니다.
* 완벽한 보안을 위해서는 프록시 서버의 문자열 필터링에만 의존하지 말고, 데이터베이스 엔진 자체의 계정 권한을 "읽기 전용(Read-Only)"으로 제한하는 2중 심층 방어 아키텍처를 설계해야 합니다.
