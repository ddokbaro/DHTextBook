# 19.1. 무대 위로 배우 호출하기: 인스턴스(Instance) 생성과 개체 할당

## 1. 도입: 텅 빈 무대와 "한국근대인물LOD"의 시작

우리는 지난 16장부터 18장까지 엑셀의 1차원적인 한계를 부수고, Protégé를 활용하여 조선시대와 근대 한국학을 아우르는 완벽한 하향식(Top-down) 뼈대 설계를 마쳤습니다. 
**"종묘배향공신(Meritorious_Subject)"**이라는 배역(Class)을 만들었고, **"관직을 역임하다(hasOffice)"**라는 동사(Object Property)를 정의했으며, 날짜와 문자열을 엄격하게 통제하는 규칙(XSD Datatype)까지 헌법으로 제정했습니다.

그런데 이 웅장한 도서관에는 아직 책이 단 한 권도 꽂혀 있지 않습니다. 뼈대만 앙상하게 남은 텅 빈 연극 무대일 뿐입니다. 

이제 기나긴 설계(T-box: Terminology)의 시간을 끝내고, 여러분이 국사편찬위원회나 규장각 사료에서 발췌한 실제 역사적 인물들을 이 무대 위로 화려하게 등판시킬 차례입니다. 추상적인 클래스(붕어빵 틀)에 밀가루 반죽을 부어, **"민영환(閔泳煥)"**이나 **"조병세(趙秉世)"**라는 구체적이고 실재하는 역사적 데이터(A-box: Assertion)를 찍어내는 위대한 생명 부여 작업을 시작하겠습니다.

## 2. 해결책 제시: 붕어빵을 구워내는 "Individuals by class" 탭

Protégé에서 구체적인 데이터를 입력하는 공간은 화면 상단의 **"Individuals by class"** 탭입니다. 
시맨틱 웹에서는 이렇게 생성된 실제 데이터 하나하나를 **"개체(Individual)"** 또는 **"인스턴스(Instance)"**라고 부릅니다. 

이 공간은 세 부분으로 나뉘어 완벽한 분업을 수행합니다.

1. **좌측 패널 (Classes):** 우리가 앞서 짜놓은 분류 책장(붕어빵 틀)을 선택합니다.
2. **중앙 패널 (Instances):** 선택한 책장에 꽂아 넣을 실제 인물(배우)을 생성합니다.
3. **우측 패널 (Property Assertions):** 등판한 배우에게 동사(Object Property)와 포스트잇(Data Property)을 붙여주어 구체적인 서사를 완성합니다.

이 3단계를 거치면, 파편화되어 있던 인문학 지식들이 기계의 뇌 속에서 거대한 지식 그래프로 엮이기 시작합니다.

## 3. 실전 적용: 종묘배향공신 "민영환"의 인스턴스 생성과 데이터 맵핑 (Turtle)

디지털인문학연구소에서 구축 중인 **"한국근대인물LOD"**의 핵심 인물, 충정공 민영환의 데이터를 Protégé 캔버스 위에서 조립해 보겠습니다.

**[1단계: 인스턴스(배우) 생성하기]**
1. **"Individuals by class"** 탭을 클릭합니다.
2. 좌측 패널에서 **"종묘배향공신(Meritorious_Subject)"** 클래스를 찾아 클릭합니다.
3. 중앙 패널 상단의 보라색 마름모(+) 버튼을 눌러, **"Min_Yeong_hwan"**이라는 인스턴스를 생성합니다. (기계는 이제 민영환이 공신임을 자동으로 추론합니다.)

**[2단계: 객체 속성(Object Property)으로 실체와 실체 잇기]**
1. 우측 패널의 **"Object property assertions"** 항목에서 플러스(+) 버튼을 누릅니다.
2. 앞서 만든 **"hasOffice(관직을 역임하다)"** 속성을 선택합니다.
3. 목적어로 연결할 또 다른 인스턴스인 **"Minister_of_War(병조판서)"**를 입력하여 두 노드를 쇠사슬로 연결합니다.

**[3단계: 데이터 속성(Data Property)으로 구체적 값 부여하기]**
1. 우측 패널의 **"Data property assertions"** 항목에서 플러스(+) 버튼을 누릅니다.
2. **"hasName(성명)"** 속성을 선택하고, 값에 `"민영환"^^xsd:string`을 입력합니다.
3. 다시 플러스(+) 버튼을 누르고, **"dateOfDeath(순국일)"** 속성을 선택한 뒤, 값에 `"1905-11-30"^^xsd:date`를 입력합니다.

마우스와 키보드로 수행한 이 일련의 입력 과정은, 단 하나의 문법적 오류도 없는 완벽한 거북이 문법(Turtle) 코드로 서버에 영구 기록됩니다.

```turtle
@prefix rdfs: [http://www.w3.org/2000/01/rdf-schema#](http://www.w3.org/2000/01/rdf-schema#) .
@prefix xsd: [http://www.w3.org/2001/XMLSchema#](http://www.w3.org/2001/XMLSchema#) .
@prefix joseon: [http://aks.ac.kr/ontologies/joseon/](http://aks.ac.kr/ontologies/joseon/) .

# 1단계: 민영환이라는 구체적 개체(Instance)를 생성하고 소속 클래스를 할당합니다.
joseon:Min_Yeong_hwan a joseon:Meritorious_Subject ;
    
    # 2단계: 객체 속성(Object Property)을 통해 다른 노드(관직)와 관계를 맺습니다.
    joseon:hasOffice joseon:Minister_of_War ;
    
    # 3단계: 데이터 속성(Data Property)을 통해 문자열과 날짜 값을 덧붙입니다.
    joseon:hasName "민영환"^^xsd:string ;
    joseon:dateOfDeath "1905-11-30"^^xsd:date .
```

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 치명적 오타: 인스턴스 주소(IRI)에 한글 이름을 때려 박는 만행**

Protégé 실무에 돌입한 연구원들이 데이터를 대량으로 입력할 때 100% 터져 나오는 최악의 인코딩 붕괴 사태가 있습니다. 

**"교수님! 인스턴스를 생성할 때 직관적으로 알아보려고 주소(IRI)를 `joseon:민영환`, `joseon:조병세`처럼 한글로 적었습니다. 그런데 나중에 웹 서버에 데이터를 올리려니 한글 주소가 전부 `%EB%AF%BC...` 같은 외계어로 깨지면서 시스템이 뻗어버렸습니다!"**

기초 세팅(16.1장)에서 신신당부했던 **"IRI 한글 사용 금지 규칙"**을 실무 데이터 입력 단계에서 까맣게 잊어버린 결과입니다. 인간의 눈에는 한글 주소가 편하겠지만, 글로벌 시맨틱 웹 생태계에서 한글로 된 식별자(IRI)는 시한폭탄과 같습니다.

더 끔찍한 문제는 **"동명이인"**입니다. 조선시대에 "이순신(李舜臣)"이라는 이름을 가진 무장이 충무공을 포함해 여러 명이라는 사실을 역사학자라면 잘 아실 것입니다. 인스턴스 주소를 이름 자체로 만들어버리면, 두 번째 이순신 데이터를 입력할 때 기존 이순신 데이터 위에 그대로 덮어쓰기가 되어버리는(Overwriting) 데이터베이스 파괴 사태가 일어납니다.

**[승리하는 아키텍트의 작명 철칙]**
1. **인스턴스의 절대 주소(IRI)는 반드시 영문표기법이나 고유 ID 번호로 부여하십시오.** (예: `joseon:person_min_yeong_hwan` 또는 주민등록번호처럼 고유한 `joseon:p0001`)
2. **인간이 읽을 친절한 한글 이름은 반드시 `rdfs:label`이나 별도의 데이터 속성(`hasName`)에 문자열(String)로 달아주십시오.** 뼈대(IRI)는 수학적 식별자로 단단하게 유지하고, 껍데기(Label)만 한글로 씌우는 이 철칙을 지켜야만 수만 건의 데이터를 다루어도 서버가 무너지지 않습니다.

## 5. 요약 및 다음 단계

* 설계된 클래스(붕어빵 틀) 안에 구체적인 역사적 데이터(붕어빵)를 찍어내는 작업을 **"인스턴스 할당(Instance Assertion)"**이라고 부르며, 이는 Protégé의 **"Individuals by class"** 탭에서 이루어집니다.
* 인스턴스를 생성한 후에는 우측 패널을 통해 다른 개체와의 관계망(**Object Property**)과 구체적인 텍스트/숫자 값(**Data Property**)을 정밀하게 입력해야 합니다.
* 인스턴스의 고유 식별자(IRI)를 만들 때는 한글 이름 충돌과 인코딩 에러를 막기 위해 반드시 영문이나 고유 ID 체계를 사용해야 합니다.

드디어 텅 빈 무대 위에 민영환이라는 훌륭한 배우가 등판하여 대사를 읊기 시작했습니다. 여러분은 이제 종묘배향공신 수십 명의 데이터를 이 무대 위로 끊임없이 쏟아낼 수 있습니다.

그런데 방금 전 언급했던 치명적인 인문학적 난제가 하나 남아있습니다. 바로 **"동명이인"**과 **"이명동인"**의 문제입니다. 이름이 같다고 같은 사람일까요? 이름이 다르게 적혀 있다고 다른 사람일까요? 기계는 이 철학적인 문제를 스스로 구분하지 못합니다.
