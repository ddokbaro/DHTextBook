# 21.2. Apache Jena Fuseki 구축과 운용: TDB 기반 로컬 SPARQL 엔드포인트 세팅

## 1. 도입: 우리의 지식 그래프에 "주소(Endpoint)"를 부여할 시간

21.1장에서 우리는 거친 숨을 몰아쉬며 리눅스(Linux) 터미널의 검은 화면과 사투를 벌였습니다. 시스템을 업데이트하고, 자바(Java)를 깔았으며, 방화벽(3030번 포트)의 육중한 철문을 활짝 열어두었습니다. 

이제 이 텅 빈 무균실 서버 위에 디지털 인문학 연구실의 가장 든든한 일꾼을 데려올 차례입니다. 
우리가 Protégé에서 땀 흘려 추출한 `modern_figures_lod_v1.ttl` 파일은 아직 죽어있는 텍스트에 불과합니다. 누군가 이 파일을 메모리에 띄우고, 외부에서 날아오는 질의어(SPARQL)를 해석하여, 다시 정답을 돌려주는 **"문지기 겸 통역사"** 역할을 수행해야 합니다.

시맨틱 웹 생태계에서는 이 외부와 소통하는 창구를 **"SPARQL 엔드포인트(Endpoint)"**라고 부릅니다. 이 엔드포인트를 가장 쉽고 빠르게 열어주면서도, W3C 표준을 100% 준수하는 경량화된 오픈소스 트리플 스토어가 바로 **"Apache Jena Fuseki(아파치 제나 후세키)"**입니다.

## 2. 해결책 제시: 가볍지만 강력한 지식의 창고, "Jena Fuseki"와 "TDB"

영국 브리스톨 대학(University of Bristol)의 연구 프로젝트에서 출발한 Apache Jena 프레임워크는, 현재 전 세계 인문학/사회과학 랩실에서 가장 널리 쓰이는 표준 지식 그래프 엔진입니다. 그중에서도 **"Fuseki"**는 복잡한 코딩 없이 클릭 몇 번으로 데이터베이스를 띄워주는 독립형(Stand-alone) 서버 모듈입니다.

Fuseki가 가진 최고의 무기는 바로 **"TDB (Triple Database)"**라는 자체 저장 방식입니다.

| 저장 방식 | 인문학적 비유 | 기술적 특징 및 장단점 |
| :--- | :--- | :--- |
| **In-Memory (메모리 기반)** | **[칠판에 적기]** 빠르지만, 지우개를 대면 다 날아감. | RAM 위에서만 작동하여 쿼리 속도는 빛처럼 빠르지만, 서버 전원이 꺼지면 모든 데이터가 허무하게 증발함. |
| **TDB (디스크 기반 영구 저장)** | **[석판에 새기기]** 묵직하지만, 천 년이 지나도 보존됨. | 데이터를 하드디스크(SSD)의 특수 폴더에 물리적으로 압축하여 기록(Persistent). 재부팅해도 데이터가 100% 보존됨. **(실무 필수)** |

우리는 Fuseki를 설치한 뒤, 반드시 **"TDB"** 방식으로 데이터베이스를 생성하여 힘들게 만든 종묘배향공신 지식 그래프가 서버 재부팅 한 번에 날아가는 참사를 막아야 합니다.

## 3. 실전 적용: Fuseki 설치부터 SPARQL 엔드포인트 개방까지

리눅스 터미널 창에 접속한 상태에서, 다음의 명령어들을 차례대로 입력하여 Fuseki를 구축해 보겠습니다.

**[작업 1: Fuseki 다운로드 및 압축 해제]**
인터넷에서 파일을 다운로드하는 리눅스 명령어는 `wget`입니다.

```bash
# 1. Apache 공식 미러 사이트에서 최신 버전의 Fuseki 압축 파일을 다운로드합니다. 
# (버전 숫자는 다운로드 시점에 따라 4.x.x 등으로 다를 수 있습니다.)
wget [https://archive.apache.org/dist/jena/binaries/apache-jena-fuseki-4.8.0.tar.gz](https://archive.apache.org/dist/jena/binaries/apache-jena-fuseki-4.8.0.tar.gz)

# 2. 다운로드한 파일의 압축을 풉니다. (tar는 압축 해제 명령어입니다.)
tar -zxvf apache-jena-fuseki-4.8.0.tar.gz

# 3. 압축이 풀린 폴더로 이동합니다.
cd apache-jena-fuseki-4.8.0
```

**[작업 2: Fuseki 서버 백그라운드 실행]**
앞선 21.1장에서 배웠던 `nohup` 마법을 사용하여, 우리가 퇴근해도 서버가 죽지 않도록 실행합니다.

```bash
# 터미널 창을 꺼도 3030번 포트에서 영구적으로 구동되도록 백그라운드 실행합니다.
nohup ./fuseki-server &
```

**[작업 3: Web UI 접속 및 데이터 적재 (GUI 환경)]**
이제 끔찍했던 검은 터미널 창을 최소화하고, 평소 쓰던 윈도우 PC의 크롬(Chrome) 브라우저를 엽니다.

1. 주소창에 `http://여러분의_서버_IP:3030`을 입력하고 엔터를 칩니다. 아름다운 Fuseki 관리자 화면(GUI)이 뜹니다!
2. 상단 메뉴에서 **"manage datasets"**를 클릭하고 **"add new dataset"** 버튼을 누릅니다.
3. 데이터베이스 이름(Dataset name)에 `joseon_lod`를 적습니다.
4. **[핵심]** Dataset type 항목에서 반드시 **"Persistent (TDB2) – data is stored on disk"**를 선택한 뒤 생성합니다.
5. 생성된 `joseon_lod` 데이터베이스의 **"upload data"** 버튼을 누르고, Protégé에서 정성껏 추출해 온 `modern_figures_lod_v1.ttl` 파일을 업로드(Upload)합니다.

축하합니다! 업로드가 완료된 순간, 여러분의 데이터는 텍스트 파일을 벗어나 전 세계를 향해 열려있는 **`http://여러분의_서버_IP:3030/joseon_lod/sparql`** 이라는 공식적인 글로벌 엔드포인트를 가지게 되었습니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 멘붕: "데이터 500만 건을 올렸더니 서버가 터졌습니다 (OutOfMemoryError)"**

대학원생들이 몇백 명 수준의 튜토리얼 데이터를 올릴 때는 Fuseki가 깃털처럼 가볍게 돌아갑니다. 하지만 국사편찬위원회의 거대한 문과방목 데이터 수백만 건(수십 메가바이트의 .ttl 파일)을 Upload 버튼으로 밀어 넣는 순간, 웹 브라우저가 하얗게 얼어붙고 터미널 창에는 끔찍한 에러 메시지가 출력됩니다.

> `java.lang.OutOfMemoryError: Java heap space`

**"교수님! 저희 서버 램(RAM)이 16GB나 되는데, 고작 50MB짜리 텍스트 파일 하나 올렸다고 메모리가 부족하다며 뻗어버렸습니다. Fuseki가 고장 난 것 아닙니까?"**

프로그램은 고장 나지 않았습니다. Java의 융통성 없는 안전장치 때문입니다. 
Java 가상머신(JVM)은 아무리 서버에 물리적인 램(RAM)이 빵빵해도, 주인이 별도로 허락하지 않으면 프로그램(Fuseki)이 쓸 수 있는 메모리의 최대치(Heap Size)를 아주 쪼잔하게 제한해 둡니다. 거대한 지식 그래프를 욱여넣으려니 당연히 그 작은 바구니가 터져버린 것입니다.

**[승리하는 아키텍트의 메모리 한계 돌파법]**
Fuseki를 실행(`nohup ./fuseki-server &`)하기 **직전**에, 터미널 창에 다음의 환경 변수 선언 명령어 한 줄을 반드시 입력하여 Java에게 메모리를 넉넉하게 쓸 수 있는 권한을 부여해야 합니다.

```bash
# Java가 사용할 수 있는 최대 메모리(Heap)를 4GB로 화끈하게 늘려줍니다.
export JVM_ARGS="-Xmx4G"
```

이 명령어 한 줄을 치고 Fuseki를 다시 실행해 보십시오. 수백만 건의 대용량 트리플도 메모리 부족 에러 없이 거침없이 TDB 블랙홀 안으로 빨려 들어가는 카타르시스를 경험하게 될 것입니다. (서버의 실제 RAM 사양에 따라 4G, 8G 등으로 조절하면 됩니다.)

## 5. 요약 및 다음 단계

* 정적인 텍스트 파일(.ttl)을 살아있는 SPARQL 서비스로 만들기 위해, 우리는 리눅스 환경에 **"Apache Jena Fuseki"**라는 독립형 트리플 스토어를 설치했습니다.
* 데이터를 올릴 때는 서버가 재부팅되어도 지식 그래프가 증발하지 않도록, 반드시 디스크에 물리적으로 기록하는 **"Persistent (TDB2)"** 타입으로 데이터베이스를 생성해야 합니다.
* 대용량의 인문학 데이터를 업로드할 때 발생하는 `OutOfMemoryError`를 막으려면, 서버 실행 전 `export JVM_ARGS="-Xmx4G"` 명령어를 통해 자바 메모리 할당량을 대폭 늘려주어야 합니다.

이제 여러분의 윈도우 PC는 꺼져도 좋습니다. 멀리 떨어진 리눅스 서버 위에서 Fuseki가 24시간 깨어있으며 전 세계 학자들의 질의를 기다리고 있습니다. 대학원 랩실 수준의 수백만 건짜리 데이터베이스라면 이 Fuseki 하나만으로도 수년을 거뜬하게 버틸 수 있습니다.

하지만, 만약 여러분이 한국학중앙연구원의 수억 건짜리 국가 통합 데이터베이스를 서비스하거나, 위키데이터(Wikidata)처럼 전 세계의 봇(Bot)들이 초당 수천 번의 쿼리를 때리는 극한의 환경에 처한다면 어떨까요? 가벼운 정찰대인 Fuseki로는 이 트래픽의 무게를 감당할 수 없습니다.
