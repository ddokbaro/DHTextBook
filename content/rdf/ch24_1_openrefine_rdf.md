# 24.1. OpenRefine + RDF Transform: 노이즈 클렌징

## 1. 도입: 파편화된 역사적 진실을 이어 붙이는 고통

디지털 인문학 프로젝트를 시작하며 국사편찬위원회나 연구실 선배들로부터 수십만 건의 조선시대 무과 방목 엑셀(CSV) 파일을 건네받았다고 상상해 보십시오. 부푼 마음으로 파일을 열어보는 순간, 여러분은 깊은 절망에 빠지게 됩니다.

합격자 이름 칸에는 "이순신", "李舜臣", "이 순 신", 심지어 오타인 "이순시"까지 섞여 있습니다. 관직명 칸에도 "전라좌수사", "전라 좌수사", "전라수군절도사"가 제각각 입력되어 있습니다. 만약 이 데이터를 그대로 지식 그래프 인프라에 밀어 넣는다면, 우리의 완벽한 서버는 이들을 모두 "서로 다른 4명의 인물"과 "서로 다른 3개의 관직"으로 인식하여 완전히 파편화된 노드(Node)들을 생성할 것입니다. 이순신의 위대한 인맥 네트워크가 갈가리 찢어지는 참혹한 비극이 발생하는 것입니다.

이 수만 건의 오타와 띄어쓰기 오류를 엑셀의 "찾기/바꾸기" 기능으로 밤을 새워가며 일일이 수정하는 것은 학자의 귀중한 시간을 낭비하는 일입니다. 우리는 기계의 지능을 빌려 이 더러운 노이즈를 일거에 씻어내야 합니다.

## 2. 해결책 제시: 언어의 세탁기 "**OpenRefine**"과 지식의 주물 틀 "**RDF Transform**"

이 고통을 단숨에 해결해 줄 구원자가 바로 "**OpenRefine(오픈리파인)**"입니다. 과거 구글(Google)이 주도하여 개발했던 이 강력한 오픈소스 도구는, 지저분한 원시 데이터를 맑은 물로 씻어내는 "**언어의 세탁기**"와 같습니다.

오픈리파인의 가장 위대한 무기는 "**군집화(Clustering)**" 알고리즘입니다. 기계가 인간의 언어적 패턴(발음, 철자 유사도 등)을 수학적으로 분석하여 "이순신"과 "이 순 신", "이순시"가 사실상 같은 단어일 확률이 높다고 판단하고, 연구자에게 묻습니다. "이 단어들을 하나의 표준어로 합칠까요?" 연구자는 그저 마우스로 "병합(Merge)" 버튼만 누르면 수백 개의 오타가 단 1초 만에 완벽한 "이순신"으로 통일됩니다.

데이터 세탁이 끝났다면, 이제 이 평면적인 표(Table) 형태의 맑은 물을 주어-서술어-목적어의 시맨틱 트리플(Triple) 구조로 얼려야 합니다. 이때 오픈리파인의 확장 플러그인인 "**RDF Transform**"이 등장합니다. 이것은 엑셀의 각 열(Column)을 우리가 설계한 온톨로지의 클래스와 속성에 맞게 꾹꾹 찍어내는 "**지식의 주물 틀**" 역할을 수행합니다.

| 데이터 정제 전 (더러운 원시 데이터) | OpenRefine 정제 후 (클린 데이터) | RDF Transform 변환 후 (지식 그래프 URI) |
| :--- | :--- | :--- |
| 이 순 신 | 이순신 | `joseon:Person_이순신` |
| 李舜臣 | 이순신 | `joseon:Person_이순신` |
| 전라 좌수사 | 전라좌수사 | `joseon:Post_전라좌수사` |
| (오타) 전라자수사 | 전라좌수사 | `joseon:Post_전라좌수사` |

## 3. 실전 적용: 마우스 클릭으로 완성하는 조선시대 관역 지식 그래프

오픈리파인을 실행하고 더러운 조선시대 관역 데이터를 불러온 뒤, 다음의 파이프라인을 따라 지식 그래프를 연성해 보겠습니다.

**[1단계: 패싯(Facet)과 군집화(Clustering)로 노이즈 제거]**
관직명 컬럼(Column)의 메뉴를 클릭하고 "**Text Facet**"을 실행하면, 화면 좌측에 각 관직명의 등장 빈도수가 집계됩니다. 여기서 "**Cluster**" 버튼을 누르면 기계가 오타들을 묶어서 보여줍니다.

1. 기계의 제안: "전라좌수사(50건)"와 "전라 좌수사(12건)", "전라자수사(2건)"를 하나로 묶을까요?
2. 연구자의 승인: "Merge" 체크박스를 선택하고 새로운 표준 단어로 "전라좌수사"를 입력한 뒤 "**Merge Selected & Re-cluster**"를 클릭합니다. 단 한 번의 클릭으로 64건의 데이터가 완벽하게 정제됩니다.

**[2단계: GREL 문법을 이용한 절대 식별자(URI) 뼈대 만들기]**
정제된 "이순신"이라는 텍스트를 전 세계 기계가 인식할 수 있는 고유 식별자(URI)로 변환해야 합니다. 오픈리파인의 전용 언어인 "**GREL(General Refine Expression Language)**"을 사용하여 새로운 컬럼을 생성합니다.

```grel
// "인물명" 컬럼의 값을 가져와서 앞에 네임스페이스 주소를 붙여 새로운 URI를 만듭니다.
// value 변수 안에는 "이순신", "원균" 등의 깨끗하게 세탁된 텍스트가 들어있습니다.
"[http://dh.aks.ac.kr/joseon/person/](http://dh.aks.ac.kr/joseon/person/)" + value
```

이 코드를 실행하면 `http://dh.aks.ac.kr/joseon/person/이순신`이라는 훌륭한 주어(Subject) 데이터가 새로운 열에 완성됩니다.

**[3단계: RDF Transform으로 트리플(Triple) 뼈대 맵핑하기]**
이제 우측 상단의 "**RDF**" 버튼을 누르고 "**Edit RDF Skeleton**" 메뉴로 들어갑니다. 직관적인 노드-링크 화면이 나타납니다.

1. **Subject (주어):** 방금 GREL로 만든 인물 URI 컬럼을 지정합니다.
2. **Predicate (서술어):** 온톨로지에서 미리 정의한 관직 임용 속성인 `core:hasPost`를 텍스트로 기입합니다.
3. **Object (목적어):** 정제 과정을 거친 관직명 컬럼을 지정하여 연결합니다.

뼈대 구성이 끝났다면 "**Export**" 버튼을 눌러 "**RDF as Turtle**" 포맷으로 추출합니다. 지저분했던 엑셀 파일이 완벽한 W3C 표준 `.ttl` 파일로 변환되어 쏟아져 나오는 지적 희열을 맛볼 수 있습니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 피눈물: "데이터가 50만 건인데 프로그램이 뻗어버렸습니다!"**

오픈리파인은 자바(Java) 기반으로 구동되며, 엑셀 데이터를 하드디스크가 아닌 **RAM(메모리)**에 통째로 올려서 분석하고 군집화합니다. 수십만 건의 대규모 역사 데이터를 넣고 분석을 시도하면, 기계가 헐떡거리다 "**Java Heap Space Out of Memory**" 에러를 뿜으며 장렬히 전사합니다.

**[승리하는 아키텍트의 극한 메모리 튜닝법]**
오픈리파인 설치 폴더에 있는 `openrefine.l4j.ini` (윈도우 환경) 또는 `openrefine.ini` (맥/리눅스 환경) 파일을 메모장으로 엽니다.
안에 적혀 있는 `-Xmx1024M` (메모리 1GB 제한)이라는 야박한 수치를, 여러분 컴퓨터의 RAM 사양에 맞춰 `-Xmx8192M` (8GB 할당) 등으로 과감하게 늘려주어야 합니다. 저장 후 프로그램을 다시 켜면 50만 건의 데이터도 부드럽게 세탁할 수 있습니다.

**시맨틱 아키텍트의 치명적 실수: "동명이인을 하나로 묶어버렸습니다!"**

기계의 "**군집화(Clustering)**" 알고리즘을 맹신하다 벌어지는 최악의 인문학적 참사입니다. 
조선시대에는 무의공 이순신(李純信)과 충무공 이순신(李舜臣)이라는 명백히 다른 두 장군이 존재합니다. 기계는 발음과 글자가 비슷하다는 이유로 이 둘을 병합(Merge)하라고 달콤하게 유혹합니다. 만약 사료의 확인 없이 마우스를 누르면, 두 장군의 혁혁한 전공과 인맥이 하나의 노드(Node)에 영구적으로 융합되어 역사가 심각하게 왜곡됩니다. 기계의 제안을 절대 맹신하지 마십시오. 데이터 병합의 최종 승인자는 반드시 사료를 비판적으로 해독할 수 있는 "인문학자"여야만 합니다.

## 5. 요약 및 다음 단계

* 파편화된 원시 데이터의 노이즈를 방치하면 지식 그래프의 연결망이 붕괴하므로, 반드시 "**OpenRefine**"의 패싯과 군집화 기능으로 데이터를 세탁해야 합니다.
* 정제된 데이터는 "**GREL**" 문법과 "**RDF Transform**" 확장 기능을 통해 직관적인 마우스 클릭만으로 완벽한 시맨틱 트리플(Turtle) 구조로 연성할 수 있습니다.
* 기계의 자동 병합을 맹신하지 않는 인문학적 비판 정신과, 대용량 처리를 위한 Java 메모리 튜닝이 파이프라인 실무의 핵심입니다.

오픈리파인은 눈으로 보면서 직관적으로 데이터를 빚어내는 최고의 세공 도구입니다. 하지만, 만약 매일 100만 건씩 쏟아지는 방대한 문헌 데이터를 다뤄야 한다면 어떻게 할까요? 마우스를 클릭하며 확인할 시간조차 없는 극한의 환경이 우리를 기다리고 있습니다.
