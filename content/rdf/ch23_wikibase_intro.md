# 23장. 협업형 인프라의 최고봉: Wikibase 로컬 구축 및 워크플로우

## 1. 도입: 데스크톱의 고립에서 벗어나 집단 지성의 바다로

우리는 지금까지 디지털 인문학 데이터베이스 구축의 험난한 산맥을 넘어왔습니다. Protégé라는 정교한 조각칼로 온톨로지라는 뼈대를 깎았고, 거북이 파일(.ttl)을 만들어 Virtuoso나 Neo4j라는 웅장한 서버 위에 띄웠습니다. 

하지만 본격적인 대형 연구 프로젝트(예: 한국학중앙연구원의 10년짜리 인물 사전 편찬 사업 등)에 돌입하면, 이 완벽해 보이던 파이프라인에서 치명적인 **'병목 현상(Bottleneck)'**이 발생합니다. 

20명의 연구원이 각자 할당받은 조선시대 인물 데이터를 지식 그래프로 입력해야 한다고 가정해 봅시다. 20명이 각자의 노트북에 Protégé를 깔고 작업한 뒤, 20개의 `.ttl` 파일을 메일이나 깃허브(GitHub)로 취합하여 수동으로 병합(Merge)해야 할까요? 만약 A 연구원과 B 연구원이 서로 소통 없이 '이순신' 개체의 URI를 각기 다르게 생성했거나, 동일한 속성을 중복해서 만들었다면 어떻게 해결해야 합니까? 

Protégé는 본질적으로 '싱글 유저(Single User)'를 위한 로컬 데스크톱 프로그램입니다. 진정한 디지털 인문학 융합 연구를 위해서는 **수십 명의 연구자가 장소와 OS에 구애받지 않고 웹 브라우저를 통해 실시간으로 접속하며, 충돌 없이 데이터를 입력하고, 누가 언제 무엇을 고쳤는지 수정 기록(Version History)을 완벽하게 추적할 수 있는 "협업형 지식 그래프 플랫폼"**이 절대적으로 필요합니다.

## 2. 해결책 제시: 위키데이터의 심장, "Wikibase(위키베이스)"

여러분은 구글 검색창 우측에 나타나는 지식 패널의 출처이자, 전 세계 최대의 오픈 지식 그래프인 **"위키데이터(Wikidata)"**를 알고 계실 것입니다. 수만 명의 자원봉사자가 지금 이 순간에도 웹 브라우저를 통해 위키데이터에 접속하여 아이템(Q-node)과 속성(P-node)을 추가하고 수정합니다. 그 거대한 혼돈 속에서도 위키데이터의 지식 그래프는 결코 무너지지 않습니다.

이 위키데이터를 무중단으로 구동하는 막강한 오픈소스 소프트웨어의 이름이 바로 **"Wikibase(위키베이스)"**입니다.

독일 위키미디어 지부(Wikimedia Deutschland)는 전 세계 연구 기관들이 자신만의 독립적인 프라이빗 위키데이터를 구축할 수 있도록 Wikibase 소프트웨어 일체를 오픈소스로 공개했습니다. 우리 연구실 서버에 이 Wikibase를 설치하는 순간, 지식 그래프 구축의 패러다임이 다음과 같이 혁명적으로 바뀝니다.

| 패러다임 비교 | 기존 방식 (Protégé + Virtuoso) | 혁신 방식 (Wikibase) |
| :--- | :--- | :--- |
| **작업 환경** | 로컬 PC 기반 1인 데스크톱 편집 | **웹 브라우저 기반 다중 접속 협업 편집** |
| **데이터 추적** | 파일(.ttl) 단위의 덮어쓰기 | **아이템 단위의 이력(History) 및 롤백(Rollback) 지원** |
| **시스템 구조** | 편집기(Protégé)와 서버(DB)가 분리됨 | **편집 GUI와 쿼리(SPARQL) 서버의 완벽한 통합** |
| **식별자 관리** | 인간이 직접 URI 문자열을 작명 및 관리 | **시스템이 절대 식별자(Q-node, P-node)를 자동 발급** |

## 3. 핵심 기술: 거대한 복합 생태계(Ecosystem)의 해부

단순히 `apt-get install` 명령어 한 줄로 설치되던 프로그램들과 달리, Wikibase는 여러 개의 거대한 소프트웨어가 톱니바퀴처럼 정밀하게 맞물려 돌아가는 '복합 생태계'입니다. 이 거대한 함선의 구조를 파악해야만 훌륭한 선장(아키텍트)이 될 수 있습니다.

1. **MediaWiki (미디어위키):** 위키백과를 돌리는 기본 웹 엔진(PHP 기반)입니다. 연구자들이 친숙한 GUI 화면을 보고 데이터를 입력하며, 로그인 및 권한 관리를 담당하는 **프론트엔드(Frontend)** 역할을 합니다.
2. **MariaDB (마리아DB):** 미디어위키 배후에서 사용자 계정 정보와 문서의 수정 이력(History), 그리고 구조화된 데이터를 JSON 덩어리 형태로 안전하게 보존하는 **관계형 데이터베이스**입니다.
3. **Wikibase Repository Extension:** 미디어위키 위에 얹혀서, 일반적인 텍스트 위키 문서를 '구조화된 데이터(트리플)'로 다룰 수 있게 변환해 주는 **핵심 시맨틱 플러그인**입니다.
4. **Blazegraph (블레이즈그래프):** Wikibase가 공식적으로 채택한 초고속 **트리플 스토어(Graph DB)**입니다.
5. **WDQS (Wikidata Query Service):** 블레이즈그래프와 연동되어 사용자가 입력한 데이터에 대해 SPARQL 쿼리를 날릴 수 있는 아름다운 웹 UI와 시각화 툴을 제공합니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 고뇌: "교수님, 그냥 옛날부터 쓰던 Semantic MediaWiki(SMW)를 쓰면 안 됩니까? 굳이 무거운 Wikibase를 깔아야 합니까?"**

디지털 인문학계에서 10년 이상 잔뼈가 굵은 연구원들이 기획 회의에서 반드시 던지는 질문입니다. SMW 역시 미디어위키 기반의 훌륭한 시맨틱 도구입니다. 하지만 철학이 완전히 다릅니다.

**[승리하는 아키텍트의 플랫폼 선택 기준]**
* **Semantic MediaWiki (SMW):** 본질적으로 **"텍스트(Article) 중심"**입니다. 서술형 백과사전 글을 쭈욱 쓰다가, 특정 단어에 괄호를 쳐서 메타데이터를 입히는 '어노테이션(Annotation)' 방식입니다. 문서를 지우면 데이터도 날아갑니다.
* **Wikibase:** 본질적으로 **"데이터(Data) 중심"**입니다. 서술형 글은 전혀 중요하지 않습니다. 오직 '이순신(Q1) - 직업(P1) - 무관(Q2)'이라는 기계가 읽을 수 있는 트리플 팩트(Fact) 덩어리만 존재합니다. 전 세계의 LOD(Linked Open Data) 클라우드와 데이터를 연동하고, 다국어 레이블을 완벽하게 지원하며, 정형화된 메타데이터를 대량으로 구축하는 것이 목적이라면 한 치의 망설임 없이 **Wikibase**를 선택해야 합니다.

## 5. 요약 및 다음 단계

* 다수의 연구자가 동시에 참여하는 대규모 디지털 인문학 프로젝트에서는 로컬 도구(Protégé)의 한계를 극복하기 위해 **웹 기반 다중 사용자 협업 플랫폼**이 필수적입니다.
* 전 세계 최대의 지식 그래프인 위키데이터를 구동하는 **Wikibase**는 아이템 단위의 이력 추적과 고유 식별자(Q/P-node) 자동 발급 기능을 제공하는 궁극의 협업 도구입니다.
* Wikibase는 MediaWiki(프론트엔드), MariaDB(이력 관리), Blazegraph(SPARQL 엔진)가 결합된 **복합 마이크로서비스 생태계**입니다.

우리는 이 거대한 생태계를 우리 연구실 서버에 올리기 위한 이론적, 아키텍처적 준비를 마쳤습니다. 
하지만 시스템을 설치하기 전, 연구자들의 뇌 구조를 먼저 리모델링해야 합니다.

다음 장인 **"23.1. 상향식(Protégé)에서 하향식(Wikibase)으로의 인식론적 대전환"**에서는 엄격한 온톨로지를 먼저 짜던 강박에서 벗어나, 데이터를 유연하게 먼저 던져놓고 관계를 엮어 나가는 Wikibase 특유의 데이터 중심적 패러다임 시프트에 대해 깊이 있게 다루겠습니다.
