# 1.3. 관계형 데이터베이스(RDB)의 치명적 한계: 조인(JOIN) 연산의 폭발과 파편화

## 1. 도입: 거미줄을 일직선으로 펴려는 어리석음

우리는 앞서 엑셀 파일로 흩어진 원시 데이터를 모아 `"**관계형 데이터베이스(RDB)**"`라는 체계적인 창고에 적재하는 훈련을 마쳤습니다. RDB는 중복을 제거하고 데이터를 깔끔하게 관리하는 데 있어서 인류가 발명한 최고의 도구입니다.

하지만 여러분이 조선시대 지식인들의 거대한 `"**학맥(學脈)**"`이나 남인과 노론의 복잡한 `"**당파 네트워크**"`를 연구하려 할 때, RDB는 갑자기 여러분의 숨통을 조여오는 족쇄로 돌변합니다.

조선시대의 족보나 학연은 마치 수만 가닥이 얽힌 거미줄과 같습니다. `"**이이(율곡)**"`라는 한 인물을 볼까요? 그는 수많은 스승에게 학문을 배웠고, 수십 명의 제자를 길러냈으며, 그 제자들은 다시 서로 혼인을 맺거나 정적이 되기도 했습니다. 

이 거미줄 같은 다차원적 관계를 가로세로로 딱딱하게 나누어진 2차원 표(Table)에 억지로 구겨 넣으려 하면 어떤 일이 벌어질까요? 제자가 100명인 인물을 표에 넣으려면 "제자1", "제자2"부터 "제자100"까지 100개의 열(Column)을 무식하게 추가하거나, 똑같은 인물 정보를 100줄로 중복해서 복사해야 합니다. 이것은 인문학적 맥락을 파괴하는 행위이자, 거미줄을 억지로 일직선으로 잡아 늘여 끊어버리는 어리석은 짓입니다.

## 2. 해결책 제시: 찢어진 족보와 조인(JOIN)의 폭발

컴퓨터 공학에서는 표에 빈칸이나 중복이 생기는 것을 막기 위해 `"**정규화(Normalization)**"`라는 수술을 감행합니다. 정규화란 쉽게 말해, 뚱뚱해진 하나의 표를 주제별로 잘게 찢어 여러 개의 작은 표로 나누는 작업입니다. "인물 표", "관직 표", "사제관계 표" 등으로 뿔뿔이 흩어놓는 것입니다.

마치 도서관 사서가 두꺼운 족보 책을 인물별, 시대별, 가문별로 낱장으로 갈기갈기 찢어서 각기 다른 서랍에 보관하는 것과 같습니다. 보관하기에는 아주 깔끔합니다. 

문제는 우리가 질문을 던질 때 발생합니다. 

우리가 **"이이의 스승의 스승과 같은 고향에 사는 사람을 찾아줘"**라고 질문하면, 데이터베이스는 찢어진 족보 조각들을 다시 하나로 이어 붙여야만 대답할 수 있습니다. 이렇게 흩어진 표들을 임시로 꿰매어 붙이는 연산을 바로 `"**JOIN(조인)**"`이라고 부릅니다. 

질문의 꼬리가 길어질수록, 즉 추적해야 할 관계의 깊이가 1단계, 2단계, 3단계로 깊어질수록 데이터베이스는 수천만 번의 표 뒤지기와 꿰매기를 반복해야 합니다. 이를 공학 용어로 `"**조인 연산의 폭발(JOIN Explosion)**"`이라고 부릅니다. 결국 서버의 메모리는 한계를 초과하여 새하얗게 얼어붙고 시스템은 다운되고 맙니다.

## 3. 실전 적용: 사제관계 추적 SQL의 비극

실제 조선시대 학맥 데이터를 통해 RDB가 네트워크 분석에 얼마나 취약한지 SQL 코드로 실증해 보겠습니다. `"**이이**"`의 학문적 뿌리를 찾기 위해 3단계 위의 스승을 추적하는 쿼리입니다.

표는 인물의 기본 정보를 담은 `"**인물_테이블**"`과 스승과 제자의 연결 고리만 담은 `"**사제관계_테이블**"` 두 개로 찢어져(정규화되어) 있습니다.

```sql
-- "이이"의 3대 스승(스승의 스승의 스승)을 찾기 위해 무한 조인을 시도하는 눈물겨운 쿼리
SELECT 
    제자.이름 AS 질문대상,
    스승1.이름 AS 일대_스승,
    스승2.이름 AS 이대_스승,
    스승3.이름 AS 삼대_스승
FROM 인물_테이블 AS 제자
-- 1단계: 이이의 스승을 찾기 위해 사제관계 표를 꿰매어 붙임
INNER JOIN 사제관계_테이블 AS 관계1 ON 제자.인물ID = 관계1.제자ID
INNER JOIN 인물_테이블 AS 스승1 ON 관계1.스승ID = 스승1.인물ID

-- 2단계: 스승1의 스승을 찾기 위해 또 다시 표를 꿰매어 붙임
INNER JOIN 사제관계_테이블 AS 관계2 ON 스승1.인물ID = 관계2.제자ID
INNER JOIN 인물_테이블 AS 스승2 ON 관계2.스승ID = 스승2.인물ID

-- 3단계: 스승2의 스승을 찾기 위해 세 번째로 표를 꿰매어 붙임
INNER JOIN 사제관계_테이블 AS 관계3 ON 스승2.인물ID = 관계3.제자ID
INNER JOIN 인물_테이블 AS 스승3 ON 관계3.스승ID = 스승3.인물ID

WHERE 제자.이름 = "이이";
```

보이십니까? 겨우 3단계 위의 스승을 찾기 위해 동일한 테이블을 6번이나 반복해서 읽어 들이고 억지로 이어 붙여야 합니다. 

만약 "이이의 제자들 중에서 다시 정승의 반열에 오른 자들의 사돈을 찾아라"처럼 5단계, 6단계를 넘어가는 질문을 던진다면 SQL 코드는 수백 줄로 늘어나고, 연산 시간은 며칠이 걸릴지도 모릅니다.

| 비교 항목 | 관계형 데이터베이스 (RDB) | 차세대 지식 그래프 (LOD) |
| :--- | :--- | :--- |
| **데이터의 본질** | 표(Table)에 담긴 정적인 기록 | 점과 선으로 이어진 동적인 네트워크 |
| **관계의 취급** | 무거운 연산(`"**JOIN**"`)을 통해 억지로 계산해 냄 | 관계 자체가 이미 저장된 최우선 데이터 |
| **탐색 깊이** | 3단계 이상 넘어가면 기하급수적으로 서버 마비 | 수십 단계를 건너뛰어도 1초 안에 초고속 탐색 |
| **적합한 인문학 연구** | 명부 정리, 통계 엑셀, 단순 목록화 | 사상적 계보, 가계도, 인물 집단사, 공간 이동망 |

## 4. 실무 트러블슈팅 (Street-smart Tips)

인문학도들이 RDB를 다루며 네트워크를 분석하려 할 때 가장 빈번하게 서버를 터뜨리는 주범이 있습니다. 바로 조인 조건(`"**ON**"`)을 빼먹고 쿼리를 실행하는 실수입니다.

조건 없이 두 테이블을 조인하면, 데이터베이스는 앞 테이블의 모든 행과 뒤 테이블의 모든 행을 무식하게 곱해버립니다. 이를 `"**카테시안 곱(Cartesian Product)**"`이라고 부릅니다.

만약 만 명의 조선시대 인물 테이블을 자기 자신과 실수로 조건 없이 조인하면, 1만 곱하기 1만, 즉 순식간에 **1억 줄**의 데이터가 생성되며 서버의 램(RAM)을 찢어발기게 됩니다. 복잡한 역사 네트워크를 SQL로 분석하려 시도할 때는 반드시 쿼리 맨 마지막에 `"**LIMIT 10**"`을 붙여서 소량의 결과만 먼저 확인하는 방어적 코딩 습관을 길러야 합니다.

## 5. 요약 및 다음 단계

* 관계형 데이터베이스(RDB)는 데이터를 중복 없이 관리하기 위해 표를 잘게 찢는 `"**정규화**"`를 수행합니다.
* 찢어진 표를 다시 이어 붙여 인물들의 관계망을 추적하는 `"**JOIN**"` 연산은, 관계가 깊어질수록 컴퓨터를 마비시키는 치명적인 공학적 모순을 안고 있습니다.
* 복잡다단한 인문학적 관계망을 2차원 표의 감옥에 가두는 것은 이제 불가능합니다.

우리는 표의 논리를 버리고, 데이터 자체가 거미줄처럼 얽혀 있는 새로운 차원의 세계로 떠나야 합니다. 다음 파트인 **[2장. 시맨틱 웹과 링크드 오픈 데이터(LOD)]**에서는 조인(JOIN)이라는 무거운 연산 없이, 데이터가 스스로 의미를 가지고 무한히 연결되는 웹 3.0의 철학 속으로 진입해 보겠습니다.
