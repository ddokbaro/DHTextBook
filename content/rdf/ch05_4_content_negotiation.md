# 5.4. 다국어 메뉴판을 든 웨이터: 콘텐츠 협상(Content Negotiation)의 HTTP 메커니즘

## 1. 도입: 똑같은 주소, 완전히 다른 두 명의 손님

우리는 앞선 5.3장에서 `"**303 See Other**"`라는 우아한 리다이렉트 방식을 통해, 역사적 실체(사람)와 그에 대한 기록(문서)을 분리하는 시맨틱 웹의 위대한 철학을 배웠습니다. 그리고 그 과정에서 서버가 인간과 기계를 구분하여 각기 다른 문서를 던져주는 `"**콘텐츠 협상(Content Negotiation)**"`이라는 마법을 살짝 엿보았습니다.

이번 장에서는 이 마법이 실제로 어떻게 작동하는지 컴퓨터 공학의 밑바닥, 즉 `"**HTTP 통신 규약**"`의 관점에서 낱낱이 해부해 보겠습니다.

아주 훌륭한 레스토랑(서버)이 있다고 상상해 보십시오. 이 레스토랑의 주소는 `http://w3id.org/joseon/person/P123` 단 하나뿐입니다. 
어느 날 두 명의 손님이 이 레스토랑 문을 열고 들어옵니다. 한 명은 예쁜 그림과 글씨를 좋아하는 평범한 인간 연구자이고, 다른 한 명은 오직 3조각의 데이터만 씹어 먹는 구글의 인공지능 로봇입니다. 

레스토랑의 웨이터(웹 서버)는 이 두 손님이 똑같은 테이블(URI)에 앉았음에도 불구하고, 인간에게는 그림이 가득한 `"**HTML 메뉴판**"`을 건네주고, 로봇에게는 기계어로 작성된 `"**Turtle(.ttl) 메뉴판**"`을 건네줍니다. 웨이터는 도대체 무슨 수로 손님의 정체를 파악한 것일까요?

## 2. 해결책 제시: HTTP "Accept" 헤더의 비밀

웨이터가 손님의 정체를 파악하는 비밀은 바로 손님들이 레스토랑 문을 열고 들어올 때 이마에 붙이고 들어오는 `"**HTTP 요청 헤더(Request Header)**"`에 숨어 있습니다.

우리가 매일 사용하는 크롬(Chrome)이나 사파리(Safari) 같은 웹 브라우저는 주소창에 엔터를 치는 순간, 서버를 향해 다음과 같은 명함을 몰래 내밉니다. 이 명함 속 가장 중요한 정보가 바로 `"**Accept(수용 가능 포맷)**"`입니다.

**"안녕하세요! 저는 인간을 모시고 온 웹 브라우저입니다. 저는 기계어는 읽을 줄 모르니, 가급적이면 인간이 볼 수 있는 `text/html` 형식의 문서를 주시면 가장 감사하겠습니다!"**

반면, 파이썬(Python)으로 짜인 데이터 수집 로봇이나 추론 엔진이 동일한 주소에 접속할 때는 개발자가 미리 명함(Accept 헤더)을 다음과 같이 조작해 둡니다.

**"삐빅. 나는 기계다. 그림이나 표는 필요 없다. 나는 오직 `text/turtle`이나 `application/ld+json` (JSON-LD) 형태의 데이터만 수용할 수 있다. 그것을 내놓아라."**

서버는 단지 접속자가 내민 이 `"**Accept**"` 명함을 읽고, 자신이 창고에 가지고 있는 데이터 포맷 중 가장 알맞은 것을 골라서 응답(Response)해 줄 뿐입니다. 클라이언트(손님)와 서버(웨이터)가 서로 어떤 포맷을 주고받을지 합의하는 이 우아한 통신 과정을 컴퓨터 공학에서는 `"**콘텐츠 협상(Content Negotiation)**"`이라고 부릅니다.

## 3. 실전 적용: cURL을 통한 해커들의 확인법

이 마법을 눈으로 직접 확인하기 위해, 검은색 터미널 창(명령 프롬프트)을 열고 `"**cURL**"`이라는 해커들의 도구를 사용하여 똑같은 URI 주소에 두 가지 다른 명함(Accept)을 내밀어 보겠습니다.

### 테스트 1: 기계의 명함으로 접속했을 때 (Turtle 요구)
`-H` 옵션을 사용하여 Accept 헤더에 시맨틱 웹 원시 코드인 `"**text/turtle**"`을 달라고 강력하게 요구해 봅니다.

```bash
# 해커의 터미널 명령어: "Turtle 포맷으로 율곡 이이(P00123) 데이터를 다오!"
curl -L -H "Accept: text/turtle" [http://w3id.org/joseon/person/P00123](http://w3id.org/joseon/person/P00123)

# 서버의 우아한 응답 결과 (기계어 데이터가 쏟아짐):
@prefix rdfs: [http://www.w3.org/2000/01/rdf-schema#](http://www.w3.org/2000/01/rdf-schema#) .
@prefix joseon: [http://w3id.org/joseon/person/](http://w3id.org/joseon/person/) .

joseon:P00123 rdfs:label "이이" ;
              [http://조선.kr/속성/호](http://조선.kr/속성/호) "율곡" .
```

### 테스트 2: 인간의 명함으로 접속했을 때 (HTML 요구)
이번에는 동일한 주소에 Accept 헤더만 인간의 언어인 `"**text/html**"`로 슬쩍 바꾸어서 던져봅니다.

```bash
# 해커의 터미널 명령어: "인간이 볼 웹페이지(HTML)로 율곡 이이(P00123) 데이터를 다오!"
curl -L -H "Accept: text/html" [http://w3id.org/joseon/person/P00123](http://w3id.org/joseon/person/P00123)

# 서버의 우아한 응답 결과 (우리가 아는 웹페이지 코드가 쏟아짐):
<!DOCTYPE html>
<html>
<head><title>이이 (율곡) - 조선시대 인물 DB</title></head>
<body>
  <h1>이이</h1>
  <p>호: 율곡</p>
</body>
</html>
```

주소(`P00123`)는 단 한 글자도 변하지 않았지만, 서버는 명함(`Accept`)의 내용에 따라 완전히 다른 박스에 데이터를 포장하여 배달해 주었습니다. 이 완벽한 분리 기술 덕분에, 시맨틱 웹은 수십억 개의 낡은 HTML 문서 생태계를 파괴하지 않고도 그 이면에 조용하고 거대한 기계들의 지식 그래프를 겹쳐서 깔아둘 수 있게 된 것입니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

디지털 인문학 데이터를 서비스하는 백엔드 개발자들을 가장 괴롭히는 것은, 인간의 웹 브라우저들이 던지는 명함(`Accept`)이 생각보다 훨씬 지저분하고 복잡하다는 점입니다.

실제로 크롬(Chrome) 브라우저가 서버에 던지는 Accept 헤더의 원본을 까보면 다음과 같이 생겼습니다.
`Accept: text/html,application/xhtml+xml,application/xml;q=0.9,image/webp,*/*;q=0.8`

여기서 `"**q=0.9**"` 같은 알 수 없는 기호들이 등장합니다. 이것은 식당 손님의 `"**선호도 가중치(Quality Factor)**"`입니다. 브라우저는 서버에게 이렇게 투정 부리는 것입니다.
*"나는 1순위로 `text/html`을 원해! 근데 만약 그게 없으면 0.9점짜리인 `application/xml`이라도 줘. 그것도 없으면 0.8점짜리인 아무 포맷(`*/*`)이나 다 받아먹을게!"*

이 복잡한 선호도 공식을 개발자가 일일이 파이썬(Python)이나 자바(Java) 코드로 짜서 분기(If-Else) 처리를 하려면 서버 로직이 끔찍하게 복잡해집니다. 

**실무자를 위한 황금 팁:** 콘텐츠 협상 로직을 절대 웹 애플리케이션(WAS) 내부의 코드로 직접 짜지 마십시오! 아파치(Apache)나 엔진엑스(Nginx) 같은 웹 서버(Web Server) 앞단에서 이 무거운 협상 과정을 미리 차단하여 처리하는 것이 서버 아키텍처의 정석입니다. 엔진엑스 설정 파일에 몇 줄만 적어두면, 0.001초 만에 `text/turtle`을 원하는 기계 손님만 골라내어 정적 파일(`.ttl`)이 있는 폴더로 토스하고, 나머지는 모두 HTML을 보여주는 화면으로 넘겨버릴 수 있습니다. 개발자의 야근을 없애는 아키텍처의 승리입니다.

## 5. 요약 및 다음 단계

* 시맨틱 웹의 서버는 동일한 주소(URI)로 들어오는 요청에 대해 접속자의 정체에 따라 다른 데이터를 제공하며, 이를 `"**콘텐츠 협상(Content Negotiation)**"`이라고 부릅니다.
* 서버가 정체를 파악하는 기준은 클라이언트가 몰래 내미는 `"**HTTP Accept 헤더**"`에 적힌 수용 가능 포맷(`text/html`, `text/turtle` 등)입니다.
* 이 기술 덕분에 인문학 데이터베이스는 인간을 위한 시각적 웹사이트와 기계를 위한 지식 그래프를 하나의 주소로 완벽하게 동시에 서비스할 수 있습니다.

지금까지 우리는 엑셀의 표를 버리고(1장), 데이터를 점과 선으로 조립하며(2~4장), 그 뼈대에 영원히 변하지 않는 이름표와 서버 응답 규약을 세우는 법(5장)까지 데이터 아키텍처의 거대한 산맥을 모두 넘었습니다.

이제 여러분의 수장고에는 완벽한 시맨틱 데이터가 가득 차 있습니다. 그렇다면 이제 다음 질문이 떠오릅니다. **"이 방대한 점과 선의 바다 속에서, 내가 원하는 조선시대 인물들을 내 마음대로 검색하고 거시적인 통계를 뽑아내려면 기계에게 도대체 어떤 언어로 질문을 던져야 할까요?"**

마침내, W3C가 제정한 시맨틱 웹 최고의 무기이자 SQL의 진화형인 지식 검색의 마법, **[6장. 논리적 제약과 철학적 충돌: OWA와 CWA]**에서, 시맨틱 웹이 세상을 바라보는 인식론적 패러다임의 대전환을 경험해 보겠습니다.
