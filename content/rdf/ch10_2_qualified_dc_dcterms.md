# 10.2. 한계 돌파: 한정어(Qualifier)와 dcterms의 시맨틱 확장

## 1. 도입: "1604년이 도대체 무슨 날짜입니까?"

앞선 10.1장에서 우리는 단순 더블린 코어(Simple DC)의 15가지 요소를 사용해 류성룡의 《징비록》을 아름답게 맵핑했습니다. 그러나 그 코드를 넘겨받은 깐깐한 서지학자나 역사학자는 곧바로 거센 항의를 해올 것입니다.

`dc:date "1604" .`

"도대체 이 1604년이 무슨 날짜입니까? 류성룡이 원고 집필을 끝낸(탈고) 날짜입니까? 아니면 목판으로 처음 인쇄된(간행) 날짜입니까? 그것도 아니면 후대 도서관에 이 책이 입고된 날짜입니까? 이토록 모호한 `dc:date` 하나로 어떻게 정밀한 역사 연구를 하란 말입니까!"

게다가 시맨틱 아키텍트인 여러분의 눈에는 더 큰 구조적 결함이 보입니다.
`dc:creator "류성룡" .`

값(Object) 자리에 들어간 `"류성룡"`은 클릭해서 다른 지식으로 뻗어나갈 수 없는 닫힌 **'문자열(String 리터럴)'**입니다. 기계 입장에서 이 글자는 위키데이터의 정교한 류성룡 인물 개체(Q485121)와 결코 조인(JOIN)될 수 없습니다. 단순 더블린 코어는 호환성은 높지만, 깊이 있는 학술 연구와 거대한 지식망(LOD)을 구축하기에는 너무나도 뭉툭하고 낡은 무기였습니다.

## 2. 해결책 제시 1: 한정어(Qualifier)를 통한 정밀한 쪼개기

더블린 코어 커뮤니티(DCMI)는 이 학자들의 거센 불만을 수용하여, 기존 15개의 뭉툭한 요소를 더 뾰족하고 세밀하게 깎아내는 업데이트를 단행했습니다. 이때 도입된 개념이 바로 `"**한정어(Qualifier)**"`입니다. 

한정어는 기존의 넓은 의미를 가진 부모 속성(Property) 아래에, 더 구체적인 자식 속성(Sub-property)들을 파생시키는 시맨틱 기술입니다. 예를 들어, 모호했던 `dc:date`는 다음과 같이 정밀한 한정어들로 분화되었습니다.

* `dcterms:created` (창작일): 원고가 쓰인 날짜
* `dcterms:issued` (발행일): 책이 출판된 날짜
* `dcterms:modified` (수정일): 내용이 개정된 날짜
* `dcterms:dateAccepted` (승인일): 학위 논문 등이 통과된 날짜

이외에도 `dc:relation(관계)` 요소는 `dcterms:isPartOf(~의 일부이다)`, `dcterms:hasVersion(~의 다른 버전이다)`, `dcterms:isFormatOf(~의 포맷 변환본이다)` 등으로 세밀하게 쪼개졌습니다. 

이제 인문학자들은 글로벌 호환성을 유지하면서도(기계는 이 모든 한정어의 조상이 결국 `dc:date`나 `dc:relation`임을 추론을 통해 알고 있습니다), 자신이 원하는 디테일을 마음껏 코딩할 수 있게 되었습니다.

## 3. 해결책 제시 2: 문자열(String)에서 사물(Thing/URI)로

한정어의 도입과 함께 더블린 코어는 낡은 네임스페이스인 `dc: (http://purl.org/dc/elements/1.1/)`를 버리고, 시맨틱 웹의 철학을 완벽하게 수용한 새로운 네임스페이스인 `"**dcterms: (http://purl.org/dc/terms/)**"`를 발표합니다.

`dcterms:`가 가져온 가장 위대한 혁신은 바로 **"문자열(String)의 감옥에서 벗어나 사물(Thing/URI)을 연결하게 된 것"**입니다.

과거 `dc:creator`는 값으로 `"류성룡"`이라는 텍스트만 받을 수 있었습니다. 하지만 `dcterms:creator`는 그 목적어 자리에 **URI 객체(Object)**를 요구합니다.

* **낡은 방식 (String):** `국학:징비록 dc:creator "류성룡" .` (여기서 사고의 확장이 끝남)
* **진보된 방식 (Thing):** `국학:징비록 dcterms:creator <http://위키데이터/Q485121> .` (이제 기계는 위키데이터로 넘어가 류성룡의 출생지, 붕당, 교우 관계까지 무한히 지식을 확장할 수 있습니다!)

이 작은 접두사의 변화(`dc` ➔ `dcterms`)가 바로 닫힌 데이터베이스를 열린 지식 그래프(LOD)로 폭발시키는 핵심 트리거(Trigger)입니다.

## 4. 실전 적용: dcterms로 진화한 《징비록》 지식 그래프

이제 10.1장에서 작성했던 뭉툭한 코드를, 한정어와 `dcterms:` 네임스페이스를 활용하여 정밀하고 연결 가능한 진정한 '시맨틱 지식 그래프'로 업그레이드해 보겠습니다.

```turtle
# 낡은 dc: 대신 진보된 dcterms: 를 기본으로 선언합니다.
@prefix dcterms: [http://purl.org/dc/terms/](http://purl.org/dc/terms/) .
@prefix 국학: [http://aks.ac.kr/data/](http://aks.ac.kr/data/) .
@prefix wd: [http://www.wikidata.org/entity/](http://www.wikidata.org/entity/) .

국학:book/징비록 
    # [1. 한정어를 통한 정밀한 날짜와 관계 표현]
    dcterms:title "징비록(懲毖錄)" ;
    dcterms:created "1598" ; # 집필 완료 연도 (명확해졌습니다!)
    dcterms:issued "1604" ;  # 실제 출판/간행 연도 (날짜의 모호함이 사라졌습니다!)
    dcterms:isPartOf 국학:collection/국보_제132호 ; # 소속 관계를 명확히 합니다.
    
    # [2. String에서 Thing(URI)으로의 대전환]
    # "류성룡"이라는 글자 대신, 글로벌 식별자(Q-ID)를 직접 연결합니다.
    dcterms:creator wd:Q485121 ; 
    
    # [3. 통제 어휘(Vocabulary) URI의 연결]
    # 주제어 역시 단순 문자열이 아닌, 개념 URI(SKOS)로 연결합니다.
    dcterms:subject 국학:concept/임진왜란 ;
    dcterms:language [http://id.loc.gov/vocabulary/iso639-2/lzh](http://id.loc.gov/vocabulary/iso639-2/lzh) . # 한문(lzh)에 대한 국제 표준 URI
```

이 코드를 본 서지학자는 날짜의 정밀함에 만족할 것이고, 컴퓨터 공학자는 모든 데이터가 URI로 아름답게 연결된 그래프 구조에 환호할 것입니다. 

## 5. 실무 트러블슈팅 (Street-smart Tips)

"교수님, 과거의 `dc:`와 최신의 `dcterms:`가 이렇게 다르다면, 우리가 새로 만드는 프로젝트에서는 무조건 `dcterms:`만 쓰면 되는 건가요? 기존 논문들을 보면 두 개를 막 섞어서 쓰던데요?"

시맨틱 아키텍처를 설계할 때 맞닥뜨리는 아주 골치 아픈 `"**하위 호환성(Backward Compatibility)**"` 문제입니다.

**시맨틱 아키텍트의 실무 가이드: "새 술은 새 부대에, 하지만 배포는 친절하게"**
1. **내부 데이터베이스 모델링:** 여러분이 2026년에 새로운 지식 그래프를 설계한다면, 낡은 `dc:`는 머릿속에서 완전히 지우십시오. 무조건 `dcterms:`만을 사용하여 데이터의 정밀도와 연결성(URI)을 극대화해야 합니다.
2. **외부 배포(Export) 시의 하이브리드 전략:** 하지만 여러분의 데이터를 가져가려는 외부 기관의 낡은 OAI-PMH 시스템이나 구형 XML 파서가 `dcterms:`를 이해하지 못하고 에러를 낼 수 있습니다. 이럴 때는 우리가 9.4장(링구아 프랑카)에서 배웠던 **"이중 등재(Dual-assertion)"** 기법을 발휘하십시오.

```turtle
# [실무형 배포 코드: 낡은 시스템과 최신 LOD 엔진을 모두 만족시키는 법]
국학:book/징비록
    dcterms:creator wd:Q485121 ; # 최신 AI와 LOD 엔진을 위한 고품질 연결 (Thing)
    dc:creator "류성룡" .        # 구형 도서관 시스템을 위한 친절한 텍스트 떡밥 (String)
```
여러분의 서버가 이렇게 두 줄을 모두 내어준다면, 어떤 구형 시스템이나 최신 시스템이 접근하더라도 완벽하게 데이터를 소화할 수 있습니다. 이것이 실무 마스터의 배려입니다.

## 6. 요약 및 다음 단계

* 단순 더블린 코어(`dc:`)의 모호함과 문자열(String) 리터럴의 한계를 극복하기 위해, DCMI는 **한정어(Qualifier)**와 **`dcterms:`** 네임스페이스를 도입했습니다.
* `dcterms:`의 도입으로 인문학자들은 `created`, `issued`처럼 정밀한 시맨틱을 구사할 수 있게 되었고, 기계는 텍스트 대신 **URI 객체(Thing)**를 추적하여 지식을 무한히 확장할 수 있게 되었습니다.
* 실무에서는 지식 그래프 내부 모델링 시 `dcterms:`를 표준으로 삼되, 레거시 시스템과의 연동을 위해 `dc:`를 병행 표기(Dual-assertion)하는 유연성이 필요합니다.

이제 우리는 더블린 코어의 뼈대와 확장 문법을 모두 손에 쥐었습니다. 하지만 15개 요소 중 `dc:type`이나 `dc:format` 같은 속성들의 값으로 아무 단어나 막 집어넣어도 될까요? "Text"라고 써야 할지 "Book"이라고 써야 할지, "이미지"라고 써야 할지 "Image"라고 써야 할지 규칙이 없다면 다시 혼돈이 찾아올 것입니다.

다음 장인 **[10.3. DCMI 유형 어휘(Type Vocabulary)와 어플리케이션 프로파일(DCAP) 설계]**에서, 값(Value)의 파편화를 막기 위한 통제 어휘의 사용법과, 우리 연구실만의 확고한 입력 규칙(DCAP)을 선언하는 아키텍처 문서를 작성해 보겠습니다.
