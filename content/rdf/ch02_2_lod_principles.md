# 2.2. 기계가 이해하는 데이터: LOD의 4원칙과 5성급(5-Star) 개방형 데이터

## 1. 도입: 게시판에 올린 엑셀 파일은 "개방"이 아닙니다

인문학 연구실에서 흔히 벌어지는 풍경이 있습니다. 연구원들이 몇 달간 밤을 새워가며 `"**임진왜란 참전 무장 명단**"`을 엑셀로 정리합니다. 그리고 이 귀중한 엑셀 파일을 연구소 홈페이지 자료실에 업로드한 뒤, "우리 연구소도 마침내 데이터를 세상에 전면 개방했다!"라며 자축합니다. 혹은 스캔한 고문헌 번역본을 `"**PDF**"` 형태로 올려두기도 합니다.

하지만 웹과 기계(Computer)의 관점에서 볼 때, 게시판에 덩그러니 올려진 엑셀 파일이나 PDF는 전 세계 데이터망과 완전히 단절된 `"**지식의 무인도**"`에 불과합니다. 구글의 거대한 인공지능이 여러분의 엑셀 파일 속 `"**이순신**"`이라는 글자를 읽고, 그것이 위키백과에 있는 `"**이순신**"`과 동일한 역사적 인물임을 스스로 깨달을 수 있을까요? 불가능합니다. 

인간이 클릭해서 다운로드 받아야만 열어볼 수 있는 파일은 진정한 의미의 초연결 지식이 아닙니다. 기계가 데이터를 직접 씹어 삼키고, 내 연구실의 지식과 다른 나라의 지식을 스스로 엮어내도록 만들려면, 우주를 관통하는 거대한 규칙 하나를 따라야 합니다.

## 2. 해결책 제시: 팀 버너스리의 "LOD 4원칙"

웹의 창시자 팀 버너스리(Tim Berners-Lee)는 고립된 데이터들을 하나의 거대한 지식 그래프로 엮어내기 위해, 누구나 반드시 지켜야 할 4가지 절대 원칙을 선포했습니다. 이를 `"**링크드 오픈 데이터(LOD) 4원칙**"`이라고 부릅니다. 

역사 데이터를 다루는 인문학자의 관점에서 이 4원칙을 풀이해 보겠습니다.

1. **사물에 `"**URI**"`를 부여하라.**
   * 세상의 모든 인물, 장소, 사건에 전 우주에서 유일무이한 식별자(이름표)를 달아주어야 합니다. "이순신"이라는 동명이인이 겹치지 않도록, `http://우리연구소.kr/인물/이순신_무신`과 같은 고유한 인터넷 주소(`"**URI**"`)를 부여하는 것입니다.
2. **그 `"**URI**"`를 HTTP 웹 주소로 만들어라.**
   * 식별자는 단순히 문서에 적어두는 암호가 되어서는 안 됩니다. 누구나 인터넷 브라우저에 그 주소를 입력하면 해당 데이터로 직접 찾아갈 수 있도록, 작동하는 웹 주소(`"**HTTP**"`)의 형태를 띠어야 합니다. 즉, 지식으로 향하는 "도로망"을 깔아주는 것입니다.
3. **표준화된 포맷(`"**RDF**"`)으로 유용한 정보를 제공하라.**
   * 그 주소로 기계가 찾아갔을 때, 인간의 언어(HTML 문서)가 아니라 기계들의 만국 공통어인 `"**RDF(트리플)**"` 형태로 데이터를 제공해야 합니다. 
4. **다른 사람의 `"**URI**"`와 링크를 연결하라.** (가장 중요)
   * 내 데이터 안에서만 놀지 말고, 전 세계가 함께 쓰는 타 기관의 식별자와 선을 이어야 합니다. 내 데이터의 "이순신"이 위키데이터(Wikidata)의 "이순신"과 동일한 인물임을 명시적으로 연결하여, 지식의 족보를 글로벌하게 교차시키는 것입니다.

이 4원칙을 얼마나 잘 지켰느냐에 따라, 팀 버너스리는 우리가 개방한 데이터의 수준을 별 1개부터 별 5개까지 등급을 매겼습니다. 이것이 바로 그 유명한 `"**5성급(5-Star) 개방형 데이터 모델**"`입니다.

## 3. 실전 적용: 엑셀 파일이 5성급 데이터로 진화하는 과정

조선시대 징비록 데이터를 예로 들어 데이터의 진화 과정을 시각적인 표로 비교해 보겠습니다.

| 등급 | 개방 형태 | 기계의 이해도 | 인문학 데이터 실증 예시 |
| :---: | :--- | :--- | :--- |
| **★** | 어떤 포맷이든 웹에 올린 데이터 | **최하** (그림에 불과함) | 징비록 원본을 스캔한 `"**PDF**"`나 사진 파일 |
| **★★** | 기계가 읽을 수 있는 구조화된 표 | **하** (특정 소프트웨어 종속) | 징비록 등장인물을 정리한 마이크로소프트 `"**엑셀(XLSX)**"` 파일 |
| **★★★** | 특정 프로그램에 종속되지 않은 열린 포맷 | **중** (표 구조의 한계) | 엑셀 대신 쉼표로 구분하여 개방한 `"**CSV**"` 파일 |
| **★★★★** | W3C 표준 사용 및 `"**URI**"` 부여 | **상** (지식 그래프의 완성) | 징비록 인물들을 `"**RDF(트리플)**"`로 변환하고 고유 주소를 부여함 |
| **★★★★★** | 다른 기관의 데이터와 `"**링크(Link)**"` 연결 | **최상** (우주적 초연결) | 내 RDF 데이터의 류성룡을 전 세계 위키데이터의 류성룡과 결합 |

별 3개까지는 여전히 엑셀의 한계, 즉 2차원 표(Table)의 늪에 빠져 있습니다. 우리가 도달해야 할 궁극의 목적지는 바로 별 5개, `"**5-Star Linked Open Data**"`입니다.

우리가 만든 이순신 데이터가 4성급을 넘어 5성급으로 도약하는 순간을 `"**Turtle(.ttl)**"`이라는 시맨틱 웹 코드로 확인해 보겠습니다.

```turtle
# 4성급 데이터: 내 연구실 안에서 완벽한 지식 그래프를 만들었습니다.
[http://우리연구소.kr/인물/이순신](http://우리연구소.kr/인물/이순신) [http://우리연구소.kr/관계/싸웠다](http://우리연구소.kr/관계/싸웠다) [http://우리연구소.kr/전투/명량해전](http://우리연구소.kr/전투/명량해전) .

# 5성급 데이터: 드디어 내 데이터와 전 세계의 지식을 "동일함(sameAs)" 속성으로 연결합니다!
# 위키데이터에서 이순신의 고유 식별자는 "Q46446"입니다.
[http://우리연구소.kr/인물/이순신](http://우리연구소.kr/인물/이순신) [http://www.w3.org/2002/07/owl#sameAs](http://www.w3.org/2002/07/owl#sameAs) [http://www.wikidata.org/entity/Q46446](http://www.wikidata.org/entity/Q46446) .
```

마지막 줄의 코드가 들어가는 순간, 마법이 일어납니다. 기계는 이제 우리 연구소의 이순신 데이터가 부족하더라도, 선을 타고 위키데이터(Wikidata)로 건너가 그곳에 축적된 수백 개국의 언어로 번역된 이순신의 세계사적 맥락을 전부 끌어와서 융합 분석을 시작하게 됩니다. 이것이 시맨틱 웹의 진정한 힘입니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

공공기관이나 대학교의 데이터 구축 사업을 진행하다 보면, IT 개발자들이 종종 이런 말을 합니다. 

"교수님, 저희 시스템은 최신 `"**REST API**"`를 열어서 데이터를 `"**JSON**"` 포맷으로 제공하고 있습니다. 완벽한 5성급 개방형 데이터입니다!"

여기에 절대 속으시면 안 됩니다. API를 통해 JSON 데이터를 주는 것은 남들이 내 데이터를 퍼가기 쉽게 만들어준 것일 뿐, 데이터 자체가 다른 세계와 연결된 것은 아닙니다. 이것은 잘 쳐주어야 `"**3성급(3-Star)**"`에 불과합니다.

데이터베이스 엔지니어에게 명확하게 요구해야 합니다. "당신들이 만든 API 데이터 안에, 이 인물이 위키데이터나 국사편찬위원회의 어떤 `"**URI**"`와 동일한지를 가리키는 `"**owl:sameAs**"` 외부 링크가 꽂혀 있습니까?" 외부를 향해 뻗어 나가는 시맨틱 링크(Edge)가 단 하나도 없다면, 그것은 결코 5성급 링크드 오픈 데이터(LOD)가 될 수 없습니다. 

## 5. 요약 및 다음 단계

* 단순히 파일을 웹에 올리는 것은 진정한 데이터 개방이 아닙니다.
* 기계가 지식을 융합하기 위해서는 모든 것에 고유한 식별자(`"**URI**"`)를 달아주고 서로 연결하는 `"**LOD 4원칙**"`을 지켜야 합니다.
* 우리의 궁극적인 목표는 내 연구실의 지식과 전 세계의 지식을 연결하는 `"**5성급(5-Star) 개방형 데이터**"`를 구축하는 것입니다.

그렇다면, 이 위대한 5성급 지식 그래프를 만들기 위해 어떤 컴퓨터 데이터베이스를 사용해야 할까요? 기존의 RDB는 불가능하다는 것을 이미 배웠습니다. 다음 장인 **[3장. 지식 그래프 아키텍처 대격돌: W3C RDF vs 산업계 Neo4j]**에서는 시맨틱 데이터를 담아내는 두 가지 거대한 엔진의 철학과 구조적 차이를 깊이 있게 해부해 보겠습니다.
