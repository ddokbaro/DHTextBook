# 27.1. 형태 그래프(Shapes Graph)를 통한 거버넌스 통제

## 1. 도입: 수백 명의 학자가 참여하는 대규모 편찬 사업의 혼돈

앞선 27장의 도입부에서 우리는 "**SHACL**"이라는 엄격한 세관원을 고용하여, 잘못된 사망 연도나 오타가 지식 그래프에 유입되는 것을 차단하는 기초적인 방법을 배웠습니다. 하나의 규칙을 세우는 것은 성공했습니다.

하지만 여러분이 한국학중앙연구원의 "조선시대 인물 네트워크 구축"이라는 대규모 국책 사업의 총괄 책임자(아키텍트)가 되었다고 상상해 보십시오. 전국에서 수백 명의 연구원과 대학원생들이 각자 사료를 읽고 데이터를 추출하여 서버로 전송하고 있습니다.
만약 중앙에서 통제하는 완벽한 규칙서가 없다면 어떤 일이 벌어질까요?
* A 대학의 연구팀은 관직 임용 연도를 "1592"라는 숫자로 보냅니다.
* B 대학의 연구팀은 "1592년"이라는 문자열로 보냅니다.
* C 대학의 연구팀은 아예 연도를 빼먹고 이름과 관직만 보냅니다.

개별적인 세관원 한두 명으로는 이 거대한 혼돈을 통제할 수 없습니다. 수백 명의 학자가 각자의 방식대로 데이터를 빚어내는 순간, 지식 그래프는 거대한 쓰레기장이 되어버립니다. 우리는 파편화된 규칙들을 하나로 묶어, 프로젝트에 참여하는 모든 이가 강제로 따라야만 하는 **"국가 단위의 지식 헌법"**을 반포해야 합니다.

## 2. 해결책 제시: 지식망의 헌법, "**형태 그래프(Shapes Graph)**"

컴퓨터 공학에서는 이 거대한 규칙의 집합체를 "**형태 그래프(Shapes Graph)**"라고 부릅니다. 

인문학적으로 비유하자면, 이것은 조선시대 《실록》을 편찬할 때 춘추관 소속 사관들에게 나누어주던 엄격한 "**편찬 수칙(거버넌스)**"과 같습니다. 형태 그래프는 단순한 문법 검사기를 넘어, "우리의 지식 그래프 세계관에는 어떤 존재들이 있고, 그들은 어떤 속성을 가져야만 하는가"를 규정하는 철학적 선언문입니다.

총괄 아키텍트인 여러분은 인물(Person), 관직(Post), 사건(Event), 문헌(Source) 등 지식 그래프를 구성하는 모든 핵심 요소에 대한 검증 규칙(Shape)들을 하나의 파일에 묶어 형태 그래프를 완성합니다.

| 비교 항목 | 개별 형태 (Shape) | 형태 그래프 (Shapes Graph) |
| :--- | :--- | :--- |
| **인문학적 비유** | 한 단어의 맞춤법 검사기 | **국가 편찬 위원회의 공식 표준어 대사전 및 문법 규정집** |
| **적용 범위** | 단일 클래스 (예: 인물) | **온톨로지 전체 (인물, 관직, 장소 등 모든 클래스의 유기적 통제)** |
| **거버넌스 효과** | 부분적인 오타 방지 | **수백 명의 연구자가 생산하는 1,000만 건 데이터의 완벽한 규격화** |

## 3. 실전 적용: 조선시대 인물-관직 거버넌스 헌법 제정하기

이제 여러 개의 규칙을 엮어 하나의 거대한 "**형태 그래프**" 문서를 작성해 보겠습니다. 이 문서는 인물(Person)뿐만 아니라 관직(Post)에 대한 규정까지 포함하여, 두 개념 사이의 관계를 입체적으로 통제합니다.

```turtle
# 1. 네임스페이스 선언
@prefix sh: [http://www.w3.org/ns/shacl#](http://www.w3.org/ns/shacl#) .
@prefix joseon: [http://dh.aks.ac.kr/joseon/](http://dh.aks.ac.kr/joseon/) .
@prefix core: [http://dh.aks.ac.kr/ontology/core/](http://dh.aks.ac.kr/ontology/core/) .
@prefix xsd: [http://www.w3.org/2001/XMLSchema#](http://www.w3.org/2001/XMLSchema#) .

# ==========================================
# [제1장: 인물(Person)에 관한 규정]
# ==========================================
joseon:PersonShape a sh:NodeShape ;
    sh:targetClass core:Person ;
    sh:closed true ; # 선언되지 않은 속성은 절대 허용하지 않음

    # 규정 1-1: 인물은 반드시 이름(Name)을 문자열로 1개만 가져야 함
    sh:property [
        sh:path core:hasName ;
        sh:datatype xsd:string ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
    ] ;

    # 규정 1-2: 인물이 관직(Post)을 가질 경우, 그 대상은 반드시 'Post' 클래스여야 함
    sh:property [
        sh:path core:hasPost ;
        sh:class core:Post ; # [핵심] 목적어가 반드시 '관직' 형태를 띠어야 함을 강제!
    ] .

# ==========================================
# [제2장: 관직(Post)에 관한 규정]
# ==========================================
joseon:PostShape a sh:NodeShape ;
    sh:targetClass core:Post ;
    sh:closed true ;

    # 규정 2-1: 관직은 반드시 품계(Rank)를 가져야 하며, 1품에서 9품 사이여야 함
    sh:property [
        sh:path core:hasRank ;
        sh:datatype xsd:integer ;
        sh:minInclusive 1 ;
        sh:maxInclusive 9 ;
        sh:message "위반: 조선시대 품계는 1품에서 9품 사이의 정수여야 합니다."
    ] .
```

이 코드가 바로 여러분의 연구실을 지탱할 "**형태 그래프(Shapes Graph)**"입니다. 
이 헌법이 반포된 이후에는, 어떤 연구원이 "이순신(Person)이 판옥선(Artifact)에 임명되었다"라는 데이터를 넣으려 하면 "제1장 규정 1-2 위반"으로 즉시 기각됩니다. 또한, "전라좌수사의 품계는 10품이다"라고 입력하면 "제2장 규정 2-1 위반"으로 차단됩니다. 

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 피눈물: "데이터와 규칙을 한 파일에 넣었더니 서버가 폭주합니다!"**

SHACL을 처음 접하는 연구자들이 흔히 저지르는 치명적인 아키텍처 실수입니다. 
초보자들은 이순신의 삶을 기록한 "**데이터 그래프(Data Graph)**"와 방금 우리가 만든 헌법인 "**형태 그래프(Shapes Graph)**"를 하나의 거북이 파일(`project.ttl`)에 모두 섞어서 작성한 뒤, 트리플 스토어(Virtuoso 등)에 한꺼번에 업로드합니다.

이렇게 하면 끔찍한 연산 지옥이 펼쳐집니다. 서버는 매번 데이터를 검색할 때마다 "이것이 역사적 사실(Data)인지, 아니면 나를 통제하는 규칙(Shape)인지"를 구분하기 위해 불필요한 추론을 반복해야 하며, 검증 속도는 수백 배로 느려집니다.

**[승리하는 아키텍트의 '물리적 분리(Physical Separation)' 원칙]**
데이터 거버넌스의 제1원칙은 **"법전(Rule)과 백성(Data)이 사는 공간을 완벽하게 분리하라"**입니다.
반드시 형태 그래프 코드는 `shapes.ttl`이라는 별도의 파일로 저장하여 서버의 "**스키마(Schema) 전용 영역**"에 등록해야 합니다. 그리고 수백만 건의 역사 데이터는 `data.ttl`에 저장하여 별도의 영역에 적재하십시오. 
최신 SHACL 검증 엔진은 이 두 그래프가 물리적으로 분리되어 있을 때, 형태 그래프를 메모리(RAM)에 가볍게 올려둔 상태에서 폭포수처럼 쏟아지는 데이터 그래프를 초고속으로 검사하는 최상의 성능을 발휘합니다.

## 5. 요약 및 다음 단계

* 대규모 디지털 인문학 프로젝트에서 수많은 학자가 생산하는 데이터의 일관성을 유지하기 위해, 파편화된 규칙들을 엮어 지식의 헌법인 "**형태 그래프(Shapes Graph)**"를 제정해야 합니다.
* 형태 그래프는 특정 클래스의 속성뿐만 아니라, 다른 클래스(`sh:class core:Post`)와의 관계까지 입체적으로 통제하는 강력한 거버넌스 도구입니다.
* 서버의 성능 저하와 연산 폭주를 막기 위해, 실제 사료를 담은 "**데이터 그래프**"와 통제 규칙을 담은 "**형태 그래프**"는 반드시 별도의 파일로 물리적 분리를 해야 합니다.

이제 여러분은 어떤 대규모 프로젝트를 맡더라도 데이터의 품질을 완벽하게 통제할 수 있는 아키텍트의 자격을 갖추었습니다. 
하지만 우리의 역사 데이터는 항상 거북이 파일(.ttl)로만 존재하지 않습니다. 만약 이 거대한 헌법(SHACL)을, 모듈 6에서 배운 "관계형 데이터베이스(MySQL)"와 연결해야 한다면 어떻게 될까요?
