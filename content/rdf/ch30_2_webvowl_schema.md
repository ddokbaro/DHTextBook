# 30.2. 온톨로지 스키마 조망: WebVOWL 다이어그램

## 1. 도입: 나무만 보고 숲을 보지 못하는 인문학자들

우리는 직전 30.1장에서 "**LodLive**"라는 훌륭한 나침반을 도입하여, 사용자가 "이순신"이라는 중심 노드에서 출발해 주변 인물들을 하나씩 탐험해 나가는 점진적 브라우징 환경을 구축했습니다. 이는 대중의 호기심을 충족시키기에 완벽한 도구입니다.

하지만 이 시스템을 평가하러 온 동료 사학자나 온톨로지 전문가들의 불만은 여기서 시작됩니다.
**"이순신과 류성룡이 연결된 것은 알겠습니다. 그런데 이 전체 지식 그래프가 도대체 어떤 '개념적 뼈대'로 설계되어 있습니까? 인물(Person)은 관직(Post) 외에 또 어떤 클래스와 연결될 수 있습니까?"**

LodLive는 "나무(개별 데이터)"를 돋보기로 관찰하는 데 특화되어 있지만, 거대한 "숲(전체 스키마)"을 조망하는 데는 철저히 무능합니다. 전문가들은 수십만 건의 개별 역사적 팩트(A-Box)가 아니라, 아키텍트인 여러분이 설계한 **"개념과 규칙의 설계도(T-Box)"** 그 자체를 보고 싶어 합니다. 텍스트로 쓰인 수백 줄의 온톨로지 파일(`.owl` 또는 `.ttl`)을 눈으로 읽고 머릿속에서 구조를 그리는 것은 인간의 한계를 벗어나는 고통스러운 작업입니다.

## 2. 해결책 제시: 지식망의 우주적 조감도, "**WebVOWL**"

텍스트에 갇힌 개념적 설계도를 화려한 시각적 다이어그램으로 단숨에 번역해 주는 웹 기반의 마법 도구가 바로 "**WebVOWL(Web-based Visualization of Ontologies)**"입니다.

인문학적으로 비유하자면, WebVOWL은 한양 도성에 사는 "백성들의 명부(데이터)"를 보여주는 것이 아니라, 한양 도성 전체의 "도시 계획도(스키마)"를 하늘에서 내려다보게 해주는 **조감도**입니다.

이 도구에 여러분의 온톨로지 규칙 파일을 집어넣으면, 기계는 클래스(Class)를 거대한 색색의 원으로, 속성(Property)을 그 원들을 잇는 화살표로, 데이터 타입(문자, 숫자)을 작은 노란색 사각형으로 치환하여 브라우저 위에 둥둥 떠다니는 우주적 네트워크를 그려냅니다.

| 조망의 대상 | 데이터 탐색 (LodLive) | 스키마 조망 (WebVOWL) |
| :--- | :--- | :--- |
| **시각화의 중심** | 이순신, 거북선 등 **개별 인스턴스 (A-Box)** | 인물, 사물 등 **추상적 클래스와 규칙 (T-Box)** |
| **사용 목적** | 역사적 사실의 확인 및 꼬리물기 탐색 | **온톨로지 설계의 논리적 결함 확인 및 전체 구조 파악** |
| **주요 사용자** | 역사에 관심 있는 일반 대중 | **데이터 모델러, 온톨로지 설계자, 총괄 아키텍트** |

## 3. 실전 적용: OWL 파일을 WebVOWL에 띄워 뼈대 검증하기

여러분이 설계한 "조선시대 관역 온톨로지"를 WebVOWL 화면에 띄우는 과정은 매우 직관적입니다. 하지만 WebVOWL은 거북이(`.ttl`) 파일이나 `.owl` 파일을 직접 읽지 못하고, 자신만의 고유한 JSON 포맷을 요구합니다.

이 장벽을 넘기 위한 파이프라인 실무는 다음과 같습니다.

1. **변환기 가동 (owl2vowl):** WebVOWL 프로젝트에서 제공하는 자바스크립트/자바 기반의 변환 도구인 `owl2vowl`을 사용합니다. 터미널에서 다음 명령어를 실행하여 우리의 온톨로지 파일을 변환합니다.
   ```bash
   # 터미널에서 온톨로지 파일을 WebVOWL 전용 JSON으로 변환
   java -jar owl2vowl.jar -file joseon_ontology.ttl
   ```
2. **시각화 엔진에 로드:** 변환되어 생성된 `joseon_ontology.json` 파일을 웹 브라우저에 띄워진 WebVOWL 인터페이스에 드래그 앤 드롭(Drag & Drop)합니다.
3. **직관적 탐색:** 화면 중앙에 `core:Person` (파란색 원)과 `core:Post` (주황색 원)가 큼직하게 떠오르고, 그 사이를 `core:hasPost`라는 화살표가 잇고 있는 웅장한 설계도가 나타납니다. `core:Person` 원 옆에는 뻗어 나간 가지 끝에 `xsd:integer` (출생 연도)와 `xsd:string` (이름) 등의 데이터 타입들이 별처럼 매달려 있습니다.

이를 통해 아키텍트는 "아, 내가 '장소(Place)'와 '전투(Event)'를 연결하는 화살표를 빼먹었구나!"라는 설계상의 치명적 논리 누락을 직관적으로 발견하고 즉시 수정할 수 있습니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 두통: "수백 개의 클래스가 거미줄처럼 엉켜서 글자가 겹쳐 안 보입니다!"**

WebVOWL에 국가 단위의 거대한 온톨로지를 넣었을 때 100% 발생하는 시각적 재앙입니다. 
기계는 수백 개의 동그라미(클래스)를 중력 시뮬레이션(Force-directed graph)을 통해 화면에 흩뿌리는데, 속성이 너무 많으면 동그라미들이 서로를 끌어당기며 화면 중앙에 거대한 교차로의 대마왕처럼 뭉쳐버립니다. 화살표와 글자가 겹쳐서 도저히 설계도를 읽을 수 없는 상태가 됩니다.

**[승리하는 아키텍트의 '필터링(Filtering)과 중력 제어' 기술]**
이 혼돈을 잠재우려면 WebVOWL 하단과 우측에 숨겨진 제어 패널을 장악해야 합니다.
1. **데이터 타입 숨기기 (Datatype Collapsing):** 가장 먼저 해야 할 일입니다. `Filter` 메뉴에서 "Datatype properties"를 끄십시오. 문자열이나 숫자(이름, 연도 등)를 나타내는 수백 개의 잔가지 노드들이 즉시 화면에서 사라지며 굵직한 핵심 뼈대(클래스 간의 관계)만 깔끔하게 남습니다.
2. **중력과 거리 조절 (Gravity & Distance):** 하단의 슬라이더를 조정하여 노드 사이의 `Link Distance`(연결선 길이)를 길게 늘이고, 뭉쳐진 원들이 서로 밀어내도록 조정합니다. 
3. **하위 클래스 접기 (Subclass Collapsing):** 만약 `core:Person` 아래에 `왕`, `신하`, `노비` 등 수십 개의 하위 클래스가 있다면, 이를 상위 클래스 하나로 접어버리는(Collapse) 기능을 활용하여 화면의 복잡도를 획기적으로 낮춰야 합니다.

## 5. 요약 및 다음 단계

* 데이터의 세부 내용이 아닌 전체 지식 그래프의 개념적 설계도(스키마)를 한눈에 파악하기 위해 "**WebVOWL**"이라는 강력한 시각화 조감도를 도입합니다.
* WebVOWL은 온톨로지 파일(`.ttl`, `.owl`)을 `owl2vowl` 도구로 변환하여 브라우저에서 읽어 들이며, 클래스를 원형 노드로, 속성을 화살표로 직관적으로 그려냅니다.
* 거대한 온톨로지의 시각적 엉킴을 해결하기 위해, 데이터 타입 숨기기와 중력 제어 등의 필터링 기능을 자유자재로 다루는 아키텍트의 UI 통제력이 필수적입니다.

이제 우리는 "나무(데이터)"를 탐색하는 LodLive와 "숲(스키마)"을 조망하는 WebVOWL이라는 완벽한 두 개의 시각화 무기를 갖추었습니다. 
그런데, 이 두 가지 도구로도 풀 수 없는 아주 기막힌 인문학적 질문이 하나 남아있습니다.
