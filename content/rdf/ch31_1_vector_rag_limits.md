# 31.1. 벡터(Vector) RAG의 파편화 문제와 추론의 붕괴

## 1. 도입: 너무나도 쉽고 달콤한 유혹, "벡터(Vector) 데이터베이스"

우리는 앞선 31장의 도입부에서 인공지능(LLM)의 환각(Hallucination)을 치료하기 위해, 기계에게 완벽한 사료를 오픈북으로 제공하는 "**RAG(검색 증강 생성)**" 아키텍처의 위대함을 깨달았습니다.

그런데 최근 IT 업계나 랭체인(LangChain) 튜토리얼을 보면, 십중팔구 RAG를 구축할 때 텍스트를 잘게 쪼개어 숫자로 변환한 뒤 "**벡터 DB(Vector Database)**"에 넣으라고 가르칩니다. 이 방식은 너무나 쉽고 달콤합니다. 복잡한 SPARQL을 배울 필요도, 온톨로지를 설계할 필요도 없습니다. 그저 《조선왕조실록》 텍스트 파일을 통째로 집어넣고 기계에게 "비슷한 문장을 찾아와!"라고 명령하면 끝납니다.

하지만 여러분이 이 달콤한 유혹에 빠져 수억 원짜리 벡터 RAG 시스템을 구축한 뒤, 인공지능에게 다음과 같은 뼈아픈 인문학적 질문을 던졌다고 상상해 보십시오.
**"이순신 장군을 백의종군하게 만든 왕의 아버지는 누구인가?"**

이 질문을 받은 벡터 RAG는 헛소리를 뱉어내거나 완전히 침묵해 버립니다. 텍스트를 문장 단위로 산산조각 내어 숫자로 뭉뚱그려 놓은 벡터 DB는, 결코 "이순신 -> 파직 -> 선조 -> 아버지 -> 덕흥대원군"으로 이어지는 이 거대한 역사의 인과율을 추론해 낼 지능이 없기 때문입니다. 우리는 이 치명적인 한계를 "**파편화의 저주**"라고 부릅니다.

## 2. 해결책 제시(이자 비판): 파쇄기에 들어간 역사책 vs 얽히고설킨 족보

벡터 RAG가 복잡한 역사적 추론 앞에서 왜 처참하게 붕괴하는지, 그 철학적 차이를 인문학적으로 비유해 보겠습니다.

벡터 기반의 RAG는 **"역사책을 파쇄기에 넣고 갈아버린 뒤, 수영장에 뿌리는 것"**과 같습니다.
문장들은 앞뒤 문맥(Context)과 연결 고리가 완전히 끊어진 채(파편화) 수영장 안을 둥둥 떠다닙니다. 사용자가 "이순신 파직"을 검색하면, 기계는 의미(숫자 거리)가 비슷한 종이 쪼가리 몇 장을 건져 올릴 뿐입니다. 그 종이 쪼가리 안에는 "왕의 아버지"에 대한 단서가 애초에 존재하지 않습니다.

반면, 우리가 수십 개의 모듈을 거치며 고집스럽게 구축해 온 "**지식 그래프(Graph RAG)**"는 **"왕실의 완벽한 족보(Genealogy)"**입니다.
이순신이라는 동그라미(노드)를 잡고 선(엣지)을 따라가면 '선조'가 나오고, 선조에서 다시 '아버지'라는 선을 따라가면 '덕흥대원군'이 나옵니다. 데이터가 파편화되지 않고 거미줄처럼 영원히 연결되어 있으므로, 아무리 복잡한 다중 홉(Multi-hop) 질문이 들어와도 기계는 흔들림 없이 정답의 경로를 따라갑니다.

| 비교 항목 | 벡터 RAG (Vector DB) | 그래프 RAG (Knowledge Graph) |
| :--- | :--- | :--- |
| **데이터의 형태** | 쪼개진 텍스트 조각 (Chunk) | **주어-서술어-목적어의 명확한 관계망 (Triple)** |
| **검색의 원리** | 단어의 의미적 유사도 (Cosine Similarity) | **노드와 엣지를 타고 넘어가는 논리적 연쇄 추론 (Path Traversal)** |
| **다중 홉 추론** | A와 C의 관계를 묻는 질문에 **완벽히 붕괴함** | A ➔ B ➔ C 로 이어지는 **정확한 논리적 답변 도출** |

## 3. 실전 적용: 벡터 RAG가 실패하는 "다중 홉(Multi-hop)"의 함정

실제 역사 데이터를 통해 벡터 시스템이 어떻게 추론에 실패하고, 지식 그래프가 어떻게 승리하는지 그 파이프라인의 차이를 극명하게 대비해 보겠습니다.

**[질문]: "원균이 전사한 해전이 일어난 장소의 현재 행정구역은 어디인가?"**
(필요한 논리적 추론: 원균 ➔ 전사한 해전(칠천량) ➔ 발생 장소(거제도) ➔ 현재 행정구역(경상남도 거제시))

**[패배하는 벡터 RAG의 작동 방식]**
1. 사용자의 질문을 벡터 숫자 뭉치로 변환합니다.
2. 수백만 개의 텍스트 조각 중 "원균", "전사", "해전", "장소"와 유사도가 높은 문장 5개(Top-K)를 무식하게 건져 올립니다.
3. 건져 올린 문장: "원균은 칠천량 해전에서 전사했다.", "칠천량 해전은 조선 수군의 뼈아픈 패배였다."
4. **결과:** LLM은 프롬프트에 들어온 텍스트 조각만 읽고 대답합니다. "원균은 칠천량 해전에서 전사했습니다. 하지만 그곳의 현재 행정구역 정보는 제공된 문서에 없어 알 수 없습니다." (추론의 단절)

**[승리하는 그래프 RAG의 작동 방식]**
1. 질문을 분석하여 지식 그래프를 관통하는 SPARQL 쿼리로 변환합니다.
2. 기계가 엣지를 타고 완벽한 다중 홉 논리 탐색을 시작합니다.
   `joseon:원균 core:전사하다 ?event .` (정답: 칠천량해전)
   `?event core:발생장소 ?place .` (정답: 거제도)
   `?place core:현재행정구역 ?modern_city .` (정답: 경상남도 거제시)
3. **결과:** LLM은 탐색이 완료된 완벽한 팩트를 바탕으로 당당하게 선언합니다. "원균 장군이 전사한 칠천량 해전의 발생 장소는 현재의 경상남도 거제시입니다."

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 착각: "검색 결과 개수(Top-K)를 5개에서 50개로 늘리면 벡터 RAG도 추론을 하지 않을까요?"**

벡터 RAG의 치명적 단점을 깨달은 개발자들이 가장 흔히 저지르는 끔찍한 실수입니다. 
"원균의 전사 장소에 대한 정보가 5개의 텍스트 조각 안에 안 들어왔어? 그럼 검색 범위를 넓혀서 비슷한 문장 50개(Top-K=50)를 건져 올려서 LLM에게 다 먹여보자!"

**[승리하는 아키텍트의 컨텍스트 윈도우(Context Window) 방어술]**
이 무식한 방법은 인공지능을 완전히 질식시켜 버립니다. 
50개의 텍스트 조각을 프롬프트에 쑤셔 넣으면, LLM이 읽어야 할 토큰(Token) 수가 폭발적으로 증가하여 API 호출 비용이 수십만 원 단위로 치솟습니다. 더 끔찍한 것은 **"길이의 저주(Lost in the Middle)"**입니다. LLM은 너무 많은 쓰레기 텍스트가 들어오면 정작 중요한 중간의 단서들을 까먹어 버리고 횡설수설하기 시작합니다.

연관성 없는 파편화된 쓰레기 문장을 50개, 100개 집어넣는다고 해서 끊어진 논리의 사슬이 이어지지 않습니다. 애초에 데이터가 "관계(Relationship)"를 잃고 파쇄되었기 때문입니다. 다중 홉 추론을 해결하는 유일하고도 가장 우아한 방법은 무식한 벡터 조각 모음이 아니라, 처음부터 완벽하게 연결된 지식 그래프(SPARQL)의 정밀한 타격(Precision)을 활용하는 것뿐입니다.

## 5. 요약 및 다음 단계

* 텍스트를 문장 단위로 쪼개어 유사도를 검색하는 **벡터(Vector) RAG**는 구축하기 쉽지만, 데이터 간의 문맥과 연결 고리를 파괴하는 "**파편화의 저주**"를 낳습니다.
* 이 파편화로 인해 벡터 RAG는 "A의 B의 C는 무엇인가?"와 같은 인문학적 **다중 홉(Multi-hop) 논리 추론** 앞에서 처참하게 붕괴합니다.
* 무분별하게 검색 조각(Top-K)을 늘려 LLM에 욱여넣는 것은 비용 폭탄과 환각만 가중시킬 뿐입니다. 오직 노드와 엣지로 완벽하게 연결된 **지식 그래프(Graph RAG)**만이 논리적 단절 없이 완벽한 팩트를 추적해 낼 수 있습니다.

이제 우리는 왜 남들이 다 쓰는 쉬운 벡터 DB를 거부하고, 기어코 이 어렵고 복잡한 지식 그래프 서버(Virtuoso)를 구축해야만 했는지 그 숭고한 철학적, 공학적 당위성을 완벽하게 증명해 냈습니다. 

하지만 여기서 가장 거대한 장벽이자 모순이 발생합니다.
"인공지능(LLM)에게 지식 그래프를 검색하게 시킨다"는 말은 논리적으로 완벽하지만, **도대체 챗GPT가 어떻게 수십 줄짜리 복잡한 SPARQL 코드를 짜서 우리 서버에 쿼리를 날릴 수 있단 말입니까?** 사용자는 "원균이 죽은 곳이 어디야?"라고 일상적인 자연어(Natural Language)로 물어볼 뿐입니다.
