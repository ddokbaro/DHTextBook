# 24.3. R2RML: 대규모 RDB 가상 지식 그래프(VKG) 구축

## 1. 도입: 반출이 금지된 거대한 "**지식의 사일로(Silo)**"를 마주하다

우리는 24.1장과 24.2장을 통해 엑셀(CSV) 형태의 원시 데이터를 지식 그래프로 훌륭하게 변환해 냈습니다. 하지만 디지털 인문학 연구가 국가적 규모로 확장되면, 우리는 전혀 다른 형태의 거대한 장벽에 부딪히게 됩니다.

한국학중앙연구원이나 국사편찬위원회와 같은 대형 기관과 협업 프로젝트를 진행하게 되었다고 상상해 보십시오. 기관의 전산실 관리자는 여러분에게 단호하게 이렇게 통보합니다. **"보안 규정상 조선시대 인물 데이터베이스 5,000만 건을 엑셀 파일로 다운로드하여 외부로 반출하는 것은 엄격히 금지되어 있습니다. 우리 기관 내부의 관계형 데이터베이스(MySQL) 서버에 직접 연결해서 사용하십시오."**

관계형 데이터베이스(RDB)는 데이터를 엄격한 표(Table)에 가두어 두는 닫힌 구조입니다. 이 거대한 "**지식의 사일로(Silo, 고립된 저장소)**" 안에서 이순신 장군은 그저 "user_table"의 45번 행(Row)에 갇힌 텍스트에 불과합니다. 데이터를 밖으로 빼낼 수도 없고, 그렇다고 이 거대한 지식의 보고를 포기할 수도 없는 진퇴양난의 상황입니다. 우리는 어떻게 이 굳게 닫힌 창고의 데이터를 우리의 유연한 지식망(RDF)으로 해방시킬 수 있을까요?

## 2. 해결책 제시: 똑똑한 통역사를 고용하다, "**가상 지식 그래프(VKG)**"와 "**R2RML**"

이 거대한 물리적 장벽을 넘기 위해, 컴퓨터 공학자들은 데이터를 복사해서 옮기는 무식한 방법을 포기했습니다. 대신 아주 똑똑한 통역사를 창고 문 앞에 세워두기로 했습니다. 이 혁신적인 아키텍처를 "**가상 지식 그래프(Virtual Knowledge Graph, VKG)**"라고 부르며, 이 통역사가 참고하는 전 세계 표준 번역 매뉴얼이 바로 W3C의 "**R2RML(RDB to RDF Mapping Language)**"입니다.

인문학적으로 직관적인 비유를 들어보겠습니다.
외국인 학자(사용자)가 한국의 전통 식당에 와서 프랑스어로 요리(SPARQL 쿼리)를 주문합니다. 주방장(관계형 데이터베이스)은 한국어(SQL 쿼리)밖에 모릅니다. 
이때 웨이터(VKG 엔진)가 다가와 "**R2RML**"이라는 메뉴판 번역본을 펼칩니다. 웨이터는 손님의 프랑스어 주문을 한국어로 완벽하게 통역하여 주방에 전달합니다. 주방장이 요리(표 형태의 데이터)를 내어주면, 웨이터는 이를 다시 프랑스식 플레이팅(RDF 트리플)으로 예쁘게 꾸며서 손님에게 제공합니다.

가장 놀라운 점은, 이 모든 과정에서 창고의 식자재(원시 데이터)를 단 한 발자국도 밖으로 빼내지 않았다는 사실입니다. 데이터는 안전하게 RDB에 머물러 있지만, 사용자의 눈에는 완벽한 지식 그래프로 보이게 됩니다.

| 비교 항목 | 물리적 ETL (Tarql 등) | 가상 지식 그래프 (R2RML 기반) |
| :--- | :--- | :--- |
| **데이터의 위치** | 원시 데이터를 복사하여 트리플 스토어에 새로 저장함 | **데이터는 기존 기관의 RDB 창고에 그대로 머묾** |
| **변환 시점** | 파이프라인을 돌릴 때 한 번에 대량 변환 (사전 작업) | **사용자가 SPARQL 쿼리를 날리는 그 순간에 실시간 변환** |
| **동기화 문제** | 원본 DB가 업데이트되면 파이프라인을 다시 돌려야 함 | **원본 DB가 업데이트되면 지식 그래프도 즉시 자동 반영됨** |

## 3. 실전 적용: R2RML 맵핑으로 닫힌 RDB 테이블을 트리플로 연성하기

국가 기관의 MySQL 데이터베이스 안에 "조선시대_관원(joseon_officials)"이라는 테이블이 있다고 가정해 보겠습니다. 이 테이블에는 "고유번호(id)", "인물명(name)", "관직명(post_name)", "임용년도(appoint_year)" 컬럼이 갇혀 있습니다.

이 차가운 표(Table)를 따뜻한 시맨틱 관계망으로 엮어주기 위해, 우리는 "**R2RML**" 문법으로 통역 매뉴얼을 작성해야 합니다.

```turtle
# 1. 네임스페이스 선언: 통역에 사용할 어휘 사전을 상단에 정의합니다.
@prefix rr: [http://www.w3.org/ns/r2rml#](http://www.w3.org/ns/r2rml#) .
@prefix joseon: [http://dh.aks.ac.kr/joseon/](http://dh.aks.ac.kr/joseon/) .
@prefix core: [http://dh.aks.ac.kr/ontology/core/](http://dh.aks.ac.kr/ontology/core/) .

# 2. 맵핑 규칙의 시작: 어떤 테이블을 통역할 것인지 지정합니다.
<#JoseonOfficialsMapping> a rr:TriplesMap ;
    rr:logicalTable [ rr:tableName "joseon_officials" ] ;

    # 3. 주어(Subject) 생성 규칙: RDB의 "name" 컬럼을 가져와서 절대 식별자(URI)로 조립합니다.
    rr:subjectMap [
        rr:template "[http://dh.aks.ac.kr/joseon/person/](http://dh.aks.ac.kr/joseon/person/){name}" ;
        rr:class core:Person ;
    ] ;

    # 4. 서술어-목적어(Predicate-Object) 생성 규칙 1: 관직 정보 연결
    rr:predicateObjectMap [
        rr:predicate core:hasPost ;
        rr:objectMap [ 
            rr:template "[http://dh.aks.ac.kr/joseon/post/](http://dh.aks.ac.kr/joseon/post/){post_name}" ;
            rr:termType rr:IRI ;
        ] ;
    ] ;

    # 5. 서술어-목적어(Predicate-Object) 생성 규칙 2: 임용년도 연결
    rr:predicateObjectMap [
        rr:predicate core:appointmentYear ;
        rr:objectMap [ 
            rr:column "appoint_year" ;  # RDB의 숫자 값을 그대로 가져옵니다.
            rr:datatype xsd:integer ;
        ] ;
    ] .
```

이 R2RML 문서를 Ontop과 같은 VKG 엔진에 등록해 두면 모든 준비가 끝납니다. 이제 전 세계의 연구자들이 엔드포인트에 접속하여 "이순신의 관직을 찾아라"라는 SPARQL 쿼리를 날릴 수 있습니다. 엔진은 0.1초 만에 R2RML 매뉴얼을 참조하여 `SELECT post_name FROM joseon_officials WHERE name = "이순신"`이라는 SQL 쿼리로 통역한 뒤, 그 결과를 RDF로 변환하여 브라우저에 뿌려줍니다. 이질적인 두 세계가 융합되는 경이로운 순간입니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 절망: "DBA가 컬럼 이름을 바꿨더니 지식 그래프가 통째로 무너졌습니다!"**

R2RML은 기본적으로 RDB의 "테이블 이름"과 "컬럼 이름"에 완전히 종속된 통역 매뉴얼입니다. 만약 국가 기관의 데이터베이스 관리자(DBA)가 시스템 개편을 이유로 `name` 컬럼을 `person_name`으로 슬쩍 바꾸어 버린다면 어떻게 될까요? 
여러분의 지식 그래프 시스템은 즉시 통역 능력을 상실하고 무수한 "**SQL Syntax Error**"를 뿜어내며 처참하게 붕괴합니다.

**[승리하는 아키텍트의 완충 지대 방어술]**
이러한 재앙을 막기 위해서는, 원본 테이블을 직접 맵핑(`rr:tableName`)하는 도박을 피해야 합니다. 기관의 DBA에게 요청하여 컬럼명이 영구적으로 변하지 않는 "**데이터베이스 뷰(DB View)**"를 하나 생성해 달라고 하십시오. 그리고 그 뷰(View)를 대상으로 R2RML을 작성(`rr:sqlQuery`)하는 것이 가장 안전한 실무 원칙입니다. DBA가 원본 테이블을 마음대로 뜯어고치더라도, 뷰(View)라는 완충 지대가 우리의 지식 그래프를 지켜줄 것입니다.

**시맨틱 아키텍트의 착각: "SPARQL 쿼리가 너무 느립니다. 온톨로지를 잘못 짰나요?"**

VKG 환경에서는 데이터가 RDB에 있습니다. 만약 "임용년도가 1592년인 인물을 모두 찾아라"라는 SPARQL 쿼리가 10분이 넘도록 끝나지 않는다면, 그것은 시맨틱 엔진의 잘못이 아닙니다. 통역된 SQL 쿼리를 받아 든 MySQL 주방장이 `appoint_year` 컬럼에 "**인덱스(Index)**"가 걸려 있지 않아 5,000만 건의 데이터를 처음부터 끝까지 일일이 뒤지고 있기 때문입니다. 가상 지식 그래프의 검색 속도는 100% 하위 RDB의 인덱스 설계 상태에 좌우된다는 점을 뼈저리게 명심해야 합니다.

## 5. 요약 및 다음 단계

* 데이터 보안과 규모 문제로 엑셀 반출이 불가능할 때는, 데이터를 밖으로 빼내지 않고 통역사를 배치하는 "**가상 지식 그래프(VKG)**" 아키텍처를 도입해야 합니다.
* "**R2RML**"은 관계형 데이터베이스의 표(Table) 구조를 W3C 표준 시맨틱 트리플로 실시간 맵핑(통역)해 주는 강력한 표준 기술입니다.
* 가상 지식 그래프의 안정성과 속도는 근간이 되는 RDB의 스키마 유지보수(DB View 활용)와 인덱스 최적화에 완벽하게 종속됩니다.

이로써 우리는 정형 데이터(CSV, RDB)를 지식 그래프로 변환하는 3대 ETL 파이프라인(OpenRefine, Tarql, R2RML)을 모두 완벽하게 정복했습니다. 이제 이미 표 형태로 잘 정리된 역사 데이터라면 그 규모가 얼마든 두려울 것이 없습니다.

하지만 역사학 연구의 진정한 보고는 엑셀 칸 속에 얌전하게 갇혀 있지 않습니다. 
방대한 《조선왕조실록》 원문 텍스트, 수만 장의 《승정원일기》 고문헌 속에 줄글로 기록된 인물과 사건들을 어떻게 기계가 스스로 읽고 지식 그래프로 뽑아낼 수 있을까요?
