# 15.1. 출처의 3원소: Entity, Activity, Agent의 삼각 구도

## 1. 도입: 데이터의 족보를 캐묻는 역사학자의 본능

디지털 인문학 프로젝트를 진행하며 연구원들이 엑셀에 피땀 흘려 입력한 수만 건의 데이터가 드디어 지식 그래프 서버에 올라갔습니다. 화면에는 조선시대 지배 엘리트들의 화려한 혼맥과 사승 관계 네트워크가 펼쳐집니다. 하지만 깐깐한 역사학자라면 이 매끈한 결과물 앞에서 반드시 날 선 질문을 던져야 합니다.

**"이 데이터베이스에 적힌 이순신의 《난중일기》 국역본 텍스트는 대체 누가 번역한 것입니까?"**

1970년대 선배 학자들이 타자기로 친 번역입니까, 아니면 2025년에 인공지능 번역기가 초벌로 돌려놓은 텍스트입니까? 만약 번역에 치명적인 오역이 섞여 있어 이순신의 행적에 대한 역사적 해석이 완전히 뒤바뀐다면 우리는 누구에게 학문적 책임을 물어야 합니까? 출처가 증명되지 않은 지식은 학문적 사료로서 사망 선고를 받은 것과 같습니다.

디지털 인문학 지식 그래프는 단순히 **"이순신이 전라좌수사에 임명되었다"**라는 결과론적 명제만을 저장하는 데 그쳐서는 안 됩니다. 그 명제가 규장각의 어떤 원본 사료에서 발췌되었고, 어떠한 번역과 가공 과정을 거쳐, 최종적으로 누구의 손에 의해 데이터로 탄생했는지 그 생애주기 전체를 함께 기록해야 합니다. 

이 숭고한 **"사료 비판(Source Criticism)"**의 철학을 기계의 뇌 속에 이식하기 위해 W3C가 제정한 국제 표준이 바로 **"PROV-O"** 온톨로지입니다. 이 위대한 온톨로지의 중심에는 세상을 세 가지 원소로 쪼개어 바라보는 삼각 구도가 자리 잡고 있습니다.

## 2. 해결책 제시: PROV-O의 핵심 3원소 (Core Triad)

PROV-O는 세상의 모든 정보 생성 과정을 개체, 활동, 행위자라는 세 가지의 명확한 렌즈로 분해합니다. 이를 식당의 요리 과정에 비유해 보겠습니다.

| PROV-O 클래스 | 인문학적 식당 비유 | 디지털 데이터의 예시 |
| :--- | :--- | :--- |
| **"prov:Entity"** (개체) | 날것의 식재료, 그리고 최종적으로 완성된 요리 접시 | 아산 현충사 소장 《난중일기》 원본, 최종적으로 서버에 적재된 RDF 트리플 |
| **"prov:Activity"** (활동) | 식재료를 썰고 볶아서 요리를 만들어내는 주방에서의 조리 과정 | 초서체 한문을 현대어로 번역하는 작업, 엑셀 데이터를 지식 그래프로 변환하는 파이썬 코드 실행 |
| **"prov:Agent"** (행위자) | 조리 과정 전반을 지휘하고 요리 맛에 책임을 지는 셰프 | 번역을 담당한 한국학 연구원, 데이터베이스를 구축한 국사편찬위원회, 자동 추출을 수행한 인공지능 모델 |

이 세 가지 클래스는 무대 위의 배우들일 뿐입니다. 이들을 엮어 완벽한 데이터의 족보를 만들어내는 5가지 핵심 속성을 반드시 기억해야 합니다.

1. **"prov:wasGeneratedBy"** (생성됨): Entity ➔ Activity (이 번역 데이터는 어제 진행된 번역 작업에 의해 생성되었다.)
2. **"prov:used"** (사용됨): Activity ➔ Entity (그 번역 작업은 현충사의 원본 고문헌을 재료로 사용했다.)
3. **"prov:wasAssociatedWith"** (관여함): Activity ➔ Agent (그 번역 작업은 디지털인문학연구소 연구원에 의해 수행되었다.)
4. **"prov:wasAttributedTo"** (귀속됨): Entity ➔ Agent (따라서 이 번역 데이터의 학문적 책임은 해당 연구원에게 귀속된다.)
5. **"prov:wasDerivedFrom"** (파생됨): Entity ➔ Entity (결론적으로 이 번역 데이터는 저 원본 고문헌으로부터 파생된 것이다.)

## 3. 실전 적용: 《난중일기》 국역 데이터베이스의 출처 코딩 (Turtle)

디지털인문학연구소의 한 연구원이 《난중일기》 원문을 현대어로 번역하여 새로운 데이터셋을 구축하는 과정을 PROV-O 삼각 구도를 활용하여 시맨틱 아키텍처로 구현해 보겠습니다. 코드를 읽으며 세 가지 원소가 어떻게 거미줄처럼 엮이는지 확인해 보십시오.

```turtle
@prefix prov: [http://www.w3.org/ns/prov#](http://www.w3.org/ns/prov#) .
@prefix 국학: [http://aks.ac.kr/data/](http://aks.ac.kr/data/) .

# 1단계: 행위자 (Agent) - 책임의 주체를 명시합니다.
국학:researcher/dh_scholar a prov:Agent ;
    prov:label "디지털인문학연구소 수석 연구원" .

# 2단계: 원본 개체 (Entity) - 번역의 재료가 된 역사적 사료를 정의합니다.
국학:document/nanjung_ilgi_original a prov:Entity ;
    prov:label "난중일기 초서체 원본 (아산 현충사 소장)" .

# 3단계: 활동 (Activity) - 번역 과정이라는 동적 사건을 무대에 올립니다.
국학:activity/translation_2025 a prov:Activity ;
    prov:label "2025년 난중일기 현대어 국역 및 디지털화 작업" ;
    # 이 활동은 원본 문헌을 기초 재료로 사용했습니다.
    prov:used 국학:document/nanjung_ilgi_original ;
    # 이 활동은 수석 연구원이 주도적으로 수행했습니다.
    prov:wasAssociatedWith 국학:researcher/dh_scholar .

# 4단계: 결과 개체 (Entity) - 최종 데이터베이스를 정의하고 족보를 연결합니다.
국학:dataset/nanjung_ilgi_korean a prov:Entity ;
    prov:label "난중일기 현대어 국역 시맨틱 데이터베이스" ;
    # 이 데이터는 앞서 선언한 번역 작업의 결과물로 생성되었습니다.
    prov:wasGeneratedBy 국학:activity/translation_2025 ;
    # 이 데이터의 오류와 성과에 대한 책임은 수석 연구원에게 귀속됩니다.
    prov:wasAttributedTo 국학:researcher/dh_scholar ;
    # 거시적인 관점에서, 이 데이터는 원본 문헌의 파생물임을 선언합니다.
    prov:wasDerivedFrom 국학:document/nanjung_ilgi_original .
```

이 코드가 서버에 적재되는 순간, 엑셀의 단순한 텍스트 덩어리였던 번역본은 명확한 기원과 책임자를 가진 권위 있는 학술 데이터로 격상됩니다. 만약 후대 학자가 이순신의 수군 통제 행적에 대한 번역 오류를 발견한다면, 기계는 단 0.1초 만에 **"prov:wasAttributedTo"** 속성을 역추적하여 책임 소재를 명확히 밝혀낼 것입니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 피로도: 오타 수정 한 번 할 때마다 활동 노드를 새로 만들어야 합니까?**

출처 추적의 정밀함에 매료된 초보 연구원들은 종종 무시무시한 과잉 모델링의 늪에 빠집니다. 실무에서 가장 많이 듣는 불만은 다음과 같습니다. 

**"교수님, 연구원이 엑셀 데이터를 만지다가 정읍현감의 한자 띄어쓰기를 하나 수정했습니다. 이것도 데이터가 변형된 것이니, 띄어쓰기 수정 작업이라는 활동 노드를 새로 만들고 기존 개체와 엮어주어야 합니까?"**

단호하게 말씀드립니다. 절대 안 됩니다. 데이터베이스의 모든 저장 버튼 클릭마다 PROV-O 노드를 찍어낸다면, 본래의 인문학 데이터보다 족보 데이터의 용량이 수백 배 더 커지는 기괴한 시스템 배꼽이 탄생합니다. 우리는 시스템의 자잘한 로그를 만드는 것이 아니라 학술적 출처를 밝히는 중입니다.

실무에서는 온톨로지 명세서를 작성할 때 출처 기록의 거칠기 단위를 사전에 엄격히 타협해야 합니다. 띄어쓰기 수정, 단순 오타 교정, 일상적인 임시 저장 등 마이크로 단위의 편집은 위키피디아의 내부 편집 역사 기능이나 버전 관리 시스템에 맡겨버리십시오. 

원본 문헌의 최초 고해상도 스캔, 한문에서 현대어로의 공식 언어 번역, 다른 기관 데이터와의 대규모 병합 등 **"데이터의 학술적 성격이나 책임 주체가 근본적으로 뒤바뀌는 매크로 단위의 마일스톤"**에만 PROV-O 삼각 구도를 엄격하게 적용해야 합니다. 기록할 가치가 있는 거대한 궤적에만 돋보기를 들이대는 것이 훌륭한 아키텍트의 덕목입니다.

## 5. 요약 및 다음 단계

* 디지털 인문학 데이터베이스의 학술적 신뢰성을 담보하기 위해, 데이터가 탄생한 전체 생애주기를 추적하는 **"PROV-O"** 온톨로지를 반드시 도입해야 합니다.
* PROV-O는 지식의 생성 과정을 철학적으로 설명하는 **"Entity"**(개체), **"Activity"**(활동), **"Agent"**(행위자)라는 3대 원소로 이루어져 있습니다.
* 이 삼각 구도를 연결 속성으로 엮어내면, 잘못된 데이터의 책임 소재를 밝히고 원본 사료를 교차 검증하는 완벽한 디지털 족보가 완성됩니다.

이제 우리는 데이터의 기원을 밝혀내는 가장 강력한 논리적 뼈대를 세웠습니다. 하지만 조선시대 고문헌이 디지털 지식 그래프로 변모하는 과정은 단 한 번의 번역 작업으로 끝나지 않습니다. 스캐너를 거치고, 인공지능의 광학 판독을 거치고, 인간 학자의 치열한 교열을 거치는 길고 복잡한 연쇄 작용입니다.

다음 장인 **"15.2. 원본 사료에서 지식 그래프까지: 디지털화 및 번역 과정의 생애주기 기록"**으로 진입하여, 아날로그 유물이 0과 1의 네트워크로 부활하는 험난한 파이프라인 전체를 촘촘한 PROV-O 체인으로 엮어내는 심화 맵핑 기술을 실습해 보겠습니다.
