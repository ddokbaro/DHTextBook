# 22.2. 대규모 네트워크 탐색(Traversal)과 Graph Data Science (GDS) 알고리즘 적용

## 1. 도입: '스파게티 뭉치'에서 권력의 지도를 읽어내는 수학의 힘

22.1장을 통해 우리는 Neo4j 인프라를 구축하고, 노드와 관계를 생성하는 법을 익혔습니다. 몇십 명 수준의 인물 관계도를 그릴 때 Neo4j Browser가 보여주는 시각화 화면은 무척 아름답고 직관적입니다. 

하지만 데이터가 수만 건, 수십만 건으로 늘어난 **"한국근대인물LOD"**나 **"조선시대 문과방목"** 전체 데이터를 다룰 때, 화면에 출력되는 것은 그저 새까맣게 뭉친 거대한 '스파게티 뭉치(Hairball)'일 뿐입니다. 인간의 육안으로는 이 복잡계(Complex System) 네트워크에서 어떠한 의미 있는 패턴도 찾아낼 수 없습니다. 

사학자들은 종종 직관과 파편적인 사료를 바탕으로 **"이 인물이 남인과 서인 사이를 오가며 막후에서 정보를 통제한 핵심 실세(Key-man)였을 것이다"** 혹은 **"이 시기 영남 학파는 내부적으로 세 개의 거대한 파벌로 쪼개져 있었다"**라고 가설을 세웁니다. 

Neo4j의 **GDS(Graph Data Science)** 라이브러리는 바로 이 인문학적 직관과 가설을 **"수학적 수치"**로 증명해 주는 강력한 인공지능 두뇌입니다. 이제 우리 서버에 이 두뇌를 이식하여, 보이지 않는 권력과 지식의 지도를 그려보겠습니다.

## 2. 해결책 제시: 인문학적 통찰을 위한 핵심 그래프 알고리즘

Neo4j GDS는 수백 가지의 복잡한 알고리즘을 제공하지만, 역사학과 디지털 인문학 연구자가 반드시 마스터해야 할 핵심 무기는 크게 두 가지 범주로 나뉩니다.

### 2.1. 중심성 알고리즘 (Centrality) : "누가 권력과 정보의 길목을 쥐고 있는가?"
* **연결 중심성 (Degree Centrality):** 단순히 아는 사람(연결된 화살표)이 가장 많은 '마당발'을 찾습니다.
* **페이지랭크 (PageRank):** 구글의 검색 엔진 알고리즘입니다. "유명하고 영향력 있는 사람들에게 지목(천거, 인용)을 많이 받은 사람이 진짜 권력자다"라는 철학을 담고 있습니다.
* **매개 중심성 (Betweenness Centrality) [★핵심]:** 서로 직접 알지 못하는 두 집단(예: 동인과 서인) 사이를 잇는 **'유일한 다리(Bridge)'** 역할을 하는 인물을 찾습니다. 정보의 흐름을 통제하고 중재하는 막후 실세를 식별하는 데 압도적인 위력을 발휘합니다.

### 2.2. 커뮤니티 탐지 알고리즘 (Community Detection) : "숨겨진 파벌과 결사체 찾기"
* **루뱅 알고리즘 (Louvain):** 사료에 명시적인 '당파' 속성이 기록되지 않았더라도, 누구와 혼인하고 누구에게 학문을 배웠는지 그 연결망의 밀도(Modularity)를 계산하여, 기계가 스스로 최적의 파벌 그룹을 쪼개어 분류해 냅니다.

## 3. 실전 적용 1단계: GDS 라이브러리 설치와 아키텍처 이해

GDS는 Neo4j 엔진에 기본으로 탑재되어 있지 않은 무거운 확장팩(Plugin)입니다. 리눅스 터미널에서 이를 다운로드하고 보안을 해제해야 합니다.

**[GDS 플러그인 설치 및 보안 승인]**
```bash
# 1. Neo4j의 확장 프로그램이 위치한 디렉터리로 이동합니다.
cd /var/lib/neo4j/plugins

# 2. GDS 라이브러리(.jar)를 다운로드합니다. (반드시 현재 설치된 Neo4j 버전에 호환되는 버전을 선택해야 합니다.)
sudo wget [https://github.com/neo4j/graph-data-science/releases/download/2.3.1/neo4j-graph-data-science-2.3.1.jar](https://github.com/neo4j/graph-data-science/releases/download/2.3.1/neo4j-graph-data-science-2.3.1.jar)

# 3. Neo4j 설정 파일에서 GDS가 시스템 자원을 마음껏 쓰도록 권한을 부여합니다.
sudo nano /etc/neo4j/neo4j.conf

# 파일 끝에 다음 문구를 추가하여 족쇄를 풉니다.
dbms.security.procedures.unrestricted=gds.*
dbms.security.procedures.allowlist=gds.*

# 4. 서버 재시작
sudo systemctl restart neo4j
```

## 4. 실전 적용 2단계: 그래프 투영(Projection)과 연산 파이프라인

이 챕터의 가장 중요한 아키텍처적 개념입니다. Neo4j의 디스크에 저장된 데이터 원본(Native Graph)에서 직접 알고리즘을 돌리면 너무 느립니다. 따라서 GDS는 분석에 필요한 노드와 화살표만 쏙 뽑아내어, 연산 속도가 수백 배 빠른 **초고속 메모리 공간(RAM)에 가상의 그래프를 띄워놓고 연산**합니다. 이를 **'그래프 투영(Graph Projection)'**이라고 부릅니다.

브라우저(`http://서버IP:7474`)의 Cypher 입력창에서 매개 중심성을 구하는 파이프라인을 실행해 봅니다.

```cypher
// [1단계: 그래프 투영] 
// 하드디스크의 전체 데이터 중 'Person' 노드와 'KNOWS(아는 사이)' 관계만 뽑아내어, 
// 메모리 상에 'inmekGraph'라는 이름의 투영 그래프를 띄웁니다.
CALL gds.graph.project(
  'inmekGraph',
  'Person',
  'KNOWS',
  { relationshipProperties: 'weight' } // 친밀도 가중치가 있다면 함께 올릴 수 있습니다.
);

// [2단계: 알고리즘 연산 (Stream)]
// 메모리에 띄워둔 'inmekGraph'를 대상으로 매개 중심성(Betweenness) 알고리즘을 가동합니다.
CALL gds.betweenness.stream('inmekGraph')
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).name AS 인물명, score AS 매개중심성지수
ORDER BY score DESC
LIMIT 10;
```

단 0.1초 만에, 수만 명의 얽히고설킨 관계망을 수학적으로 뚫고 지나가 **"가장 높은 정보 통제력을 가진 10명"**의 명단과 그 점수(Score)가 도출됩니다. 

## 5. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 절망: "알고리즘 연산을 시작하자마자 서버가 뻗어버립니다 (OOM)!"**

앞서 설명했듯 GDS 알고리즘은 데이터를 디스크에서 **RAM(메모리)**으로 통째로 복사(투영)하여 연산합니다. 22.1장에서 설정한 자바 힙(Heap) 메모리가 수십만 건의 노드와 엣지를 품을 만큼 충분히 크지 않으면 즉시 `OutOfMemoryError(OOM)`를 뿜고 Neo4j가 비명횡사합니다.

**[승리하는 아키텍트의 극한 메모리 튜닝]**
GDS를 본격적으로 돌리려면 서버 사양부터 재점검해야 합니다. 만약 32GB RAM을 가진 서버라면 `neo4j.conf`를 다음과 같이 공격적으로 튜닝하십시오.
1. **`server.memory.heap.max_size=16G`**: GDS가 알고리즘을 계산하고 그래프를 투영하는 '직접적인 작업대'입니다. 전체 RAM의 50% 정도를 과감히 투자하십시오.
2. **`server.memory.pagecache.size=10G`**: 디스크의 데이터를 읽어오기 위한 캐시 공간입니다.

**시맨틱 아키텍트의 딜레마: "방향성이 없는 관계(Symmetric)는 어떻게 투영합니까?"**

"A가 B의 스승이다(TEACHES)"라는 관계는 명확한 방향(`A -> B`)이 있지만, "A와 B가 동문이다(CO_ALUMNI)"라는 관계는 쌍방향입니다. 그런데 Neo4j는 기본적으로 모든 화살표에 방향을 강제합니다. 알고리즘을 돌릴 때 이 방향을 어떻게 해석하느냐에 따라 파벌의 모양이 완전히 달라집니다.

**[승리하는 아키텍트의 투영 옵션 조작]**
그래프를 투영할 때, 기계에게 "방향을 무시하고 연결된 사실 그 자체에 집중하라"고 지시할 수 있습니다. 
```cypher
CALL gds.graph.project(
  'undirectedGraph',
  'Person',
  { CO_ALUMNI: { orientation: 'UNDIRECTED' } }
);
```
이렇게 `orientation: 'UNDIRECTED'` 옵션을 주면, 기계는 화살표 방향을 무시하고 왕복 2차선 도로처럼 양방향으로 데이터를 연산하여 인문학적 '관계 맺음'의 본질에 다가섭니다.

## 6. 요약 및 다음 단계

* **GDS(Graph Data Science)**는 인간의 눈으로 해독 불가능한 대규모 스파게티 네트워크에서, 수학적 알고리즘을 통해 **핵심 인물(중심성)**과 **파벌(커뮤니티)**을 식별해 내는 Neo4j의 인공지능 라이브러리입니다.
* GDS의 연산은 하드디스크가 아닌 메모리(RAM) 위에서 이루어지므로, 사용 전 데이터를 메모리로 끌어올리는 **그래프 투영(Graph Projection)** 단계가 반드시 선행되어야 합니다.
* 성공적인 연산을 위해서는 **방향성(Orientation)**에 대한 인문학적 해석과, 알고리즘이 뻗지 않도록 돕는 강력한 **Heap 메모리 튜닝**이 뒷받침되어야 합니다.

이제 우리는 무결점의 인프라 위에서 가장 고도화된 수학적 분석 툴까지 손에 쥐었습니다. 하지만 마음 한구석에는 여전히 해결되지 않은 숙제가 남아있습니다. 21장에서 정성껏 만든 **표준 RDF 데이터**와, 22장의 **Neo4j 실험실**이 서로 단절되어 있다는 사실입니다.
