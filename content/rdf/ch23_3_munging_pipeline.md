# 23.3. 백엔드 동기화 파이프라인: 미디어위키 JSON에서 Blazegraph로의 '먼징(Munging)'

## 1. 도입: "교수님! 방금 만든 데이터가 SPARQL 화면에서 조회가 안 됩니다!"

우리는 23.2장에서 Nginx와 Docker를 활용해 위키베이스(Wikibase)를 성공적으로 배포했습니다. 연구실에 이 시스템을 오픈한 첫날, 가장 열정적인 대학원생이 다급하게 뛰어와 이렇게 외칠 것입니다.

**"위키 화면(프론트엔드)에서 분명히 '정조(Q100)' 아이템을 만들고 데이터를 입력했는데, 위키데이터 쿼리 서비스(WDQS) 화면으로 넘어가서 쿼리를 날려보면 텅 빈 결과만 나옵니다. 시스템이 고장 났습니다!"**

이 당혹스러운 현상을 이해하려면, 우리가 구축한 Wikibase가 단순히 하나의 데이터베이스를 통째로 공유하는 1차원적 시스템이 아니라는 사실을 깨달아야 합니다. Wikibase는 사용자가 **"데이터를 입력하고 수정하는 저장소(Write DB)"**와 **"데이터를 초고속으로 검색하는 저장소(Read DB)"**가 완전히 물리적으로 분리된, 극도로 진화된 아키텍처를 가지고 있습니다.

## 2. 핵심 기술: 데이터의 험난한 여행 (JSON ➔ Munging ➔ RDF)

사용자가 위키 GUI 화면에서 '저장' 버튼을 누르는 순간부터, 그 지식이 SPARQL 엔드포인트에 닿기까지 데이터는 눈에 보이지 않는 험난한 3단계를 거치게 됩니다.

### ① 저장 단계 (MariaDB - JSON 포맷)
여러분이 위키 화면에서 입력한 '정조 - 직업 - 국왕'이라는 데이터는 아직 시맨틱 트리플 형태가 아닙니다. 프론트엔드 엔진인 MediaWiki는 이 데이터를 거대한 하나의 **JSON 텍스트 덩어리(Blob)**로 뭉쳐서 일반적인 관계형 데이터베이스인 **MariaDB**에 저장합니다. (이 MariaDB 안에서는 우리가 배운 고도의 SPARQL 조회가 절대 불가능합니다.)

### ② 해체 및 변환 단계 (WDQS Updater - Munging)
이때 뒷단에 숨어있는 **'Updater(업데이터)'**라는 백그라운드 도커 컨테이너가 쉴 새 없이 MediaWiki의 '최근 바뀜(Recent Changes)' 피드를 감시하고 있습니다. 
새로운 데이터가 감지되면, Updater는 이 JSON 덩어리를 낚아채어 W3C 표준 RDF 트리플(S-P-O) 형식으로 쪼개고 재조립합니다. 

IT 업계에서는 이렇게 거칠고 복잡한 원시 데이터를 씹고 뜯고 파싱하여 완전히 다른 형태의 유용한 포맷으로 변환하는 일련의 험난한 과정을 **먼징(Data Munging)**이라고 부릅니다. 이 과정에서 놀라운 마법이 일어납니다.

**[인문학적 디테일: 하나의 사실이 수십 개의 트리플로 폭증하는 이유]**
위키베이스는 단순한 트리플(A -> B)을 넘어서, 그 사실에 대한 출처(Reference), 한정어(Qualifier), 순위(Rank)를 부여할 수 있습니다. 따라서 "정조의 직업은 국왕이다"라는 1건의 JSON 데이터는 먼징을 거치며 다음과 같이 쪼개집니다.
* `wd:Q100 wdt:P39 wd:Q1234` (정조의 직업은 국왕이다 - 단순 조회용)
* `wd:Q100 p:P39 wds:Q100-uuid` (정조는 '직업-국왕'이라는 구체적 진술 노드를 가진다)
* `wds:Q100-uuid ps:P39 wd:Q1234` (그 진술의 핵심 값은 국왕이다)
* `wds:Q100-uuid pq:P580 "1776-00-00"` (그 진술의 시작일 한정어는 1776년이다)

### ③ 적재 단계 (Blazegraph - RDF 포맷)
Updater가 해체한 수백 개의 정교한 트리플들은 최종적으로 그래프 전용 데이터베이스인 **Blazegraph**에 적재(Load)됩니다. 이때부터 비로소 사용자는 WDQS 화면에서 SPARQL 쿼리를 통해 데이터를 조회할 수 있게 됩니다. 정상적인 상태라면 이 전체 여정은 **1~2초** 내에 빛의 속도로 완료됩니다.

## 3. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 피눈물: "1시간이 지났는데도 데이터가 안 넘어옵니다! (동기화 지연)"**

만약 위키 화면에서 아이템을 만들었는데 SPARQL 쿼리에서 조회가 안 된다면, Blazegraph가 고장 난 것이 아닙니다. 십중팔구 중간에서 데이터를 나르는 우체부, 즉 **Updater 컨테이너가 기절해 버린 것**입니다. 서버의 메모리가 일시적으로 부족했거나 도커를 잘못 껐다 켰을 때 발생하는 최악의 상태입니다.

**[승리하는 아키텍트의 파이프라인 심폐소생술]**
이 동기화 파이프라인이 멈췄을 때 아키텍트는 당황하지 않고 리눅스 터미널을 열어야 합니다.

1. **로그 확인으로 사망 선고 내리기**
   ```bash
   docker logs my-wikibase-wdqs-updater-1 --tail 50
   ```
   (컨테이너 이름은 폴더명에 따라 다를 수 있습니다.) 로그가 멈춰있거나 `Exception` 에러를 무한 반복하며 뿜고 있다면 즉시 심폐소생술에 들어갑니다.

2. **1단계 처방: 컨테이너 강제 재시작**
   ```bash
   docker restart my-wikibase-wdqs-updater-1
   ```
   가벼운 꼬임은 이 명령어로 해결됩니다. Updater가 깨어나며 그동안 밀려있던 JSON 덩어리들을 미친 듯이 씹어먹기 시작합니다.

3. **2단계 처방: 동기화 포인터(Poller) 강제 초기화**
   서버가 강제 종료되어 데이터의 싱크가 완전히 깨진 경우, Updater는 "내가 어디까지 동기화했더라?" 하고 패닉에 빠집니다. 이때는 동기화 지점을 리셋하는 극약 처방을 해야 합니다.
   ```bash
   docker exec -it my-wikibase-wdqs-updater-1 /runUpdate.sh --reset
   ```
   이 과정을 거치면 시스템이 MediaWiki의 최근 바뀜 기록을 처음부터 다시 훑으며 유실된 트리플들을 빠짐없이 Blazegraph로 복구해 냅니다.

## 4. 요약 및 다음 단계

* 우리가 구축한 Wikibase는 입력용 관계형 DB(MariaDB)와 쿼리용 그래프 DB(Blazegraph)가 분리된 고도화된 아키텍처입니다.
* 이 둘 사이를 이어주는 핵심 파이프라인이 바로 **Updater**이며, JSON을 구조화된 RDF 트리플로 해체하고 변환하는 과정을 **먼징(Munging)**이라고 부릅니다.
* 입력된 데이터가 SPARQL에 나오지 않는다면 100% Updater 컨테이너의 문제이므로, 리눅스 터미널에서 즉각적인 재시작(`restart`)과 리셋(`--reset`) 조치가 필요합니다.

이제 인프라의 내부 구조와 데이터가 흘러가는 배관(Pipeline)까지 완벽하게 파악했습니다. 아키텍트의 임무는 끝났습니다. 이제 이 튼튼한 인프라 위에서, 실제 연구자들이 수만 건의 데이터를 어떻게 하면 수작업 없이 빠르고 깔끔하게 쏟아부을 수 있는지 도구를 쥐여줄 차례입니다.
