# 26.1. 기존 구체화(Reification)의 저주와 한계 돌파

## 1. 도입: 화살표에 꼬리표를 달기 위한 과거 학자들의 눈물겨운 꼼수

26장의 도입부에서 우리는 역사적 이설(異說)과 출처를 표현하기 위해 화살표(관계) 자체에 포스트잇을 붙여야 한다는 인문학적 당위성을 깨달았습니다. 그리고 그것을 아주 우아하게 해결해 준 최신 마법인 "**RDF-star**"를 만났습니다.

그렇다면 여기서 한 가지 강력한 의문이 들어야 합니다. **"RDF-star 기술이 2021년에야 등장했다면, 그 이전 수십 년 동안 컴퓨터 공학자들과 인문학자들은 도대체 사료의 출처를 어떻게 기록하고 있었던 것일까?"**

과거의 학자들도 화살표에 꼬리표를 달고 싶어 미칠 지경이었습니다. 하지만 당시 W3C의 엄격한 규칙은 "오직 동그라미(노드)에만 포스트잇을 붙일 수 있다"고 강제했습니다. 그래서 과거의 선배 아키텍트들은 규칙을 깨지 않으면서 목적을 달성하기 위해, 지식 그래프 역사상 가장 기괴하고 끔찍한 꼼수를 발명해 냈습니다. 

이것을 컴퓨터 공학의 용어로 "**구체화(Reification)**"라고 부릅니다. 이 기술은 디지털 인문학의 데이터베이스를 끝없는 팽창의 저주에 빠뜨렸던 원흉입니다.

## 2. 해결책 제시(이자 비판): 마네킹을 세우는 끔찍한 노동, "**구체화(Reification)**"

"**구체화(Reification)**"의 철학은 매우 기형적입니다. 화살표 자체에 메모를 적을 수 없으니, **"화살표의 모양을 본뜬 거대한 가짜 마네킹(새로운 노드)을 하나 세운 뒤, 그 마네킹에 메모를 붙이자"**라는 발상입니다.

인문학적으로 비유해 보겠습니다. 
"원균이 칠천량 해전에서 전사했다"라는 문장이 있습니다. 여러분은 여기에 "이 문장은 선조실록에 적혀 있다"라는 포스트잇을 붙이고 싶습니다.
과거의 "**구체화**" 방식에서는 이를 위해 무려 4개의 새로운 서류를 작성해야 했습니다.
1. "내가 지금부터 문장 마네킹 번호 1번을 만들겠다."
2. "그 마네킹의 주어는 원균이다."
3. "그 마네킹의 서술어는 전사하다이다."
4. "그 마네킹의 목적어는 칠천량 해전이다."
이렇게 4단계를 거쳐 거대한 마네킹을 하나 조립한 뒤에야, 비로소 5번째 서류에 "이 마네킹의 출처는 선조실록이다"라고 적을 수 있었습니다.

| 비교 항목 | 과거의 "**구체화(Reification)**" | 현대의 "**RDF-star**" |
| :--- | :--- | :--- |
| **작동 원리** | 1개의 사실을 표현하기 위해 4개의 가짜 노드를 생성함 | **가짜 노드 없이 꺾쇠(`<< >>`)로 화살표를 직접 감쌈** |
| **트리플(Triple) 개수** | 출처 1개를 달기 위해 총 **5줄**의 코드가 필요함 | **단 1줄**로 완벽하게 처리됨 |
| **데이터베이스 용량** | 100만 건의 사료가 500만 건으로 끔찍하게 팽창함 | 데이터베이스의 용량 팽창이 없음 |

## 3. 실전 적용: 구체화의 저주를 RDF-star로 정화하기

이 끔찍한 저주가 코드로 어떻게 생겼는지, 그리고 우리가 배운 최신 문법이 이를 어떻게 구원했는지 조선시대 원균 장군의 전사 기록을 통해 직관적으로 비교해 보겠습니다.

**[과거의 끔찍한 방식: 구체화(Reification)]**
```turtle
# 1. 원균이 칠천량에서 전사했다는 "가짜 마네킹 노드(_:stmt1)"를 생성합니다.
_:stmt1 a rdf:Statement ;
        rdf:subject joseon:원균 ;
        rdf:predicate core:전사하다 ;
        rdf:object event:칠천량해전 .

# 2. 조립이 끝난 가짜 마네킹에 출처를 붙입니다. (너무 길고 가독성이 최악입니다)
_:stmt1 core:statedIn source:선조실록 .
```

**[현대의 우아한 방식: RDF-star]**
```turtle
# 1. 마네킹 따위는 만들지 않습니다. 화살표 전체를 꺾쇠(<< >>)로 감싸고 바로 출처를 붙입니다.
<< joseon:원균 core:전사하다 event:칠천량해전 >> core:statedIn source:선조실록 .
```

코드를 눈으로 직접 확인하는 순간, 디지털 인문학 아키텍트로서 왜 우리가 반드시 최신 엔진(Blazegraph 등)을 도입하여 "**RDF-star**" 문법을 써야 하는지 그 지적 희열과 철학적 당위성을 뼈저리게 느낄 수 있습니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 피눈물: "조선왕조실록 데이터를 넣었더니 검색 속도가 100배 느려졌습니다!"**

만약 여러분이 과거의 논문이나 오래된 교재를 보고 "**구체화(Reification)**" 방식으로 사료의 출처를 맵핑했다고 가정해 봅시다. 
100만 건의 실록 데이터는 구체화 마네킹을 거치며 500만 건의 데이터로 무한 팽창합니다. 더 끔찍한 것은 정보를 조회할 때 사용하는 "**SPARQL**" 쿼리입니다. 
"선조실록에 기록된 원균의 전사 장소를 찾아라"라는 단순한 질문을 던지기 위해, 기계는 500만 개의 데이터 속에서 `rdf:Statement`, `rdf:subject`, `rdf:predicate`, `rdf:object`를 모두 찾아 조인(JOIN)하는 미친듯한 연산을 수행해야 합니다. 결국 서버의 메모리가 폭발하며 영원한 멈춤 상태에 빠지게 됩니다.

**[승리하는 아키텍트의 데이터 마이그레이션(Migration) 원칙]**
디지털 인문학계에 존재하는 수많은 레거시(과거) 데이터베이스들은 아직도 이 구체화 방식으로 묶여 있는 경우가 많습니다. 유능한 아키텍트라면 외부 기관에서 데이터를 건네받았을 때, 코드 안에 `rdf:Statement`라는 단어가 섞여 있는지 매의 눈으로 감시해야 합니다. 만약 발견된다면 파이프라인(ETL) 단계에서 SPARQL `CONSTRUCT` 구문을 활용하여 과거의 구체화 쓰레기들을 우아한 `<< s p o >>` 형태의 "**RDF-star**" 문법으로 일괄 변환(Cleansing)하는 정화 작업을 반드시 선행해야만 시스템의 붕괴를 막을 수 있습니다.

## 5. 요약 및 다음 단계

* 과거에는 화살표에 출처를 달기 위해 가짜 마네킹 노드를 4개나 생성하는 기형적인 "**구체화(Reification)**" 꼼수를 사용했습니다.
* 이 낡은 방식은 데이터베이스를 5배로 팽창시키고 SPARQL 쿼리를 지옥으로 만드는 치명적인 성능 저하의 저주를 낳았습니다.
* "**RDF-star**"는 이 저주를 끊어내고, 꺾쇠(`<< >>`) 하나로 가장 직관적이고 가벼운 인문학적 출처 표기를 완성한 시맨틱 웹의 위대한 혁신입니다.

이제 우리는 왜 RDF-star가 등장해야만 했는지, 그 역사적이고 공학적인 배경을 완벽하게 이해했습니다. 
그렇다면 이 혁신적인 꺾쇠(`<< >>`) 문법, 이른바 "**중첩 트리플(Nested Triples)**"을 활용하여 얽히고설킨 복잡한 조선시대 당파 싸움의 이설들을 어떻게 구조적으로 모델링할 수 있을까요?

다음 장인 "**26.2. 중첩 트리플(<< s p o >>)을 이용한 모델링**"으로 진입하여, 하나의 사실을 둘러싸고 여러 사료가 각기 다른 주장을 펼치는 다차원적인 역사 데이터를 가장 논리적이고 우아하게 코딩하는 최고급 아키텍처 설계를 직접 실습해 보겠습니다!
