# 32.2. 교착어 난제 극복: 종성 연산을 통한 조사 결합 엔진

## 1. 도입: 비싼 유령 작가를 해고해야 하는 "오프라인"의 현실

앞선 32.1장에서 우리는 기계의 딱딱한 데이터(Triple)를 인간의 문장으로 유려하게 바꿔주는 "**LLM 하이브리드 버벌라이제이션**"의 위력을 확인했습니다. 인공지능이라는 천재 유령 작가는 한국어의 까다로운 조사(은/는/이/가)를 기가 막히게 맞춰주었습니다.

하지만 여러분이 국가 기관의 "폐쇄망(On-Premise)" 보안 환경에서 프로젝트를 진행하거나, 초당 수천 명의 대중이 접속하여 쿼리를 날리는 초대형 지식 포털을 운영하게 되었다고 가정해 보십시오. 
문장 하나를 예쁘게 다듬기 위해 매번 외부의 챗GPT API를 호출한다면, 서버 비용은 한 달 만에 수천만 원을 돌파할 것이며, 외부 망 접속이 차단된 서버에서는 아예 작동조차 하지 않습니다.

결국 디지털 인문학 아키텍트는 비싼 유령 작가(LLM)를 해고하고, 다시 차가운 파이썬(Python) 백엔드 코드로 돌아와야 합니다. 
우리의 미션은 명확합니다. **"인공지능의 도움 없이, 기계가 스스로 '이순신'에는 '은'을 붙이고, '선조'에는 '는'을 붙이는 100% 무결점의 한국어 문법 엔진을 만들어라!"**

## 2. 해결책 제시: 세종대왕과 컴퓨터 공학자의 만남, "**유니코드(Unicode) 종성 연산**"

한국어는 단어에 조사나 어미가 찰싹 달라붙는 전형적인 "**교착어(Agglutinative language)**"입니다. 그리고 조사의 형태를 결정하는 유일한 물리적 법칙은 바로 앞 단어 맨 끝 글자의 **"받침(종성, Jongseong)"** 존재 여부입니다.

기계의 뇌는 글자의 "모양"을 볼 수 없습니다. 대신 기계는 글자를 "**숫자(Unicode)**"로 인식합니다. 
놀랍게도, 한글을 유니코드에 등재한 위대한 컴퓨터 공학자들은 세종대왕의 창제 원리를 완벽한 수학적 행렬로 구현해 두었습니다. 

현대 한글 11,172자는 "가(44032)"부터 "힣(55203)"까지 규칙적인 숫자로 배열되어 있습니다. 이 배열의 핵심 비밀은 **"초성(19개) × 중성(21개) × 종성(28개)"**의 규칙입니다. 종성 28개 중 첫 번째(0번 인덱스)는 "받침이 없는 상태"를 의미합니다.
즉, 어떤 한글 글자의 유니코드 숫자에서 "가(44032)"를 뺀 뒤, 이를 **28로 나눈 나머지(Modulo)**를 구하면 그 글자의 받침 유무를 수학적으로 완벽하게 증명해 낼 수 있습니다!

| 연산 과정 | 예시 1: "신" (이순신) | 예시 2: "조" (선조) |
| :--- | :--- | :--- |
| **마지막 글자 추출** | "신" | "조" |
| **유니코드 변환 (`ord()`)** | 50880 | 51312 |
| **기준점(가, 44032) 빼기** | 50880 - 44032 = 6848 | 51312 - 44032 = 7280 |
| **28로 나눈 나머지 (`% 28`)** | 6848 % 28 = **16** (받침 있음!) | 7280 % 28 = **0** (받침 없음!) |
| **최종 조사 결합** | 이순신 + **"은"** | 선조 + **"는"** |

## 3. 실전 적용: 파이썬(Python) 자동 조사 결합 엔진 구축하기

이 위대한 수학적 공식을 활용하여, SPARQL에서 넘어온 어떤 단어든 올바른 조사를 찰떡같이 붙여주는 범용 파이썬 함수를 만들어 보겠습니다. 이 엔진은 LLM API 호출 없이 단 0.001초 만에 실행됩니다.

```python
def attach_josa(word, josa_type):
    # 1. 단어의 가장 마지막 글자 하나만 추출합니다.
    last_char = word[-1]
    
    # 2. 마지막 글자가 한글인지 확인합니다. ("가" ~ "힣" 범위 내인지)
    if "가" <= last_char <= "힣":
        # 3. [핵심] 유니코드 수학 연산: 44032를 빼고 28로 나눈 나머지를 구합니다.
        jongseong_index = (ord(last_char) - 44032) % 28
        
        # 나머지가 0보다 크면 받침(종성)이 존재하는 것입니다.
        has_jongseong = jongseong_index > 0
    else:
        # 한글이 아닌 경우(영어, 숫자 등) 안전망을 위해 괄호 형태로 반환합니다.
        return f"{word}({josa_type.split('/')[0]})"

    # 4. 사용자가 요청한 조사 타입에 따라 받침 유무를 판별하여 결합합니다.
    if josa_type == "은/는":
        return f"{word}은" if has_jongseong else f"{word}는"
    elif josa_type == "이/가":
        return f"{word}이" if has_jongseong else f"{word}가"
    elif josa_type == "을/를":
        return f"{word}을" if has_jongseong else f"{word}를"
    elif josa_type == "과/와":
        return f"{word}과" if has_jongseong else f"{word}와"
    elif josa_type == "으로/로":
        # 'ㄹ' 받침(인덱스 8)일 때는 예외적으로 '로'가 붙습니다. (예: "서울로")
        if jongseong_index == 8 or not has_jongseong:
            return f"{word}로"
        else:
            return f"{word}으로"
            
    return word

# 백엔드 테스트 실행
print(attach_josa("이순신", "은/는") + " " + attach_josa("거북선", "을/를") + " 건조했다.")
# 출력: "이순신은 거북선을 건조했다."

print(attach_josa("선조", "이/가") + " " + attach_josa("한양", "으로/로") + " 피난을 갔다.")
# 출력: "선조가 한양으로 피난을 갔다."
```

이 알고리즘이 서버에 이식되는 순간, 여러분의 시스템은 외부 인공지능의 도움 없이도 수백만 건의 트리플을 가장 자연스러운 한국어 서사로 쏟아내는 완벽한 독립 엔진으로 거듭납니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 치명적 실수: "영조 2는? 선조 1은? 숫자로 끝나는 데이터에서 에러가 납니다!"**

우리의 수학적 유니코드 엔진은 "한글" 앞에서는 무적입니다. 하지만 지식 그래프 데이터에는 `core:선조_1` (첫 번째 선조 데이터)이나 `1592` 같은 숫자로 끝나는 식별자 라벨이 무수히 많습니다. 

방금 짠 코드는 마지막 글자(`1` 또는 `2`)가 "가"와 "힣" 사이에 속하지 않으므로, 기계적으로 `선조_1(은)` 이라는 촌스러운 안전망 텍스트를 반환해 버립니다. 이는 서비스의 질을 크게 떨어뜨립니다.

**[승리하는 아키텍트의 숫자 발음 매핑술]**
이 문제를 해결하려면 아키텍트는 기계에게 **"숫자를 한국어로 발음하는 법"**을 가르쳐야 합니다. 
숫자 '1'은 "일"로 발음되므로 받침(ㄹ)이 있어서 "은/이/을"이 와야 하고, 숫자 '2'는 "이"로 발음되므로 받침이 없어 "는/가/를"이 와야 합니다.

코드의 상단에 다음과 같은 아라비아 숫자의 한글 발음 매핑(Mapping) 사전과 정규표현식을 추가하여 엔진을 2단계로 고도화해야 합니다.

```python
# 아라비아 숫자 끝자리의 한글 발음 매핑 사전
number_pronunciation = {
    '0': '영', '1': '일', '2': '이', '3': '삼', '4': '사', 
    '5': '오', '6': '육', '7': '칠', '8': '팔', '9': '구'
}

# (함수 내부 로직 추가)
last_char = word[-1]
if last_char.isdigit():
    # 마지막 글자가 아라비아 숫자일 경우, 사전을 통해 한글 발음으로 강제 변환합니다!
    last_char = number_pronunciation[last_char]
    
# 이후 유니코드 연산 로직을 그대로 태웁니다.
```

이러한 예외 처리(디테일)가 모일 때, 비로소 `선조_1은`, `영조_2는`과 같이 숫자로 끝나는 인문학 식별자 앞에서도 100% 무결점의 한국어 문법을 자랑하는 거대한 버벌라이제이션 파이프라인이 완성됩니다.

## 5. 요약 및 대단원 마무리 (모듈 8의 자연어 처리 종료)

* LLM을 사용할 수 없는 대규모 트래픽 혹은 폐쇄망 서버 환경에서는, 백엔드 코딩(Python)만으로 완벽한 조사 결합 엔진을 구현해야 합니다.
* 한글은 유니코드의 수학적 행렬(`초성 × 중성 × 종성`) 구조로 설계되어 있으므로, 마지막 글자에서 기준점을 빼고 28로 나누는 "나머지(Modulo) 연산"을 통해 받침(종성) 유무를 100% 판별해 낼 수 있습니다.
* 아라비아 숫자로 끝나는 라벨의 경우, 숫자를 한글 발음(`1 ➔ 일`)으로 치환한 뒤 유니코드 연산을 수행하는 예외 처리 방어술이 반드시 적용되어야 합니다.

축하합니다! 이제 여러분의 조선시대 지식 그래프는 기계어(SPARQL)에서 시작하여, 환각이 제거된 검색(Graph RAG)을 거치고, 마침내 세종대왕의 창제 원리를 품은 완벽한 한국어 문장(Verbalization)으로 대중의 모니터에 도달했습니다.
