# 8.2. 글로벌 허브 연계: 위키데이터 Q-ID와 owl:sameAs 기반의 조인(JOIN) 알고리즘

## 1. 도입: 이름표가 다르면 남남인가요?

우리는 지난 장에서 `SERVICE` 키워드를 사용해 인터넷 선 너머 위키데이터(Wikidata) 서버의 지식을 소환하는 마법을 배웠습니다. 하지만 실전에서 이 마법을 부리려고 하면 곧바로 거대한 장벽에 가로막히게 됩니다. 바로 `"**식별자의 불일치**"` 문제입니다.

여러분의 연구소 서버에서는 '홍대용'을 `http://조선.kr/person/P00456`이라고 부릅니다. 하지만 위키데이터에서는 그를 `https://www.wikidata.org/entity/Q625121`이라고 부릅니다. 기계의 입장에서 이 두 주소는 완전히 다른 외계어일 뿐입니다. 

기계에게 "우리 서버의 P00456과 위키데이터의 Q625121은 사실 같은 존재야!"라고 가르쳐주지 않는다면, 아무리 `SERVICE` 구문을 화려하게 써도 두 데이터는 결코 하나로 합쳐지지(JOIN) 않습니다. 서로 다른 우주에 살고 있는 데이터들을 하나의 선으로 묶어주는 강력한 `"**시맨틱 접착제**"`가 필요합니다.

## 2. 해결책 제시: 데이터의 도플갱어 선언, owl:sameAs

시맨틱 웹의 표준 온톨로지(OWL)에는 이 문제를 해결하기 위한 인류 역사상 가장 강력한 술어(Predicate)가 정의되어 있습니다. 바로 `"**owl:sameAs**"`입니다.



`owl:sameAs`는 "이 주소와 저 주소는 전 우주에서 완벽하게 동일한 개체(Entity)를 가리킨다"라는 절대적인 선언입니다. 이 선언이 지식 그래프에 한 줄 들어가는 순간, 기계는 두 URI를 하나의 존재로 인식하고 양쪽 서버에 흩어진 속성들을 자유자재로 끌어와 합치기 시작합니다. 

특히 전 세계 지식의 허브인 위키데이터의 고유 번호(Q-ID)를 우리 데이터와 `owl:sameAs`로 연결하는 작업은, 우리 연구소의 좁은 우물을 전 세계의 광활한 정보 바다와 연결하는 `"**LOD의 고속도로**"`를 뚫는 것과 같습니다.

## 3. 실전 적용: owl:sameAs를 활용한 실시간 데이터 병합 쿼리

이제 실제로 우리 서버의 데이터와 위키데이터를 `owl:sameAs`라는 징검다리를 통해 합쳐보겠습니다. 우리 서버에 "P00456(홍대용)은 위키데이터의 Q625121과 같다"라는 데이터가 이미 입력되어 있다고 가정합니다.

```sparql
PREFIX owl: [http://www.w3.org/2002/07/owl#](http://www.w3.org/2002/07/owl#)
PREFIX wd: [http://www.wikidata.org/entity/](http://www.wikidata.org/entity/)
PREFIX wdt: [http://www.wikidata.org/prop/direct/](http://www.wikidata.org/prop/direct/)
PREFIX 속성: [http://조선.kr/prop/](http://조선.kr/prop/)

SELECT ?이름 ?위키데이터설명 ?이미지
WHERE {
  # [1] 로컬 탐색: 우리 서버에서 인물의 이름과 'sameAs' 링크를 찾습니다.
  ?인물 속성:이름 ?이름 .
  ?인물 owl:sameAs ?위키ID . # 여기서 ?위키ID는 [http://www.wikidata.org/entity/Q625121](http://www.wikidata.org/entity/Q625121) 이 됩니다.

  # [2] 원격 연합: 찾아낸 ?위키ID를 들고 위키데이터 서버로 건너갑니다.
  SERVICE [https://query.wikidata.org/sparql](https://query.wikidata.org/sparql) {
    # 위키데이터 서버에게 ?위키ID에 대한 설명과 사진 주소를 요청합니다.
    ?위키ID rdfs:comment ?위키데이터설명 .
    ?위키ID wdt:P18 ?이미지 . # P18은 위키데이터의 'image' 속성입니다.
    
    # 한국어 설명만 골라내는 필터 (에티켓!)
    FILTER (lang(?위키데이터설명) = "ko")
  }
}
```

**작동 원리 해부:**
1. 기계는 로컬 서버에서 `owl:sameAs` 관계를 통해 홍대용의 위키데이터 주소(Q625121)를 확보합니다.
2. 이 주소를 `"**조인 키(Join Key)**"`로 삼아 위키데이터 서버에 접속합니다.
3. 위키데이터는 자신이 가진 전 세계 수만 장의 사진 중 Q625121에 해당하는 사진을 찾아 우리에게 돌려줍니다.
4. 최종적으로 여러분의 화면에는 우리 서버의 `"홍대용"` 이름 옆에, 위키데이터에서 실시간으로 긁어온 `"실학자이자 천문학자..."`라는 설명과 `"초상화 이미지"`가 나란히 출력됩니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

"교수님, `owl:sameAs`가 그렇게 강력하다면 세상의 모든 비슷한 데이터들을 다 이 걸로 묶어버리면 안 될까요?"

신입 연구원들이 의욕에 앞서 저지르는 가장 위험한 실수가 바로 `"**무분별한 sameAs 남용**"`입니다. `owl:sameAs`는 논리학적으로 매우 엄격한 관계입니다. A와 B가 `sameAs`라면, A가 가진 모든 더러운 속성과 오염된 정보도 B의 것이 됩니다.

**[시맨틱 아키텍트의 실무 가이드: 유사성과 동일성의 구분]**
* **역사적 인물:** 홍대용(우리 서버)과 홍대용(위키데이터)은 생몰년도와 업적이 일치하므로 `owl:sameAs`를 써도 무방합니다.
* **지명과 장소:** '조선 시대의 한양'과 '현재의 서울'은 지리적으로 겹치지만 인문학적 맥락과 경계가 완전히 다릅니다. 이 둘을 `owl:sameAs`로 묶어버리면 "서울은 1394년에 건국되었다"라는 논리적 모순이 발생합니다.
* **해결책:** 대상이 완벽하게 일치하지 않고 단순히 관련이 있는 정도라면 `owl:sameAs` 대신, 조금 더 느슨한 관계인 `"**skos:exactMatch**"`나 `"**rdfs:seeAlso**"`를 사용하는 것이 학술적 데이터의 무결성을 지키는 현명한 선택입니다.

## 5. 요약 및 다음 단계

* `owl:sameAs`는 서로 다른 URI를 가진 두 개체가 전 우주적으로 동일함을 선언하는 최상위 시맨틱 접착제입니다.
* 위키데이터의 Q-ID와 우리 데이터를 `owl:sameAs`로 매핑하면, 전 세계의 방대한 외부 지식을 우리 데이터처럼 실시간으로 활용할 수 있습니다.
* 다만, `sameAs`는 논리적 파급력이 매우 크므로, 역사적 맥락이 조금이라도 다르다면 `skos:exactMatch` 등의 느슨한 관계를 검토해야 합니다.

이제 우리는 전 세계의 서버를 넘나들며 데이터를 합치는 법을 배웠습니다. 하지만 연합 질의는 인터넷 선을 타고 원격으로 데이터를 가져오기 때문에 속도가 느려지거나 오류가 날 위험이 큽니다.
