# 29.1. 구글을 위한 데이터 아일랜드: JSON-LD 아키텍처

## 1. 도입: 도자기 표면에 직접 보증서를 새겨 넣던 과거의 악몽

앞선 29장의 도입부에서 우리는 구글 검색 로봇에게 지식 그래프를 온전히 전달하기 위해 웹페이지 뒷면에 몰래 보증서를 심어두는 전략을 배웠습니다. 그리고 그 보증서의 포맷으로 구글이 가장 사랑하는 "**JSON-LD**"를 소개했습니다.

하지만 시맨틱 웹의 역사를 되짚어보면, 구글이 처음부터 JSON-LD를 권장했던 것은 아닙니다. 과거의 학자들과 개발자들은 웹페이지에 지식을 심기 위해 "**마이크로데이터(Microdata)**" 또는 "**RDFa**"라는 매우 고통스럽고 파괴적인 방식을 사용했습니다. 

인문학적으로 비유하자면, 마이크로데이터 방식은 조선시대 백자(웹페이지 화면)가 진짜임을 증명하기 위해, 백자의 아름다운 표면(HTML 태그) 위에 검은색 매직으로 빽빽하게 "이름: 백자, 제작 연도: 15세기"라고 보증서 내용을 직접 낙서해 버리는 것과 같습니다. 화면을 예쁘게 꾸미는 디자인 코드(`<div>`, `<span>`)와 기계가 읽어야 하는 시맨틱 데이터(`itemprop`, `itemtype`)가 하나의 줄에 끔찍하게 뒤섞여 버린 것입니다. 이로 인해 디자이너와 데이터 아키텍트 모두가 지옥을 맛보아야 했습니다.

## 2. 해결책 제시: 화면과 데이터의 완벽한 분리, "**데이터 아일랜드(Data Island)**"

이 끔찍한 혼돈을 끝내기 위해 등장한 모던 웹의 위대한 철학이 바로 "**데이터 아일랜드(Data Island)**" 아키텍처입니다. 그리고 이 철학을 완벽하게 구현한 기술이 바로 "**JSON-LD**"입니다.

데이터 아일랜드란 직역하면 "**데이터의 섬**"입니다. 백자의 표면(HTML 화면)에는 그 어떤 매직 낙서도 하지 않습니다. 백자는 온전히 디자이너의 영역으로 남겨두어 가장 아름답게 전시합니다. 대신, 백자를 받치고 있는 전시대 밑바닥에 잘 정리된 "독립된 보증서 봉투(JSON-LD 블록)"를 살짝 숨겨두는 것입니다. 

화면을 그리는 코드와 데이터를 담은 코드가 물리적으로 완벽하게 분리되어 서로의 영역을 침범하지 않습니다. 구글의 로봇은 화려한 백자 표면을 훑어보느라 고생할 필요 없이, 밑바닥의 봉투(섬)만 쏙 빼가서 데이터를 100%의 정확도로 수집해 갑니다.

| 비교 항목 | 마이크로데이터 (과거의 악몽) | JSON-LD (모던 웹의 표준) |
| :--- | :--- | :--- |
| **작동 방식** | HTML 태그 속성에 데이터를 직접 주입함 | **HTML과 독립된 `<script>` 태그 안에 데이터만 따로 모아둠** |
| **코드 가독성** | 디자인 태그와 데이터가 뒤섞여 스파게티 코드가 됨 | **구조화된 JSON 형태로 가독성이 극대화됨** |
| **유지 보수** | 화면 디자인을 수정하면 데이터 구조도 함께 파괴됨 | **화면을 뜯어고쳐도 데이터 보증서는 전혀 타격을 입지 않음** |

## 3. 실전 적용: 세종대왕 웹페이지의 끔찍한 과거와 우아한 현재

"세종대왕"을 소개하는 간단한 웹페이지를 만들 때, 과거의 방식과 현재의 JSON-LD 방식이 어떻게 다른지 코드를 통해 극명하게 대비해 보겠습니다.

**[과거의 끔찍한 방식: 마이크로데이터]**
디자인 요소인 `<h1>`, `<span>` 태그 안에 시맨틱 데이터 속성(`itemscope`, `itemprop`)이 기생충처럼 파고들어 있습니다.

```html
<div itemscope itemtype="[http://schema.org/Person](http://schema.org/Person)">
  <h1 itemprop="name">세종대왕</h1>
  <p><span itemprop="jobTitle">조선의 제4대 국왕</span>으로, 훈민정음을 창제하셨습니다.</p>
</div>
```

**[모던 웹의 우아한 방식: JSON-LD 데이터 아일랜드]**
인간이 보는 화면 코드(HTML)와 기계가 보는 데이터 코드(JSON-LD)를 완벽하게 분리했습니다.

```html
<div>
  <h1>세종대왕</h1>
  <p>조선의 제4대 국왕으로, 훈민정음을 창제하셨습니다.</p>
</div>

<script type="application/ld+json">
{
  "@context": "[http://schema.org](http://schema.org)",
  "@type": "Person",
  "name": "세종대왕",
  "jobTitle": "조선의 제4대 국왕"
}
</script>
```

눈으로 보기만 해도 개발자의 인지적 과부하가 사라지는 것을 느낄 수 있습니다. 이것이 구글이 전 세계의 모든 웹마스터에게 JSON-LD만을 강제하다시피 권장하는 결정적인 이유입니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 절망: "웹페이지 폰트 크기를 바꿨더니, 구글 검색 순위가 폭락했습니다!"**

이것은 아직도 과거의 마이크로데이터(Microdata) 방식을 버리지 못한 구형 플랫폼(예: 오래된 워드프레스 테마나 그누보드)에서 100% 발생하는 대참사입니다. 

어느 날 디자이너가 "세종대왕"이라는 글자가 너무 작다며, `<h1>` 태그를 지우고 `<div>` 태그에 복잡한 CSS 클래스를 덕지덕지 붙여서 화면을 개편했다고 가정해 봅시다. 
과거 방식에서는 `<h1>` 태그 안에 `itemprop="name"`이라는 핵심 시맨틱 데이터가 들어 있었습니다. 디자이너가 화면을 예쁘게 고치려고 태그를 지우는 순간, 구글에게 전달되던 "이름: 세종대왕"이라는 핵심 데이터도 허공으로 함께 날아가 버린 것입니다. 구글 봇은 다음 날 방문하여 "이 페이지는 이제 누구를 설명하는지 알 수 없는 쓰레기 페이지다"라고 판정하고 검색 순위를 나락으로 떨어뜨립니다.

**[승리하는 아키텍트의 방화벽(Firewall) 구축술]**
이러한 디자인 부서와 데이터 부서 간의 참혹한 충돌을 막기 위해, 총괄 아키텍트는 프로젝트 초기에 반드시 **"JSON-LD 강제 도입"**을 선언해야 합니다.
JSON-LD를 도입하여 데이터 아일랜드를 구축하면, 프론트엔드 디자이너가 화면의 `<h1>`을 지우든, 표를 엎어버리든, 화려한 애니메이션을 넣든 구글의 검색 순위(SEO)에는 단 1%의 타격도 가지 않습니다. 데이터는 밑바닥의 `<script>` 섬 안에서 완벽하게 보호받고 있기 때문입니다. 화면의 잦은 개편이 필수적인 현대 웹 서비스에서 JSON-LD는 단순한 선택지가 아니라, 데이터의 생명줄을 지키는 가장 강력한 방화벽입니다.

## 5. 요약 및 다음 단계

* 화면의 HTML 태그 안에 데이터를 직접 새겨 넣던 과거의 "**마이크로데이터(Microdata)**" 방식은 코드의 가독성을 파괴하고 유지 보수를 지옥으로 만들었습니다.
* 이를 해결하기 위해 모던 웹은 인간을 위한 화면(HTML)과 기계를 위한 데이터(JSON-LD)를 물리적으로 분리하는 "**데이터 아일랜드(Data Island)**" 아키텍처를 채택했습니다.
* JSON-LD를 사용하면 웹페이지의 디자인이 수백 번 바뀌어도 검색엔진에 전달되는 시맨틱 지식망(SEO 데이터)은 전혀 훼손되지 않고 완벽하게 보호됩니다.

이제 우리는 구글 로봇에게 데이터를 전달하는 가장 우아한 그릇(JSON-LD)을 완벽하게 빚어냈습니다. 
하지만 그릇이 훌륭하다고 해서 구글 봇이 내용을 무조건 이해하는 것은 아닙니다. 
우리가 아무리 완벽한 JSON-LD를 만들어서 `"조선시대_관직명": "영의정"`이라고 적어주어도, 미국에 있는 구글 봇은 "조선시대_관직명"이라는 단어를 알아듣지 못합니다. 그들은 오직 전 세계 공용어인 "**Schema.org**" 단어장만 이해할 수 있습니다.

다음 장인 "**29.2. 인문학 사료의 Schema.org 매핑 전략**"으로 진입하여, 우리가 고집스럽게 구축해 온 한국학 전용 온톨로지 어휘들을 구글이 완벽하게 이해할 수 있는 글로벌 범용 어휘(Schema.org)로 솜씨 좋게 번역해 내는 시맨틱 통역의 정수를 마스터해 보겠습니다!
