# 23.1. 상향식(Protégé)에서 하향식(Wikibase)으로의 인식론적 대전환

## 1. 도입: 철학의 충돌, "완벽한 설계도(뼈대)가 먼저인가, 사실(살)이 먼저인가?"

Wikibase라는 거대한 협업 시스템을 우리 연구실 서버에 기술적으로 올리기 전에, 디지털 인문학자로서 우리는 머릿속에 자리 잡은 '데이터 모델링 철학'을 전면적으로 수정해야 합니다. 

우리가 17장부터 20장까지 혹독하게 훈련했던 **Protégé(프로테제)**는 극도로 연역적이고 수학적인 도구입니다. 
"클래스(Class)를 먼저 정의하고, 그 하위에 정교한 계층 구조를 만들며, 속성(Property)이 가질 수 있는 주어와 목적어의 자격(Domain과 Range)을 명확히 제한한 뒤에야 비로소 인물 데이터(Instance)를 넣는다." 
이것은 완벽한 논리적 뼈대(T-box)를 밑바닥부터 탄탄하게 세우고, 그 구조적 기반 위에 개별적인 사실(A-box)을 쌓아 올리는 **상향식(Bottom-up) 아키텍처**입니다.

하지만 역사학이나 문학, 철학 등 인문학의 사료는 이토록 수학 공식처럼 깔끔하게 떨어지지 않습니다. 방목이나 실록을 읽다 보면 처음에 온톨로지를 설계할 때는 전혀 예상치 못했던 새로운 관계(예: '사약을 받음', '적파와 서파의 갈등', '꿈에 나타남')가 끝없이 튀어나옵니다. Protégé 체제에서는 이렇게 예외적인 관계가 나올 때마다 연구를 멈추고, 온톨로지 설계자가 T-box를 다시 뜯어고친 뒤 추론기(Reasoner)의 충돌(Inconsistency)이 없는지 확인하는 극심한 피로가 동반됩니다. 완벽주의가 오히려 데이터 구축의 발목을 잡는 것입니다.

## 2. 해결책 제시: Wikibase의 하향식(Top-down) 융통성과 개방성

Wikibase는 이러한 온톨로지 강박관념에서 우리를 완전히 해방시킵니다. 철저하게 **"데이터 중심(Data-centric)"**이자, 일단 사료에 등장하는 사실(Fact)들을 캔버스에 툭툭 던져놓고 필요에 따라 관계를 엮어 나가는 **하향식(Top-down) 유연성**을 제공합니다.

| 철학적 특징 | Protégé 기반 모델링 (상향식) | Wikibase 기반 모델링 (하향식) |
| :--- | :--- | :--- |
| **모델링 순서** | 스키마(온톨로지) 완벽 설계 ➔ 데이터 입력 | **데이터(아이템) 자유 입력 ➔ 필요할 때 속성(Property) 즉석 생성** |
| **속성(Property)의 대우** | URI를 미리 선언하고 제약조건(Domain/Range)을 엄격히 논리적으로 검사 | **GUI 화면에서 '새 속성 만들기' 버튼을 눌러 즉시 생성 후 즉시 사용** |
| **개체 식별자 부여** | 사람이 직접 URI 문자열을 고안하여 작명 (예: `joseon:Min_Yeong_hwan`) | **시스템이 의미가 배제된 절대 숫자 식별자를 자동 부여 (예: `Q42`)** |
| **인문학적 적합성** | 잘 정제된 소규모 확정 데이터, 명확한 분류 체계 구축에 유리 | **계속해서 변화하고 팽창하는 미지의 대규모 사료 융합에 압도적 유리** |

## 3. 핵심 기술: Q-node와 P-node가 빚어내는 언어의 해방

Wikibase 생태계에 들어서면, 우리는 더 이상 긴 영문 URI나 복잡한 클래스 계층구조로 머리를 싸매지 않습니다. 세상의 모든 지식을 오직 두 가지 단위로 쪼개어 관리합니다.

1. **Item (아이템 / Q-node):** 세상에 존재하는 모든 명사(인물, 장소, 사건, 개념)입니다. '이순신'을 생성하면 시스템이 무심하게 **`Q1`**이라는 고유 번호를 던져줍니다. '한양'을 만들면 **`Q2`**가 됩니다.
2. **Property (속성 / P-node):** Q-node 사이를 잇는 화살표(서술어)입니다. '태어난 곳'이라는 속성을 만들면 **`P1`**이 부여됩니다.

이제 연구원은 복잡한 거북이(Turtle) 문법을 몰라도, 웹 브라우저에서 `Q1(이순신)` 화면을 열고, 속성에 `P1(태어난 곳)`, 값에 `Q2(한양)`를 입력하는 것만으로 완벽한 시맨틱 트리플 구조를 생성하게 됩니다.

**[인문학적 통찰: 무의미한 숫자가 가져온 다국어의 기적]**
식별자에 영단어(`hasBirthPlace`)를 쓰지 않고 `P1`, `Q1`처럼 무의미한 숫자를 쓰는 것은 놀라운 기적을 만들어냅니다. `Q1`이라는 본질적인 식별자 위에 한국어 라벨로는 "이순신", 영어 라벨로는 "Yi Sun-sin", 한자로는 "李舜臣"이라는 포스트잇을 무한대로 붙일 수 있습니다. 프랑스 학자가 프랑스어로 접속하면 `Q1`이 "Yi Sun-sin"으로 보이고, 한국 학자에게는 "이순신"으로 보입니다. 특정 언어나 철자에 종속되지 않는 진정한 글로벌 지식 그래프가 완성되는 지점입니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 두려움: "교수님! Domain과 Range 제약이 없으면 데이터가 엉망진창(Garbage)이 되지 않습니까?"**

Protégé의 엄격함에 익숙해진 대학원생들은 Wikibase의 이 자유로움에 극도의 불안을 느낍니다. 
"아무나 '태어난 곳(P1)'의 목적어에 장소(Q2)가 아니라 사람(Q3)을 집어넣어 버리면 어떻게 합니까? 추론기가 에러를 잡아주지도 않잖아요!"

**[승리하는 아키텍트의 소프트 제약(Soft Constraint) 활용법]**
Wikibase가 유연하다고 해서 데이터의 무결성을 포기한 것은 아닙니다. 
Protégé가 데이터를 아예 입력조차 못 하게 막는 **'하드 제약(Hard Constraint)'**을 쓴다면, Wikibase는 일단 입력은 받아주되 빨간색 경고창을 띄워주는 **'소프트 제약(Soft Constraint)'** 방식을 씁니다.

Wikibase에서 '태어난 곳(P1)'이라는 속성(Property) 페이지를 엽니다. 이곳에 **"이 속성의 값 유형 제약조건(Value type constraint)"**을 선언해 둘 수 있습니다. 만약 누군가 '장소'가 아닌 '사람'을 목적어에 넣으면, 화면에 붉은색 깃발 아이콘과 함께 "이 속성의 값은 지리적 장소여야 합니다"라는 경고 메시지가 출력됩니다. 데이터의 유연한 확장을 막지 않으면서도, 연구자들의 입력 실수를 친절하게 교정해 주는 진정한 협업 시스템의 지혜입니다.

## 5. 요약 및 다음 단계

* 복잡하고 유동적인 인문학 사료를 구축하기 위해서는 스키마를 100% 설계한 뒤 데이터를 넣는 Protégé(상향식) 방식보다, **데이터를 먼저 입력하고 속성을 유연하게 엮어나가는 Wikibase(하향식)** 방식이 훨씬 적합합니다.
* Wikibase는 세상의 모든 개념을 **Item(Q-node)**으로, 관계를 **Property(P-node)**라는 숫자로 치환하여 특정 언어에 종속되지 않는 완벽한 다국어 지식망을 구축합니다.
* 데이터 무결성에 대한 우려는 융통성 없는 사전 차단(Hard Constraint)이 아니라, 시스템이 제공하는 **소프트 제약조건(경고 시스템)**을 통해 협업 과정에서 자연스럽게 교정됩니다.
