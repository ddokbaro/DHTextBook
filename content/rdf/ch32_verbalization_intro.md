# 32장. 트리플 자연어 변환(Verbalization)과 한국어 처리

## 1. 도입: 기계의 정답은 왜 이토록 차갑고 불친절한가?

우리는 31장을 거치며 "이순신 장군이 처음 출전한 해전이 무엇인가?"라는 사용자의 자연어 질문(NLQ)을 인공지능이 SPARQL로 완벽하게 번역해 내는 기적(Graph RAG)을 맛보았습니다. 이 완벽한 쿼리를 받은 지식 그래프 서버(Virtuoso)는 단 0.1초 만에 오류 없는 100% 팩트의 정답을 찾아냅니다.

하지만 데이터베이스가 사용자에게 최종적으로 뱉어낸 결과물을 보십시오.
**`[ { "event": "http://dh.aks.ac.kr/joseon/사천해전" }, { "event": "http://dh.aks.ac.kr/joseon/당포해전" } ]`**

이것은 정답이 맞습니다. 하지만 일반 대중이나 역사학자가 스마트폰 화면에서 이런 흉측한 JSON 껍데기와 `http://...` 로 시작하는 기계의 식별자(URI)를 보고 싶어 할까요? 사용자는 차가운 데이터의 파편이 아니라, **"이순신 장군이 처음 출전한 해전은 사천해전과 당포해전입니다."**라는 따뜻하고 친절한 "**인간의 서사(Narrative)**"를 원합니다. 

질문을 기계의 언어로 통역하는 데 성공했다면, 이제 기계의 대답을 다시 인간의 언어로 통역하여 돌려주는 마지막 다리가 필요합니다.

## 2. 해결책 제시: 팩트에 온기를 불어넣는 마법, "**자연어 변환(Verbalization)**"

컴퓨터 공학에서는 기계의 형태소(Triple, URI)를 인간이 읽기 편한 일상적인 문장으로 길어 올리는 이 기술을 "**자연어 변환(Verbalization, 버벌라이제이션)**"이라고 부릅니다.

인문학적으로 비유하자면, 지식 그래프 서버는 창고에서 갓 캐낸 "**날것의 식재료(Fact)**"를 던져주는 사냥꾼입니다. 사냥꾼이 던진 피 묻은 고기와 흙 묻은 감자를 그대로 식탁에 올릴 수는 없습니다. 우리는 이 재료들을 다듬고, 양념을 치고, 예쁜 접시에 담아내는 "**궁중 요리사(Verbalizer)**"의 아키텍처를 세워야 합니다.

요리사는 기계가 건네준 `주어(Subject) - 서술어(Predicate) - 목적어(Object)`라는 3단어의 트리플 구조를 해체한 뒤, 인간의 문법 규칙에 맞게 조사와 어미를 붙여 매끄러운 한 줄의 역사적 문장으로 재조립합니다.

| 데이터 처리 단계 | 기계의 형태 (RDF Triple) | 인간의 형태 (Verbalization) |
| :--- | :--- | :--- |
| **원시 데이터 (Raw)** | `joseon:이순신` `core:hasPost` `joseon:전라좌수사` | 텍스트 조각들의 뭉치 |
| **단어 추출 (Labeling)** | "이순신", "관직", "전라좌수사" | 식별자(URI)에서 라벨 텍스트 분리 |
| **자연어 변환 (Verbalized)** | **"이순신은 전라좌수사라는 관직을 가졌다."** | **완벽한 인간의 역사 서사 문장** |

## 3. 실전 적용: 트리플을 한국어 문장으로 조립하는 기본 원리

가장 기초적인 자연어 변환은 여러분이 백엔드 서버(Python 등)에 미리 만들어둔 "**템플릿(문장 틀)**"에 기계가 가져온 단어를 쏙쏙 끼워 넣는 방식으로 이루어집니다.

만약 SPARQL 쿼리 결과로 `?subject`(이순신), `?predicate`(전사하다), `?object`(노량해전) 이라는 3개의 텍스트를 얻었다고 가정해 봅시다. 
백엔드 아키텍트는 서술어(`?predicate`)의 종류에 따라 각기 다른 문장 틀을 준비해 둡니다.

```python
# 파이썬 기반의 기초적인 자연어 변환(Verbalization) 템플릿 로직

subject = "이순신"
predicate = "전사하다"  # core:diedAt 속성에서 추출한 라벨
object_val = "노량해전"

# 1. 서술어가 "전사하다(diedAt)"일 경우의 문장 템플릿
if predicate == "전사하다":
    # 템플릿: [주어] 장군은 [목적어]에서 전사하셨습니다.
    sentence = f"{subject} 장군은 {object_val}에서 전사하셨습니다."

# 2. 서술어가 "임명되다(hasPost)"일 경우의 문장 템플릿
elif predicate == "임명되다":
    sentence = f"{subject} 장군은 {object_val}에 임명되셨습니다."

print(sentence)
# 출력 결과: "이순신 장군은 노량해전에서 전사하셨습니다."
```

이렇게 미리 준비된 거푸집(템플릿)을 통과하는 순간, 기계의 차가운 팩트는 비로소 인간이 읽고 감동할 수 있는 훌륭한 역사 교과서의 한 구절로 재탄생합니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 절망: "이순신는 노량해전를 승리했습니다? 기계가 외국인처럼 말합니다!"**

영어 기반의 지식 그래프를 다루던 서양의 아키텍트들은 자연어 변환(Verbalization)을 아주 쉽게 생각합니다. 영어는 `Subject(John) + Predicate(likes) + Object(Apple)`를 그대로 이어 붙이면 완벽한 문장("John likes Apple")이 되기 때문입니다.

하지만 한국의 디지털 인문학 아키텍트들에게는 전 세계에서 가장 끔찍하고 가혹한 문법적 시련이 기다리고 있습니다. 바로 "**교착어(Agglutinative language)**"로서의 한국어가 가진 "**조사(은/는/이/가/을/를)**"의 저주입니다.

위의 파이썬 템플릿 코드에서 `f"{subject}는 {object_val}를..."` 이라고 고정된 조사를 박아두었다고 가정해 봅시다.
* 데이터가 `subject="선조"`, `object_val="임진왜란"` 이면 ➔ **"선조는 임진왜란를..."** (어색함)
* 데이터가 `subject="이순신"`, `object_val="한산도"` 이면 ➔ **"이순신는 한산도를..."** (매우 어색함)

**[승리하는 아키텍트의 종성(받침) 판별술]**
한국어에서 조사를 결정하는 유일하고 절대적인 규칙은 바로 앞 단어의 마지막 글자에 **"받침(종성, Jongseong)"**이 있는지 없는지입니다. 
"선조"는 받침이 없으므로 '는/를'이 와야 하고, "이순신"은 '신(ㄴ)'이라는 받침이 있으므로 '은/을'이 와야 합니다. 기계는 이 글자 모양을 전혀 모르기 때문에, 템플릿에 고정된 조사를 쓰면 100% 외국인이 어눌하게 말하는 듯한 치명적인 시스템 결함이 발생합니다.

따라서 한국어 지식 그래프의 자연어 변환 파이프라인에는, 문장을 조립하기 직전에 단어의 맨 끝 글자 유니코드(Unicode)를 수학적으로 분해하여 받침 유무를 판별하고 올바른 조사를 자동으로 끼워 넣는 "**형태소 처리 엔진**"이 반드시 동반되어야만 합니다.

## 5. 요약 및 다음 단계

* SPARQL 검색 결과로 도출된 차가운 식별자(URI) 덩어리를 인간이 읽기 편한 자연스러운 문장으로 번역하는 과정을 "**자연어 변환(Verbalization)**"이라고 합니다.
* 기본적인 변환은 백엔드에서 미리 준비한 템플릿(문장 틀)에 기계가 찾아온 주어와 목적어를 끼워 넣는 방식으로 팩트에 온기를 불어넣습니다.
* 영미권과 달리, 한국어는 단어의 결합 시 받침 유무에 따라 조사가 시시각각 변하는 극악의 "교착어" 난제를 뚫어내야만 완벽한 자연어 생성이 가능합니다.

이제 우리는 기계의 답변을 인간의 언어로 포장해야 하는 강력한 당위성과, 그 과정에서 마주칠 한국어 특유의 문법적 지뢰들을 모두 파악했습니다.

그렇다면, 수만 가지나 되는 역사적 상황(전투, 관직 임명, 유배, 사약 등)을 아키텍트가 일일이 파이썬 `if-else` 문으로 템플릿을 짜는 것이 과연 현실적인 일일까요? 이 고된 노동을 거대 언어 모델(LLM)의 생성 능력에 맡길 수는 없을까요?
