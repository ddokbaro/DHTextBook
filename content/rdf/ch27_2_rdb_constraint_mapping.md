# 27.2. RDB 제약조건의 시맨틱 매핑

## 1. 도입: 데이터를 이사할 때, "법률"은 누가 챙기는가?

우리는 24장에서 국가 기관의 거대한 관계형 데이터베이스(RDB)를 엑셀로 빼내지 않고, 가상 지식 그래프(VKG)를 통해 시맨틱 세계로 연결하는 훌륭한 파이프라인을 구축했습니다. 그리고 방금 전 27.1장에서는 지식망의 헌법인 "**형태 그래프(Shapes Graph)**"를 제정하여 데이터를 통제하는 법을 배웠습니다.

이제 이 두 세계를 합쳐볼 시간입니다. 인문학자로서 깊은 철학적 고민을 해봅시다. 
원래 한국학중앙연구원의 데이터베이스(MySQL) 안에는 DBA(데이터베이스 관리자)가 십수 년간 정성껏 설정해 둔 아주 깐깐한 "**제약조건(Constraints)**"들이 걸려 있었습니다. "이순신 장군의 이름 칸은 절대 비워둘 수 없다", "관직 코드는 반드시 관직 테이블에 있는 것만 써야 한다" 같은 엄격한 규칙들입니다.

그런데 우리가 이 표(Table) 형태의 데이터를 얽히고설킨 지식 그래프(RDF)로 변환하여 가져오는 순간, RDB가 가지고 있던 이 강력한 "법률"들은 허공으로 증발해 버립니다. 지식 그래프 서버는 RDB의 법률을 알아듣지 못하기 때문입니다. 법률이 사라진 무법지대에 데이터를 쏟아부으면, 결국 이름이 없는 유령 노드나 정체불명의 관직이 생겨나며 지식망은 처참하게 붕괴합니다. 

데이터만 이사(Migration)하는 것은 반쪽짜리 아키텍처입니다. 우리는 구시대의 낡은 "**법률(SQL 제약조건)**"을 새로운 세계의 "**헌법(SHACL)**"으로 우아하게 통역하여 이식해야만 합니다.

## 2. 해결책 제시: 구시대의 법전을 신대륙의 헌법으로 번역하다

컴퓨터 공학에서는 이 통역 과정을 "**시맨틱 매핑(Semantic Mapping)**"이라고 부릅니다. 
관계형 데이터베이스(RDB)의 문법인 "**SQL**"과 시맨틱 웹의 검증 문법인 "**SHACL**"은 서로 생긴 모습은 다르지만, 데이터를 엄격하게 통제하고자 하는 철학적 목적은 완벽하게 동일합니다.

디지털 인문학 아키텍트라면, RDB 설계도를 받아 든 즉시 머릿속에서 다음과 같은 번역기가 자동으로 돌아가야 합니다.

| RDB 제약조건 (구시대의 법률) | SHACL 번역 (신대륙의 헌법) | 인문학적 작동 원리 (조선시대 인물 예시) |
| :--- | :--- | :--- |
| `"**NOT NULL**"` (빈칸 금지) | `sh:minCount 1` | 인물 데이터에 "이름" 속성이 최소 1개는 반드시 존재해야 함을 강제합니다. |
| `"**FOREIGN KEY**"` (외래 키) | `sh:class` 또는 `sh:node` | 관직 임용 데이터의 목적어가 반드시 "관직(Post)" 클래스에 속한 노드여야 함을 강제합니다. |
| `"**CHECK (age >= 0)**"` (값 검증) | `sh:minInclusive 0` | 인물의 나이나 품계가 마이너스(-)가 되는 물리적 모순을 차단합니다. |
| `"**UNIQUE**"` (중복 금지) | `sh:maxCount 1` | 한 명의 인물이 2개의 "출생 연도"를 동시에 가지는 역사적 기적을 차단합니다. |

## 3. 실전 적용: MySQL 테이블 설계도를 SHACL로 통역하기

국사편찬위원회의 DBA가 여러분에게 "조선시대 관원(`Joseon_Official`)" 테이블의 SQL 설계도를 건네주었습니다. 

**[원본 RDB의 법률 (SQL)]**
```sql
-- 낡은 데이터베이스의 깐깐한 제약조건들
CREATE TABLE Joseon_Official (
    id INT PRIMARY KEY,
    name VARCHAR(50) NOT NULL,            -- 이름은 빈칸일 수 없다!
    post_id INT,                          -- 관직 코드 (빈칸일 수 있음)
    FOREIGN KEY (post_id) REFERENCES Post(id), -- 관직 코드는 반드시 Post 테이블에 존재해야 한다!
    birth_year INT CHECK (birth_year > 1300)   -- 출생 연도는 1300년도 이후여야 한다!
);
```

우리는 이 SQL 코드를 단 한 글자도 빠짐없이 완벽한 "**SHACL**" 거북이 문법으로 통역해야 합니다. 

**[통역된 신대륙의 헌법 (SHACL)]**
```turtle
@prefix sh: [http://www.w3.org/ns/shacl#](http://www.w3.org/ns/shacl#) .
@prefix joseon: [http://dh.aks.ac.kr/joseon/](http://dh.aks.ac.kr/joseon/) .
@prefix core: [http://dh.aks.ac.kr/ontology/core/](http://dh.aks.ac.kr/ontology/core/) .
@prefix xsd: [http://www.w3.org/2001/XMLSchema#](http://www.w3.org/2001/XMLSchema#) .

joseon:OfficialShape a sh:NodeShape ;
    sh:targetClass core:Person ;

    # 1. NOT NULL 번역: "이름은 빈칸일 수 없다"
    sh:property [
        sh:path core:hasName ;
        sh:datatype xsd:string ;
        sh:minCount 1 ; # [핵심] 최소 1번은 등장해야 함 (NOT NULL)
        sh:maxCount 1 ; # [핵심] 동시에 중복을 막음 (UNIQUE)
    ] ;

    # 2. FOREIGN KEY 번역: "관직 코드는 Post 테이블에 있어야 한다"
    sh:property [
        sh:path core:hasPost ;
        sh:class core:Post ; # [핵심] 연결된 대상이 반드시 'Post(관직)' 클래스여야 함
        sh:minCount 0 ;      # 관직이 없는 백수(NULL)일 수도 있으므로 최소값은 0으로 둡니다.
    ] ;

    # 3. CHECK 번역: "출생 연도는 1300년 이후여야 한다"
    sh:property [
        sh:path core:birthYear ;
        sh:datatype xsd:integer ;
        sh:minExclusive 1300 ; # [핵심] 1300보다 커야 함 (CHECK 조건)
        sh:message "위반: 조선시대 인물의 출생 연도는 1300년 이후여야 합니다."
    ] .
```

이 코드가 지식 그래프 서버에 등록되는 순간, 과거 RDB 시대의 견고했던 데이터 무결성이 시맨틱 웹 생태계 안에서 완벽하게 부활하여 작동하기 시작합니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 치명적 실수: "빈칸 허용(Nullable) 외래 키를 맹신하다 지식망이 폭발했습니다!"**

이것은 RDB에서 SHACL로 매핑할 때 인문학자들이 가장 많이 저지르는 논리적 에러입니다.
SQL 설계도에서 `"**FOREIGN KEY**"`를 보았을 때, 많은 초보 아키텍트들은 "무조건 다른 대상과 연결되어야 하는구나!"라고 착각하여 SHACL 코드에 `sh:minCount 1` (반드시 1개 이상 존재해야 함)을 적어버립니다.

**[승리하는 아키텍트의 관대한 유연성 통제술]**
RDB의 뼈아픈 진실 중 하나는, 특별히 `"**NOT NULL**"`이라고 명시하지 않는 이상 `"**FOREIGN KEY**"` 속성 자체는 비어있어도(NULL) 합법이라는 것입니다. 
조선시대 무과에 막 급제한 이순신은 아직 발령받은 관직이 없을 수 있습니다 (즉, `post_id`가 NULL입니다). 
이 데이터를 우리가 만든 깐깐한 SHACL(minCount 1)에 밀어 넣으면, "이순신은 관직이 없으므로 불량 데이터다!"라며 입국을 거부당하는 인문학적 참사가 벌어집니다. 

따라서 `"**FOREIGN KEY**"`를 번역할 때는 그 대상의 형태(`sh:class`)는 엄격하게 통제하되, 존재 여부 자체는 **`sh:minCount 0`**으로 설정하여 아직 관직이 없는 선비들의 입국을 허락하는 유연한 아키텍처를 설계해야만 합니다.

## 5. 요약 및 다음 단계

* 관계형 데이터베이스(RDB)의 데이터를 지식 그래프로 가져올 때는, 데이터뿐만 아니라 RDB에 걸려있던 엄격한 제약조건(법률)들도 함께 이식해야 합니다.
* SQL의 `"**NOT NULL**"`, `"**FOREIGN KEY**"`, `"**CHECK**"` 등의 제약조건들은 SHACL의 `sh:minCount`, `sh:class`, `sh:minInclusive` 등의 문법으로 1:1 시맨틱 매핑이 가능합니다.
* RDB의 외래 키(Foreign Key)는 빈칸(NULL)을 허용할 수 있으므로, SHACL 번역 시 인물의 역사적 생애 주기(예: 아직 관직이 없는 상태)를 고려하여 유연하게 설계해야 합니다.

이제 우리는 외부의 낡은 데이터베이스 규칙까지 최신 지식 그래프의 헌법으로 완벽하게 흡수하는 경지에 이르렀습니다. 이로써 단일 속성에 대한 오타나 빈칸 문제는 완벽히 차단되었습니다.

하지만 진정한 역사적 모순은 하나의 속성이 아니라 "두 개의 속성이 부딪힐 때" 발생합니다. 
만약 어떤 연구원이 "이순신의 출생 연도는 1545년이고, 무과 급제 연도는 1540년이다"라고 입력했다면 어떨까요? 출생(1545)도 숫자이고, 급제(1540)도 숫자이므로 방금 우리가 만든 단일 검증기는 이를 무사통과시킬 것입니다. 하지만 태어나기도 전에 무과에 급제하는 기적이 일어난 셈입니다.
