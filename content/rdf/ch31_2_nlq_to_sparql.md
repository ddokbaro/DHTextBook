# 31.2. NLQ(자연어 질의) to SPARQL 변환과 스키마 주입

## 1. 도입: 인간의 입술과 기계의 뇌 사이, 건널 수 없는 강

우리는 31.1장에서 팩트의 파편화를 막기 위해 무식한 벡터(Vector) 검색을 버리고, 완벽한 논리적 관계망을 가진 지식 그래프(Graph RAG)를 선택했습니다. 인공지능(LLM)에게 완벽한 팩트를 쥐여주면 환각(Hallucination)은 완전히 사라진다는 위대한 진리를 깨달았습니다.

하지만 여기서 디지털 인문학 아키텍트를 절망에 빠뜨리는 거대한 모순이 하나 발생합니다.
사용자는 여러분의 서비스에 접속하여 일상적인 자연어(NLQ, Natural Language Query)로 묻습니다.
**"임진왜란 때 이순신 장군이 거북선을 이끌고 출전한 첫 해전이 뭐야?"**

그런데 우리의 무결성 지식 그래프 서버(Virtuoso)는 오직 기계어인 "**SPARQL**"만 알아듣습니다. 사용자의 한글 질문을 서버에 그대로 던지면 기계는 "문법 오류(Syntax Error)"를 뱉어내며 파업합니다. 그렇다고 역사학자나 일반 대중에게 "질문이 있으시면 `SELECT ?battle WHERE { ... }` 형식으로 코딩해서 물어보세요"라고 강요할 수는 없는 노릇입니다. 인간의 입술(자연어)과 기계의 뇌(SPARQL) 사이에는 건널 수 없는 깊은 강이 흐르고 있습니다.

## 2. 해결책 제시: LLM을 통역사로 고용하다, "**NL2SPARQL**"과 "**스키마 주입**"



이 건널 수 없는 강에 다리를 놓기 위해, 우리는 인공지능(LLM)의 역할을 완전히 뒤바꾸어야 합니다.
지금까지 우리는 LLM을 "역사적 정답을 대답하는 소설가"로 쓰려다 환각이라는 낭패를 보았습니다. 이제 LLM의 역할은 정답을 내는 것이 아니라, **"인간의 질문을 기계의 쿼리로 번역하는 최고급 통역사(Text-to-SQL/SPARQL)"**로 강등(혹은 승격)되어야 합니다.

하지만 통역사(LLM)가 번역을 하려면 반드시 우리가 만든 **"단어장(온톨로지 스키마)"**을 쥐여주어야 합니다. LLM은 세상 모든 지식을 알지만, 여러분의 연구실에서 독자적으로 정의한 `core:참여하다`나 `joseon:이순신` 같은 고유한 접두어와 속성명은 절대 알지 못하기 때문입니다. 

우리가 만든 지식망의 뼈대(클래스와 속성 목록)를 LLM의 프롬프트에 통째로 밀어 넣는 이 위대한 기술을 컴퓨터 공학에서는 "**스키마 주입(Schema Injection)**"이라고 부릅니다.

| 역할 분담 | 과거의 잘못된 RAG 방식 | 최신 Graph RAG (NL2SPARQL) |
| :--- | :--- | :--- |
| **LLM의 임무** | 사용자의 질문에 직접 대답함 (환각 발생) | **사용자의 질문을 SPARQL 코드로만 번역함** |
| **정답의 출처** | LLM의 불확실한 사전 학습 기억 | **번역된 SPARQL이 Virtuoso 서버를 타격하여 100% 팩트를 가져옴** |
| **필수 요소** | 벡터 유사도 검색 | **프롬프트 내 온톨로지 스키마 주입 (Schema Injection)** |

## 3. 실전 적용: 자연어 질문을 SPARQL로 번역하는 기적의 프롬프트

이제 챗GPT(또는 Claude 등) API에 우리의 조선시대 스키마를 주입하여, 완벽한 SPARQL 번역기로 개조하는 실제 시스템 프롬프트(System Prompt)를 작성해 보겠습니다.

**[아키텍트의 NL2SPARQL 시스템 프롬프트]**
```text
너는 조선시대 지식 그래프(Knowledge Graph)의 SPARQL 쿼리 작성 전문가다.
사용자의 자연어 질문을 분석하여, 아래 제공된 [온톨로지 스키마]만을 사용하여 완벽하고 실행 가능한 SPARQL 쿼리를 작성하라.

[온톨로지 스키마 (Schema Injection)]
- Prefixes: 
  PREFIX core: [http://dh.aks.ac.kr/ontology/core/](http://dh.aks.ac.kr/ontology/core/)
  PREFIX joseon: [http://dh.aks.ac.kr/joseon/](http://dh.aks.ac.kr/joseon/)
- Classes: core:Person (인물), core:Event (사건/해전), core:Artifact (사물/함선)
- Properties: 
  core:participatedIn (도메인: Person, 레인지: Event) -> "인물이 사건에 참여하다"
  core:usedWeapon (도메인: Person, 레인지: Artifact) -> "인물이 무기를 사용하다"

[제약 사항]
1. 절대로 위 [온톨로지 스키마]에 없는 클래스나 속성을 상상해서 지어내지 마라. (환각 금지)
2. 출력은 마크다운 코드 블록(```sparql ... ```)으로만 제공하고 다른 설명은 덧붙이지 마라.
```

**[사용자의 자연어 질문 (User Prompt)]**
> "이순신 장군이 거북선을 이끌고(사용하여) 참여한 해전들을 모두 찾아줘."

**[LLM의 훌륭한 통역 결과 (Output)]**
```sparql
PREFIX core: [http://dh.aks.ac.kr/ontology/core/](http://dh.aks.ac.kr/ontology/core/)
PREFIX joseon: [http://dh.aks.ac.kr/joseon/](http://dh.aks.ac.kr/joseon/)

SELECT ?event
WHERE {
  joseon:이순신 core:participatedIn ?event .
  joseon:이순신 core:usedWeapon joseon:거북선 .
  ?event a core:Event .
}
```

이 코드를 받은 우리의 백엔드 서버는 이를 Virtuoso에 던지고, 단 0.1초 만에 `joseon:사천해전`, `joseon:당포해전` 이라는 완벽한 무결성의 팩트를 추출해 냅니다. 기계의 언어를 몰라도, 자연어만으로 1,000만 건의 지식 그래프를 쥐락펴락하는 마법이 완성된 것입니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 피눈물: "LLM이 엉뚱한 속성명을 상상해서 쿼리 에러가 쏟아집니다!"**

LLM에게 스키마를 주입했음에도 불구하고 가장 빈번하게 터지는 사고입니다. 
사용자가 "이순신이 싸운 전투 찾아줘"라고 물어보면, 챗GPT는 순간적으로 우리가 주입한 `core:participatedIn`을 잊어버리고, 자기가 인터넷에서 흔히 보았던 `core:foughtIn`이나 `core:전투하다` 같은 정체불명의 속성명을 창조해서 쿼리를 짜버립니다. 당연히 이 쿼리를 서버에 던지면 데이터가 0건(Empty)으로 나오게 됩니다.

**[승리하는 아키텍트의 '퓨샷 프롬프팅(Few-shot Prompting)' 방어술]**
단순히 "이 단어장만 써라"라고 지시(Zero-shot)하는 것만으로는 LLM의 창의성(환각)을 완벽히 억누를 수 없습니다. 번역의 정확도를 99% 이상으로 끌어올리려면, 프롬프트 안에 반드시 **"모범 사례(Few-shot Examples)"**를 3개에서 5개 정도 강제로 주입해야 합니다.

```text
[모범 사례 (Few-shot Examples)]
Q: 원균이 죽은 곳은 어디야?
A: SELECT ?place WHERE { joseon:원균 core:diedAt ?place . }

Q: 선조의 아버지는 누구인가?
A: SELECT ?father WHERE { joseon:선조 core:hasFather ?father . }
```

인공지능은 "지시문"보다 "예시"를 훨씬 더 강력하게 모방하는 습성이 있습니다. 이렇게 인간이 미리 짜둔 정답 쿼리 패턴을 프롬프트 하단에 박아주면, LLM은 스스로 창의성을 발휘하려는 충동을 억누르고 여러분이 제시한 퓨샷(Few-shot)의 문법과 속성명을 철저하게 모방하여 완벽하게 안전한 SPARQL을 생성해 냅니다.

## 5. 요약 및 대단원 마무리 (모듈 8의 핵심 돌파)

* 사용자의 일상적인 질문(자연어)을 기계어(SPARQL)로 변환하기 위해, 우리는 LLM을 정답을 내는 소설가가 아닌 "**최고급 쿼리 번역기(NL2SPARQL)**"로 활용해야 합니다.
* LLM이 엉뚱한 쿼리를 짜는 것을 막기 위해, 우리가 독자적으로 설계한 온톨로지 구조와 속성명들을 시스템 프롬프트에 통째로 욱여넣는 "**스키마 주입(Schema Injection)**" 과정이 필수적입니다.
* 번역의 성공률을 극대화하고 존재하지 않는 속성을 지어내는 환각을 억제하려면, 프롬프트 내에 반드시 3~5개의 완벽한 모범 쿼리 쌍을 제공하는 "**퓨샷 프롬프팅(Few-shot Prompting)**" 기법을 동원해야 합니다.

이제 우리는 자연어로 물어보면 완벽한 SPARQL이 만들어지고, 그 SPARQL이 무결성 데이터베이스에서 정확한 팩트를 뽑아오는 경이로운 Graph RAG의 "검색(Retrieval)" 파이프라인을 완성했습니다.

하지만 잠시 생각해 봅시다. 
서버가 뽑아온 결과는 `joseon:사천해전`, `joseon:당포해전` 이라는 차가운 식별자(URI) 덩어리입니다. 일반 사용자에게 "정답은 `joseon:사천해전` 입니다"라고 텍스트를 던져주면 무미건조하기 짝이 없을 것입니다. 기계가 뱉어낸 이 딱딱한 트리플의 파편들을, 어떻게 하면 다시 "이순신 장군이 거북선을 이끌고 처음 출전한 곳은 사천해전과 당포해전입니다."라는 아름답고 자연스러운 인간의 서사(Narrative)로 포장할 수 있을까요?
