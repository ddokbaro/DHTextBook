# 5.3. 인간과 기계를 동시에 만족시키는 마법: 콘텐츠 협상과 httpRange-14 (303 See Other)

## 1. 도입: 이순신 장군을 다운로드할 수 있습니까?

시맨틱 웹을 공부하는 디지털 인문학자들이 반드시 부딪히는 아주 기괴하고도 철학적인 질문이 하나 있습니다. 

우리는 앞선 장에서 이순신이라는 역사적 인물에게 `http://w3id.org/joseon/person/P123`이라는 영구 식별자(URI)를 부여했습니다. 자, 이제 이 주소를 웹 브라우저 주소창에 입력하고 엔터를 치면 무엇이 화면에 나타나야 할까요? 

인문학자들은 당연히 "이순신의 생애가 적힌 예쁜 웹페이지가 떠야지!"라고 대답할 것입니다. 하지만 컴퓨터 공학자들은 정색하며 반론합니다. "잠깐! 저 URI는 이순신이라는 `"**역사적 실체(사람)**"`를 가리키는 이름표라고 하지 않았습니까? 웹 브라우저가 어떻게 16세기에 죽은 사람 자체를 인터넷 선을 통해 다운로드합니까? 저 주소가 가리키는 것은 `"**문서**"`가 아니라 `"**사람**"`이므로, 웹페이지가 뜨는 것은 논리적 모순입니다!"

이것은 농담이 아닙니다. 초창기 웹 표준 기구(W3C)의 천재들을 무려 4년 동안이나 밤새워 토론하게 만들었던 시맨틱 웹 역사상 가장 유명하고 치열했던 논쟁, 바로 `"**httpRange-14**"` 이슈입니다. 기계는 철저하게 논리적이기 때문에, `"**사람(Non-information Resource)**"`을 가리키는 주소와 `"**그 사람에 대한 문서(Information Resource)**"`를 가리키는 주소를 완벽하게 분리하지 않으면 전 세계의 지식 그래프 논리가 붕괴해 버립니다. 

이 철학적 딜레마를 서버 시스템은 도대체 어떻게 해결했을까요?

## 2. 해결책 제시: "303 See Other"의 위대한 결단

웹의 창시자 팀 버너스리와 W3C는 이 딜레마를 해결하기 위해 HTTP 통신 규약의 `"**상태 코드(Status Code)**"`를 기가 막히게 활용하는 위대한 결단을 내립니다. 그것이 바로 `"**303 See Other (다른 곳을 보시오)**"`라는 특수한 응답입니다.

여러분이 웹 브라우저에 인물의 식별자(`.../person/P123`)를 입력하면, 서버는 16세기의 인물 자체를 전송할 수 없으므로 당황하지 않고 다음과 같이 우아하게 응답합니다.

*"당신이 요청한 P123은 문서가 아니라 물리적인 '사람'이므로 인터넷으로 전송해 드릴 수 없습니다. 하지만 대신에, 그 사람에 대해 잘 설명해 놓은 **'문서가 있는 다른 곳(303 See Other)'**으로 안내해 드릴 테니 그쪽으로 가보십시오!"*

이 `"**303 응답**"`을 받은 웹 브라우저는 0.1초 만에 서버가 일러준 새로운 문서 주소(`.../page/P123.html`)로 자동 이동(`"**리다이렉트**"`)하여 여러분의 모니터에 예쁜 이순신 웹페이지를 띄워줍니다. 이로써 역사적 실체를 가리키는 고유 주소(URI)의 철학을 완벽히 지키면서도, 사용자에게는 필요한 문서를 전달하는 논리적 완결성이 달성된 것입니다.



## 3. 실전 적용: 기계와 인간을 구분하는 "콘텐츠 협상(Content Negotiation)"

여기서 마법이 하나 더 추가됩니다. 
서버가 `"**303 See Other**"`로 다른 곳을 안내해 줄 때, 접속한 녀석이 구글의 인공지능(기계)인지, 아니면 우리 연구실의 대학원생(인간)인지 귀신같이 알아채고 서로 다른 형태의 문서를 던져주는 기술입니다. 이를 `"**콘텐츠 협상(Content Negotiation)**"`이라고 부릅니다.

원리는 식당의 메뉴 주문과 같습니다. 접속자가 식당(서버)에 들어올 때, HTTP 통신의 `"**Accept(수용 가능 포맷)**"`라는 헤더에 자신이 먹고 싶은 데이터의 형태를 미리 적어서 제출합니다.

### 시나리오 A: 인간 연구자가 웹 브라우저로 접속할 때
* **연구자의 요청 (Accept):** "나는 텍스트 읽기를 좋아하는 크롬 브라우저다. 인간이 보기 좋은 `"**text/html**"` 문서를 주면 좋겠다."
* **서버의 303 응답:** "당신은 인간이군요! P123 인물은 전송할 수 없으니, 인간이 읽기 좋은 예쁜 표가 그려진 `http://조선.kr/page/P123.html` 주소로 가보십시오(303)."
* **결과:** 화면에 이순신 장군의 영정과 생애가 담긴 예쁜 홈페이지가 뜹니다.

### 시나리오 B: 파이썬(Python) 추론 엔진이 접속할 때
* **기계의 요청 (Accept):** "나는 추론 연산을 해야 하는 프로그램이다. 예쁜 그림은 필요 없고, 오직 기계가 읽기 편한 3조각의 `"**text/turtle**"` 데이터를 원한다."
* **서버의 303 응답:** "당신은 기계군요! P123 인물은 전송할 수 없으니, 기계가 파싱하기 좋은 트리플 코드가 담긴 `http://조선.kr/data/P123.ttl` 주소로 가보십시오(303)."
* **결과:** 화면에 압축적이고 우아한 시맨틱 웹 원시 코드가 출력됩니다.

이 기술 덕분에 우리는 `http://w3id.org/joseon/person/P123` 이라는 단 하나의 영구 식별자(PID) 주소만 명함에 파서 전 세계에 뿌리면 됩니다. 그 주소 하나가 인간과 기계를 완벽하게 동시에 만족시키는 셈입니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

디지털 인문학 서버를 외주 개발 업체에 맡겨서 구축할 때, 시맨틱 웹의 깊은 철학을 모르는 일반적인 백엔드(Backend) 개발자들은 리다이렉트를 구현하라고 하면 십중팔구 `"**301 Moved Permanently(영구 이동)**"`나 `"**302 Found(임시 이동)**"` 코드를 써버립니다.

"교수님, 301이든 303이든 어차피 사용자는 예쁜 페이지로 자동 이동하는데 뭐가 다릅니까? 301이 검색 엔진 최적화(SEO)에도 더 좋습니다!"라고 그들은 항변할 것입니다.

하지만 시맨틱 웹 생태계에서 `"**301**"`과 `"**303**"`의 차이는 하늘과 땅 차이입니다.
만약 개발자가 이순신 주소(`/person/P123`)에 `"**301 영구 이동**"`을 걸어서 웹페이지 주소(`/page/P123.html`)로 보내버리면, 기계는 논리적으로 이렇게 학습해 버립니다.
*"아! 이순신이라는 역사적 인물은 어제부로 완전히 사라졌고, 이제부터 이순신이라는 존재의 본질은 .html 확장자를 가진 디지털 파일로 영원히 바뀌었구나!"*

이순신 장군이 한낱 HTML 파일로 전락하는 인문학적 모독이자 데이터의 논리적 파괴입니다. 여러분의 지식 그래프가 무식한 오류 덩어리가 되는 것을 막으려면, 서버 엔지니어에게 아파치(Apache)나 Nginx 설정에 다음과 같이 명확한 303 룰을 적어달라고 강력하게 요구하십시오.

```nginx
# Nginx 웹 서버에서의 콘텐츠 협상 및 303 See Other 설정 예시 실무 코드
# Accept 헤더에 turtle을 요구하는 기계가 오면 .ttl 파일 경로로 303 리다이렉트
if ($http_accept ~* "text/turtle") {
    return 303 [http://조선.kr/data/$1.ttl](http://조선.kr/data/$1.ttl);
}
# 그 외의 일반 웹 브라우저가 오면 .html 파일 경로로 303 리다이렉트
return 303 [http://조선.kr/page/$1.html](http://조선.kr/page/$1.html);
```
서버 개발자가 이 `"**303 See Other**"`의 철학을 이해하고 구현해 내는 순간, 여러분의 인문학 데이터베이스는 단순한 게시판을 넘어 진정한 의미의 `"**링크드 오픈 데이터(LOD)**"` 서버로 도약하게 됩니다.

## 5. 요약 및 다음 단계

* 시맨틱 웹의 URI는 문서가 아니라 실존하는 대상을 가리키므로, 기계의 논리적 모순(`"**httpRange-14**"`)을 피하기 위해 대상을 직접 전송하지 않습니다.
* 대신 서버는 `"**303 See Other**"` 응답을 사용하여, 그 대상에 대해 설명하는 문서가 있는 새로운 주소로 안내합니다.
* 이때 `"**콘텐츠 협상(Content Negotiation)**"` 기술을 활용하면, 하나의 URI로 접속자의 정체(인간 vs 기계)를 파악하여 HTML이나 Turtle(.ttl) 등 맞춤형 데이터를 응답할 수 있습니다.

지금까지 우리는 엑셀을 버리고(1장), 점과 선으로 데이터를 모델링하며(2~3장), 그 뼈대에 영원히 변하지 않는 이름표와 서버 응답 규약을 세우는 법(4~5장)까지 데이터 아키텍처의 거대한 산맥을 모두 넘었습니다.

이제 여러분은 완벽한 시맨틱 데이터를 손에 쥐었습니다. 그렇다면 다음 질문이 떠오릅니다. **"이 방대한 점과 선의 바다에서, 내가 원하는 조선시대 인물들을 내 마음대로 검색하고 통계를 뽑아내려면 기계에게 어떻게 질문해야 할까요?"**

마침내, W3C가 제정한 시맨틱 웹 최고의 무기이자 SQL의 진화형인 지식 검색의 마법, 다음 파트인 **[6장. 지식을 탐색하는 마법의 주문: SPARQL 질의어 마스터하기]**로 진입하겠습니다.
