# 18장. 관계의 문법과 수학적 성질 (Properties)

## 1. 도입: 명사만 둥둥 떠다니는 적막한 우주

우리는 앞선 17장에서 Protégé의 **"Classes"**(클래스) 탭을 활용하여 조선시대의 신분제와 관료제를 훌륭하게 설계했습니다. 이제 우리의 데이터베이스 안에는 **"인물"**, **"관직"**, **"행정구역"**이라는 잘 짜인 책장들이 수직으로 늘어서 있습니다.

하지만 역사학자로서 이 뼈대를 가만히 들여다보면 무언가 심각하게 빠져있다는 것을 깨닫게 됩니다. 바로 **"움직임(Action)"**입니다. 
명사(Noun)만으로는 결코 역사가 이루어지지 않습니다. 역사는 **"이순신"**이라는 인물이 **"전라좌수사"**라는 관직을 **"역임하고"**, **"한산도"**라는 공간에 **"주둔하며"**, 1592년이라는 시간에 왜군을 **"격파하는"** 동적이고 유기적인 관계의 연속입니다.

엑셀은 명사들을 같은 행(Row)에 나란히 배치할 뿐, 그들 사이에 어떤 인문학적 관계가 존재하는지 문법적으로 설명하지 못합니다. 단절된 클래스들을 거미줄처럼 엮어내어 거대한 지식의 네트워크를 폭발시키기 위해, 우리는 기계에게 명사와 명사를 이어주는 **"동사(Verb)"**를 가르쳐야 합니다. 이 동사를 시맨틱 웹에서는 **"속성(Property)"**이라고 부릅니다.

## 2. 해결책 제시: 세계를 엮는 두 가지 화살표, Object와 Data Property

Protégé는 세상의 모든 동사(관계)를 그 목적어의 성격에 따라 엄격하게 두 가지로 분류합니다. 이 두 가지 화살표의 차이를 명확히 이해하는 것이 시맨틱 아키텍트의 첫 번째 관문입니다.

| 속성의 종류 | 인문학적 문법 (화살표의 목적지) | 조선시대 지식 그래프 예시 |
| :--- | :--- | :--- |
| **"Object Property"** (객체 속성) | **"명사 ➔ 명사"** (개체와 개체를 연결함) | 이순신 ➔ **"관직을_역임하다"** ➔ 전라좌수사 |
| **"Data Property"** (데이터 속성) | **"명사 ➔ 텍스트/숫자"** (개체에 값을 부여함) | 이순신 ➔ **"태어난_연도는"** ➔ "1545" |

* **"Object Property"**: 인물과 관직, 스승과 제자처럼 지식 그래프 내부에 존재하는 **"노드(Node)와 노드 사이"**를 이어주는 강력한 쇠사슬입니다.
* **"Data Property"**: 이름 문자열, 출생 연도, 나이처럼 계산하거나 출력하기 위해 개체에 딱 붙여놓은 **"포스트잇(값)"**입니다.

## 3. 실전 적용: 조선시대 관계망의 동사 창조하기 (Turtle)

Protégé의 상단 메뉴를 보면 **"Entities"** 탭 아래에 **"Object Properties"**와 **"Data Properties"**라는 독립된 탭이 존재합니다. 여기서 조선시대 지식망을 구동할 핵심 동사들을 만들어 보겠습니다.

**[작업 1: Object Property 만들기]**
1. **"Object Properties"** 탭으로 이동합니다.
2. 최상위 개념인 **"owl:topObjectProperty"**를 선택하고 새 속성 추가 버튼을 누릅니다.
3. **"관직을_역임하다(hasOffice)"**라는 속성을 생성합니다.

**[작업 2: Data Property 만들기]**
1. **"Data Properties"** 탭으로 이동합니다.
2. 최상위 개념인 **"owl:topDataProperty"**를 선택하고 새 속성 추가 버튼을 누릅니다.
3. **"출생연도(hasBirthYear)"**라는 속성을 생성합니다.

여러분이 두 개의 탭을 오가며 동사를 만들어내는 동안, 기계는 텍스트 이면에 다음과 같은 시맨틱 문법을 완벽하게 새겨 넣습니다.

```turtle
@prefix rdfs: [http://www.w3.org/2000/01/rdf-schema#](http://www.w3.org/2000/01/rdf-schema#) .
@prefix owl: [http://www.w3.org/2002/07/owl#](http://www.w3.org/2002/07/owl#) .
@prefix joseon: [http://aks.ac.kr/ontologies/joseon/](http://aks.ac.kr/ontologies/joseon/) .

# 1. 개체와 개체를 잇는 관계 (Object Property) 선언
# 기계여, 이것은 인물 노드와 관직 노드를 연결할 강력한 쇠사슬이다!
joseon:hasOffice a owl:ObjectProperty ;
    rdfs:label "관직을_역임하다" .

# 2. 개체와 단순 텍스트/숫자를 잇는 관계 (Data Property) 선언
# 기계여, 이것은 인물 노드에 숫자를 붙여줄 단순한 포스트잇이다!
joseon:hasBirthYear a owl:DatatypeProperty ;
    rdfs:label "출생연도" .
```

이제 우리의 지식 그래프는 **"이순신"**이라는 인물에 **"전라좌수사"**라는 실체 노드를 단단히 결속시키고, 동시에 **"1545"**라는 숫자를 꼬리표처럼 달아줄 준비를 마쳤습니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 파멸적 실수: 위대한 관직을 한낱 "텍스트 포스트잇"으로 전락시키기**

초보 연구원들이 Protégé에서 데이터를 모델링할 때 저지르는 가장 흔하고 치명적인 실수는 바로 **"Object Property"**를 써야 할 곳에 **"Data Property"**를 남발하는 행위, 일명 **"문자열의 함정(String Trap)"**입니다.

**"교수님! 인물의 관직을 기록하기 위해 Data Property 탭에서 `관직이름을_적다(hasOfficeName)`라는 속성을 만들고, 거기에 `전라좌수사`라는 글자를 키보드로 정성껏 타이핑해서 넣었습니다. 잘했지요?"**

아닙니다! 시스템의 확장성을 완전히 파괴해 버렸습니다. 
여러분이 **"전라좌수사"**를 별도의 인스턴스 노드(개체)로 만들어서 **"Object Property"**로 연결하지 않고, 그냥 텍스트 문자열(Data Property)로 타이핑해 버리면 기계는 이를 인문학적 실체로 인식하지 않습니다. 

기계의 눈에 그 텍스트는 **"전.라.좌.수.사."**라는 5개의 글자 뭉치에 불과합니다. 나중에 다른 연구자가 **"전라좌수사 관할에 속한 군영은 어디인가?"**를 질의하려고 해도, 텍스트 문자열에는 다른 노드를 연결할 수 없으므로 지식의 네트워크가 거기서 허무하게 끊어져 버립니다.

**[실무 철칙]**
역사적으로 다른 개체와 관계를 맺을 가능성이 단 1%라도 있는 명사(관직명, 지명, 책 이름)는 무조건 클래스와 인스턴스로 독립시키고 **"Object Property"**로 연결해야 합니다. **"Data Property"**는 더 이상 다른 노드와 연결될 필요가 없는 궁극의 종착역(연도, 나이, 단순 이름 문자열)에만 극히 제한적으로 사용해야 합니다.

## 5. 요약 및 다음 단계

* 고립된 클래스(명사)들을 연결하여 역사적 서사를 만들기 위해서는 **"동사"**의 역할을 하는 **"속성(Property)"**을 Protégé에서 생성해야 합니다.
* 노드와 노드를 잇는 강력한 관계망은 **"Object Property"**로, 개체에 연도나 문자열을 부여하는 단순 꼬리표는 **"Data Property"**로 엄격히 구분하여 설계해야 합니다.
* 관직이나 지명처럼 추후 다른 데이터와 연결될 인문학적 실체들을 절대 단순 텍스트(Data Property)로 입력하는 실수를 저질러서는 안 됩니다.

이제 지식망을 엮어낼 화살표(동사)까지 성공적으로 준비했습니다. 
하지만 이 화살표가 아무에게나 마구 날아가서는 안 됩니다. **"관직을_역임하다"**라는 화살표는 오직 **"인물"**만이 쏠 수 있고, 그 화살표를 맞는 목적지는 반드시 **"관직"**이어야 한다는 엄격한 헌법이 필요합니다.
