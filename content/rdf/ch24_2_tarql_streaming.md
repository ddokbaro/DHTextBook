# 24.2. Tarql: SPARQL 1.1 문법을 응용한 거대 CSV 파일 변환

## 1. 도입: 거대한 사료의 산더미에 짓눌려 무너진 책상

앞선 24.1장에서 우리는 "**OpenRefine(오픈리파인)**"이라는 훌륭한 세공 도구를 통해 더러운 노이즈를 씻어내고 데이터를 빚어내는 법을 배웠습니다. 수만 건 정도의 데이터라면 오픈리파인은 최고의 선택입니다.

하지만 여러분이 국사편찬위원회의 "조선왕조실록 기사 색인"이나 "역대 문무과 방목 전체" 데이터를 건네받았다고 상상해 보십시오. 엑셀의 행(Row) 개수만 무려 200만 건에 달합니다. 이 거대한 CSV 파일을 오픈리파인에 밀어 넣으면 어떻게 될까요? 기계는 윙윙거리며 괴음을 내다가 "**Out of Memory**" 에러를 내뱉고 그대로 장렬하게 전사합니다. 

오픈리파인은 마치 폭 1미터짜리 책상 위에 200만 장의 사료를 한꺼번에 다 올려놓고 한눈에 보려는 욕심 많은 학자와 같습니다. 책상의 크기, 즉 컴퓨터의 "**RAM(메모리)**"이 사료의 무게를 버티지 못하고 무너져 내린 것입니다. 그렇다면 우리는 200만 건의 데이터를 1만 건씩 200번으로 쪼개서 변환하는 고통스러운 수작업을 해야만 할까요? 

우리는 기계의 노예가 아닙니다. 지식망을 직조하는 아키텍트로서, 메모리의 한계를 근본적으로 우회하는 완전히 새로운 파이프라인 설계가 필요합니다.

## 2. 해결책 제시: 책상이 아닌 "컨베이어 벨트"의 철학, "**Tarql**"

이 거대한 엑셀 데이터를 처리하기 위해 우리는 "**Tarql(타르큐엘)**"이라는 명령줄 기반의 가볍고 무자비한 변환 도구를 사용할 것입니다.

Tarql이 200만 건의 데이터를 단 몇 십 초 만에 처리하는 비결은 "**스트리밍(Streaming)**"이라는 컴퓨터 공학의 철학에 있습니다.
* **OpenRefine (거대한 책상):** 모든 데이터를 한 번에 메모리(RAM)에 다 올려야만 작업이 가능합니다.
* **Tarql (컨베이어 벨트):** 데이터를 메모리에 쌓아두지 않습니다. 엑셀의 첫 번째 줄(Row)을 읽어 들여 지식 그래프로 변환하고 하드디스크에 써버린 뒤, 그 기억을 메모리에서 완전히 지워버립니다. 그리고 다음 줄을 읽습니다. 이 컨베이어 벨트 방식은 데이터가 200만 건이든 2억 건이든 메모리를 거의 차지하지 않고 일정한 속도로 영원히 파이프라인을 돌릴 수 있습니다.

또한 Tarql은 우리가 21장에서 피땀 흘려 배운 "**SPARQL(스파클)**" 문법을 그대로 재활용합니다. 
지금까지 우리는 데이터베이스에서 정보를 "조회"하기 위해 "**SELECT**" 구문을 썼습니다. Tarql에서는 사료를 바탕으로 새로운 지식의 구조를 "찍어내기" 위해 "**CONSTRUCT**"라는 강력한 구문을 사용합니다.

## 3. 실전 적용: 엑셀 데이터를 지식 그래프로 찍어내는 주물 공장

우리에게 `bangmok.csv`라는 200만 건짜리 방목 엑셀 파일이 있다고 가정해 보겠습니다. 이 파일에는 "이름", "관직", "임용년도"라는 헤더(Header)가 존재합니다.

| 이름 | 관직 | 임용년도 |
| :--- | :--- | :--- |
| 이순신 | 전라좌수사 | 1592 |
| 정도전 | 판삼사사 | 1392 |

이제 Tarql에게 "엑셀을 읽어서 어떻게 트리플(Triple)로 찍어낼 것인지" 명령을 내리는 설계도 파일(`mapping.sparql`)을 작성해야 합니다.

```sparql
# 1. 네임스페이스 선언: 우리가 사용할 지식 그래프의 절대 주소들을 미리 선언합니다.
PREFIX joseon: [http://dh.aks.ac.kr/joseon/](http://dh.aks.ac.kr/joseon/)
PREFIX core: [http://dh.aks.ac.kr/ontology/core/](http://dh.aks.ac.kr/ontology/core/)

# 2. CONSTRUCT 구문: 컨베이어 벨트를 지나가는 데이터가 최종적으로 찍혀 나올 "트리플의 모양"을 디자인합니다.
CONSTRUCT {
  ?personURI a core:Person ;
             core:hasName ?이름 ;                  # 엑셀의 "이름" 컬럼 값을 그대로 문자열로 씁니다.
             core:hasPost ?postURI ;
             core:appointmentYear ?임용년도 .      # 엑셀의 "임용년도" 컬럼 값을 그대로 씁니다.
  
  ?postURI a core:Post ;
           core:postName ?관직 .
}
# 3. FROM 구문 (Tarql 특화): 엑셀의 한 줄(Row)을 읽어올 때마다 변수를 어떻게 가공할지 정의합니다.
FROM <file:bangmok.csv>
WHERE {
  # BIND 구문과 URI() 함수를 사용해, 엑셀의 한글 텍스트를 기계가 인식하는 절대 식별자(URI)로 조립합니다.
  BIND(URI(CONCAT("[http://dh.aks.ac.kr/joseon/person/](http://dh.aks.ac.kr/joseon/person/)", ?이름)) AS ?personURI)
  BIND(URI(CONCAT("[http://dh.aks.ac.kr/joseon/post/](http://dh.aks.ac.kr/joseon/post/)", ?관직)) AS ?postURI)
}
```

이 설계도를 저장한 뒤, 리눅스 서버나 윈도우 터미널(CMD)에서 마법의 명령어 한 줄을 실행합니다.

```bash
# tarql 프로그램을 실행하여, mapping.sparql 설계도를 바탕으로 bangmok.csv를 읽고, 그 결과를 output.ttl에 쏟아부어라!
tarql mapping.sparql bangmok.csv > output.ttl
```

명령어를 치는 순간, 기계는 컨베이어 벨트를 맹렬하게 돌리며 200만 건의 평면적인 엑셀 데이터를 입체적인 W3C 표준 거북이(`.ttl`) 파일로 변환하여 쏟아냅니다. 메모리 에러는 절대 발생하지 않습니다.

## 4. 실무 트러블슈팅 (Street-smart Tips)

**시맨틱 아키텍트의 피눈물: "엑셀에 빈칸이 있었더니 유령 노드(Ghost Node)가 생성되었습니다!"**

이것은 Tarql을 처음 쓰는 연구원들이 100% 마주하는 치명적인 재앙입니다. 
원시 데이터인 CSV 파일에는 종종 "관직" 칸이나 "임용년도" 칸이 비어있는(NULL) 행(Row)이 존재합니다. 만약 "이름" 칸이 비어있는 줄이 컨베이어 벨트를 타고 들어오면, Tarql은 문자열 결합(`CONCAT`)을 시도하다가 `http://dh.aks.ac.kr/joseon/person/` 이라는, 이름도 정체도 없는 끔찍한 "**유령 식별자**"를 생성해 버립니다. 이 유령 노드들이 수만 개씩 서버에 쌓이면 지식 그래프 전체의 쿼리 성능이 붕괴합니다.

**[승리하는 아키텍트의 필터링 방어술]**
컨베이어 벨트에 불량품이 들어오면 망치로 내려쳐서 버려야 합니다. `mapping.sparql`의 `WHERE` 블록 안에 반드시 "**FILTER**" 구문을 삽입하여, 핵심 변수가 비어있는 쓰레기 행(Row)은 변환하지 말고 건너뛰도록 지시해야 합니다.

```sparql
WHERE {
  # "이름" 컬럼이 존재하고(bound), 그 값이 빈 문자열("")이 아닐 때만 아래 작업을 수행하라!
  FILTER(bound(?이름) && ?이름 != "")
  
  BIND(URI(CONCAT("[http://dh.aks.ac.kr/joseon/person/](http://dh.aks.ac.kr/joseon/person/)", ?이름)) AS ?personURI)
}
```
이 단 한 줄의 방어 코드가 여러분의 거룩한 지식의 성채를 쓰레기 데이터로부터 지켜내는 가장 강력한 방패가 됩니다.

## 5. 요약 및 다음 단계

* "**Tarql**"은 거대한 엑셀 데이터를 한 번에 메모리에 올리지 않고, 한 줄씩 읽고 버리는 "**스트리밍(Streaming)**" 방식을 사용하여 메모리 한계를 완벽하게 극복합니다.
* 우리가 배운 "**SPARQL 1.1**" 문법의 "**CONSTRUCT**" 구문을 그대로 활용하여, 평면적인 CSV 데이터를 입체적인 지식 그래프(RDF) 뼈대로 찍어낼 수 있습니다.
* 실무 파이프라인 구축 시에는 반드시 빈칸(NULL) 데이터로 인해 발생하는 유령 노드를 막기 위해 "**FILTER**" 구문으로 불량 데이터를 걸러내야 합니다.

이제 우리는 수백만 건의 엑셀 데이터조차 콧노래를 부르며 지식 그래프로 변환할 수 있는 막강한 화력을 손에 쥐었습니다. 

하지만, 만약 한국학중앙연구원의 전산실에서 우리에게 "엑셀 파일"조차 주지 않고, **"보안 때문에 파일 반출은 안 됩니다. 그냥 저희 서버에 있는 거대한 관계형 데이터베이스(MySQL)에 직접 접속해서 데이터를 가져가세요"**라고 통보한다면 어떻게 해야 할까요?
